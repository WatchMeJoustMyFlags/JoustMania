# Use Case: Play Zombies

## Overview

**Use Case ID:** UC-023
**Use Case Name:** Play Zombies
**Primary Actor:** Player
**Goal:** Survive as a human until time runs out, or (as a zombie) convert every human
**Status:** Tested
**Requirements:** FR-023, FR-148, FR-149

## Preconditions

- A Zombies game was started with at least four players, the mode's minimum (UC-010 BR-001).

## Main Success Scenario

1. System makes `zombie.initial_count` players (default 2, at most players − 1) zombies, opens the gameplay stream and runs a `zombie_intro` over it: zombies grey, humans white; frames that arrive during the intro are read and discarded (only disconnects are kept, as in UC-021 A1). After the countdown System primes the EMA (the startup guard, UC-030 BR-003) and only then starts the game timer (step 2). Event order: `game_starting` → `players_initialized` → `zombie_intro_start` / `zombie_intro_end` → `countdown_start` / `countdown_end` → `game_started` (Zombies publishes `game_started` after the countdown, the base modes before it).
2. System starts a timer of `((players × 3) / 16) × 60` seconds and announces remaining time at the 60 s, 30 s and 10 s marks (`time_announcement` with `seconds_remaining`, plus the matching voice line). A mark fires once, when the timer crosses it (`previous > mark >= remaining`), also for durations that never land on a whole second (22.5 s, 67.5 s, ...). There is no 3-minute mark. After the win is latched (BR-005) no further announcement is published.
3. A human whose movement exceeds the threshold is converted to a zombie (`human_converted`) and gets a grace period of `death_grace_period_seconds`. The controller shows one death flash with one rumble, then, 0.5 s later, the zombie colour (grey); later deaths follow step 4; the base kill path sends no second death effect for a converted human (issue #1342). The 0.5 s runs off the game loop (issue #2023): the conversion (`human_converted`, the win check) takes effect at once and other players' frames keep being processed meanwhile. The 0.5 s ends within the 1 s post-win hold (UC-020 BR-003), so a winning conversion shows grey before the winner rainbow. The grey is not set when the zombie dies within the 0.5 s (its death effect keeps the LED off, and a respawn sets the colour itself, step 4) or the game has stopped; a grey write on a gameplay stream that has died is skipped, and the reopened stream restores it (UC-030 BR-006). A disconnect goes through the same kill path: a disconnected human is converted, a disconnected zombie dies and still respawns after its delay, out of reach of its LED (the player is not removed).
4. A zombie whose movement exceeds its fixed threshold (`zombie.thresholds`) dies and respawns after a random time between `zombie.respawn_min_seconds` and `zombie.respawn_max_seconds` (default 2 to 10 s). While dead it shows the death effect (LED off); on respawn System sets the zombie colour, then flashes, so the respawned zombie plays grey with a fresh `death_grace_period_seconds` grace (issue #1342). A zombie does not respawn once the winner is latched (BR-003) or the game has stopped running. A respawn LED write that fails on a gameplay stream that has died is skipped: the zombie still respawns, the respawn timer ends without an error, and the reopened stream restores the zombie colour (UC-030 BR-006, #2021).
5. When the timer expires with humans alive, System publishes `zombie_winner` (humans) and `game_ended`.

## Alternative Flows

### A1: All humans converted

**Trigger:** No humans left (step 3)
**Flow:**

1. System publishes `zombie_winner` (zombies) and `game_ended`.
2. Use case ends.

### A2: Instructions on

**Trigger:** The host has switched spoken instructions on (`game_instructions`, FR-014, UC-012 A3) when the game starts (step 1)
**Flow:**

1. After the `zombie_intro`, System plays the `zombie-instructions` clip as in UC-020 A5 and waits for it before the countdown and the music. The gameplay stream is open and drained meanwhile, as during the intro (frames discarded, disconnects kept). A force-end during the wait skips the countdown and the start (no music, no `game_started`, no `countdown_start`); the gameplay stream is already open in this mode, so it is not skipped but released when the game ends. A force-end during the intro skips the clip.
2. Use case continues at step 2.

## Postconditions

### Success Postconditions

- The winning side is in the event stream; the session is ENDED.

### Failure Postconditions

- `game_error` ends the session.

## Business Rules

### BR-001: Duration formula

The duration is `((players × 3) / 16) × 60` seconds, i.e. 11.25 s per player: 22.5 s for 2 players, 45 s for 4, 90 s for 8, 135 s for 12 and 180 s for 16. The formula is a product decision and stays as is; the old docstring claim of ~3 minutes for 4 players was stale (D-G6, #1736, resolved).

### BR-002: Fixed tempo and thresholds

By design (maintainer decision 2026-10-22, #1273, as for Werewolf in UC-022 BR-001), Zombies runs without the tempo music loop: music stays at normal speed (1.0) and humans keep the slow threshold table all game. Zombies use the fixed thresholds of `zombie.thresholds`, ignoring tempo and agent factors (moved from UC-030 A3 by #1500). Zombies runs its own `run()` around the base game loop; like the base start it publishes `game_starting`, refuses fewer than two players with `ValueError` before the stream opens (the session publishes `game_error`, UC-010 BR-001), runs the EMA warm-up of the startup guard (UC-030 BR-003) and sets the game's flag evaluation context (D-G3; moved from UC-031 BR-001 by #1500).

Tempo and pacing interventions (`adjust_music_tempo`, `set_pacing_profile`) are accepted in Zombies but have no effect, because Zombies has no tempo loop; denying them in the matrix is a product follow-up.

Flag context: the session already sets `game_kind` and the experiment (`experiment_id`, `arm`) before the game is created (`game_session.py`), so a shadow Zombies game resolved experiments before #1273 too. The Zombies start adds `targetingKey=game_mode`, `game_mode`, `controller_count` and `sensitivity` for the flag reads made during the game (today the shield activation mode and charge delay); it adds no experiment exposure.

Lobby: selecting Zombies announces the mode by voice (`MENU_VOX_ZOMBIES`) and shows the grey (`White40`) lobby colour (issue #1276).

### BR-003: Root-span outcome

Zombies runs its own `run()` and records the game root-span outcome as in UC-020 BR-003: `completed` for a natural end, or `force_ended` with the force-end reason (`game.end_reason`) when force-ended. A force-end after the loop ended does not rewrite the outcome.

A force-end declares no winner (issue #1343): while the game runs, no `zombie_winner`, no winner rainbow, no victory voice and no rainbow wait happen, the player spans end with `winner=false` and `winning_team` `none`, and `game_ended` carries `winner` `none` with `outcome` `force_ended` and `reason`. The winner is latched once, in the step that decides the win, before `zombie_winner` is published, so a force-end during the 1 s hold after a win (all humans converted, or the timer at 0) keeps that winner and its end-of-game effects. The game outcome (`completed`) is latched in that same step, so a force-end that lands while the event is being published keeps the winner and `game_ended` names the same side; a force-end that lands before the win check declares no winner even when the win condition is met (issue #1988). A gameplay stream that ends without a win also ends with `winner` `none`.

### BR-004: Interventions

Which agent interventions Zombies accepts is decided by the intervention capability matrix (`services/game_coordinator/interventions.py`, UC-040); this rule only states how Zombies applies an accepted `revive_player` (issue #1342):

- On a dead zombie, `revive_player` respawns it at once through the same respawn as step 4: the pending respawn timer is cancelled, the zombie colour is set, then the flash, and the zombie gets the larger of `death_grace_period_seconds` and the revive spawn grace. The LED stays grey (before #1342 the generic revive turned it white, D-G27).
- On a human (always alive) it is a no-op and returns false.
- Once the winner is latched (BR-003) or the game has stopped running, it is ignored and returns false: no LED write, no grace.
- Zombies records the revive as the `zombie_respawned` span event with `respawn.cause` = `revive` (a timer respawn has `timer`); like NonStop's native respawn path it publishes no `player_revived` event (and Zombies publishes no bus event for a respawn).

State change before output: the respawn marks the zombie alive and cancels its timer before the first stream write, so a revive racing the timer (or a second revive) respawns it once.

### BR-005: Win-check precedence

The win check runs after every motion sample and every disconnect. "No humans left" is tested before time-up, so a conversion that empties the humans in the same check as the timer reaching 0 gives the zombies the win. The timer only decrements `time_remaining`; a time-up takes effect at the first check after it reaches 0. Within one frame the controller order decides which sample is processed first. The first outcome is latched: later checks (the 1 s hold) publish nothing again and the timer announces nothing.

### BR-006: Run-end cleanup

Zombies ends every `run()` (natural end, force-end, error) through the shared run-end cleanup of UC-020: open shield charge spans are closed (UC-040 A32, #1837), Zombies' own `cleanup()` cancels the game timer and respawn tasks, and this session's player analytics are cleared (#775). Issue #1938 (Zombie part).
