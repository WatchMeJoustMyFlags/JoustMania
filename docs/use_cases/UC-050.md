# Use Case: Roll Out a Controller Backend Progressively

## Overview

**Use Case ID:** UC-050
**Use Case Name:** Roll Out a Controller Backend Progressively
**Primary Actor:** Operator
**Goal:** Move controllers to a new HID backend a few at a time, advanced by the agent while health is good
**Status:** Implemented
**Requirements:** FR-071, FR-074, NFR-016, NFR-017

## Preconditions

- At least one real controller on a python HID adapter (mock-only controllers are not routed; `unstable` is only registered with a python adapter).
- `rollout_enabled` is on (otherwise the agent only dry-runs).

## Main Success Scenario

1. Operator sets `target_backend` (e.g. `unstable` for the demo, or `rust`) and `strategy=progressive` in the `rollout` set through the flag service (`scripts/flags.sh`).
2. System's controller manager publishes rollout target, strategy and count on the ~1 Hz `controller.bluetooth_health` span together with Bluetooth health samples.
3. The agent sees an active rollout and evaluates infrastructure fitness: event gap ≤ 50 ms, dropped events ≤ 2 %, movement update rate ≥ 10 Hz.
4. Fitness passes, the observed stage has caught up with the last count the agent wrote, and the dwell time since the last expansion (`AGENT_ROLLOUT_DWELL_SECONDS`, default 15 s) has elapsed; the first expansion needs no dwell.
5. The agent advances `current_controller_count` to the next stage (0 → 1 → 3 → 6 → all) through the flag service (a stack overlay, [UC-053](UC-053.md) A1).
6. The controller manager routes the first N controllers (sorted by serial) to the target backend on its next cycle.
7. Steps 3 to 6 repeat until all controllers are on the target.
8. Every cycle is recorded as an `agent.infrastructure.decision` span.

## Alternative Flows

### A1: Immediate strategy

**Trigger:** `strategy=immediate` (step 1)
**Flow:**

1. The controller manager routes every controller to the target at once; the agent only observes.
2. Use case continues at step 8.

### A2: Fitness fails

**Trigger:** A threshold is violated (step 3)
**Flow:**

1. The agent rolls the stage back (UC-051).
2. Use case ends.

### A3: Dry run

**Trigger:** `rollout_enabled` is off (step 5)
**Flow:**

1. The agent records the expansion it would make and changes nothing.
2. Use case continues at step 8.

### A4: Manual override

**Trigger:** A controller has per-serial `bluetooth_backend` targeting (UC-052) (step 6)
**Flow:**

1. The manual routing wins over the rollout for that controller.
2. Use case continues at step 7.

### A5: Rollout flags unreadable

**Trigger:** The controller manager cannot read the `rollout` flags (flagd error, provider not ready) (step 2)
**Flow:**

1. The controller manager omits `bluetooth.target_backend`, `bluetooth.rollout_count` and `bluetooth.rollout_strategy` from the health span and sets `bluetooth.rollout_read_error=true`, so a read failure is not reported as `strategy=off` (#1489).
2. The agent treats the rollout state as unknown: it records no decision and keeps its rollout record (BR-001); it neither expands, rolls back nor resets.
3. Both services log a warning once when the read error starts and an info line once when it clears, so a persistent outage is visible without a line per cycle.
4. Use case continues at step 2 on the next health span.

## Postconditions

### Success Postconditions

- All controllers run on the target backend; the trace shows each stage and its fitness.

### Failure Postconditions

- The rollout stays at its last stage (or rolls back, UC-051).

## Business Rules

### BR-001: Agent writes only the count

The agent writes `current_controller_count`; `target_backend` and `strategy` are human-owned.

The flag service, not the agent's memory, holds the stage. The agent's record of its last written stage, last expansion and rollback in flight holds only while the rollout is active and the flag service still serves that write. When an operator ends the rollout (no target backend observed and no `bluetooth.rollout_read_error`, A5), resets `current_controller_count` (a value the agent did not write), or the flag service restarts (a new boot epoch drops every overlay), the agent forgets the record and the next rollout climbs from the observed stage, without an agent restart (#1384). A running post-rollback cooldown (UC-051 step 5) is kept and expires on its own. While its write is still served, a lagging observation keeps holding the expansion (step 4); when the flag service cannot be read, the record is kept.

### BR-002: Fresh data required

The agent decides only when at least one controller has fresh health data.

### BR-003: A dry run keeps no rollout state

With `rollout_enabled` off (A3) the agent commits its last written stage, expansion time, rollback-in-flight mark and cooldown only for a write that landed (#1339). Rehearsed decisions are paced separately: one would-be expansion per dwell and one would-be rollback per cooldown, each logged and traced with `dry_run` / `rollout.dry_run`. The cooldown of an earlier real write still applies during a dry run, and a rehearsed rollback's cooldown also holds the first real expansion after `rollout_enabled` is turned back on (conservative: the rehearsal saw an unhealthy stage). Turning `rollout_enabled` back on resumes the rollout without an agent restart. Whether the write landed is read once, at the write, so a flag flip between the decision and the write cannot desync the state.
