# Use Case: Present the Talk Demo

## Overview

**Use Case ID:** UC-070
**Use Case Name:** Present the Talk Demo ("Two Standards Walk Into an Agent")
**Primary Actor:** Presenter
**Secondary Actors:** Agent, Player, Model API
**Goal:** Show live that OpenTelemetry is the agent's nervous system and OpenFeature its will
**Trigger:** Presenter starts the live part of the talk (the first beat, step 1)
**Status:** Tested
**Requirements:** FR-090, FR-091, FR-092, FR-093, FR-094, FR-095, FR-045, FR-042, FR-056, NFR-010, NFR-011, NFR-012, NFR-015, NFR-018, C-004, C-014, C-016, C-018, C-032, C-033

Backend roles follow C-018 (Jev, Claude and an OpenAI-compatible endpoint are the Model API): **Jev** is the main in-game backend, **Claude** is the manual in-game backup and
writes the post-game summary (retro), **rules** is the automatic floor. The experiments / shadow-game segment is not
part of this talk; it is described in `docs/agent-dry-run-runbook.md` (UC-043). On the talk stage the
experiment loop runs only in the screen-only fallback when Bluetooth fails at the venue (A9); the stage baseline keeps
`experiments_enabled` off otherwise. Besides the dashboard Agent tab and Jaeger, the Grafana stage view **Talk: Two
Standards** (folder Talk, [UC-035](UC-035.md) step 6) shows the beats' metrics; the talk runbook places it.

Beats 2 to 6 need no agent restart: the agent re-reads its lifecycle flags every 1 s and evaluates without the RPC cache ([flags.md §1.3](../specs/flags.md#13-reload-semantics), #1715).

## Main Success Scenario

1. **Observe:** With a game running on `rules` (on the stage stack the players start it from the menu), the presenter
   shows the dashboard Agent tab and an `agent.decide` span in Jaeger (rationale, confidence).
   On the mock stack (`make dry-run`) the game is played by `tools/demo/demo_driver.py` (FR-092: `--scenario statue`
   for the observe beat, `death_cascade` or `skill_gap` to provoke an `act` in step 2); the driver starts the game
   itself and force-ends it when the scenario is done, unless it runs with `--keep-game`.
2. **Switch to the main in-game backend:** Presenter runs `scripts/agent-backend.sh jev` (UC-044). Calm play yields `noop`
   (Jev's gate p_yes about 0.16); players near the death threshold or a collapsing game yield `act` (p_yes about
   0.72 / 0.68 ≥ 0.6), with the gate value on the stage-1 chat span. Rounds take about 0.22-0.34 s (noop) and
   0.47-0.57 s (act) (BR-002). An act is perceptible: a shield turns the player's LED and dashboard tile white with a
   countdown badge and plays the shield sound (UC-040 A16), a tempo change is heard in the music, an audio cue
   plays the lobby ping.
3. **Permissions, threshold:** Presenter runs `scripts/agent-backend.sh jev-threshold strict` (0.95); the answers
   that acted are now `held`, calm answers stay `noop`. Presenter restores `jev-threshold gate`.
4. **Backup:** Presenter runs `scripts/agent-backend.sh claude` (manual flip, no automatic chain); decisions show
   backend `claude`, the global threshold and about 3 s latency (BR-002).
5. **Kill switch:** Presenter runs `scripts/agent-killswitch.sh off` right after a Claude call starts; from the cycle
   in which the agent sees `enabled` off there are no decisions on any backend, a Claude answer that lands after that
   is `discarded` with `kill_switch` (also a timeout or an error, which then never falls back to rules), and
   post-game model calls stop too; the infrastructure loop (governed by `rollout_enabled`) is not stopped (UC-045).
   The call itself is not cancelled. Presenter runs `scripts/agent-killswitch.sh on` (A10 when the answer landed
   first).
6. **Rollback:** Presenter runs `scripts/agent-backend.sh jev`; no container restarts.
7. **Degrade:** Presenter selects the shipped `blackhole` variant of `decision.jev.base_url` (TEST-NET-1 over https)
   or cuts the uplink (restored before the game ends); decisions fall back to rules in the same cycle
   (`fallback_reason` `timeout` when the 2.5 s Jev timeout expires, or `error` when the network rejects the call within it) and the game keeps playing (UC-040 A2).
8. **Summary:** The game ends (the last player standing wins, or the presenter ends it from the menu; on the mock
   stack the demo driver ends it); the `agent.llm.retro` span shows Claude's session assessment and suggested
   improvements (`inference.used=claude`, `retro.suggestion` events), linked to the game trace.
9. Presenter runs `scripts/talk-stage.sh reset`, which restores the stage baseline, and then the pre-flight check.

## Alternative Flows

### A1: Infrastructure beat (optional)

**Trigger:** Stage stack with a real controller on the python adapter, after the degrade beat (step 7). Cut from the talk (hardware only, see the talk runbook); UC-050 / UC-051 are parked since 2026-10-19. This flow is **parked** with them (maintainer decision, 2026-10-20, #1655): it stays as written and its code and tests stay, but it is not audited and does not hold back this use case until UC-050 / UC-051 are un-parked (#1322); FR-071 (progressive rollout) and FR-072 (automatic rollback) left this Requirements line for the same reason and stay with UC-050 and UC-051
**Flow:**

1. Presenter turns `rollout_enabled` (`agent.json`) and `remediation_allowed` (`rollout.json`) on first, then sets `target_backend=unstable` and, last, `strategy=progressive` (UC-050); the agent expands, detects the violation and rolls back (UC-051), then repeats about every 30 s.
2. Presenter resets the rollout flags (`strategy`, `target_backend`, `current_controller_count`, `remediation_allowed`, `rollout_enabled`) through the flag service (runbook section 4); no agent restart: the agent drops its last written stage once the rollout is inactive or the served stage is no longer its write (UC-050 BR-001, #1384). A post-rollback cooldown still running (up to `AGENT_ROLLOUT_COOLDOWN_SECONDS`, 30 s) holds the first expansion of the next run. A dry run keeps no rollout state either (UC-050 BR-003).
3. Use case continues at step 8.

### A2: Jev unreachable or slow at the venue

**Trigger:** Decisions show `jev -> rules` with `timeout`, `error` or `backend_unavailable` (step 2 or 6)
**Flow:**

1. Rules decided every affected cycle, so the game did not stall.
2. Presenter flips the backup backend, `scripts/agent-backend.sh claude`.
3. From step 2: Presenter runs the threshold beat on Claude, where the global threshold applies:
   `scripts/agent-backend.sh threshold strict` turns the answers that acted into `held`, and
   `scripts/agent-backend.sh threshold default` restores it. Use case continues at step 5 (the backup beat is done).
4. From step 6: the `jev -> rules` rows already show the degrade beat, so the presenter narrates them as step 7.
   Use case continues at step 8, on Claude.

### A3: Remote decisions time out on Claude

**Trigger:** A Claude call exceeds `decision.claude.timeout_ms` (default 5000 ms; warm Haiku about 2.7-3.0 s,
Sonnet about 2.85 s) (step 4)
**Flow:**

1. Decisions show `fallback` with `timeout`.
2. Presenter selects the `patient` variant (8000 ms) of `decision.claude.timeout_ms` through the flag service
   (BR-001) and stays on Claude, so a Claude call can be in flight for the kill-switch beat; a call that still
   times out after the flip is discarded there all the same (step 5). `scripts/talk-stage.sh reset` (step 9)
   restores the `default` timeout.
3. Use case continues at step 5.

### A4: Budget exhausted

**Trigger:** The shared per-minute budget of remote model calls (decisions, the post-game summary and the experiment proposer, NFR-011) is
full when a remote backend wants to call (step 2 or step 4)
**Flow:**

1. The stage baseline already selects the `stage` budget (30 per minute, BR-003), so the budget runs out only when
   `AGENT_LLM_MAX_REQUESTS_PER_MINUTE` is set below 30 (it caps the flag, #1788; the pre-flight check WARNs), or when
   more than one game calls at once (each game at most one call per `decision.min_interval_ms`, 3 s, NFR-012;
   shadow games count too in the fallback, A9).
2. Decisions fall back to rules with `llm_budget_exhausted`; at game end the retro is gated before any span is
   created (only the log `agent.llm.retro_gated` with `fallback_reason=llm_budget_exhausted`; at step 8 it shows
   as A5).
3. Presenter narrates the fallback and waits: the budget is a sliding 60 s window, so calls resume once older calls
   leave it. An env override below 30 stays until the agent is restarted with it removed, which the talk does not do.
4. Use case continues at step 2 (from step 2) or step 4 (from step 4).

### A5: No summary at game end

**Trigger:** No `agent.llm.retro` span with `llm.retro.parse_ok=true` for the finished game (step 8)
**Flow:**

1. No retro span at all: the budget was full at game end (A4) or the game ended stale ([UC-042](UC-042.md) A6).
2. A span with `inference.used=none`: `inference.fallback_reason` names the cause, `no_backend_available`
   (the effective `inference.backend` is not `claude` or there is no `ANTHROPIC_API_KEY`, UC-042 Pre-2) or `agent_disabled` (the kill switch was off at game end).
3. A span with `inference.used=claude` and `llm.retro.parse_ok=false`: the model call failed (`llm.infer.error`,
   span status error, log `agent.llm.retro_failed`).
4. Presenter shows the summary of an earlier game.
5. Use case continues at step 9.

### A6: Second vendor (optional)

**Trigger:** Presenter shows a second vendor after the rollback (step 6)
**Flow:**

1. Presenter runs `scripts/agent-backend.sh openai <variant>`. The model and base URL variants exist only when they
   were added to `services/flagd/agent.json` by a reviewed edit before the stack started (C-033); a variant the
   flag file does not define is refused before anything is switched. With the shipped `unset` model or without
   `DECISION_OPENAI_API_KEY`, decisions show `openai -> rules` with `backend_unavailable`.
2. Presenter runs `scripts/agent-backend.sh jev`.
3. Use case continues at step 7.

### A7: Permissions beat (optional)

**Trigger:** Presenter shows the allow-list after the threshold beat (step 3)
**Flow:**

1. Presenter runs `scripts/talk-stage.sh permissions none 12`; on a remote backend no new decide rows appear, because the agent skips a call whose only option would be `noop` (UC-040 A14); on rules every non-noop decision is blocked `not_allowed`.
2. After 12 s, or when the presenter presses Enter, the helper restores the baseline `interventions_allowed` (`standard`). It also restores it when the beat is interrupted (Ctrl-C, closed terminal, `TERM`).
3. Use case continues at step 4.

### A8: A beat left the flags off the baseline

**Trigger:** The helper of a beat was killed before it could restore (e.g. `SIGKILL`), or a flag was flipped by hand and not flipped back; the pre-flight check FAILs (step 9)
**Flow:**

1. Presenter runs `scripts/talk-stage.sh reset`: every stage overlay is cleared and every baseline flag of the agent set is set to its stage variant, whatever the beat left behind; game-scoped interventions need no reset (they die with their game, [UC-053](UC-053.md) BR-003).
2. Presenter runs `scripts/talk-preflight.sh`; it passes.
3. Use case ends.

### A9: Bluetooth down at the venue (screen-only fallback)

**Trigger:** Fewer than `TALK_MIN_CONTROLLERS` real controllers are connected at the venue, which the pre-flight check reports as a FAIL before the talk (BR-006), or the real controllers drop during a beat (step 1 to step 7)
**Flow:**

1. Presenter runs `scripts/talk-stage.sh fallback on`: it sets `llm.eligible_game_kinds=real_and_shadow` (remote
   backends may decide on shadow games), `experiments_enabled=on`, `experiment_dynamic_enabled=on` (the agent
   declares experiments itself) and `experiment_tick_seconds` to its 10 s variant, the stage `fallback` section of
   `scripts/talk-baseline.json`, in place.
2. The experiment loop spawns shadow games on pattern-driven mock controllers (UC-046) over
   `experiment.mock_archetypes` (the baseline `all`, BR-003), which includes `calm_long`, which kills nobody and runs until
   `experiment.max_game_seconds` (300 s), so a game is in progress (BR-007, with its gaps).
3. With no real game live, the dashboard follows the newest live shadow game (BR-005): the current-backend strip
   shows its backend with the `shadow` badge, and the Controllers tab adds that game's tiles (LED colour, shield
   badge, alive or dead) under a "following shadow game" banner. Real and lobby controllers stay on the grid; the
   lobby and the menu never show the shadow controllers.
4. The pre-flight check WARNs (not FAILs) on the real-controller count and accepts the fallback variants (BR-006).
5. Beats 2 to 7 run on the shadow game's decisions; remote calls on shadow games count against
   `llm.max_requests_per_minute`, which bounds the cost. The kill-switch beat (step 5) aborts the experiments and
   force-ends their shadow games, so the screen has no game until the agent is switched back on and the next
   experiment tick (10 s) has declared an experiment and spawned its games (BR-007); the presenter narrates that gap
   or skips the beat.
6. Presenter runs `scripts/talk-stage.sh fallback off` (or `reset`) when real controllers are back, or after the talk.
7. Use case continues at step 8.

### A10: The Claude answer lands before the kill switch

**Trigger:** The in-flight Claude answer reaches the agent before the agent sees `enabled` off (step 5)
**Flow:**

1. The answer is recorded with its normal outcome (`act`, `noop`, `held` or a fallback) and an `act` is applied.
2. No later cycle decides on any backend until the agent is switched on again; the presenter points at the
   absence of new rows instead of a `discarded` row.
3. Presenter runs `scripts/agent-killswitch.sh on`.
4. Use case continues at step 6.

## Postconditions

### Success Postconditions

- Each beat showed its observable on the dashboard and in Jaeger: step 1 a decide row and its `agent.decide` span;
  step 2 rows with backend `jev` (`noop` on calm play; `act` with a perceptible effect in the game when play
  provoked it); step 3 `held` rows under the strict Jev threshold; step 4 rows with backend `claude` and the global
  threshold; step 5 no new rows while the agent is off and a `discarded` row with `kill_switch` (or A10); step 6 rows
  with backend `jev` again and no container restarted; step 7 `jev -> rules` rows with `timeout` or `error` while the
  game keeps running; step 8 an `agent.llm.retro` span with `inference.used=claude` and `llm.retro.parse_ok=true`.
- After step 9 the flags are at the stage baseline and the pre-flight check reports no FAIL.

### Failure Postconditions

- Whatever beat failed, every game kept playing and the agent never stalled it: when the selected backend could not
  answer, rules decided in the same cycle (C-004), and with the kill switch off nothing decided. No beat restarted a
  container or edited a flag file; every flag a beat changed is an overlay on the flag service (BR-001), so
  `scripts/talk-stage.sh reset` restores the stage baseline whatever a beat left behind (A8; the parked A1's rollout flags have their own
  reset, A1 step 2).

## Business Rules

### BR-001: Demo flags through the flag service

The helper scripts change flags through the flag service of the stack that is up (`FLAG_SERVICE_URL`, default the envoy route `http://localhost/flags`); they edit no file, so the same commands work on the rehearsal (`services/flagd/ci/` baseline) and the Pi stage stack (`services/flagd/`).

### BR-002: Latencies are measurements, timeouts are the limits

The Jev and Claude latencies and confidences in this use case are development-machine measurements (decide contract
§8), not acceptance limits; stage latencies are measured in rehearsal (runbook section 9, #743). The limits are the
timeouts of NFR-010: a remote decision slower than `decision.<backend>.timeout_ms` (Jev 2.5 s, Claude 5 s at the
stage baseline) falls back to rules with `timeout`.

### BR-003: Stage baseline lives in the stage helper

The stage baseline (glossary) is `decision.backend=rules`, `decision.act_confidence_threshold=default` (0.8),
`decision.jev.act_confidence_threshold=gate` (0.6), `decision.capture_content=on`, `decision.min_interval_ms`,
`decision.claude.timeout_ms` and `decision.jev.timeout_ms` at `default` (5000 ms, 2500 ms), `decision.claude.model=haiku`,
`llm.eligible_game_kinds=real_only`, `enabled` and `interventions_enabled` on, `interventions_allowed=standard`,
`policy.max_interventions_per_minute=aggressive` (4 per minute), `experiments_enabled` and `rollout_enabled` off;
`talk-stage.sh reset` also returns `decision.jev.base_url`, `decision.openai.*`, `llm.max_requests_per_minute=stage`
(30), `experiment.mock_archetypes=all`, `experiment_dynamic_enabled=off` and `experiment_tick_seconds=default`, and
leaves `decision.jev.model` alone. `standard` lets `grant_shield` and `adjust_music_tempo` fire, and `aggressive`
keeps a beat's act from being refused by the per-game budget the previous beat spent (NFR-015, #1326; the shipped
default stays 2). This baseline lives in `scripts/talk-baseline.json` (read by `scripts/talk-stage.sh` and
`scripts/talk-preflight.sh`), not in the shipped flag files, whose `interventions_allowed` default stays `ambient`
(#1301).

### BR-004: The pre-flight check proves the audience can perceive an act

`scripts/talk-preflight.sh` FAILs when `interventions_allowed` is not the stage baseline (it names `none` and `probe`
explicitly), when the resolved allow-list contains no perceptible intervention (glossary), and when the writer
default audio cue (`defaultAudioCue` in `services/agent/actions/writer.go`) does not resolve to a file in the running
audio container (`python -m services.audio.sound_catalog`). It also FAILs when a variant a beat flips to is not
declared (`decision.jev.act_confidence_threshold` needs `strict` and `gate` for step 3; `decision.jev.base_url` needs
`blackhole` for step 7) and WARNs when the `patient` variant of `decision.claude.timeout_ms` (A3) is missing: the
beat helpers refuse an undeclared variant only on stage, so the pre-flight finds it first (#743).

### BR-005: The dashboard follows a shadow game only when no real game is live

The game the dashboard follows is the real (primary) game while it is `STARTING` or `RUNNING` (the dashboard also
accepts `ENDING`, which no session sets, entity model GAME_SESSION). The dashboard polls `ListGames` every 2 s
(backing off up to 15 s on errors, paused while the tab is hidden). Without one
it is the newest live shadow game (state `STARTING` or `RUNNING` in `ListGames`, newest `start_time_ms`), and it stays
on that game while it is live, also across a transient poll error, so concurrent shadow games do not make the view
flicker. The current-backend strip describes the followed shadow game when it has decide rows; without a live real
game and without such rows it describes the game of the newest row of any kind. The controller grid hides the
players of live shadow games, except the followed game's players, which it adds (from `GetGameState(game_id)`; alive
or dead from `PlayerInfo.alive`; shield badges from that game's own `StreamGameEvents(game_id)`); a controller that
is in no live shadow game (a real or lobby controller) is never hidden, and the player count covers the tiles shown.
Shadow (pattern) controllers stay reserved: hidden from the lobby and the menu (UC-046); the filter is dashboard-only.

### BR-006: The pre-flight check counts real controllers

`scripts/talk-preflight.sh` counts the connected controllers that controller-manager reports
(`GetConnectedControllers` through envoy, which connect-proxy relays to controller-manager, C-014; reserved
controllers are not listed) whose serial is not a mock serial
(`MOCK...`, `mock_...`). Fewer than `TALK_MIN_CONTROLLERS` (default 2) is a FAIL that names the fallback; with the
fallback on (`llm.eligible_game_kinds=real_and_shadow`) it is a WARN. Controller-manager unreachable is a FAIL (a WARN
with the fallback on) that does not suggest the fallback, which needs controller-manager too. With the fallback on,
the check expects the `fallback` variants of `scripts/talk-baseline.json` (`llm.eligible_game_kinds`,
`experiments_enabled`, `experiment_dynamic_enabled`, `experiment_tick_seconds`) instead of the stage baseline.

### BR-007: The fallback keeps shadow games in progress, with bounded gaps

The fallback relies on the experiment loop: `experiments_enabled=on` and an experiment declared. The heuristic
dynamic declarer (`experiment_dynamic_enabled=on`) declares at most one experiment per experiment tick, also after the
kill-switch beat or a `fallback off` aborted the running ones. The experiment seed (the `experiment_seed` flag) is not
declared again while it stays set: the agent remembers the last seed value it acted on and acts only on a different
value. A successful declare, a skip because the seed's flag already has a live experiment (no stacking), a refused or
failed declare and a malformed value (declares nothing, logs one WARN) all set that value. Reading `off` (`{}`) on any
tick, also with the gates off, clears it, so `off` (visible for one `experiment_tick_seconds`) and then the same value
declares it again; an unreadable flag changes nothing ([UC-043](UC-043.md) A1, #1907). The archetype selection `experiment.mock_archetypes` must include `calm_long`, which kills
nobody and runs until `experiment.max_game_seconds`; `talk-stage.sh reset` restores the shipped `all` selection, and
`fallback on` and the pre-flight check WARN in fallback mode when `calm_long` is missing. A shadow game is in progress,
but the screen can be without one in two gaps: from the kill-switch beat until the first experiment tick after the
agent is switched on again, and, when no other experiment runs, between an experiment's last game and the first game
of the next one; when the declarer finds a flag to
declare, each gap lasts up to one `experiment_tick_seconds` (10 s in the fallback) plus the start-up of the next shadow
game (A9 step 5).

### BR-008: The dynamic declarer experiments on game tuning only

The dynamic declarer never experiments on a flag of its built-in denylist (`defaultDynamicDenylist`, compiled into
the agent): the experiment plumbing `shadow_policy`, the session capacity
`max_concurrent_games` and `max_shadow_games`, the tempo source `tempo_schedule_mode`, the lobby start controls
`force_all_start` and `force_all_start_seconds`, and the ceremony timing `countdown_phase_duration_ms` and
`winner_rainbow_duration_ms`. These do not tune play, so an experiment on them measures nothing (#1316). The built-in list is a floor: the `experiment_dynamic_denylist` flag only adds keys to it
(effective denylist = built-in list plus the flag's keys), and the floor also filters an explicit
`experiment_dynamic_candidates` list. An empty, blank or unreadable flag value means exactly the built-in list, so no
flag value can shrink it (C-034: a flag may only tighten; #1907). Without a candidate list the declarer rotates over
every tunable `game.json` flag outside the effective denylist.
