# Use Case: Stop the Agent with Flags

## Overview

**Use Case ID:** UC-045
**Use Case Name:** Stop the Agent with Flags
**Primary Actor:** Operator
**Goal:** Stop, or make inert, every in-game agent effect, the experiment loop and every paid model call immediately and reversibly (infrastructure rollout has its own gates, A4)
**Status:** Implemented
**Requirements:** FR-042, FR-049, FR-050, FR-051, FR-066, C-002

## Preconditions

- The agent runs.

## Main Success Scenario

1. Operator runs `scripts/agent-killswitch.sh off` (sets `enabled` off).
2. flagd reloads the file.
3. On its next cycle the agent stops evaluating and emits a throttled `agent.disabled` span instead of decisions.
4. Any remote answer still in flight is discarded on landing (`kill_switch`).
5. On the next experiment tick the agent aborts running experiments.
6. From the next game end, the retro is capture-only (`inference.fallback_reason=agent_disabled`) and the proposer does nothing: no model call, no budget slot, no `game.json` write.
7. Operator runs `scripts/agent-killswitch.sh on` to resume.

## Alternative Flows

### A1: Observe without acting

**Trigger:** Operator turns `interventions_enabled` off instead (step 1)
**Flow:**

1. The agent keeps deciding and spanning, but nothing is written to `interventions.json`.

### A2: Narrow the allow-list

**Trigger:** Operator sets `interventions_allowed` to `none` (or the host does it from the controller, UC-013)
**Flow:**

1. Remote backends are offered only `noop`; any other decision is blocked `not_allowed` by the agent and the coordinator.

### A3: Flagd unreachable

**Trigger:** The agent cannot read flags
**Flow:**

1. `enabled`, `interventions_enabled` and `rollout_enabled` fail closed (off).

### A4: Stop infrastructure remediation

**Trigger:** Operator wants the agent to stop expanding or rolling back the controller-backend rollout (step 1)
**Flow:**

1. `enabled` does not govern the infrastructure loop: with the agent off, it keeps observing `controller.bluetooth_health` and evaluating fitness.
2. Operator sets `rollout_enabled` off (`agent.json`, read live per rollout action); expansion and rollback become dry runs (decided, not applied).
3. Alternatively, operator sets `remediation_allowed` off; a failing stage is then only recommended (`remediation.action=recommended_only`), never rolled back automatically.
4. Operator turns the flag back on to resume (UC-050, UC-051).
5. Use case ends.
## Postconditions

### Success Postconditions

- No new agent effect reaches any game; existing state interventions stay in `interventions.json` until changed.
- The infrastructure rollout is unaffected by `enabled`; it is stopped only through `rollout_enabled` / `remediation_allowed` (A4).

### Failure Postconditions

- None: every gate fails closed.

## Business Rules

### BR-001: Three independent gates

`enabled` (existence), `interventions_enabled` (actuation) and `interventions_allowed` (permission) are separate flags; any one can stop interventions.

### BR-002: Post-game model calls obey the kill switch

The retro reads `enabled` at each game end; with the agent off it records a capture-only span with `inference.fallback_reason=agent_disabled` and makes no model call. The M7-4 proposer checks `enabled` (and `experiments_enabled`) at each game end and again before writing `game.json`; with the agent off it makes no model call and writes nothing (FR-042, FR-066; D-A5 resolved by PR #1284).
