# Use Case: Configure Settings in Admin Mode

## Overview

**Use Case ID:** UC-012
**Use Case Name:** Configure Settings in Admin Mode
**Primary Actor:** Host
**Goal:** Calibrate the game from a controller and persist the settings
**Status:** Tested
**Requirements:** FR-008, FR-014, FR-016, FR-017, FR-018, NFR-006, C-008

## Preconditions

- The menu is RUNNING; no other controller is in admin mode. The button stream also runs while the menu is stopped, so `on_button` ignores the combo unless the menu is RUNNING (STOPPED, GAME_STARTING) and handles the press as an ordinary button.

## Main Success Scenario

1. Host presses Cross, Circle, Square and Triangle together.
2. System flashes the controller white, switches it to ADMIN (persistent white) and starts a 60 s timer.
3. Host presses Move to cycle the option: sensitivity (blue), num_teams (turquoise), force_all_start (orange), agent_control (purple). For sensitivity, num_teams and force_all_start the system then announces the option's EFFECTIVE value (human baseline plus any active agent delta, [OWNERSHIP_MODEL](../OWNERSHIP_MODEL.md) section 6) with the step 5 colour pulse and voice line. The value is the flag service's effective value (not the in-process flagd client, which lags a write by up to a sync interval, #2092); when the flag service cannot be read, only the option colour is given (#1739).
4. Host presses Select to step the selected option forward or Start to step it backward.
5. System sends the option's new variant to the flag service as a persisted admin value ([UC-053](UC-053.md) A2) and gives feedback: a colour pulse and a voice line (sensitivity: 5 levels blue to red; num_teams: number voice; force_all_start: on/off voice). When an agent overlay makes the effective value differ from the new baseline, the system then follows with the agent cue (magenta pulse) and the effective value's colour and voice line (BR-006).
6. The flag service pushes the setting to flagd at once; the next game uses the new value, also after a restart of the flag service.
7. Host presses PS to leave admin mode.
8. System returns the controller to CONNECTED (dim).

## Alternative Flows

### A1: Circle cycles sensitivity directly

**Trigger:** Host presses Circle (step 3)
**Flow:**

1. System cycles `sensitivity` forward through ultra_slow … ultra_fast with colour and voice feedback.
2. Use case continues at step 6.

### A2: Show battery levels

**Trigger:** Host presses Triangle (step 3)
**Flow:**

1. System flashes every controller in a colour for its battery level (≥ 100 green, ≥ 80 turquoise, ≥ 60 blue, ≥ 40 yellow, else red) for 1 s.
2. Use case continues at step 3.

### A3: Toggle instructions

**Trigger:** Host presses Square (step 3)
**Flow:**

1. System toggles `game_instructions` (user set, persisted admin value) with a green / red pulse and voice.
2. From the next game start on, the game coordinator reads it: when it is on, the mode's instruction clip plays before the countdown and the countdown waits for it (UC-020 A5; JoustFFA only, other modes have no clip yet). The baseline is off (#1550); the host opts in.
3. Use case continues at step 3.

### A4: Timeout

**Trigger:** 60 s have passed since the host entered admin mode (step 3)
**Flow:**

1. System exits admin mode. The timer is not extended by activity.
2. Use case continues at step 8.

### A5: Write fails

**Trigger:** The flag service refuses the write or cannot be reached (step 5)
**Flow:**

1. System logs an error (CRITICAL when the flag service cannot be reached); the setting is not applied. A write that applied but could not be persisted is logged as an error and holds until the flag service restarts.
2. Use case continues at step 3.

### A6: Agent control and force start

**Trigger:** Host selects `agent_control` (see UC-013) or holds the trigger (see UC-014) (step 3)
**Flow:**

1. System hands over to UC-013 (agent control) or UC-014 (force start).
2. Use case ends.

## Postconditions

### Success Postconditions

- The new setting is a persisted admin value on the flag service and applies from the next game on; the flag files are unchanged.

### Failure Postconditions

- The setting is unchanged.

## Business Rules

### BR-001: Settings are frozen per game

Admin changes apply to the **next** game; a running game keeps the values it started with (`force_all_start` is read at force start).

### BR-002: Not every flag is controller-cycled

`random_assignment`, `nonstop.time_limit_seconds`, `invincibility_seconds`, `fight_club.min_rounds` and `werewolf.reveal_time_seconds` are set by file or flagd only (#815).

### BR-003: Werewolf sensitivity

`sensitivity` targeting forces level 3 for Werewolf, so the admin baseline does not apply there.

### BR-004: One admin session at a time

Only one controller holds admin mode (#1341). While another controller holds it, a second controller's combo is ignored and the press is handled as an ordinary button; admin buttons and the PS exit from a controller that does not own the session are ignored. The lock is released when the owner leaves ADMIN (PS exit, timeout, disconnect) and when the menu clears controller states (lobby reset, button stream reconnect, StopMenu). A session whose owner is no longer in ADMIN does not hold the lock and is released at the next combo.

### BR-005: Admin button map

Buttons of the controller that owns the admin session (`handlers/admin.py` `handle_button_event`; BR-004 applies to all other controllers):

| Button | Action | Feedback |
|--------|--------|----------|
| Move | Next option, wrapping: sensitivity, num_teams, force_all_start, agent_control (step 3) | Option colour for 1 s, then white again |
| Select | Step the selected option forward (step 4); agent_control: escalate (UC-013) | Value pulse and voice (step 5); agent_control: own colours and numbered voice (UC-013) |
| Start | Step the selected option backward (step 4); agent_control: restrict (UC-013) | Value pulse and voice (step 5); agent_control: own colours and numbered voice (UC-013) |
| Cross | Next game mode (UC-011) | Mode colour pulse and voice |
| Circle | Cycle sensitivity (A1) | Sensitivity pulse and voice |
| Triangle | Show battery levels (A2) | Battery colours on every controller |
| Square | Toggle instructions (A3) | Green / red pulse and voice |
| Trigger (hold) | Force start (UC-014) | Charging LED |
| PS | Leave admin mode (step 7) | Controller returns to CONNECTED |

Value feedback colours (`_show_value_feedback`): sensitivity 0 to 4 is blue, turquoise, green, orange, red (voice per level); num_teams (2 to 6) is a gradient from green at 2 to red at 6, with a number voice; force_all_start is green when on and red when off, with a true / false voice. With `force_all_start` on a force start takes every connected controller, otherwise the ready controllers plus the host (UC-014 step 3).

### BR-006: Announcements are effective, steps are baseline

Selecting an option (step 3, Move) announces the EFFECTIVE value. Stepping a value (steps 4 and 5, Select / Start, and Circle in A1) still writes the human baseline `defaultVariant` and first announces the NEW SETTING; if an agent overlay makes the effective value differ from it, the system follows with the agent cue (magenta pulse, as the coordinator's #818 cue) and the effective value. Without an overlay nothing follows (OWNERSHIP_MODEL section 6; D-M6, #1739). The overlay is read from the flag service's view of the flag right after the write (its effective value differs from the new baseline), never from the in-process flagd client, which can still serve the previous value for up to a sync interval and would announce a second, stale value (#2092). The persisted host write clears a stack overlay and ranks above a `real` promotion overlay, and experiment arms (shadow games only) and game-scoped interventions are not part of this flag's effective value, so the follow-up fires only when another stack write lands between the write and the read.

### BR-007: Presses are debounced on event time

The menu debounces each button per controller on the time the press HAPPENED (the `ButtonEvent.timestamp` the controller manager stamps, in ms), not on the time the menu gets to process it. A stalled menu loop (GC, a slow flag write, a busy Pi) therefore never merges two distinct presses into one: presses further apart than the interval (admin 300 ms; the lobby's connected / ready handlers share the same `ButtonDebouncer` at 100 ms, [UC-010](UC-010.md), [UC-011](UC-011.md)) all apply, presses closer than it are one press. An event without a timestamp falls back to the processing time. No proto change.
