# Use Case: Unpair a Controller

## Overview

**Use Case ID:** UC-005
**Use Case Name:** Unpair a Controller
**Primary Actor:** Operator
**Goal:** Make the Pi forget one PS Move controller on every Bluetooth adapter, e.g. a borrowed controller or one registered on the wrong adapter
**Status:** Tested
**Requirements:** FR-123, C-009

## Preconditions

- The stack is running with the pairing daemon (UC-001) and the dashboard.
- The controller was paired over USB earlier (UC-001), so BlueZ holds at least one registration for its Bluetooth address.

## Main Success Scenario

1. Operator selects "Unpair" on the controller's card on the dashboard.
2. System asks the operator to confirm, naming the controller's serial, that it disconnects now and that a controller still plugged in over USB is paired again only after it is unplugged and plugged back in (A8).
3. Operator confirms.
4. System sends the unpair request for the controller's Bluetooth address through the connect-proxy (`POST /pairing/unpair`) to the pairing daemon (`POST /controllers/{address}/unpair`, BR-003).
5. System finds every PS Move registration of that address (BR-001) on every adapter and removes each one through BlueZ (`Adapter1.RemoveDevice`), which also drops its trust and link key and closes its connection; a registration BlueZ has not loaded (its adapter is not plugged in) is deleted from `/var/lib/bluetooth` (BR-002).
6. System forgets that the controller was paired in this daemon session, so the next time it is plugged in over USB it is paired again (UC-001, not UC-001 A1); a controller still on USB waits for that unplug and replug (A8).
7. System answers with one result per registration found (`removed` or `already_absent`), the adapters, and whether the controller is on USB (`on_usb`); the dashboard shows the result on the card and in the event feed.
8. The controller manager sees the controller disconnect and removes it from the lobby (UC-002 A1).

## Alternative Flows

### A1: Operator cancels

**Trigger:** Operator declines the confirmation (step 3)
**Flow:**

1. System sends no request; nothing changes.
2. Use case ends.

### A2: Controller is in a running game

**Trigger:** The controller plays in a running game when the operator confirms (step 3)
**Flow:**

1. System does not refuse: the confirmation in step 2 warns that a player in a running game is eliminated.
2. Use case continues at step 4; at step 8 the disconnect also eliminates the player (UC-002 A1 step 3, UC-020 A2).

### A3: Controller is not connected

**Trigger:** The controller is switched off or out of range, so the dashboard shows no card for it (step 1)
**Flow:**

1. Operator sends `POST /pairing/unpair` with the controller's Bluetooth address directly (for example with `curl` through envoy on port 80).
2. Use case continues at step 5; step 8 does not apply.

### A4: Unknown serial

**Trigger:** The scan finds no registration of the address that BR-001 accepts, in BlueZ or in `/var/lib/bluetooth` (step 5)
**Flow:**

1. System removes nothing and answers "not registered" (HTTP 404); the dashboard shows the message. Registrations that were found but are gone by the time they are removed (BlueZ answers `DoesNotExist`, or the directory has vanished) are not this flow: they count as `already_absent` and the answer is 200 (BR-002).
2. Use case ends.

### A5: Not a Bluetooth address

**Trigger:** The serial is not a Bluetooth address, e.g. a mock controller (`MOCK0001`) (step 4)
**Flow:**

1. System rejects the request (HTTP 400) and removes nothing. The dashboard does not offer "Unpair" on cards whose serial is not a Bluetooth address.
2. Use case ends.

### A6: A pairing or another unpair is running

**Trigger:** The pairing daemon is pairing a controller over USB (UC-001 from adapter selection, step 3, through the trust, step 5, including the BlueZ restart), or another unpair is running, e.g. a double click (step 5)
**Flow:**

1. System refuses (HTTP 409) and removes nothing: a pairing is not cut in half, and no registration is judged during the BlueZ restart window. A USB pairing that starts while an unpair runs waits for it. A pairing holds the lock for a bounded time: each rust-hid call has a 15 s deadline and the backend's pair step a 20 s one, so a hung backend fails that pairing instead of blocking unpairs.
2. Use case ends; the operator retries a few seconds later.

### A7: Pairing daemon or BlueZ unavailable

**Trigger:** The connect-proxy cannot reach the pairing daemon, BlueZ answers with an error, the system bus fails, or a removal fails (step 4 or 5)
**Flow:**

1. System answers with an error and the dashboard shows it: HTTP 502 from the connect-proxy when the daemon is unreachable; HTTP 503 from the pairing daemon for a BlueZ or D-Bus error or any unexpected error, and for any registration that could not be removed, with the per-registration results (`removed`, `already_absent`, `failed`) in the body. Registrations removed before the failure stay removed. When bluetoothd is not running at all (nobody owns `org.bluez`, or the system bus socket is missing), this is not A7: the saved registrations are removed from `/var/lib/bluetooth` (BR-002).
2. Use case ends; the operator can retry.

### A8: Controller still plugged in over USB

**Trigger:** The controller is on USB when it is unpaired (step 6)
**Flow:**

1. System does not pair it again while it stays plugged in, which would undo the unpair the operator just asked for. (A pairing no longer restarts the Bluetooth service, UC-001 BR-005, so this rule protects the operator's intent, not the other controllers.) The answer says `on_usb: true`, and the dashboard asks the operator to unplug it.
2. When the controller has left USB and is plugged in again, System pairs it as in UC-001. The daemon notices this by polling USB (`pairing.poll_interval`, default 10 s): a poll that no longer sees the controller, or sees it under another HID device path, re-arms pairing. An unplug and replug within one poll that keeps the same device path goes unnoticed, so the operator leaves it unplugged for about 10 s. A pairing that was already waiting for the unpair to finish re-checks this before it selects an adapter.
3. Use case ends.

### A9: Remove every PS Move pairing from the host

**Trigger:** The operator wants a clean slate for all controllers (a wrong adapter layout, stale registrations after an adapter change, a venue reset) instead of one controller (step 1); the host has a shell and the dashboard is not needed
**Flow:**

1. Operator runs `scripts/hardware/reset_bluetooth_connections.sh --dry-run` on the host; System lists the PS Move registrations it would remove (`python -m psmove_pairing.registrations --dry-run` in the pairing-daemon container) and changes nothing, and the pairing daemon is not restarted.
2. Operator runs `scripts/hardware/reset_bluetooth_connections.sh`. System runs `python -m psmove_pairing.registrations` inside the running `pairing-daemon` container (Compose as the Pi runs it, `scripts/setup/joustmania-compose.sh exec`), or, when that container is not running, in a one-off container (`run --rm --no-deps`). Every PS Move registration of every address is removed as in steps 5 to 6 with the same matcher (BR-001) and storage rules (BR-002); other Bluetooth devices (keyboards, headsets) are left alone; the host is not rebooted.
3. After a real run System restarts the pairing daemon (`restart pairing-daemon`) so it forgets the controllers it verified this session and re-pairs them over USB. A run in a one-off container needs no restart.
4. The script exits non-zero when any removal failed (UC-005 A7 results); the daemon is restarted nevertheless.
5. Operator plugs each controller in over USB again (UC-001); the controller is paired anew.
6. Use case ends.

## Postconditions

### Success Postconditions

- BlueZ holds no registration and no trust for the controller on any adapter, and adapter load (UC-001 BR-001) no longer counts it.
- The controller is disconnected; it can be paired again over USB (UC-001), after an unplug and replug if it was on USB (A8).

### Failure Postconditions

- Nothing changed (A1, A4, A5, A6), or only the registrations removed before a BlueZ failure are gone (A7).

## Business Rules

### BR-001: PS Move devices only

A registration is taken only when the address has at least one registration that is a PS Move, by the same matcher as the registration reset (C-011, #1429): BlueZ reports a `Modalias` with Sony's vendor id `054C` and product id `03D5` (ZCM1) or `0C5E` (ZCM2), or, without a `Modalias`, the name `Motion Controller`, the device class `0x002508` and the HID service UUID all match; a saved registration counts when its `info` file's `[DeviceID]` names vendor `0x054C` and product `0x03D5` or `0x0C5E`. Once one matched, the copies of the same address that carry no device identity (no `Modalias` and no class in BlueZ, no `[DeviceID]` saved: a controller trusted over USB that never connected to that adapter) are taken too, so the controller is gone from every adapter. A copy identified as another device is never taken, and other addresses are never touched. If only identity-less copies exist, nothing is taken (A4); they go at the controller's next re-pair (UC-001 BR-004).

### BR-002: Saved registrations and idempotency

BlueZ owns the storage of the adapters it presents; those registrations are removed only through BlueZ. A directory `/var/lib/bluetooth/<adapter>/<address>` of an adapter BlueZ does not present (unplugged) is deleted directly (the pairing daemon mounts `/var/lib/bluetooth` read-write). When bluetoothd is not running (nobody owns `org.bluez`, or the system bus socket is missing), every saved registration of the address is deleted, which is safe because bluetoothd reads them only at startup; any other D-Bus error removes nothing (A7). A registration that is already gone counts as `already_absent`, which is success: repeating an unpair answers 200 or, once nothing is found, 404.

### BR-003: Operator-only endpoint without authentication

The unpair endpoint is an operator action with no authentication; the trust model is "whoever reaches the stack is the operator", as for the rest of the dashboard. It is narrowed in three ways:

- The pairing daemon binds its port 8002 (health and control API) only to the addresses in `CONTROL_BIND`. The daemon runs on the host network in the full and the lite stack (#1402) and binds loopback and the docker0 gateway (`127.0.0.1,172.17.0.1`, override with `PAIRING_CONTROL_BIND`), which is what `host.docker.internal` resolves to for the connect-proxy (`extra_hosts: host-gateway`); the LAN cannot reach port 8002. An address that cannot be bound at start (docker0 not up yet) is retried in the background with backoff (1 s doubling to 30 s) until it binds; `/healthz` reports `control_bind.requested` and `control_bind.bound`, the gauge `pairing_control_bind_unbound_addresses` counts the missing ones, and `scripts/talk-preflight.sh` warns when the connect-proxy cannot reach `host.docker.internal:8002` (#1450).
- The connect-proxy rejects (HTTP 403) a request that does not come from the stack's own pages, so a web page open on the operator's laptop cannot unpair controllers (#1450):
  - a `Host` that is not an IP literal (IPv4 or IPv6, any port), `localhost` or the Pi's own host name as `<name>` or `<name>.local` (read once at start from the host's `/etc/hostname`, mounted read-only into the connect-proxy; ignored when absent; Raspberry Pi OS default `raspberrypi` / `raspberrypi.local`) or one of the extra names in `JOUSTMANIA_HOSTNAMES` (comma-separated, case-insensitive, empty by default). This stops DNS rebinding, where an attacker's host name resolves to the Pi and the page sends matching `Origin` and `Host` values that both name the attacker's host;
  - a `Sec-Fetch-Site` header other than `same-origin` or `none`, when the browser sends one;
  - an `Origin` header that names another host than the request's `Host` (cross-site request forgery).

  The dashboard is same-origin behind envoy, so the browser sends the Host the operator typed: the Pi's IP, its host name or `<host name>.local` (mDNS), or a name listed in `JOUSTMANIA_HOSTNAMES` (add any other name the operator uses, e.g. a DNS alias, in `.env.local`). `curl` and scripts send no `Origin` or `Sec-Fetch-Site` and pass when they address the Pi by IP, `localhost`, its host name or a listed name.
- `POST /pairing/unpair` through envoy on port 80 is reachable by anyone on the Pi's network, so keep the Pi on a trusted network (the talk uses a phone hotspot). A host firewall (e.g. ufw) must allow the Docker bridge to reach host port 8002, or the connect-proxy answers 502.
