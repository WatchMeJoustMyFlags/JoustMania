# Use Case: Unpair a Controller

## Overview

**Use Case ID:** UC-005
**Use Case Name:** Unpair a Controller
**Primary Actor:** Operator
**Goal:** Make the Pi forget one PS Move controller on every Bluetooth adapter, e.g. a borrowed controller or one registered on the wrong adapter
**Status:** Implemented
**Requirements:** FR-123, C-009

## Preconditions

- The stack is running with the pairing daemon (UC-001) and the dashboard.
- The controller was paired over USB earlier (UC-001), so BlueZ holds at least one registration for its Bluetooth address.

## Main Success Scenario

1. Operator selects "Unpair" on the controller's card on the dashboard.
2. System asks the operator to confirm, naming the controller's serial and that it disconnects now.
3. Operator confirms.
4. System sends the unpair request for the controller's Bluetooth address through the connect-proxy (`POST /pairing/unpair`) to the pairing daemon (`POST /controllers/{address}/unpair`, BR-003).
5. System finds every PS Move registration of that address (BR-001) on every adapter and removes each one through BlueZ (`Adapter1.RemoveDevice`), which also drops its trust and link key and closes its connection; a registration BlueZ has not loaded (its adapter is not plugged in) is deleted from `/var/lib/bluetooth` (BR-002).
6. System forgets that the controller was paired in this daemon session, so plugging it in over USB pairs it again (UC-001, not UC-001 A1).
7. System answers with the number of removed registrations and the adapters they were on; the dashboard shows the result.
8. The controller manager sees the controller disconnect and removes it from the lobby (UC-002 A1).

## Alternative Flows

### A1: Operator cancels

**Trigger:** Operator declines the confirmation (step 3)
**Flow:**

1. System sends no request; nothing changes.
2. Use case ends.

### A2: Controller is in a running game

**Trigger:** The controller plays in a running game when the operator confirms (step 3)
**Flow:**

1. System does not refuse: the confirmation in step 2 warns that a player in a running game is eliminated.
2. Use case continues at step 4; at step 8 the disconnect also eliminates the player (UC-002 A1 step 3, UC-020 A2).

### A3: Controller is not connected

**Trigger:** The controller is switched off or out of range, so the dashboard shows no card for it (step 1)
**Flow:**

1. Operator sends `POST /pairing/unpair` with the controller's Bluetooth address directly (for example with `curl` through envoy on port 80).
2. Use case continues at step 5; step 8 does not apply.

### A4: Unknown serial

**Trigger:** BlueZ and `/var/lib/bluetooth` hold no PS Move registration for the address (step 5)
**Flow:**

1. System removes nothing and answers "not registered" (HTTP 404); the dashboard shows the message.
2. Use case ends.

### A5: Not a Bluetooth address

**Trigger:** The serial is not a Bluetooth address, e.g. a mock controller (`MOCK0001`) (step 4)
**Flow:**

1. System rejects the request (HTTP 400) and removes nothing. The dashboard does not offer "Unpair" on cards whose serial is not a Bluetooth address.
2. Use case ends.

### A6: Controller is being paired

**Trigger:** The pairing daemon is pairing this controller over USB right now (UC-001 steps 3 to 5) (step 5)
**Flow:**

1. System refuses (HTTP 409) and removes nothing, so the pairing is not cut in half.
2. Use case ends; the operator can unpair once the USB pairing has finished.

### A7: Pairing daemon or BlueZ unavailable

**Trigger:** The connect-proxy cannot reach the pairing daemon, or BlueZ does not answer on D-Bus (step 4 or 5)
**Flow:**

1. System answers with an error (HTTP 502 from the connect-proxy, 503 from the pairing daemon) and the dashboard shows it; registrations removed before the failure stay removed.
2. Use case ends; the operator can retry.

## Postconditions

### Success Postconditions

- BlueZ holds no registration and no trust for the controller on any adapter, and adapter load (UC-001 BR-001) no longer counts it.
- The controller is disconnected; it can be paired again over USB (UC-001).

### Failure Postconditions

- Nothing changed (A1, A4, A5, A6), or only the registrations removed before a BlueZ failure are gone (A7).

## Business Rules

### BR-001: PS Move devices only

A registration is removed only when it is a PS Move, by the same matcher as the registration reset (C-011, #1429): BlueZ reports a `Modalias` with Sony's vendor id `054C` and product id `03D5` (ZCM1) or `0C5E` (ZCM2 / ZCM2E), or, without a `Modalias`, the name `Motion Controller`, the device class `0x002508` and the HID service UUID all match. A saved-only registration counts when its `info` file's `[DeviceID]` names vendor `0x054C` and product `0x03D5` or `0x0C5E`. Any other device with the same address is left alone, and other devices are never touched. A registration with none of these properties (a controller paired over USB that never connected) is not matched (A4); its copies on other adapters go at its next re-pair (UC-001 BR-004).

### BR-002: Saved-only registrations

A directory `/var/lib/bluetooth/<adapter>/<address>` that BlueZ has not loaded, typically because that adapter is not plugged in, is deleted directly (the pairing daemon mounts `/var/lib/bluetooth` read-write). Registrations BlueZ has loaded are removed only through BlueZ.

### BR-003: Operator-only endpoint without authentication

The unpair endpoint is an operator action with the same trust model as the rest of the stack: there is no authentication, so anyone who reaches envoy on port 80 (or the pairing daemon's port 8002 on the host) can call it. The pairing daemon serves it on its health port 8002: on the host network in the full stack, where the connect-proxy reaches it through the Docker host gateway (`host.docker.internal`), and on the Compose network as `pairing-daemon:8002` in the lite stack. Keep the Pi on a trusted network (the talk uses a phone hotspot).
