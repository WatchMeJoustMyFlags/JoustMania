# Use Case: Play Joust Free-for-All

## Overview

**Use Case ID:** UC-020
**Use Case Name:** Play Joust Free-for-All
**Primary Actor:** Player
**Goal:** Be the last player standing
**Status:** Tested
**Requirements:** FR-020, FR-027, FR-030, FR-032, FR-035, FR-036

## Preconditions

- A JoustFFA game was started with at least two players (UC-010).

## Main Success Scenario

1. System assigns every player to team 0, publishes `players_initialized` and gives each player a unique colour in the `color_assignment` phase (shown when the gameplay stream starts).
2. System starts the game music at `audio_volume.countdown_music`, publishes `game_started`, plays the countdown (UC-010 step 6) and then raises the music to the game volume.
3. Players try to jostle each other's controllers while keeping their own still.
4. System alternates the music between normal-speed (1.0×) and 1.3× windows (UC-031) and adjusts thresholds accordingly.
5. System eliminates any player whose movement exceeds the threshold (UC-030) and publishes `player_death` with the serial and the number of players left (#1258).
6. When one player is left, System publishes `game_winner` with the serial, shows a rainbow on the winner for `winner_rainbow_duration_ms` (default 3 s) and plays "congratulations".
7. System publishes `player_analytics` for each player (when `analytics.enabled` is on) and `game_ended` with the duration.

## Alternative Flows

### A1: Tie

**Trigger:** No player is left at a win check, which happens only when an agent elimination (UC-040, `eliminate_player`) and another death fall between two win checks (step 6)
**Flow:**

1. System publishes `game_tie` instead of `game_winner`; no rainbow is shown.
2. Use case continues at step 7.

### A2: Player disconnects

**Trigger:** A controller disconnects during the game (step 3), including during the countdown or the EMA warmup; such a disconnect is handled before the first gameplay frame
**Flow:**

1. System eliminates the player through the normal death path (`player_death`, explosion, death effect; no motion involved) and checks the win condition at once (BR-001).
2. Use case continues at step 6 when one player is left, otherwise at step 3.

### A3: Agent intervention

**Trigger:** The agent applies an intervention (UC-040) (step 3)
**Flow:**

1. System applies it through the game's own code paths (e.g. tempo change, shield, elimination) and publishes `agent_intervention`. `revive_player` is denied in FFA by the coordinator's mode capability matrix (`mode_unsupported`).
2. Use case continues at step 3.

### A4: Force-ended

**Trigger:** The game is force-ended (UC-027: operator Stop, `ForceEndGame`, agent `end_game`, a real game preempting a shadow game) while the game loop still runs, whatever the alive count (step 3)
**Flow:**

1. System stops the game loop without a winner: no `game_winner`, no rainbow, no "congratulations". A force-end before the game has started (during colour assignment or the instruction wait) skips the start (no `game_started`, countdown, stream or music) and ends with exactly one `game_ended`, outcome `force_ended`.
2. System records outcome `force_ended` with the force-end reason (BR-003). Every survivor's span gets `player_survived`, not `victory`, and no player has `winner = true`.
3. System publishes `player_analytics` for each player and `game_ended` with the duration, `outcome = force_ended` and the reason, then `game_force_ended` (UC-027 step 3).
4. Use case ends.

### A5: Instructions on

**Trigger:** The host has switched spoken instructions on (`game_instructions`, user set; FR-014, UC-012 A3) when the game starts, after colour assignment and before the music and the countdown (step 2)
**Flow:**

1. System reads `game_instructions` at game start (use time, not cached). When it is off, or cannot be read, or the game is a shadow game (no audience), the main scenario runs unchanged: no clip, no wait.
2. System plays the mode's instruction clip (JoustFFA: `FFA-instructions`) before it starts the game music, and waits until the clip has finished: it waits for the clip length the audio service reports in `PlaySoundResponse.duration_seconds`, capped at 60 s. A clip that is not heard (`play_audio` off, audio hardware not open, file missing) reports 0 s, so the game does not wait. A force-end during the wait stops it at once, and the game does not start: no gameplay stream, no music, no `game_started`, no `countdown_start`; the game ends as in A4 steps 2 to 4 (`outcome = force_ended`, BR-003). The system also sends the audio service `StopSound` (best effort and bounded to 2 s: a failure or timeout is logged and never blocks the end), so the clip does not keep playing after the game has ended (#1586).
3. System records `game.instructions` on `initialization_phase` (`played`, `off`, `shadow`, `no_audio` when there is no audio client, `failed` when `PlaySound` fails, or `no_clip` for a mode without a clip; other modes have no clip mapping yet, so they record `no_clip` and do not wait, and their recordings and `Sound` entries stay for the backlog, #1550; only `played` waits) and, when played, a `game.instructions_played` event with the clip and its length (telemetry.md §3.2).
4. Use case continues at step 2.

## Postconditions

### Success Postconditions

- The game session is ENDED, the outcome (`winner`, `tie` or `force_ended`, BR-003) and the winner, if any, are in the event stream, and the lobby is restored.

### Failure Postconditions

- On an internal error, System publishes `game_error` and ends the session.

## Business Rules

### BR-001: Win condition

The game ends when at most one player is alive; win detection runs after every controller sample of a frame and after every disconnect, so the last player standing can never die through motion.

### BR-002: Grace period

`death_grace_period_seconds` has no effect in FFA (no respawn).

### BR-003: End-of-game outcome

Every JoustFFA game ends with exactly one outcome (#1328):

| Outcome | When | Recorded |
|---|---|---|
| `winner` | the loop ended on BR-001 with one player alive | `game_winner` (serial); `victory` with `winner = true` on the winner's span only |
| `tie` | the loop ended on BR-001 with no player alive (A1) | `game_tie`; no `victory` event |
| `force_ended` | the game was force-ended (A4), whatever the alive count | the force-end reason; `player_survived` on each survivor's span; no `victory`, no winner |

`force_ended` takes precedence while the game loop runs: a force-end that lands while one player is left but before the loop ended still records `force_ended`, because the game did not reach its win condition. The outcome is latched when the loop ends (win condition met, or loop stopped): a force-end that arrives afterwards (during the post-win hold, the winner rainbow or teardown, e.g. `preempted_by_real_game`) stops the effects early but does not change a `winner` or `tie` outcome. The outcome is on the game root span (`game.outcome`, `game.end_reason` for `force_ended`, `game.winner` for `winner`), on a `game.outcome` event of `teardown_phase`, in the `game_ended` event (`outcome`, `reason`) (telemetry.md §3.2, §5), and as the `outcome` label of `games_completed_total` (telemetry.md §6, shown by the Game & Players dashboard's "Games by Outcome" panel; #1427). The label has five bounded values: these outcomes, `completed` (also for an unknown or unreadable outcome) and `error` for a session that published `game_error` (gRPC clients not initialized, mode creation failed, or the game loop raised), so a failed start never shares a slice with a natural end. Before #1328 a force-ended FFA game put `victory` (with `winner = false`) on every survivor, which read as several victories. Dry run #2 game `game_1c65c87d4f26` was force-ended at ~114 s by the dry-run driver (`ForceEndGame`, reason `dry_run_2`) with four players alive.

Other modes: see UC-021, UC-022, UC-023, UC-025, UC-026 (each records `completed` or `force_ended` with the reason).
