# Use Case: Observe the System

## Overview

**Use Case ID:** UC-035
**Use Case Name:** Observe the System
**Primary Actor:** Operator, Presenter
**Goal:** See what the game, the controllers and the agent are doing, from one URL
**Trigger:** An operator or the presenter opens `http://<host>/` in a browser (the stack's single entry point, BR-001)
**Status:** Implemented
**Requirements:** FR-043, FR-059, FR-080, FR-081, FR-082, FR-084, FR-085, FR-103, FR-122, NFR-002, NFR-003, NFR-021, NFR-022, NFR-023, NFR-024, C-014, C-015

## Preconditions

- The full stack runs (not the lite stack, which has no Jaeger, VictoriaMetrics, Loki or Grafana).

## Main Success Scenario

1. System (envoy on port 80) serves the dashboard and, under the same host, Jaeger (`/jaeger/`), Grafana (`/grafana/`), VictoriaMetrics (`/victoria-metrics/`), the agent's experiment dossier (`/experiments`) and the browser API, which connect-proxy translates to the services' gRPC calls (C-014, BR-001).
2. System shows the dashboard's Controllers view: a live controller grid (LED colour, acceleration, connection-quality badge with its p95 and longest report gap, BR-005; an agent-shield badge with its countdown while a shield runs, FR-084) fed by the dashboard's own gameplay stream, an observer that never claims a controller (BR-006, #1595); and the game state, alive count and event feed (game start and end, with the winner from `game_winner`; the Starting state on `countdown_start`; the Ended state on `game_ended`, `game_force_ended`, `game_error` ("Game ended with an error") or `game_start_error` (with its error message); eliminations; agent shields) from the game event stream, which connect-proxy relays from the game coordinator (A4 when either stream drops).
3. Operator opens the Agent tab; System shows the decision feed from `agent.decide` spans in Jaeger, the agent activity and effective flags from Loki log lines, and intervention write counts from VictoriaMetrics (A3 when a source is down).
4. Operator opens the Experiments tab; System shows the running cohort experiments and their arms from agent log lines in Loki (A1 for one experiment's dossier).
5. Operator follows a game in Jaeger: the game's root span (named after the mode), its phases, one span per player, and the agent's in-game spans as remote children of `game_cycle` (UC-040 BR-013); coordinator and agent spans name the game kind in two vocabularies (BR-002).
6. Operator watches the Grafana dashboards, in four folders: Game (game and players, including the per-player acceleration against the warning and death lines; controllers and Bluetooth, including the connection quality per controller, BR-005, and each adapter's identity, HCI error counters and link roles, FR-122), Agent (decisions by backend and outcome, remote-model latency and usage, interventions and their measured effect, shadow games), Platform (infrastructure and services; flags and the flag service) and Talk (one dashboard for the talk, `Talk: Two Standards`, UC-070). Every latency panel reads histograms with their declared buckets (BR-004). The dashboards, their panels and the metric names are listed in [telemetry.md §6](../specs/telemetry.md#6-metrics) (#1427).
7. Operator searches the logs in Grafana (Explore on Loki), by the game's trace id.

## Alternative Flows

### A1: Experiment dossier

**Trigger:** Operator opens `/experiments` or `/experiments/<id>` (step 4)
**Flow:**

1. System (the agent) answers `/experiments` with the list of experiments from its journal (id, status, flag, candidate, verdict, start and end; an HTML table for a browser, JSON otherwise) and `/experiments/<id>` with that experiment's dossier as JSON (thesis, arms, games with their outcome and fitness, verdict, decision, notes and trace hints). An unknown id is answered 404 `experiment not found`; with the agent down, envoy answers with its own error.
2. Use case continues at step 5.

### A2: Alert fires (retired)

**Trigger:** None since #1425: Prometheus alerting was removed (FR-083 Rejected, maintainer decision 2026-10-16); the operator watches Grafana instead (step 6). The ID is kept so it is not reused.
**Flow:**

1. No alert rules are loaded; VictoriaMetrics (`/victoria-metrics/`) is the only metrics store (#1449).
2. Use case continues at step 6.

### A3: A telemetry backend or the agent is down

**Trigger:** Jaeger, VictoriaMetrics, Loki, Grafana or the agent is unreachable while the operator uses the dashboard (step 3; Grafana and the agent also at step 4, step 6 and A1)
**Flow:**

1. The collector keeps exporting to the others: each backend has its own exporter, the agent fan-out is best effort and never blocks the pipeline (NFR-024), and the collector's memory limit bounds what queues up for a down backend (NFR-021).
2. The dashboard shows what it can still read. A panel that has rendered keeps its last data and marks it `stale — last updated <n>s ago`; a panel that never rendered shows `Could not reach Jaeger for agent.decide spans.` (Jaeger down) or `Could not reach Loki for agent telemetry.` / `Could not reach Loki for experiment telemetry.` (Loki down). With VictoriaMetrics down the Applied count shows `n/a` ("VictoriaMetrics unreachable") and the blocked counts come from Loki. With the agent down the Agent and Experiments tabs show no new agent rows, and `/experiments` fails (A1). With Grafana down the Metrics tab's embedded dashboard and the log links fail; the rest of the dashboard is unaffected.
3. Use case continues at step 3.

### A4: The dashboard loses a live stream

**Trigger:** The gameplay stream or the game event stream to the browser ends or fails (connect-proxy, the controller manager or the game coordinator restarts) (step 2)
**Flow:**

1. When the gameplay stream fails or ends, the controller grid shows `Connection lost. Retrying...`; when the game event stream fails or ends, the event feed and the shield badges stop updating, without a message.
2. The dashboard reopens a stream that failed and a stream that ended cleanly (connect-proxy ends the game event stream when the coordinator's stream ends), every 2 s until it opens again, so the next game's events show (#1706).
3. Use case continues at step 2.

## Postconditions

### Success Postconditions

- The operator can find one game's spans in Jaeger and its series in VictoriaMetrics by its game id, and its log lines in Loki by the game's trace id.

### Failure Postconditions

- With any telemetry backend, the collector or the agent down, the game services never wait on telemetry: recording a span, a metric or a log line neither blocks nor raises on the game path (export runs on background threads, NFR-024), so a game starts, runs its loop at the NFR-003 rate and ends as it does with telemetry up. Telemetry recorded while a backend was down may be missing from that backend.

## Business Rules

### BR-001: One entry point

Envoy on port 80 is the only host entry for the UIs and the HTTP and browser APIs. Every other published port, and the interface it is published on, is listed in C-015; docs that say `:8080` are stale (D-E1). The pairing daemon's unpair port is narrowed by UC-005 BR-003.

### BR-002: Two `game.kind` vocabularies

Coordinator spans and metrics say `primary` / `shadow`, agent spans say `real` / `shadow` (D-T7); a search for one game kind in Jaeger or VictoriaMetrics uses the vocabulary of the service that emitted it. The mapping (`primary` is `real`; an empty or unknown kind is never real) is owned by the entity model (GAME_SESSION `game_kind_telemetry` / `game_kind_flags`).

### BR-003: Dead alerts (retired)

Retired by #1425: the alert rules were removed together with Prometheus alerting (A2), so the dead `GameCrashRate` / `ServiceUpdatePending` rules (D-T3) are gone. The ID is kept so it is not reused.

### BR-004: Histograms export their declared buckets

Every histogram is exported with the bucket boundaries it declares: a Python `Histogram(..., buckets=[...])` in `lib/otel_metrics.py` passes them to the OTel SDK as explicit bucket boundaries, and the Go agent histograms set `WithExplicitBucketBoundaries` (`gen_ai.client.*` use the GenAI semantic-convention advisory boundaries). Without them the SDK defaults (0, 5, 10, 25, ...) put every sub-second latency into the first bucket, so each latency p95 reads about 4.75 s (#1434). The collector's `span_metrics` connector sets explicit buckets (5 ms to 32 s) on the `agent.decide` duration histogram (#1427). A histogram records only values in the unit its buckets are sized for: `agent_intervention_effect_delta` records the deltas of the 0..1 progress-type fitness signals only (`*_progress`, `*_ratio`, `balanced.skill_gap`); the elapsed-time and constant-threshold keys stay on the `agent.intervention.effect` spans (#1444).

### BR-005: Connection quality per controller

The controller manager classifies each controller's link from the gaps between consecutive fresh frames (a poll that returns a new report) over a rolling 10 s window: the p95 gap (nearest rank) is good at ≤ 22 ms, fair at ≤ 30 ms and poor above 30 ms; the longest gap, including the still-open gap since the last fresh frame, is good at ≤ 30 ms, fair at ≤ 50 ms and poor above 50 ms. The controller's class is the worse of the two. A controller that delivered frames before and has been silent for the whole window is poor (its open gap is the longest gap); only a controller that has not yet delivered two fresh frames is unknown, and then no badge or quality series is shown. The thresholds are the upstream JoustMania gameplay-derived ratings (provisional, not yet validated on Pi hardware with this measurement). Gaps are taken at the controller manager's poll pick-up (monotonic clock), so they are quantised to the 10 ms poll interval and sub-poll jitter is invisible; time the poll loop itself runs late (event-loop contention; discovery, LED and health work run on their own tasks since #1447, NFR-002) is subtracted from every gap that spans it, so a loop stall does not rate every controller worse; the same subtraction applies to the health span's `bluetooth.event_gap_ms`; a link gap that overlaps a controller-manager loop stall is understated by up to the stall's length (FR-122, #1431).

### BR-006: The dashboard's gameplay stream is an observer

A gameplay stream that never sent colours (an observer: the dashboard's `WatchGameplayData`, #1595) never consumes a game signal. Mid-game disconnects (`GameplayDataUpdate.disconnects`, #580), the per-controller health counters (`GameplayData.health`) and the mock death latch's frame budget (#926) are read once, so only game streams (those that sent colours in their config) drain them (every open game stream gets each disconnect, UC-002 BR-004), also while their alive filter is empty (NonStop's respawn window, a reconnect with nobody alive); an observer's frames carry no `disconnects` and no `health` and do not count against a death latch. An observer stream runs at its requested rate capped at `game_loop.update_frequency_hz` (the dashboard asks for 30 Hz), while a game stream runs at the flag rate, except a pattern game's stream, which is pinned to its archetype's `stream_rate_hz` for the whole game and ignores the flag ([UC-046](UC-046.md) step 4, FR-103). connect-proxy forwards only the browser's rate (missing or 0 and below = 30 Hz, capped at 30 Hz), never colours or a filter, so a browser cannot claim controllers, set their LEDs or open a game stream.
