# Use Case: Observe the System

## Overview

**Use Case ID:** UC-035
**Use Case Name:** Observe the System
**Primary Actor:** Operator
**Goal:** See what the game, the controllers and the agent are doing, from one URL
**Status:** Implemented
**Requirements:** FR-043, FR-059, FR-080, FR-081, FR-082, FR-084, FR-085, NFR-021, NFR-022, NFR-023, NFR-024, C-015

## Preconditions

- The full stack runs (not the lite stack).

## Main Success Scenario

1. Operator opens `http://<host>/` (envoy on port 80).
2. System shows the dashboard: a live controller grid (LED colour, acceleration) fed by the gameplay stream.
3. Operator opens the Agent tab; System shows the decision feed from `agent.decide` spans in Jaeger, the agent activity and effective flags from Loki log lines, and intervention write counts from VictoriaMetrics.
4. Operator opens the Experiments tab; System shows cohort runs from agent log lines.
5. Operator follows a game in Jaeger (`/jaeger/`): the game's root span (named after the mode), its phases, one span per player, and the agent's in-game spans as remote children of `game_cycle` (UC-040 BR-013).
6. Operator watches Grafana dashboards (`/grafana/`): game quality, controllers, Bluetooth, interventions, agent operations.
7. Operator searches logs in Grafana / Loki.

## Alternative Flows

### A1: Experiment dossier

**Trigger:** Operator opens `/experiments` or `/experiments/<id>` (step 4)
**Flow:**

1. System renders the experiment journal (intent, events, summary) from the agent.
2. Use case continues at step 5.

### A2: Alert fires (retired)

**Trigger:** None since #1425: Prometheus alerting was removed (FR-083 Rejected, maintainer decision 2026-10-16) because nothing received the alerts; the operator watches Grafana (step 6) and the dashboard (step 2). The ID is kept so it is not reused.
**Flow:**

1. No alert rules are loaded; Prometheus (`/prometheus/`) only scrapes and serves queries.
2. Use case continues at step 6.

### A3: Telemetry backend down

**Trigger:** Jaeger, VictoriaMetrics or the agent is unreachable (step 3)
**Flow:**

1. The collector keeps exporting to the others; the agent fan-out is best effort and never blocks the pipeline.
2. Use case continues at step 3.

## Postconditions

### Success Postconditions

- The operator can correlate a game id across traces, metrics and logs.

### Failure Postconditions

- None for the game: observability failures never affect gameplay.

## Business Rules

### BR-001: One entry point

Envoy on port 80 is the only host entry for the UIs and HTTP APIs; docs that say `:8080` are stale (D-E1). For service-to-service use from the host-networked pairing daemon, the host also exposes flagd sync (8015), rust-hid gRPC (50058) and the otel-collector's OTLP gRPC receiver (4317), and the pairing daemon binds its health and metrics port (8002) on the host. The otel-collector also publishes its Prometheus exporter (8889) for external scraping.

### BR-002: Two `game.kind` vocabularies

Coordinator spans say `primary` / `shadow`, agent spans say `real` / `shadow` (D-T7).

### BR-003: Dead alerts (retired)

Retired by #1425: the alert rules were removed together with Prometheus alerting (A2), so the dead `GameCrashRate` / `ServiceUpdatePending` rules (D-T3) are gone. The ID is kept so it is not reused.

The backend-comparison latency panels (step 6) read `controller_input_lag_seconds`: the age of the controller sample when it is sent on a game gameplay stream, from the controller manager's poll pick-up; the Bluetooth / HID hop is not included (#1335, resolved by #1376). The service-health "gRPC client errors" panels read `grpc_client_errors_total` (outbound calls from the Python services, by callee `service`, `method` and `code`); errors in the middle of a stream and non-Python clients are not counted yet (#1426).
