# Use Case: Observe the System

## Overview

**Use Case ID:** UC-035
**Use Case Name:** Observe the System
**Primary Actor:** Operator, Presenter
**Goal:** See what the game, the controllers and the agent are doing, from one URL
**Trigger:** An operator or the presenter opens `http://<host>/` in a browser (the stack's single entry point, BR-001)
**Status:** Tested
**Requirements:** FR-043, FR-059, FR-080, FR-081, FR-082, FR-084, FR-085, FR-103, FR-122, NFR-002, NFR-003, NFR-021, NFR-022, NFR-023, NFR-024, C-014, C-015

## Preconditions

- The full stack runs (not the lite stack, which has no Jaeger, VictoriaMetrics, Loki or Grafana).

## Main Success Scenario

1. System (envoy on port 80) serves the dashboard and, under the same host, Jaeger (`/jaeger/`), Grafana (`/grafana/`), VictoriaMetrics (`/victoria-metrics/`), the agent's experiment dossier (`/experiments`) and the browser API, which connect-proxy translates to the services' gRPC calls (C-014, BR-001).
2. System shows the dashboard's Controllers view: a live controller grid (LED colour, acceleration, connection-quality badge with its p95 and longest report gap, BR-005; an agent-shield badge, FR-084: "Charged" (with the seconds to expiry, or none when the charge never expires) while the player holds a shield charge, UC-040 A30; the shield countdown while a shield runs; both, "Shield 4.2s · Charged", when a charge waits under a running shield; #1837) fed by the dashboard's own gameplay stream, an observer that never claims a controller (BR-006, #1595); and the game state, alive count and event feed (game start on `game_start` and end, with the winner from `game_winner` or the `game_ended` `winner` (a controller serial shows the controller, a team name "team <name>", `none` "No winner" with the `reason` or non-result `outcome`, e.g. "(force-ended)", #1935; without a `winner` field: Swapper, Traitor, Teams and Random Teams `winning_team` as "Team <index>" with `-1` or `none` "No winner" (#2003), Tournament `champion` as the controller, a plain "Game ended!" for neither, as does a stringified `None` or empty `winner` or `champion`, #1977); the Running state on `game_start` and `game_started`, the Starting state on `countdown_start` and Running again on `countdown_end` (the base modes send `game_started` before the countdown, #1767; Werewolf, Zombies, Tournament and Fight Club send it after the countdown); the Ended state on `game_ended`, `game_force_ended`, `game_error` ("Game ended with an error") or `game_start_error` (with its error message); eliminations; agent shields and shield charges, with feed lines for a charge, its trigger activation and its expiry) from the game event stream, which connect-proxy relays from the game coordinator (A4 when either stream drops).
3. Operator opens the Agent tab; System shows, from spans in Jaeger, the decision feed (`agent.decide`), the activity feed (blocked decisions from the `agent.decision` spans of the decide poll's game traces, rollout rows from `agent.infrastructure.decision` with `remediation.action` `expand`, `rollback` or `recommended_only`) and the effective flags of the followed game (`agent.flag_state`: decision backend, act threshold, battery threshold, max interventions per minute, game mode, kill switch, objectives, allow-list; the game is chosen like the current-backend strip, UC-070 BR-005, so a shadow game never replaces the stage game; while a real game is live it is that game's own flag state, searched for when its game has not decided yet, and the "no flag state" hint until it arrives, never the previous game's), and the applied and blocked intervention counts from VictoriaMetrics (A3 when a source is down). Jaeger queries never use the browser clock: the first query sends no start time, later ones start at the newest span already seen minus an overlap (#2059).
4. Operator opens the Experiments tab; System shows the cohort experiments and their arms from the newest `experiment.progress` span of each experiment in Jaeger: per arm the samples, mean fitness and games in flight, Δ (experimental minus control mean), the verdict (running while `proposed` / `running`; `verdict.outcome` once it concluded (`concluded`, `promoting`, `done`, `discarded`), else that status; an `aborted` experiment shows `aborted`, its interim `verdict.outcome` only as "(interim: <outcome>)"; the newest snapshot is the latest span start in µs, on a tie the later lifecycle status) and the end reason; live experiments plus the newest finished ones (#2059; A1 for one experiment's dossier).
5. Operator follows a game in Jaeger: the game's root span (named after the mode), its phases, one span per player, and the agent's in-game spans as remote children of `game_cycle` (UC-040 BR-013); coordinator and agent spans name the game kind in two vocabularies (BR-002).
6. Operator watches the Grafana dashboards, in four folders: Game (game and players, including the per-player acceleration against the warning and death lines; controllers and Bluetooth, including the connection quality per controller, BR-005, and each adapter's identity, HCI error counters and link roles, FR-122), Agent (decisions by backend and outcome, remote-model latency and usage, interventions and their measured effect, shadow games), Platform (infrastructure and services; flags and the flag service) and Talk (one dashboard for the talk, `Talk: Two Standards`, UC-070). Every latency panel reads histograms with their declared buckets (BR-004). The dashboards, their panels and the metric names are listed in [telemetry.md §6](../specs/telemetry.md#6-metrics) (#1427).
7. Operator searches the logs in Grafana (Explore on Loki), by the game's trace id.

## Alternative Flows

### A1: Experiment dossier

**Trigger:** Operator opens `/experiments` or `/experiments/<id>` (step 4)
**Flow:**

1. System (the agent) answers `/experiments` with the list of experiments from its journal: for a browser (`Accept: text/html` without `application/json`, or `?format=html`) an HTML table of id, status, flag, candidate, verdict, start and thesis; JSON otherwise (id, hypothesis, flag, candidate, objective, status, verdict, start and, once concluded, end) and `/experiments/<id>` with that experiment's dossier as JSON (thesis, arms, games with their outcome and fitness, verdict, decision, notes and trace hints). The decision follows how the experiment ended, not only its verdict (#1731): `promoted` when it ended `done`, `reverted` when it ended `done` but its journal holds a `promotion` event with outcome `reverted` (the kill switch or the watch undid the real default, [UC-043](UC-043.md) A1; the status stays `done`, #1869), `discarded` when it ended `discarded` (also a promote verdict whose promotion could not act, [UC-043](UC-043.md) A4, A9), `refined` when it ended `discarded` on an inconclusive verdict, `aborted` when it was aborted, and empty while it runs, including while a promotion runs (status `promoting`, #1869; a journal left at `concluded` keeps its verdict label, since the journal cannot tell it from a live one). The `/experiments` list and the dashboard's Experiments tab show the verdict, not the decision. An unknown id is answered 404 `experiment not found`; with the agent down, envoy answers with its own error.
2. Use case continues at step 5.

### A2: Alert fires (retired)

**Trigger:** None since #1425: Prometheus alerting was removed (FR-083 Rejected, maintainer decision 2026-10-16); the operator watches Grafana instead (step 6). The ID is kept so it is not reused.
**Flow:**

1. No alert rules are loaded; VictoriaMetrics (`/victoria-metrics/`) is the only metrics store (#1449).
2. Use case continues at step 6.

### A3: A telemetry backend or the agent is down

**Trigger:** Jaeger, VictoriaMetrics, Loki, Grafana, the collector or the agent is unreachable while the operator uses the dashboard (step 3 and step 4; Grafana and the agent also at step 6 and A1; Loki only at step 7, the dashboard no longer reads it, #2059)
**Flow:**

1. The collector keeps exporting to the others: each backend has its own exporter, the agent fan-out is best effort and never blocks the pipeline (NFR-024), and the collector's memory limit bounds what queues up for a down backend (NFR-021). The collector starts and runs without its backends (no `depends_on` on them, restart `unless-stopped`); data for a backend that is not up yet is queued in memory and retried with the collector's default bounded retry (about 5 min), so a backend that comes up later than that loses the early data; the queue is bounded by NFR-021 (UC-060 BR-004).
2. The dashboard shows what it can still read. A panel that has rendered keeps its last data and marks it `stale — last updated <n>s ago`; a panel that never rendered shows `Could not reach Jaeger for agent.decide spans.`, `Could not reach Jaeger for agent telemetry.` or `Could not reach Jaeger for experiment telemetry.` (Jaeger down: the request fails, times out, answers non-2xx or carries Jaeger errors). Jaeger up without matching spans is not an error: the panel names the missing span (`No agent.flag_state spans in Jaeger yet …`, `No experiment.progress spans in Jaeger yet …`), which is also what an agent image without these spans shows. With VictoriaMetrics down the Applied and Blocked counts show `n/a` ("VictoriaMetrics unreachable"); with Jaeger down and VictoriaMetrics up they still show. With the agent or the collector down Jaeger answers but no new spans arrive: the Agent and Experiments tabs show no new agent rows. With the agent down `/experiments` also fails (A1). With Grafana down the dashboard's embedded Grafana view (its Metrics tab) and its outbound Grafana links fail; the rest of the dashboard is unaffected.
3. Use case continues at step 3.

### A4: The dashboard loses a live stream

**Trigger:** The gameplay stream or the game event stream to the browser ends or fails (connect-proxy, the controller manager or the game coordinator restarts) (step 2)
**Flow:**

1. When the gameplay stream fails or ends, the controller grid shows `Connection lost. Retrying...`; when the game event stream fails or ends, the event feed and the shield badges stop updating, without a message, and on reopen the badges are cleared (the coordinator's event bus has no replay, so a badge would otherwise outlive a missed end).
2. The dashboard reopens a stream that failed and a stream that ended cleanly (connect-proxy ends the game event stream when the coordinator's stream ends), every 2 s until it opens again, so the next game's events show (#1706).
3. Use case continues at step 2.

## Postconditions

### Success Postconditions

- The operator can find one game's spans in Jaeger and its series in VictoriaMetrics by its game id, and its log lines in Loki by the game's trace id.

### Failure Postconditions

- With any telemetry backend, the collector or the agent down, the game services never wait on telemetry: recording a span, a metric or a log line neither blocks nor raises on the game path (export runs on background threads, NFR-024), so a game starts, runs its loop at the NFR-003 rate and ends as it does with telemetry up. Telemetry recorded while a backend was down may be missing from that backend.


## Business Rules

### BR-001: One entry point

Envoy on port 80 is the only host entry for the UIs and the HTTP and browser APIs. Every other published port, and the interface it is published on, is listed in C-015; docs that say `:8080` are stale (D-E1). The pairing daemon's unpair port is narrowed by UC-005 BR-003.

### BR-002: Two `game.kind` vocabularies

Coordinator spans and metrics say `primary` / `shadow`, agent spans say `real` / `shadow` (D-T7); a search for one game kind in Jaeger or VictoriaMetrics uses the vocabulary of the service that emitted it. The mapping (`primary` is `real`; an empty or unknown kind is never real) is owned by the entity model (GAME_SESSION `game_kind_telemetry` / `game_kind_flags`).

### BR-003: Dead alerts (retired)

Retired by #1425: the alert rules were removed together with Prometheus alerting (A2), so the dead `GameCrashRate` / `ServiceUpdatePending` rules (D-T3) are gone. The ID is kept so it is not reused.

### BR-004: Histograms export their declared buckets

Every histogram is exported with the bucket boundaries it declares: a Python `Histogram(..., buckets=[...])` in `lib/otel_metrics.py` passes them to the OTel SDK as explicit bucket boundaries, and the Go agent histograms set `WithExplicitBucketBoundaries` (`gen_ai.client.*` use the GenAI semantic-convention advisory boundaries). Without them the SDK defaults (0, 5, 10, 25, ...) put every sub-second latency into the first bucket, so each latency p95 reads about 4.75 s (#1434). The collector's `span_metrics` connector sets explicit buckets (5 ms to 32 s) on the `agent.decide` duration histogram (#1427). A histogram records only values in the unit its buckets are sized for: `agent_intervention_effect_delta` records the deltas of the 0..1 progress-type fitness signals only (`*_progress`, `*_ratio`, `balanced.skill_gap`); the elapsed-time and constant-threshold keys stay on the `agent.intervention.effect` spans (#1444).

### BR-005: Connection quality per controller

The controller manager classifies each controller's link from the gaps between consecutive fresh frames (a poll that returns a new report) over a rolling 10 s window: the p95 gap (nearest rank) is good at ≤ 22 ms, fair at ≤ 30 ms and poor above 30 ms; the longest gap, including the still-open gap since the last fresh frame, is good at ≤ 30 ms, fair at ≤ 50 ms and poor above 50 ms. The controller's class is the worse of the two. A controller that delivered frames before and has been silent for the whole window is poor (its open gap is the longest gap); only a controller that has not yet delivered two fresh frames is unknown, and then no badge or quality series is shown. The thresholds are the upstream JoustMania gameplay-derived ratings (provisional, not yet validated on Pi hardware with this measurement). Gaps are taken at the controller manager's poll pick-up (monotonic clock), so they are quantised to the 10 ms poll interval and sub-poll jitter is invisible; time the poll loop itself runs late (event-loop contention; discovery, LED and health work run on their own tasks since #1447, NFR-002) is subtracted from every gap that spans it, so a loop stall does not rate every controller worse; the same subtraction applies to the health span's `bluetooth.event_gap_ms`; a link gap that overlaps a controller-manager loop stall is understated by up to the stall's length (FR-122, #1431).

### BR-006: The dashboard's gameplay stream is an observer

A gameplay stream that never sent colours (an observer: the dashboard's `WatchGameplayData`, #1595) never consumes a game signal. Mid-game disconnects (`GameplayDataUpdate.disconnects`, #580), the per-controller health counters (`GameplayData.health`) and the mock death latch's frame budget (#926) are read once, so only game streams (those that sent colours in their config) drain them (every open game stream gets each disconnect, UC-002 BR-004), also while their alive filter is empty (NonStop's respawn window, a reconnect with nobody alive), and then only for the controllers of their own roster (the empty filter means every controller in a frame, but a game never consumes another game's mock latches, health counters or trigger latch, #1610); an observer's frames carry no `disconnects` and no `health` and do not count against a death latch. An observer stream runs at its requested rate capped at `game_loop.update_frequency_hz` (the dashboard asks for 30 Hz), while a game stream runs at the flag rate, except a pattern game's stream, which is pinned to its archetype's `stream_rate_hz` for the whole game and ignores the flag ([UC-046](UC-046.md) step 4, FR-103). connect-proxy forwards only the browser's rate (missing or 0 and below = 30 Hz, capped at 30 Hz), never colours or a filter, so a browser cannot claim controllers, set their LEDs or open a game stream.
