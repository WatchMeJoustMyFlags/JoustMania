# Use Case: Observe the System

## Overview

**Use Case ID:** UC-035
**Use Case Name:** Observe the System
**Primary Actor:** Operator, Presenter
**Goal:** See what the game, the controllers and the agent are doing, from one URL
**Trigger:** An operator or the presenter opens `http://<host>/` in a browser (the stack's single entry point, BR-001)
**Status:** Tested
**Requirements:** FR-043, FR-059, FR-080, FR-081, FR-082, FR-084, FR-085, FR-103, FR-122, NFR-002, NFR-003, NFR-021, NFR-022, NFR-023, NFR-024, C-014, C-015

- The full stack runs (not the lite stack, which has no Jaeger, VictoriaMetrics, Loki or Grafana).

## Main Success Scenario

1. System (envoy on port 80) serves the dashboard and, under the same host, Jaeger (`/jaeger/`), Grafana (`/grafana/`), VictoriaMetrics (`/victoria-metrics/`), the agent's experiment dossier (`/experiments`) and the browser API, which connect-proxy translates to the services' gRPC calls (C-014, BR-001).
2. System shows the dashboard's Controllers view: a live controller grid (LED colour, acceleration, connection-quality badge with its p95 and longest report gap, BR-005; the HCI adapter the controller is connected through (`hci0`, `hci1`, ..., a badge from `controller_adapter_info` in VictoriaMetrics, hidden while only one adapter is seen or the adapter is unknown, and a per-adapter count in the grid header, BR-009, #2133); an agent-shield badge, FR-084: "Charged" (with the seconds to expiry, or none when the charge never expires) while the player holds a shield charge, UC-040 A30; the shield countdown while a shield runs; both, "Shield 4.2s · Charged", when a charge waits under a running shield; #1837) fed by the dashboard's own gameplay stream, an observer that never claims a controller (BR-006, #1595); and the game state, alive count and event feed (game start on `game_start` and end, with the winner from `game_winner` or the `game_ended` `winner` (a controller serial shows the controller, a team name "team <name>", `none` "No winner" with the `reason` or non-result `outcome`, e.g. "(force-ended)", #1935; without a `winner` field: Swapper, Traitor, Teams and Random Teams `winning_team` as "Team <index>" with `-1` or `none` "No winner" (#2003), Tournament `champion` as the controller, a plain "Game ended!" for neither, as does a stringified `None` or empty `winner` or `champion`, #1977); the Running state on `game_start` and `game_started`, the Starting state on `countdown_start` and Running again on `countdown_end` (the base modes send `game_started` before the countdown, #1767; Werewolf, Zombies, Tournament and Fight Club send it after the countdown); the Ended state on `game_ended`, `game_force_ended`, `game_error` ("Game ended with an error") or `game_start_error` (with its error message); eliminations; agent shields and shield charges, with feed lines for a charge, its trigger activation and its expiry; in a hold game the energy bar of each player, BR-008) from the game event stream, which connect-proxy relays from the game coordinator (A4 when either stream drops).
3. Operator opens the Agent tab; System shows, from spans in Jaeger, the decision feed (`agent.decide`; each linked `agent.decision` reads `allowed`, `blocked`, or `not applied: <reason>` when the write gate dropped the write, #2093), the activity feed (blocked decisions from the `agent.decision` spans of the decide poll's game traces, rollout rows from `agent.infrastructure.decision` with `remediation.action` `expand`, `rollback` or `recommended_only`) and the effective flags of the followed game (`agent.flag_state`: decision backend, act threshold, battery threshold, max interventions per minute, game mode, kill switch, objectives, allow-list and the `interventions_enabled` write gate, with a warning while the agent is enabled but the write gate is off, #2093; the game is chosen like the current-backend strip, UC-070 BR-005, so a shadow game never replaces the stage game; while a real game is live it is that game's own flag state, searched for by its `game.id` when its game has not decided yet, and the "no flag state" hint until it arrives, never the previous game's), and the applied and blocked intervention counts from VictoriaMetrics (`agent_intervention_writes_total` and `agent_decisions_total`, by `game_kind`, #2294): the real-game (`primary`) counts lead, the shadow-game counts sit on their own labelled line, and the blocked-by-action and blocked-by-reason breakdowns cover real games only; a series without `game_kind` (an agent image older than #2294) counts as real (A3 when a source is down). Jaeger queries never use the browser clock: the first query sends no start time, later ones start at the newest span already seen minus an overlap (#2059); the decide poll paces itself on the answer size, stops re-fetching a settled game's trace and searches the live real game by `game.id` (BR-011, #2287).
4. Operator opens the Experiments tab; System shows the cohort experiments and their arms from the newest `experiment.progress` span of each experiment in Jaeger: per arm the samples, mean fitness and games in flight, Δ (experimental minus control mean), the verdict (running while `proposed` / `running`; `verdict.outcome` once it concluded (`concluded`, `promoting`, `done`, `discarded`), else that status; an `aborted` experiment shows `aborted`, its interim `verdict.outcome` only as "(interim: <outcome>)"; the newest snapshot is the latest span start in µs, on a tie the later lifecycle status) and the end reason; when the experiment's promotion was refused because another writer owns the real overlay (UC-043 A19, #2276), the card also shows "would promote <flag>=<value>; real value owned by <writer>" from the `experiment.recommendation.*` attributes; live experiments plus the newest finished ones (#2059; A1 for one experiment's dossier).
5. 6. 7. Operator searches the logs in Grafana (Explore on Loki), by the game's trace id.

## Alternative Flows

### A1: Experiment dossier

**Trigger:** Operator opens `/experiments` or `/experiments/<id>` (step 4)
**Flow:**

1. System (the agent) answers `/experiments` with the list of experiments from its journal: for a browser (`Accept: text/html` without `application/json`, or `?format=html`) an HTML table of id, status, flag, candidate, verdict, start and thesis; JSON otherwise (id, hypothesis, flag, candidate, objective, status, verdict, start and, once concluded, end) and `/experiments/<id>` with that experiment's dossier as JSON (thesis, arms, games with their outcome and fitness, verdict, decision, notes and trace hints). The decision follows how the experiment ended, not only its verdict (#1731): `promoted` when it ended `done`, `reverted` when it ended `done` but its journal holds a `promotion` event with outcome `reverted` (the kill switch or the watch undid the real default, [UC-043](UC-043.md) A1; the status stays `done`, #1869), `deferred` when it ended `done` and its last `promotion` event is `deferred` (a hold key's `real` write still waits for the end of the real game, UC-043 A17 step 3), `discarded` also when it ended `done` but its last `promotion` event is `discarded` (that waiting write was dropped: superseded, expired, kill switch, mode change or shutdown), `discarded` when it ended `discarded` (also a promote verdict whose promotion could not act, [UC-043](UC-043.md) A4, A9), `refined` when it ended `discarded` on an inconclusive verdict, `aborted` when it was aborted, and empty while it runs, including while a promotion runs (status `promoting`, #1869; a journal left at `concluded` keeps its verdict label, since the journal cannot tell it from a live one). The `/experiments` list and the dashboard's Experiments tab show the verdict, not the decision. An unknown id is answered 404 `experiment not found`; with the agent down, envoy answers with its own error.

### A3: A telemetry backend or the agent is down

**Trigger:** Jaeger, VictoriaMetrics, Loki, Grafana, the collector or the agent is unreachable while the operator uses the dashboard (step 3 and step 4; Grafana and the agent also at step 6 and A1; Loki only at step 7, the dashboard no longer reads it, #2059)
**Flow:**

1. The collector keeps exporting to the others: each backend has its own exporter, the agent fan-out is best effort and never blocks the pipeline (NFR-024), and the collector's memory limit bounds what queues up for a down backend (NFR-021). The collector starts and runs without its backends (no `depends_on` on them, restart `unless-stopped`); data for a backend that is not up yet is queued in memory and retried with the collector's default bounded retry (about 5 min), so a backend that comes up later than that loses the early data; the queue is bounded by NFR-021 (UC-060 BR-004).
2. The dashboard shows what it can still read. A panel that has rendered keeps its last data and marks it `stale — last updated <n>s ago`; a panel that never rendered shows `Could not reach Jaeger for agent.decide spans.`, `Could not reach Jaeger for agent telemetry.` or `Could not reach Jaeger for experiment telemetry.` (Jaeger down: the request fails, times out, answers non-2xx or carries Jaeger errors). Jaeger up without matching spans is not an error: the panel names the missing span (`No agent.flag_state spans in Jaeger yet …`, `No experiment.progress spans in Jaeger yet …`), which is also what an agent image without these spans shows. With VictoriaMetrics down (request failed or HTTP error) the Applied and Blocked counts show `n/a` ("VictoriaMetrics unreachable"); an empty answer from a reachable VictoriaMetrics is `0` (no interventions yet, #2288). Both counts cover the same last 10 minutes; Blocked leaves out `already_applied` (the value was already in place, not a refusal, UC-040 A35); the counts are split by the `game_kind` label of the agent counters, real games (`primary`, an unlabelled series counts as real) first and shadow games on their own line (#2294); with Jaeger down and VictoriaMetrics up they still show. With the agent or the collector down Jaeger answers but no new spans arrive: the Agent and Experiments tabs show no new agent rows. With the agent down `/experiments` also fails (A1). With VictoriaMetrics down the adapter badges and the header counts keep their last value and are marked stale (the badge title and the header say `stale`); if they never rendered, no adapter is shown and the grid is unaffected (BR-009). The stage settings strip (BR-010) keeps its last values marked `stale` when both its sources fail, and shows `—` for a value no source reports; one source down only blanks what only it carries. With Grafana down the dashboard's embedded Grafana view (its Metrics tab) and its outbound Grafana links fail; the rest of the dashboard is unaffected.
3. Use case continues at step 3.

## Postconditions

### Success Postconditions

- The operator can find one game's spans in Jaeger and its series in VictoriaMetrics by its game id, and its log lines in Loki by the game's trace id.

### Failure Postconditions

- With any telemetry backend, the collector or the agent down, the game services never wait on telemetry: recording a span, a metric or a log line neither blocks nor raises on the game path (export runs on background threads, NFR-024), so a game starts, runs its loop at the NFR-003 rate and ends as it does with telemetry up. Telemetry recorded while a backend was down may be missing from that backend.


## Business Rules

### BR-001: One entry point

Envoy on port 80 is the only host entry for the UIs and the HTTP and browser APIs. Every other published port, and the interface it is published on, is listed in C-015; docs that say `:8080` are stale (D-E1). The pairing daemon's unpair port is narrowed by UC-005 BR-003.

### BR-002: Two `game.kind` vocabularies

Coordinator spans and metrics say `primary` / `shadow`, agent spans say `real` / `shadow` (D-T7); a search for one game kind in Jaeger or VictoriaMetrics uses the vocabulary of the service that emitted it. The mapping (`primary` is `real`; an empty or unknown kind is never real) is owned by the entity model (GAME_SESSION `game_kind_telemetry` / `game_kind_flags`).

### BR-003: Dead alerts (retired)

Retired by #1425: the alert rules were removed together with Prometheus alerting (A2), so the dead `GameCrashRate` / `ServiceUpdatePending` rules (D-T3) are gone. The ID is kept so it is not reused.

### BR-004: Histograms export their declared buckets

Every histogram is exported with the bucket boundaries it declares: a Python `Histogram(..., buckets=[...])` in `lib/otel_metrics.py` passes them to the OTel SDK as explicit bucket boundaries, and the Go agent histograms set `WithExplicitBucketBoundaries` (`gen_ai.client.*` use the GenAI semantic-convention advisory boundaries). Without them the SDK defaults (0, 5, 10, 25, ...) put every sub-second latency into the first bucket, so each latency p95 reads about 4.75 s (#1434). The collector's `span_metrics` connector sets explicit buckets (5 ms to 32 s) on the `agent.decide` duration histogram (#1427). A histogram records only values in the unit its buckets are sized for: `agent_intervention_effect_delta` records the deltas of the 0..1 progress-type fitness signals only (`*_progress`, `*_ratio`, `balanced.skill_gap`); the elapsed-time and constant-threshold keys stay on the `agent.intervention.effect` spans (#1444).

### BR-005: Connection quality per controller

The controller manager classifies each controller's link from the gaps between consecutive fresh frames (a poll that returns a new report) over a rolling 10 s window: the p95 gap (nearest rank) is good at ≤ 22 ms, fair at ≤ 30 ms and poor above 30 ms; the longest gap, including the still-open gap since the last fresh frame, is good at ≤ 30 ms, fair at ≤ 50 ms and poor above 50 ms. The controller's class is the worse of the two. A controller that delivered frames before and has been silent for the whole window is poor (its open gap is the longest gap); only a controller that has not yet delivered two fresh frames is unknown, and then no badge or quality series is shown. The thresholds are the upstream JoustMania gameplay-derived ratings (provisional, not yet validated on Pi hardware with this measurement). Gaps are taken at the controller manager's poll pick-up (monotonic clock), so they are quantised to the 10 ms poll interval and sub-poll jitter is invisible; time the poll loop itself runs late (event-loop contention; discovery, LED and health work run on their own tasks since #1447, NFR-002) is subtracted from every gap that spans it, so a loop stall does not rate every controller worse; the same subtraction applies to the health span's `bluetooth.event_gap_ms`; a link gap that overlaps a controller-manager loop stall is understated by up to the stall's length (FR-122, #1431).

### BR-006: The dashboard's gameplay stream is an observer

### BR-007: The battery scale on the controller card

The gameplay stream's `GameplayData.battery` carries the controller's last-known battery. On the Rust HID path (the shipped path, `proto/psmove_hid.proto`) the value is a percentage in steps of 20 (0, 20, 40, 60, 80, 100); the psmoveapi path and older fixtures use 0-5. The dashboard card reads both the way `battery_to_pct` does (`controller_manager/metrics.py`): a value of 5 or less is a 0-5 level times 20, anything above is already a percentage, clamped to 0-100, so a Rust 40 does not show as 100 % (#2112). The bar colour is `high` above 50%, `medium` above 20%, otherwise `low`. Charging and charged both arrive as 100 (the HID layer maps 0xEE and 0xEF to 100), so a charging controller reads 100% (gap, no proto change). The separate battery roster that also used this scale was removed in #2132 (A5 Obsolete).

### BR-008: Hold energy tile (#2096)

- In a hold game (UC-040 BR-024) each player's tile shows a bar of the energy against the cap, a thin second bar of the budget remaining against the budget, the text `Hold <energy>s/<cap>s · budget <left>s` and the state, with the levels of the controller LED (UC-040 BR-026): `empty` (below the minimum burst), `low` (below a third of the cap), `charged`, `full` (at `min(cap, budget remaining)`), `active` (draining, highlighted), plus `recharging` while the pool fills by itself and `budget used up` once less than a minimum burst of budget is left. A marker names the last source of energy: `agent` after a grant, `recharge` while recharging. A game that is not a hold game publishes no energy event, so its tiles show no bar.
- Source: the game event `player_shield_energy` ([telemetry.md](../specs/telemetry.md) §5), published at every transition the controller gets a hold command for (UC-040 BR-026: the start of the game loop, an activation, the end of an activation, a grant, a reconnect), from the coordinator's outbound hold task, never from the frame path. Between two transitions the energy is a linear function of time (UC-040 BR-024), so the event carries the rate and the dashboard computes the rest. A keyframe re-publishes a living player's state when that player had no energy event for 2 s, so a dashboard opened mid-game, a reopened stream (A4) or a dropped event gets the bar back within about 4 s (twice the 2 s keyframe interval: the keyframe timeout restarts on every wake, and a dropped keyframe adds one more interval). Events of one player coalesce like the controller commands; at most two per minimum burst per player plus one per grant, plus one keyframe per 2 s. The event is droppable on the event bus: a subscriber whose queue is a quarter full or more loses it on its own loop, so energy events never hold more than a quarter of a queue and at least three quarters stay for `player_death`, `game_ended` and `game_winner` (a full queue still drops any event); it records no span event, and the menu logs it at DEBUG. A shadow game publishes none: a shadow game can be a hold game only when its archetype presses the trigger (UC-040 BR-019, UC-046 BR-018), and then it still sets the agent's hold gauges and sends the hold layers to its mock controllers, but no `player_shield_energy` event (no dashboard bar for a game without an audience, and no energy events on the shared bus queues).
- Why not VictoriaMetrics: dashboard data comes from telemetry where it can, but a live bar cannot use it. The coordinator exports metrics every 100 ms, yet VictoriaMetrics (v1.144) answers an instant query 30 s late by default (`-search.latencyOffset`) and 2.5 to 4 s late with `nocache=1` (measured on a throwaway instance, #2096): a 5 s pool would be drawn after it emptied. The per-player shield gauges stay planned for the agent's view (telemetry.md §6), where seconds of lag are acceptable.
- The bar interpolates linearly from the last event's `energy_ms` and `rate_ms_per_s`, measured against the browser's monotonic receipt time (`performance.now()`); no wall-clock timestamp is compared, so no browser clock is trusted. A draining bar stops after `remaining_ms` (the activation's end), a filling bar at `full_ms`; values are clamped to [0, cap]. When the end of an activation is not followed by an event (a dropped one), the bar shows the idle state at the drained level. Every event resets the state. The bar is cleared on `game_start`, game end, `player_death` and a lost event stream (A4); `ShieldStore` clears its shield entry on `player_shield_energy`, and a hold activation publishes no `player_shielded` (UC-040 BR-026).

### BR-009: Adapter on the controller card (#2133)

- Each controller card shows the HCI adapter its link runs on (`hci0`, `hci1`, ...), so an operator sees an unbalanced Bluetooth load (#2125) without opening Grafana. The grid header shows a count per adapter ("hci0: 5 · hci1: 4"), also with one adapter ("hci0: 9"). The per-card badge is hidden while only one adapter is seen.
- Source: the existing `controller_adapter_info{serial,adapter}` series ([telemetry.md](../specs/telemetry.md) §6, #1468), read from VictoriaMetrics through envoy's `/victoria-metrics/` with `timestamp(controller_adapter_info)` and `nocache=1`, polled every 10 s while the page is visible. No proto field and no new metric. The join key is the controller manager's serial, the same one the gameplay stream carries.
- One adapter per serial: OTLP writes no staleness marker, so after a controller moved adapter both series can answer for a short time; the series with the newest sample timestamp wins.
- A serial without a series (mock controllers, USB, a failed sysfs lookup) shows no adapter badge and is left out of the counts. A reconnect whose adapter lookup returns an empty name clears the controller manager's stored adapter (UC-002 A4), so the series goes instead of keeping the old `hciN`.
- Why VictoriaMetrics and not the stream: the adapter changes only on reconnect, and seconds of lag are acceptable (contrast with BR-008): the label can trail a reconnect by 2.5 to 4 s with `nocache=1`, so at worst about 14 s (10 s poll plus that lag). Polling runs only while the Controllers tab is shown and the page is visible. The badge names the adapter, not the link health (BR-005 is the live signal). The lite stack has no VictoriaMetrics (Pre-1) and shows no adapters.
- Known gap: the real adapter path (sysfs walk to `hciN`) is verified on Pi hardware only; mock controllers report none, so no e2e test asserts a label.

### BR-011: The Agent tab bounds its Jaeger cost (#2287)

- Jaeger's search returns whole traces, so the decide poll (step 3, every 1.5 s) downloads the whole trace of every game it matches, and a live real game's trace grows with the game (4.9 MB per poll on the stage Pi). The dashboard bounds that cost without dropping a row it shows:
- Pace: after an answer of `n` characters the next decide poll waits at least `n / 512 KiB` seconds (at most 15 s; at most 5 s while a real game is live, so the presenter's decision strip refreshes at least every 5 s at the price of up to about 1 MB/s for the stage game's 4.9 MB trace), so one browser on the Agent tab makes Jaeger send at most about 512 KiB/s however large the game trace grows; answers up to about 768 KiB keep the 1.5 s cadence. Errors and slow answers still back off as before.
- Settle: each search keeps its own window. While the newest decide it holds is new, the next search starts at that decide minus 62 s (the longest configurable decide timeout, 60 s, `decision.<backend>.timeout_ms` in flags.md, plus 2 s span export delay; spans export when they end, so a slow decide that started earlier still arrives); once that decide has stayed the newest for 62 s of browser-elapsed time (a duration, never a browser timestamp, so the clock-skew rule of step 3 holds), the search starts just after it, so an ended or quiet game's trace is no longer re-downloaded.
- Target: while a real game is live and its id is known (UC-070 BR-005), the decide search asks for that game's `game.id`, so shadow games with their own traces (`telemetry.experiment_game_parent=link`, #2255) cannot fill the trace limit and push the stage game's decides off the strip; the shadow games' decides come from a `game.kind=shadow` search every fourth poll. Without a live real game one search covers all decides (UC-070 A9).
- The flag-state fallback search (step 3) for the same game repeats at most every 30 s; another game, or a retry after a failed search, searches at once.
- Hidden: no Jaeger search runs while the Agent tab is not shown, the page is hidden or it sits in the back/forward cache; showing it again polls at once (#2059).

**Code / tests:** `services/dashboard/src/agent.ts` (`decideSearches`, `pollDecides`, `QueryWindow`, `decidePaceMs`, `FlagFallbackPacer`), `services/dashboard/src/jaeger.ts`, `services/dashboard/src/poller.ts`, `services/dashboard/src/main.ts`; tests `services/dashboard/src/__tests__/decidePoll.test.ts`.

### BR-012: Background load of an open dashboard (#2290)

- Hidden page: the Controllers gameplay stream (30 Hz) is aborted when the page is hidden (`document.visibilityState`) or parked in the back/forward cache (`pagehide`), shows no `Connection lost. Retrying...` for it (also when the page is shown again before the aborted call has settled) and is reopened on show (`pageshow`); a page that starts hidden opens no stream. The pollers of BR-009 and the Agent and Experiments tabs already pause the same way (PageGate, #2059).
- Follow poll (`GetGameState` + `ListGames`, every 2 s): runs only while the Controllers or Agent tab is shown and the page is visible; other tabs, a hidden page or the back/forward cache stop it, and showing the tab polls at once.
- Iframes: the Grafana Metrics iframe gets its `src` on the first open of its tab and is blanked (`about:blank`) 60 s after its tab is left, or at once when the page is hidden or parked in the back/forward cache, so its 5 s refresh costs nothing in the background (returning to the tab within 60 s keeps the loaded Grafana, no reload); the Jaeger search iframe loads on the first open of the Traces tab and then stays.
- The decide poll's pacing is BR-011 (#2300); the stage settings poller (BR-010) pauses the same way. The game event stream stays open on every tab (low rate, drives the status bar).
