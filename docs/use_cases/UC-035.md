# Use Case: Observe the System

## Overview

**Use Case ID:** UC-035
**Use Case Name:** Observe the System
**Primary Actor:** Operator
**Goal:** See what the game, the controllers and the agent are doing, from one URL
**Status:** Implemented
**Requirements:** FR-043, FR-059, FR-080, FR-081, FR-082, FR-084, FR-085, FR-122, NFR-021, NFR-022, NFR-023, NFR-024, C-015

## Preconditions

- The full stack runs (not the lite stack).

## Main Success Scenario

1. Operator opens `http://<host>/` (envoy on port 80).
2. System shows the dashboard: a live controller grid (LED colour, acceleration, connection-quality badge with its p95 and longest report gap, BR-005) fed by the gameplay stream.
3. Operator opens the Agent tab; System shows the decision feed from `agent.decide` spans in Jaeger, the agent activity and effective flags from Loki log lines, and intervention write counts from VictoriaMetrics.
4. Operator opens the Experiments tab; System shows cohort runs from agent log lines.
5. Operator follows a game in Jaeger (`/jaeger/`): the game's root span (named after the mode), its phases, one span per player, and the agent's in-game spans as remote children of `game_cycle` (UC-040 BR-013).
6. Operator watches Grafana dashboards (`/grafana/`): game quality, controllers (including the connection quality per controller, BR-005), Bluetooth (including each adapter's identity, HCI error counters and the local role of each link, read-only from the pairing daemon; names in [telemetry.md §6](../specs/telemetry.md#6-metrics), FR-122), interventions, agent operations, infrastructure and services (which services report, their CPU, memory and threads, gRPC clients, the host and VictoriaMetrics; #1427). `controller_input_lag_seconds` (the age of a controller sample when it is sent on a game's gameplay stream, measured from the controller manager's poll pick-up; the Bluetooth / HID hop is not included; #1335, resolved by #1376) has no dashboard panel since the backend-comparison dashboard was deleted (#1427); the operator queries it in Grafana Explore. The Infrastructure & Services "gRPC client errors" panels show `grpc_client_errors_total`: failed outbound calls and failed stream setups from the Python services, by callee `service`, `method` and `code` (errors in the middle of a stream and non-Python clients are not counted yet, #1426).
7. Operator searches logs in Grafana / Loki.

**Trigger:** Jaeger, VictoriaMetrics or the agent is unreachable (step 3)
**Flow:**

2. Use case continues at step 3.

## Postconditions

### Success Postconditions

- The operator can correlate a game id across traces, metrics and logs.

### Failure Postconditions

- None for the game: observability failures never affect gameplay.

## Business Rules

### BR-001: One entry point

Envoy on port 80 is the only host entry for the UIs and HTTP APIs; docs that say `:8080` are stale (D-E1). For service-to-service use from the host-networked pairing daemon, the host also exposes flagd sync (8015), rust-hid gRPC (50058) and the otel-collector's OTLP gRPC receiver (4317), and the pairing daemon binds its health, metrics and unpair port (8002) on the host, only on loopback and the docker0 gateway (`CONTROL_BIND`; the connect-proxy reaches it through the Docker host gateway, UC-005 BR-003). The otel-collector's Prometheus exporter (8889) was removed with the Prometheus container (#1449); external tools query VictoriaMetrics through `/victoria-metrics/`.

### BR-002: Two `game.kind` vocabularies

Coordinator spans say `primary` / `shadow`, agent spans say `real` / `shadow` (D-T7).

### BR-003: Dead alerts (retired)

Retired by #1425: the alert rules were removed together with Prometheus alerting (A2), so the dead `GameCrashRate` / `ServiceUpdatePending` rules (D-T3) are gone. The ID is kept so it is not reused.

### BR-004: Histograms export their declared buckets

Every histogram is exported with the bucket boundaries it declares: a Python `Histogram(..., buckets=[...])` in `lib/otel_metrics.py` passes them to the OTel SDK as explicit bucket boundaries, and the Go agent histograms set `WithExplicitBucketBoundaries` (`gen_ai.client.*` use the GenAI semantic-convention advisory boundaries). Without them the SDK defaults (0, 5, 10, 25, ...) put every sub-second latency into the first bucket, so each latency p95 reads about 4.75 s (#1434).

### BR-005: Connection quality per controller

The controller manager classifies each controller's link from the gaps between consecutive fresh frames (a poll that returns a new report) over a rolling 10 s window: the p95 gap (nearest rank) is good at ≤ 22 ms, fair at ≤ 30 ms and poor above 30 ms; the longest gap, including the still-open gap since the last fresh frame, is good at ≤ 30 ms, fair at ≤ 50 ms and poor above 50 ms. The controller's class is the worse of the two. A controller that delivered frames before and has been silent for the whole window is poor (its open gap is the longest gap); only a controller that has not yet delivered two fresh frames is unknown, and then no badge or quality series is shown. The thresholds are the upstream JoustMania gameplay-derived ratings (provisional, not yet validated on Pi hardware with this measurement). Gaps are taken at the controller manager's poll pick-up (monotonic clock), so they are quantised to the 10 ms poll interval and sub-poll jitter is invisible; time the poll loop itself runs late (discovery, LED or health work) is subtracted from every gap that spans it, so a loop stall does not rate every controller worse; a link gap that overlaps a controller-manager loop stall is understated by up to the stall's length (FR-122, #1431).
