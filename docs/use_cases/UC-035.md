# Use Case: Observe the System

## Overview

**Use Case ID:** UC-035
**Use Case Name:** Observe the System
**Primary Actor:** Operator
**Goal:** See what the game, the controllers and the agent are doing, from one URL
**Status:** Implemented
**Requirements:** FR-043, FR-059, FR-080, FR-081, FR-082, FR-084, FR-085, FR-122, NFR-021, NFR-022, NFR-023, NFR-024, C-015

## Preconditions

- The full stack runs (not the lite stack).

## Main Success Scenario

1. Operator opens `http://<host>/` (envoy on port 80).
2. System shows the dashboard: a live controller grid (LED colour, acceleration, connection-quality badge with its p95 and longest report gap, BR-005) fed by the gameplay stream (the server stream `WatchGameplayData`, relayed by connect-proxy from the controller manager's `StreamGameplayData`, #1595).
3. Operator opens the Agent tab; System shows the decision feed from `agent.decide` spans in Jaeger, the agent activity and effective flags from Loki log lines, and intervention write counts from VictoriaMetrics.
4. Operator opens the Experiments tab; System shows cohort runs from agent log lines.
5. Operator follows a game in Jaeger (`/jaeger/`): the game's root span (named after the mode), its phases, one span per player, and the agent's in-game spans as remote children of `game_cycle` (UC-040 BR-013).
6. Operator watches Grafana dashboards (`/grafana/`): game and players (live games, their settings and thresholds, games started and completed by outcome, deaths, game-loop health, movement intensity, and a per-player drill-down of the 100 Hz acceleration against the warning and death lines; #1427), controllers (including the connection quality per controller, BR-005), Bluetooth (including each adapter's identity, HCI error counters and the local role of each link, read-only from the pairing daemon; names in [telemetry.md §6](../specs/telemetry.md#6-metrics), FR-122), agent decisions and interventions (decide backend and outcome from the collector's span metrics over the `agent.decide` spans, remote-backend model latency and usage, interventions from the agent and the coordinator side, measured effect per fitness signal, shadow games; #1427), infrastructure and services (which services report, their CPU, memory and threads, gRPC clients, the host and VictoriaMetrics; #1427), flags (every flag evaluation by flag, variant and reason from the standard OpenFeature OTel hooks, evaluation errors and fallbacks, the flag service's writes, live games, sync streams and snapshot, and flagd's health; #1427), and one stage view for the talk (live games, decisions by backend and outcome, interventions applied, flag evaluations, flag-service writes, recent `agent.decide` traces; #1427). The dashboards sit in four folders: Game, Agent, Platform and Talk. `controller_input_lag_seconds` (the age of a controller sample when it is sent on a game's gameplay stream, measured from the controller manager's poll pick-up; the Bluetooth / HID hop is not included; #1335, resolved by #1376) has no dashboard panel since the backend-comparison dashboard was deleted (#1427); the operator queries it in Grafana Explore. The Infrastructure & Services "gRPC client errors" panels show `grpc_client_errors_total`: failed outbound calls and failed stream setups from the Python services, by callee `service`, `method` and `code` (errors in the middle of a stream and non-Python clients are not counted yet, #1426).
7. Operator searches logs in Grafana / Loki.

## Business Rules

### BR-001: One entry point

Envoy on port 80 is the only host entry for the UIs and HTTP APIs; docs that say `:8080` are stale (D-E1). For service-to-service use from the host-networked pairing daemon, the host also publishes flagd sync (8015), rust-hid gRPC (50058) and the otel-collector's OTLP gRPC receiver (4317), on `127.0.0.1` only so none is reachable from the venue network (#1319). The Pi start path (`scripts/setup/joustmania-start.sh` and `joustmania.service`) runs every compose command with `-f docker-compose.yml`, so the dev `docker-compose.override.yml`, which publishes the gRPC and mock control ports on all interfaces, is never loaded there (#1319). The pairing daemon binds its health, metrics and unpair port (8002) on the host, only on loopback and the docker0 gateway (`CONTROL_BIND`; the connect-proxy reaches it through the Docker host gateway, UC-005 BR-003). The otel-collector's Prometheus exporter (8889) was removed with the Prometheus container (#1449); external tools query VictoriaMetrics through `/victoria-metrics/`.

### BR-002: Two `game.kind` vocabularies

Coordinator spans say `primary` / `shadow`, agent spans say `real` / `shadow` (D-T7).

### BR-003: Dead alerts (retired)

Retired by #1425: the alert rules were removed together with Prometheus alerting (A2), so the dead `GameCrashRate` / `ServiceUpdatePending` rules (D-T3) are gone. The ID is kept so it is not reused.

### BR-004: Histograms export their declared buckets

Every histogram is exported with the bucket boundaries it declares: a Python `Histogram(..., buckets=[...])` in `lib/otel_metrics.py` passes them to the OTel SDK as explicit bucket boundaries, and the Go agent histograms set `WithExplicitBucketBoundaries` (`gen_ai.client.*` use the GenAI semantic-convention advisory boundaries). Without them the SDK defaults (0, 5, 10, 25, ...) put every sub-second latency into the first bucket, so each latency p95 reads about 4.75 s (#1434). The collector's `span_metrics` connector sets explicit buckets (5 ms to 32 s) on the `agent.decide` duration histogram (#1427). A histogram records only values in the unit its buckets are sized for: `agent_intervention_effect_delta` records the deltas of the 0..1 progress-type fitness signals only (`*_progress`, `*_ratio`, `balanced.skill_gap`); the elapsed-time and constant-threshold keys stay on the `agent.intervention.effect` spans (#1444).

### BR-005: Connection quality per controller

The controller manager classifies each controller's link from the gaps between consecutive fresh frames (a poll that returns a new report) over a rolling 10 s window: the p95 gap (nearest rank) is good at ≤ 22 ms, fair at ≤ 30 ms and poor above 30 ms; the longest gap, including the still-open gap since the last fresh frame, is good at ≤ 30 ms, fair at ≤ 50 ms and poor above 50 ms. The controller's class is the worse of the two. A controller that delivered frames before and has been silent for the whole window is poor (its open gap is the longest gap); only a controller that has not yet delivered two fresh frames is unknown, and then no badge or quality series is shown. The thresholds are the upstream JoustMania gameplay-derived ratings (provisional, not yet validated on Pi hardware with this measurement). Gaps are taken at the controller manager's poll pick-up (monotonic clock), so they are quantised to the 10 ms poll interval and sub-poll jitter is invisible; time the poll loop itself runs late (event-loop contention; discovery, LED and health work run on their own tasks since #1447, NFR-002) is subtracted from every gap that spans it, so a loop stall does not rate every controller worse; the same subtraction applies to the health span's `bluetooth.event_gap_ms`; a link gap that overlaps a controller-manager loop stall is understated by up to the stall's length (FR-122, #1431).

### BR-006: The dashboard's gameplay stream is an observer

A gameplay stream that never sent colours (an observer: the dashboard's `WatchGameplayData`, #1595) never consumes a game signal. Mid-game disconnects (`GameplayDataUpdate.disconnects`, #580), the per-controller health counters (`GameplayData.health`) and the mock death latch's frame budget (#926) are read once, so only game streams (those that sent colours in their config) drain them (every open game stream gets each disconnect, UC-002 BR-004), also while their alive filter is empty (NonStop's respawn window, a reconnect with nobody alive); an observer's frames carry no `disconnects` and no `health` and do not count against a death latch. An observer stream runs at its requested rate capped at `game_loop.update_frequency_hz` (the dashboard asks for 30 Hz), while a game stream runs at the flag rate. connect-proxy forwards only the browser's rate (missing or 0 and below = 30 Hz, capped at 30 Hz), never colours or a filter, so a browser cannot claim controllers, set their LEDs or open a game stream.
