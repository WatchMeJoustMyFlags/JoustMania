# Use Case: Observe a Game

## Overview

**Use Case ID:** UC-041
**Use Case Name:** Observe a Game
**Primary Actor:** Agent
**Goal:** Know each live game's state from telemetry alone
**Trigger:** A game service exports a span or metric batch over OTLP
**Status:** Tested
**Requirements:** FR-040, FR-041, NFR-024, C-001

## Preconditions

- The collector fans traces and OTLP metrics out to the agent on port 4317.

## Main Success Scenario

1. System (game services) export spans and metrics over OTLP to the collector.
2. The collector forwards them to the agent (best effort: 2 s timeout, no retries; A6 when a batch is lost).
3. The agent skips its own telemetry (resources whose `service.name` is its own).
4. The agent extracts per-player and per-game signals from known metrics (acceleration, playstyle, alive, battery, skill, movement variance, thresholds, tempo, game active, duration) and from span attributes and `player_death` events (every game mode feeds the per-player movement and skill metrics, BR-006), and keeps each controller's display name from `controller_info` (used to name targeted players on its decision spans) and the game's trace ids from `game_trace_correlation` (BR-004). Signals without a game id are handled in A5.
5. The agent partitions the signals by `game_id` into one context per game and normalises `game_kind` (`primary` → `real`; `shadow`, empty and unknown kinds pass through unchanged and never count as real: fail closed, FR-041); the game-state gauges (tempo, thresholds, sensitivity, mode, loop rate) carry `game_kind, game_id`, so each reaches its own game's context (#1379).
6. The agent evaluates the game when it is active and has a fresh player, one whose last signal arrived within `lifecycle.player_ttl_seconds` (default 5 s) (UC-040).
7. When the game ends (`game_active` 1 → 0, or A4), the agent records in the game's context which signal ended it (its end reason: `zero`, `root_span` or `stale`; not the coordinator's `game.end_reason`) and runs, in order, once per game: experiment conclusion, retro, game summary, proposer (UC-042, UC-043; BR-005); a game that ended `stale` gets only the experiment release (A4 step 3).

## Alternative Flows

### A1: Infrastructure signals

**Trigger:** A `controller.bluetooth_health` span arrives (~1 Hz) (step 4)
**Flow:**

1. The agent updates its infrastructure context for the rollout loop (UC-050). The span carries no game id or player attribute, so it changes no game's context and triggers no game evaluation.
2. Use case continues at step 1 with the next batch.

### A2: Stale data

**Trigger:** A player or session sends nothing for `lifecycle.player_ttl_seconds` / `lifecycle.session_grace_seconds` (step 5)
**Flow:**

1. At its eviction tick (`lifecycle.evict_interval_seconds`, default 1 s) the agent evicts the player (default TTL 5 s) or resets the session's state (default grace 15 s); a game context with no players, no active game and its grace over is dropped. All three values are hot-reloaded flags.
2. A later signal of an evicted player recreates it; a later signal for an ended game id that was dropped recreates a context that stays ended (BR-005).
3. Use case continues at step 4 with the next batch.

### A3: Duration gauge missing or stale

**Trigger:** During an active game, `game_duration_seconds` has not been received or its value has not advanced for 5 s (step 4)
**Flow:**

1. The agent derives the elapsed game time from when it saw `game_active` go 0 → 1, never below the last gauge value (BR-003).
2. Use case continues at step 5.

### A4: The `game_active` 0 never arrives

**Trigger:** An active game's `game_active` 0 datapoint is not exported, for example because retire or force-end removed the series first (step 7)
**Flow:**

1. When the game's root span reaches the agent (it is exported when the game's session ends), the agent ends the game. Its duration bracket closes at the span's end time. A later `game_active` 1 for that game id does not start it again.
2. If neither the 0 nor the root span arrives and the game's `game_active` series stays silent for 60 s (a fixed value, not a flag), the agent ends the game at its next eviction tick (A2), with the duration bracket closed at the last `game_active` datapoint. No telemetry for a live game means the agent's telemetry broke, so ending the game is the safe default; the end is counted in `agent_game_end_stale_total`.
3. A game ended this way (its context's end reason is `stale`) has incomplete data, so it is excluded from experiments: an experiment game is released without a fitness sample (UC-043) and its slot is refilled, and a pattern pair reruns as [UC-046](UC-046.md) BR-015 defines for a stale end; a real game adds no recent-real fitness sample, and the retro, game summary and proposer skip it (UC-042).
4. The game stays ended for the agent even if its `game_active` series resumes (the game may still be running): the agent runs no further evaluation, decisions or interventions for that game id (BR-005).
5. Use case continues at step 7 (BR-005); the game's context is then evicted as in A2.

### A5: Signals without a game id

**Trigger:** A datapoint or span carries no `game_id` (step 5)
**Flow:**

1. The agent puts it into one shared fallback context. Controller signals without a game id (battery, connection) always land there; id-less signals of two games running at the same time mix in it, which is why no intervention is ever written for it (A5 step 3).
2. A `game_active` 0 → 1 in the fallback context starts a new game there with a synthetic id `session-<n>`; a second 1 while that game is active changes nothing. The fallback context is never dropped and keeps no ended-id record, so a later 0 → 1 starts `session-<n+1>`.
3. The agent may evaluate the fallback context (UC-040), but the intervention writer refuses its `session-<n>` id ([UC-040](UC-040.md) BR-002), so nothing reaches any game.
4. A `game_active` 0 or a silent series (A4 step 2) ends the fallback game and runs the game-end chain (step 7); a root span never does, because it carries a game id.
5. Use case continues at step 6.

### A6: A telemetry batch is lost while the agent runs

**Trigger:** The collector cannot deliver a batch to the agent within 2 s, the delivery fails, or its queue of 1000 batches is full (step 2)
**Flow:**

1. The collector drops the batch without a retry; the agent does not notice and counts nothing (only the collector's own metrics show the drop).
2. Gauges are exported again at every export interval (flag `metrics_export_interval_ms`, 100 ms for the game coordinator), so a lost `game_active`, `game_trace_correlation` or elimination-order datapoint is restored by the next batch; a lost `game_active` 1 starts the game one interval later.
3. Span data is exported once and is not restored: a lost `player_death` event leaves the elimination order to the `game_player_elimination_order` gauge, and a lost root span leaves the game's end to the `game_active` 0 or to the stale end (A4).
4. Use case continues at step 4 with the next batch.

## Postconditions

### Success Postconditions

- The agent holds a current context per live game id, built only from OTel signals: its active flag, players and game state are those of the last batch received, except that a game that has ended stays ended (BR-005).

### Failure Postconditions

- The game services and the collector never wait for the agent (best effort, no retry), telemetry still reaches Jaeger and VictoriaMetrics, and signals labeled with one game id never enter another game's context. An agent that was down rebuilds its contexts from the signals that arrive after it returns.

## Business Rules

### BR-001: Metrics are timely, spans are late

Metrics carry the live picture: they arrive within about a second and each batch that changes a live game can trigger an evaluation. A span batch also wakes the evaluation and adds span-derived state to the game context: the elimination order (`player_death` events), `game.mode`, `game.kind` and the experiment id and arm. Decisions may use that state (rules R1/R2 read the elimination order; the LLM eligibility check reads the game kind). Player spans close at game end and the collector batches traces, so span-derived state lags the game; spans also serve audit and the elimination order.

### BR-002: Game summaries are not durable

Game summaries are not written to disk. Their game-level aggregates live only in the agent's in-memory cross-game window and are lost when the agent restarts (UC-042 BR-004, BR-005; the summary file writer was removed in #1368).

### BR-003: Elapsed game time is live

The game coordinator refreshes `game_duration_seconds` every 1 s while a game is RUNNING (real and shadow games) and sets its final value when the game ends. The agent uses the gauge while it is fresh; otherwise it falls back as in A3. The in-game elapsed time never decreases within a game. At game end the agent uses the larger of the gauge and its own start → end time, so every game-end consumer sees the same duration.

### BR-004: The game's trace ids reach the agent as metric labels

The game coordinator publishes the `game_trace_correlation` gauge (value 1 while the game is live) with the game's trace id, the root span id and, once each span opens, the `gameplay_phase` and `game_cycle` span ids (`gameplay_phase_span_id`, `game_cycle_span_id`). Each time an id becomes known it replaces the gauge series (the old label set is removed, so one series per live game remains), and the series is removed when the game is retired. The agent keeps the last non-empty value of each label for the game and uses them to parent its in-game spans (UC-040 BR-013). Modes that run their own loop without a `game_cycle` span publish only the ids they have.

### BR-005: A game ends exactly once

A game ends for the agent on whichever end signal arrives first: the `game_active` 1 → 0 datapoint, the game root span or a silent `game_active` series (A4). The game-end chain (step 7) runs once per game; the later signals change nothing. Game ids are unique per game start and never reused, so once a game id has ended, a later `game_active` 1 for it (out-of-order delivery, or a series that resumes after a stale end) does not start it again, also after its context was evicted. The agent keeps the ids of the last 512 ended games in memory only: after an agent restart a late `game_active` 1 for a game that ended before the restart starts it again (accepted limit). Signals without a game id follow A5. The game's duration at the end, and the start → end bracket of its timeline, close at the game's own end as the agent saw it: the time the 0 arrived, the root span's end time, or the arrival of the last `game_active` datapoint (A4). A game that has ended no longer keeps its context from being evicted (#1494).

### BR-006: Every game mode produces the per-player movement and skill inputs

Every game mode gives each player a movement tracker when the game starts (while `analytics.enabled` is on), so the per-player gauges the agent decides on (`game_player_accel_magnitude`, `game_player_movement_zone`, `game_player_peak_accel`, `game_player_playstyle`, `game_player_movement_variance`, `game_player_skill_level`, `game_player_movement_variance_aggregate`) and, at game end, one `player_analytics` summary per player and the `analytics.*` attributes on the player span's end event exist in all ten modes, not only in Free-for-All, Teams, Random Teams and Non-Stop (#2358). A sample is taken on each frame whose motion the mode checks for a death: in Fight Club and Tournament only the two fighters' frames count, so a waiting player's tracker does not advance until it fights, and its `survival_time_ms` in the end summary is the time it spent fighting, not the time it was in the game. While a Fight Club or Tournament player waits (before its first round or match, and between its fights), it exports no `game_player_*` gauge: the coordinator removes them, `game_player_alive` included, when it goes back to waiting, and sets `game_player_alive` 1 again when it is seated for its next fight, whose frames bring the other gauges back; a Tournament loser keeps `game_player_alive` 0 and its elimination order. The tracker keeps its samples, so the end summary covers every fight. Werewolf and Zombies span events carry the attributes only for players alive at the end, as Free-for-All and Teams do.
