# Use Case: Observe a Game

## Overview

**Use Case ID:** UC-041
**Use Case Name:** Observe a Game
**Primary Actor:** Agent
**Goal:** Know each live game's state from telemetry alone
**Status:** Implemented
**Requirements:** FR-040, FR-041, NFR-024, C-001

## Preconditions

- The collector fans traces and OTLP metrics out to the agent on port 4317.

## Main Success Scenario

1. System (game services) export spans and metrics over OTLP to the collector.
2. The collector forwards them to the agent (best effort: 2 s timeout, no retries).
3. The agent skips its own telemetry.
4. The agent extracts per-player and per-game signals from known metrics (acceleration, playstyle, alive, battery, skill, movement variance, thresholds, tempo, game active, duration) and from span attributes and `player_death` events.
5. The agent partitions the signals by `game_id` into one context per game and normalises `game_kind` (`primary` → `real`).
6. The agent evaluates the game when it is active and has a fresh player (UC-040).
7. When the game ends (`game_active` 1 → 0), the agent runs, in order: experiment conclusion, retro, game summary, proposer (UC-042, UC-043).

## Alternative Flows

### A1: Infrastructure signals

**Trigger:** A `controller.bluetooth_health` span arrives (~1 Hz)
**Flow:**

1. The agent updates its infrastructure context for the rollout loop (UC-050).

### A2: Stale data

**Trigger:** A player or session sends nothing for `lifecycle.player_ttl_seconds` / `lifecycle.session_grace_seconds`
**Flow:**

1. The agent evicts it (TTLs are hot-reloaded flags).

### A3: Duration gauge missing or stale

**Trigger:** During an active game, `game_duration_seconds` has not been received or its value has not advanced for 5 s (step 4)
**Flow:**

1. The agent derives the elapsed game time from when it saw `game_active` go 0 → 1, never below the last gauge value (BR-003).
2. Use case continues at step 5.

## Postconditions

### Success Postconditions

- The agent holds a current context per live game, built only from OTel signals.

### Failure Postconditions

- If the agent is down, telemetry still reaches Jaeger and VictoriaMetrics; the agent rebuilds context when it returns.

## Business Rules

### BR-001: Metrics are timely, spans are late

Metrics drive decisions; player spans close at game end and are used for audit and elimination order.

### BR-002: Game summaries are not durable

Game summaries are written to a directory that is not on a volume (lost on container re-creation).

### BR-003: Elapsed game time is live

The game coordinator refreshes `game_duration_seconds` every 1 s while a game is RUNNING (real and shadow games) and sets its final value when the game ends. The agent uses the gauge while it is fresh; otherwise it falls back as in A3. The in-game elapsed time never decreases within a game. At game end the agent uses the larger of the gauge and its own start → end time, so every game-end consumer sees the same duration.
