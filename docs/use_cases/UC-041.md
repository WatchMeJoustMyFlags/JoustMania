# Use Case: Observe a Game

## Overview

**Use Case ID:** UC-041
**Use Case Name:** Observe a Game
**Primary Actor:** Agent
**Goal:** Know each live game's state from telemetry alone
**Status:** Implemented
**Requirements:** FR-040, FR-041, NFR-024, C-001

## Preconditions

- The collector fans traces and OTLP metrics out to the agent on port 4317.

## Main Success Scenario

1. System (game services) export spans and metrics over OTLP to the collector.
2. The collector forwards them to the agent (best effort: 2 s timeout, no retries).
3. The agent skips its own telemetry.
4. The agent extracts per-player and per-game signals from known metrics (acceleration, playstyle, alive, battery, skill, movement variance, thresholds, tempo, game active, duration) and from span attributes and `player_death` events, and keeps each controller's display name from `controller_info` (used to name targeted players on its decision spans) and the game's trace ids from `game_trace_correlation` (BR-004).
5. The agent partitions the signals by `game_id` into one context per game and normalises `game_kind` (`primary` → `real`); the game-state gauges (tempo, thresholds, sensitivity, mode, loop rate) carry `game_kind, game_id`, so each reaches its own game's context (#1379).
6. The agent evaluates the game when it is active and has a fresh player (UC-040).
7. When the game ends (`game_active` 1 → 0, or A4), the agent records which signal ended it (`zero`, `root_span` or `stale`) and runs, in order, once per game: experiment conclusion, retro, game summary, proposer (UC-042, UC-043; BR-005).

## Alternative Flows

### A1: Infrastructure signals

**Trigger:** A `controller.bluetooth_health` span arrives (~1 Hz) (step 4)
**Flow:**

1. The agent updates its infrastructure context for the rollout loop (UC-050).
2. Use case ends.

### A2: Stale data

**Trigger:** A player or session sends nothing for `lifecycle.player_ttl_seconds` / `lifecycle.session_grace_seconds` (step 5)
**Flow:**

1. The agent evicts it (TTLs are hot-reloaded flags).
2. Use case ends.

### A3: Duration gauge missing or stale

**Trigger:** During an active game, `game_duration_seconds` has not been received or its value has not advanced for 5 s (step 4)
**Flow:**

1. The agent derives the elapsed game time from when it saw `game_active` go 0 → 1, never below the last gauge value (BR-003).
2. Use case continues at step 5.

### A4: The `game_active` 0 never arrives

**Trigger:** An active game's `game_active` 0 datapoint is not exported, for example because retire or force-end removed the series first (step 7)
**Flow:**

1. When the game's root span reaches the agent (it is exported when the game's session ends), the agent ends the game. Its duration bracket closes at the span's end time. A later `game_active` 1 for that game id does not start it again.
2. If neither the 0 nor the root span arrives and the game's `game_active` series stays silent for 60 s, the agent ends the game at its next eviction tick, with the duration bracket closed at the last `game_active` datapoint. No telemetry for a live game means the agent's telemetry broke, so ending the game is the safe default; the end is counted in `agent_game_end_stale_total`.
3. A game ended this way (end reason `stale`) has incomplete data, so it is excluded from experiments: an experiment game is released without a fitness sample (as a preempted or errored game, UC-043), a real game adds no recent-real fitness sample, and the retro, game summary and proposer skip it (UC-042).
4. Use case continues at step 7 (BR-005); the game's context is then evicted as in A2.

## Postconditions

### Success Postconditions

- The agent holds a current context per live game, built only from OTel signals.

### Failure Postconditions

- If the agent is down, telemetry still reaches Jaeger and VictoriaMetrics; the agent rebuilds context when it returns.

## Business Rules

### BR-001: Metrics are timely, spans are late

Metrics drive decisions; player spans close at game end and are used for audit and elimination order.

### BR-002: Game summaries are not durable

Game summaries are not written to disk. Their game-level aggregates live only in the agent's in-memory cross-game window and are lost when the agent restarts (UC-042 BR-004, BR-005; the summary file writer was removed in #1368).

### BR-003: Elapsed game time is live

The game coordinator refreshes `game_duration_seconds` every 1 s while a game is RUNNING (real and shadow games) and sets its final value when the game ends. The agent uses the gauge while it is fresh; otherwise it falls back as in A3. The in-game elapsed time never decreases within a game. At game end the agent uses the larger of the gauge and its own start → end time, so every game-end consumer sees the same duration.

### BR-004: The game's trace ids reach the agent as metric labels

The game coordinator publishes the `game_trace_correlation` gauge (value 1 while the game is live) with the game's trace id, the root span id and, once each span opens, the `gameplay_phase` and `game_cycle` span ids (`gameplay_phase_span_id`, `game_cycle_span_id`). Each time an id becomes known it replaces the gauge series (the old label set is removed, so one series per live game remains), and the series is removed when the game is retired. The agent keeps the last non-empty value of each label for the game and uses them to parent its in-game spans (UC-040 BR-013). Modes that run their own loop without a `game_cycle` span publish only the ids they have.

### BR-005: A game ends exactly once

A game ends for the agent on whichever end signal arrives first: the `game_active` 1 → 0 datapoint, the game root span or a silent `game_active` series (A4). The game-end chain (step 7) runs once per game; the later signals change nothing. Game ids are unique per game start and never reused, so once a game id has ended, a later `game_active` 1 for it (out-of-order delivery, or a series that resumes after a stale end) does not start it again, also after its context was evicted. Signals without a game id share one context, where a 0 → 1 still starts a new game. The game's duration at the end, and the start → end bracket of its timeline, close at the game's own end (the 0's arrival, the root span's end time or the last `game_active` datapoint), not at when the agent learned of it. A game that has ended no longer keeps its context from being evicted (#1494).
