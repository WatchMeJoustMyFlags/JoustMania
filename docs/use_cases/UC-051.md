# Use Case: Roll Back Automatically on Degradation

## Overview

**Use Case ID:** UC-051
**Use Case Name:** Roll Back Automatically on Degradation
**Primary Actor:** Agent
**Goal:** Take a degrading backend away from players without a human
**Status:** Tested
**Requirements:** FR-072, NFR-016, NFR-017

## Preconditions

- A progressive rollout is past stage 0 (UC-050).
- `rollout_enabled` and `remediation_allowed` are both on.

## Main Success Scenario

1. The agent evaluates infrastructure fitness on the current stage and finds a violation (e.g. the `unstable` adapter delivers ~8 Hz with gaps over 50 ms and 10 % drops).
2. The agent sets `current_controller_count` back to `none` (0) in `rollout.json`.
3. The controller manager routes every controller back to its default backend on the next cycle.
4. The agent records the rollback on an `agent.infrastructure.decision` span and logs `agent.rollout_rollback`.
5. The agent blocks re-expansion for `AGENT_ROLLOUT_COOLDOWN_SECONDS` (default 30 s).

## Alternative Flows

### A1: Remediation not allowed

**Trigger:** `remediation_allowed` is off (step 2)
**Flow:**

1. The agent records `recommended_only` (`agent.rollout_rollback_recommended`) and changes nothing.

### A2: Agent restarts during cooldown

**Trigger:** The agent restarts within the cooldown (step 5)
**Flow:**

1. The cooldown is lost (kept in memory only).

## Postconditions

### Success Postconditions

- No controller uses the degrading backend; the incident is visible as a trace.

### Failure Postconditions

- With remediation off, the degraded stage stays until a human acts.

## Business Rules

### BR-001: `target_backend` is untouched

Rollback changes only the count; the target stays for a later retry.

### BR-002: Remediation flag read from the file

`remediation_allowed` is read from `rollout.json` directly, not through flagd (D-A12).
