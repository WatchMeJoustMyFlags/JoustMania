# Use Case: Recalibrate the Shadow Players from Real Games

## Overview

**Use Case ID:** UC-047
**Use Case Name:** Recalibrate the Shadow Players from Real Games
**Primary Actor:** Agent
**Secondary Actors:** Operator
**Trigger:** Another N eligible real games have ended since the last completed calibration (N = `calibration.every_n_games`, default 100, BR-001), or the operator starts a calibration by hand
**Goal:** Keep the archetypes that drive shadow games ([UC-046](UC-046.md)) close to how people really play, by refitting them to recent real games and keeping the result only when a holdout shows the shadow games got more realistic, so that experiment verdicts ([UC-043](UC-043.md)) rest on a substrate that resembles real play (#1055, #1017)
**Status:** Draft
**Requirements:** FR-204, FR-205, C-022, C-019, C-020, C-021, C-033, C-034, C-035, C-040

Context: the first realism characterization of the stage Pi ([UC-043](UC-043.md) A22, FR-203) found shadow games matching real games on mean movement intensity, but with about 20 times less movement variance, far fewer deaths and longer games. Many real games on the Pi are test games: one person shakes a controller while the others lie still. This use case leaves those games out and refits the archetypes to the rest (maintainer idea, 2026-11-01).

Open decision TBD-A1: a calibrated set lives in an evidence record on the agent's volume, outside the flag files, because on the Pi a flag file changes only with a release (C-033, C-040). That needs the C-019 amendment proposed in BR-008, **pending maintainer confirmation**. This use case stays Draft until it is confirmed.

## Preconditions

- **Pre-1:** `enabled` and `experiments_enabled` are on ([UC-043](UC-043.md) Pre-1): a calibration runs shadow games, so it needs the same permission as experiments.
- **Pre-2:** The agent's volume `agent-experiments` is writable and the metrics store (VictoriaMetrics) is reachable from the agent.
- **Pre-3:** The selection `experiment.mock_archetypes` resolves to valid archetypes ([UC-046](UC-046.md) BR-003); its archetypes are the ones calibrated.

## Main Success Scenario

1. A real game ends. The agent appends the game id and whether `calibration.test_session` was on to its calibration journal (BR-003).
2. System counts the eligible real games (BR-002) that ended since the last completed calibration (BR-007). When the count reaches `calibration.every_n_games`, read at that moment, it starts a calibration with trigger `auto`.
3. System takes the most recent N eligible games and splits them by end time: every 4th game goes to the holdout, the others to the fit set (BR-004).
4. System splits the fit games into 3 bands by death rate per minute and fits each archetype to its band (BR-005). The result is the candidate set.
5. System runs three groups of validation shadow games (BR-006): the active set with seed group A, the active set with seed group B (the A/A run), and the candidate set with seed group A.
6. System measures each group against the holdout with the [UC-043](UC-043.md) A22 metrics and computes the paired KS drop and the A/A noise floor (BR-006).
7. The drop clears the noise floor (BR-006). System writes the evidence record with outcome `accepted` (BR-007); that one write makes the candidate the active set (BR-008).
8. Experiments pinned from now on use the active set; experiments that have already pinned their archetypes keep them ([UC-046](UC-046.md) A5).
9. Use case ends.

## Alternative Flows

### A1: Operator starts a calibration by hand

**Trigger:** The operator runs `scripts/agent-calibrate.sh run`, instead of the count reaching N (step 2)
**Flow:**

1. System starts a calibration with trigger `manual`, whatever the count. It uses the most recent N eligible games, or all of them when fewer are available.
2. Use case continues at step 3.

### A2: Too few eligible games

**Trigger:** Fewer than 32 eligible games are available, or a band gets fewer than 8 fit games (step 3 or 4)
**Flow:**

1. System runs no shadow game and changes nothing.
2. System writes the evidence record with outcome `insufficient_games`, the number of eligible games and the excluded count per reason (BR-002, BR-003).
3. Use case ends.

### A3: The fit does not improve realism

**Trigger:** The paired KS drop does not clear the noise floor (step 7)
**Flow:**

1. System keeps the active set.
2. System writes the evidence record with outcome `rejected`, the per-metric KS distances of all three groups and the noise floor.
3. Use case ends. The next automatic calibration starts after another N eligible games (step 2).

### A4: A calibration is already running

**Trigger:** A manual or automatic start while a calibration runs (step 2, A1)
**Flow:**

1. System starts no second calibration and writes no record. A manual start is answered with `calibration_running` and the running calibration's id.
2. Use case ends for the refused start; the running calibration continues at its current step.

### A5: The calibration stops before its outcome

**Trigger:** The metrics store does not answer or answers with an error, `enabled` or `experiments_enabled` turns off, `shadow_policy` blocks shadow games, or a validation game has no result after two reruns (A6) (step 3, or any later step)
**Flow:**

1. System stops the calibration before any change to the active set. A running validation game is torn down as an experiment game is ([UC-043](UC-043.md) A1).
2. System writes the evidence record with outcome `aborted` and the reason (`data_unavailable`, `agent_disabled`, `experiments_disabled`, `shadow_blocked`, `validation_incomplete`).
3. Use case ends. An aborted calibration is not completed, so the count stays at or above N; the next automatic start waits at least 1 hour after the aborted one (BR-001).

### A6: A validation game cannot complete

**Trigger:** A real game preempts a validation shadow game ([UC-043](UC-043.md) A2), or a validation game ends without a usable result ([UC-046](UC-046.md) A9) (step 5)
**Flow:**

1. System runs that game again with the same archetype and seed, at most twice.
2. When it still has no result, System stops the calibration as A5 with the reason `validation_incomplete`.
3. Otherwise use case continues at step 5.

### A7: Agent restarts during a calibration

**Trigger:** The agent stops (crash, restart, power loss) while a calibration runs (step 3, or any later step)
**Flow:**

1. On start the agent finds the calibration's record without an outcome and completes it with outcome `aborted` and the reason `restart`; the next automatic start waits 1 hour as in A5.
2. The active set is unchanged: it changes only by the atomic write of a complete `accepted` or `rolled_back` record (BR-008).
3. Use case ends.

### A8: Operator rolls back

**Trigger:** The operator runs `scripts/agent-calibrate.sh rollback`, after an accepted calibration (step 7) or while one runs (step 3, or any later step)
**Flow:**

1. A rollback is not a calibration: it works also while `enabled` or `experiments_enabled` is off and runs no shadow game. A running calibration is stopped first and recorded `aborted` with the reason `rollback`.
2. When the flag-file archetypes are in use (no calibrated set active), System changes nothing and answers `nothing_to_roll_back`; use case ends.
3. System writes a record with outcome `rolled_back` whose after set is the active set's previous set (the flag-file archetypes after the first calibration); that write makes it active (BR-008). Repeating the rollback walks further back.
4. Experiments pinned from now on use the restored set. A rollback counts as a completed calibration (BR-007), so the next automatic calibration starts after another N eligible games.
5. Use case ends.

## Postconditions

### Success Postconditions

- The candidate set is active for experiments pinned after the calibration; the replaced set is its previous set.
- One evidence record holds the before and after sets with their digests, the games used and excluded, the KS distances, the noise floor and the constants used (BR-007).
- No real-game rule, flag or flag file has changed (C-022).

### Failure Postconditions

- The active set is unchanged.
- One evidence record names the outcome (`insufficient_games`, `rejected`, `aborted`) and its reason.
- No real-game rule, flag or flag file has changed (C-022).

## Business Rules

### BR-001: Trigger and retry

`calibration.every_n_games` (`agent` set, human-owned, never agent-written, C-034) holds N, read at use time (C-035): variants `off` = 0 (no automatic calibration; manual runs and rollback still work), `50`, `default` = 100, `200`. Only the declared variants are valid, so N is never below 32 (BR-004). After an aborted calibration (A5, A7) the next automatic start waits at least 1 hour, so a failing calibration cannot occupy the shadow-game slot back to back.

### BR-002: Eligible real game

A real game (`game_kind` `primary`) is eligible only when all of these hold:

- its mode is `JoustFFA`, the only mode pattern games run (C-021);
- it lasted at least 10 s, from its `game_duration_seconds` series as [UC-043](UC-043.md) A22 places games (on the stage Pi the median real game lasts 16 s; shorter games are mostly false starts);
- at least 2 players moved: a player moved when the last value of their `game_player_movement_variance` gauge in the game is at least 0.005 g² (a controller lying still stays far below);
- no player dominates: the highest movement variance is less than 10 times the second highest (the "one person shaking a controller" test pattern);
- it is not marked as test (BR-003);
- its series are in the metrics store; a game whose series are missing or expired is excluded with the reason `metrics_missing`.

Agent interventions and the player count are not filtered: a real game is fitted as it was played.

### BR-003: Test session mark

`calibration.test_session` (`agent` set, `on` / `off`, default `off`, human-owned, never agent-written) lets the operator mark a session as test: a real game that ends while it is `on` is ineligible, and so is a real game whose end the agent did not journal (the agent was not running). The operator sets it with `scripts/agent-calibrate.sh test-session on|off`, a stack overlay without `persist`, so a flag-service restart returns it to `off`. `scripts/agent-calibrate.sh status` shows the mark, the eligible count and the excluded count per reason, so a forgotten `on` is visible.

### BR-004: Holdout split

Ordered by end time, every 4th eligible game is in the holdout and the rest is in the fit set; the holdout is never used to fit. A calibration needs at least 32 eligible games: 24 fit games for 3 bands of 8 (BR-005) and 8 holdout games, the minimum sample of an A22 metric.

### BR-005: Fit per band

The fit games are split into 3 bands of equal size by death rate per minute (low, middle, high death rate; ties ordered by end time). Each archetype has a fixed band, so its meaning does not swap between calibrations: `calm_long` and `slow_cascade` low; `jittery_novices`, `late_burst` and any other name middle; `close_race` and `quick_cascade` high. A band needs at least 8 fit games (A2). Several archetypes share a band but keep their own shape, so they stay distinct and are never averaged into one.

Fit method: a closed-form moment match on the motion function of [UC-046](UC-046.md) BR-002, deterministic for the same inputs. `base` and `drift` match the band's median intensity in the first and last 10 % of a game. One scale factor on `amp`, `d_amp` and `burst_h` matches the band's median movement variance; `d_amp` is the "jitter", the spread between players, because pattern games add no random variation (C-020). `burst_period_s` matches the band's median near-death frequency per player-minute, one burst per near-death. `period_s`, `phase`, `d_phase`, `players`, `stream_rate_hz` and a `trigger_policy` keep their values, because 1 Hz gauges cannot resolve sub-second motion. A fitted value outside the BR-003 bounds is clamped to the bound, and the clamp is recorded.

### BR-006: Validation and acceptance

Each validation group has 4 games per selected archetype (24 games per group with the six shipped archetypes; 72 per calibration). Seed group A uses the one-shot runner's seed from the archetype name ([UC-046](UC-046.md) BR-006) plus 0 to 3, seed group B plus 4 to 7. They are shadow games with no experiment arm, marked with the calibration id, one at a time ([UC-046](UC-046.md) BR-010), between the games of any running experiment, never experiment samples.

Metrics: every A22 metric with a per-game or per-player distribution (not the aggregate death rate, not the Jaeger cross-check) that has at least 8 values in the holdout and in each group; k is their number. Per metric m, against the same holdout:

- paired drop d_m = KS(active, A) − KS(candidate, A);
- A/A difference a_m = KS(active, A) − KS(active, B);
- noise floor σ = sqrt(mean of a_m²) / sqrt(k).

The candidate is accepted when the mean of d_m is at least 2σ and no single d_m is below −2 · sqrt(mean of a_m²) (no metric got clearly worse). The evidence record stores every d_m, a_m and σ. With 24 games per group and a holdout of 25 (N = 100), one KS distance has a sampling error of about 0.14, so the rule resolves drops of the size #2542 measured (KS 0.59 on movement variance, 0.78 on near-death frequency) and rejects small ones.

### BR-007: Evidence record

Every calibration writes one evidence record (layout and path: [services.md](../specs/services.md#agent), planned): the calibration id, the trigger (`auto`, `manual`), start and end time, the outcome (`accepted`, `rejected`, `insufficient_games`, `aborted`, `rolled_back`) and its reason, the holdout and fit game ids, the excluded count per reason (BR-002, BR-003), the before and after sets with their digests and the flag-file digest of each archetype, every d_m, a_m and σ, any clamped value, and the constants used (BR-008). A rollback writes a record too, with outcome `rolled_back`.

A **completed calibration** is a record with outcome `accepted`, `rejected` or `rolled_back`; step 2 counts from the end time of the newest one. Records are never deleted.

### BR-008: Calibrated set, writer and the proposed C-019 amendment

The **calibrated set** is one parameter object per calibrated archetype name. The active set is the after set of the newest `accepted` or `rolled_back` record; with no such record, the flag-file archetypes are in use. An archetype name the active set does not hold keeps its flag-file parameters.

The agent is the only writer of records. `scripts/agent-calibrate.sh` (`run`, `rollback`, `status`, `test-session on|off`) reaches it through the agent's HTTP port (13134, planned endpoints in services.md); a rollback cancels a running calibration through the same call before it writes. Every record that changes the active set carries the digest of the active set it replaces, and the agent refuses the write when that digest is no longer the active one (compare-and-swap), so a calibration that finishes after a rollback is recorded `aborted` with the reason `active_changed` instead of undoing it.

Every pattern game records the archetype name, its parameter digest and the calibration id (empty for flag-file parameters), so a trace names the exact parameters.

Proposed amendment of C-019 (TBD-A1, **pending maintainer confirmation**), conditions:

a. Fail closed: an unreadable, truncated or invalid record ([UC-046](UC-046.md) BR-003 validators, run on load), or a missing volume, falls back to the flag-file archetypes with a WARN, never to a partial set.
b. Durable atomic write: temporary file, fsync, rename, fsync of the directory.
c. Release edits win: each record stores the flag-file digest of each calibrated name; when a release changes that variant, its calibrated entry is ignored and the mismatch is reported in `status`.
d. One writer with compare-and-swap (above), and records are never pruned.
e. Explicit rollback chain: each set names its previous set; the flag-file archetypes are a defined state, not an absence.
f. The active set (calibration id, digests) is visible in `status` and on the pattern-game traces, so nobody believes the flag file is in force.
g. Realism only: acceptance looks at realism, never at experiment fitness; after each accepted calibration the A23 validity bar ([UC-043](UC-043.md) A23) is re-checked before an objective counts as validated again. A23 keeps comparing with all real games of its window, not only the games eligible here.

Constants (each a reviewed edit, not a flag, per C-035: an operator does not tune them on stage, and the evidence record stores the values used): minimum duration 10 s; movement floor 0.005 g²; dominance ratio 10; 3 bands of at least 8 fit games; every 4th game in the holdout; 4 validation games per archetype per group; acceptance at 2σ; 1 hour wait after an aborted calibration.
