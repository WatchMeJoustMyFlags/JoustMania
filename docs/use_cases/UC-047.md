# Use Case: Recalibrate the Shadow Players from Real Games

## Overview

**Use Case ID:** UC-047
**Use Case Name:** Recalibrate the Shadow Players from Real Games
**Primary Actor:** Agent
**Secondary Actors:** Operator
**Trigger:** Another N eligible real games have ended since the last completed calibration (N = `calibration.every_n_games`, default 100, BR-001), or the operator starts a calibration by hand
**Goal:** Keep the archetypes that drive shadow games ([UC-046](UC-046.md)) close to how people really play, by refitting them to recent real games and keeping the result only when a holdout shows the shadow games got more realistic, so that experiment verdicts ([UC-043](UC-043.md)) rest on a substrate that resembles real play (#1055, #1017)
**Status:** Draft
**Requirements:** FR-204, FR-205, C-022, C-019, C-020, C-021, C-033, C-034, C-035, C-040

Context: the first realism characterization of the stage Pi ([UC-043](UC-043.md) A22, FR-203) found shadow games matching real games on mean movement intensity, but with about 20 times less movement variance, far fewer deaths and longer games. Many real games on the Pi are test games: one person shakes a controller while the others lie still. This use case leaves those games out and refits the archetypes to the rest (maintainer idea, 2026-11-01).

TBD-A1 resolved (maintainer decision, 2026-11-01: calibration is device-specific, because different game environments mean different behaviour): the calibrated set belongs to one device and lives in that device's evidence records on its own `agent-experiments` volume. It is never written back to git and never shared between devices; the flag files are only the baseline (C-019 as amended, BR-008). This use case stays Draft until the reworked spec is reviewed.

Retention constraint and maintainer decision (2026-11-01, #1055): VictoriaMetrics on the stage Pi keeps only 7 days, shorter than the window N = 100 eligible games needs (about 1 to 2 weeks of play at the measured ~11 eligible games a day). The per-game eligibility inputs (BR-002) and fit metrics (BR-006) therefore come from a game journal the agent keeps on its own `agent-experiments` volume (BR-009), not from re-querying the metrics store at calibration time.

Implementation status (#1055): step 1, the game journal (BR-009), is implemented (PR 1, data collection only). PR 2 adds the pure selection core in `services/agent/calibration/` (BR-002 eligibility, the step 2 / A1 window after a journal watermark, the BR-004 holdout split and the BR-005 bands), with no runtime wiring: nothing calls it yet. Steps 2 to 10, A1 to A9 and BR-001, BR-005 (fit) to BR-008 are planned; no calibration, fit, acceptance or endpoint runs yet.

## Preconditions

- **Pre-1:** `enabled` and `experiments_enabled` are on ([UC-043](UC-043.md) Pre-1): a calibration runs shadow games, so it needs the same permission as experiments.
- **Pre-2:** The agent's volume `agent-experiments` is writable, and both stores on it work: the game journal (BR-009) is readable and accepts writes, and the evidence store (BR-007) is readable. The calibration reads no metrics store: real games come from the journal and validation games from the agent's own game-end snapshots (BR-006).
- **Pre-3:** The selection `experiment.mock_archetypes` resolves to valid archetypes ([UC-046](UC-046.md) BR-003); its archetypes are the ones calibrated.

## Main Success Scenario

1. A real game ends. The agent appends one record for the game to its game journal: the game id, mode, end time and duration, whether `calibration.test_session` was on (BR-003), per player the BR-002 eligibility inputs, and the BR-006 fit metrics it can measure (BR-009).
2. System counts the eligible real games (BR-002) journaled on this device after the watermark of the last completed calibration (BR-007), in journal append order. When the count reaches `calibration.every_n_games`, read at that moment, it starts a calibration with trigger `auto`.
3. System opens the evidence record (no outcome yet, BR-007), takes the most recent N eligible games in journal append order and splits them: every 4th game goes to the holdout, the others to the fit set (BR-004).
4. System runs the first validation group, the active set with seed group A (BR-006).
5. System splits the fit games into 3 bands by elimination pace and fits each archetype to its band, as ratios against its group-A games (BR-005). The result is the candidate set.
6. System runs the two other validation groups: the active set with seed group B (the A/A run) and the candidate set with seed group A (BR-006).
7. System measures each group against the holdout with the BR-006 metrics and computes the paired KS drop and the A/A noise floor.
8. The candidate meets the acceptance rule (BR-006). System writes the evidence record with outcome `accepted` (BR-007); that one write makes the candidate the active set (BR-008).
9. Experiments pinned from now on use the active set; experiments that have already pinned their archetypes keep them ([UC-046](UC-046.md) A5).
10. Use case ends.

## Alternative Flows

### A1: Operator starts a calibration by hand

**Trigger:** The operator runs `scripts/agent-calibrate.sh run`, instead of the count reaching N (step 2)
**Flow:**

1. System starts a calibration with trigger `manual`, whatever the count. It uses the most recent N eligible games after the watermark (BR-007), or all of them when fewer are available. N is `calibration.every_n_games` read at that moment; while it is `off` (0) or unreadable, N is 100, the flag's default variant. While Pre-1 does not hold (`enabled` or `experiments_enabled` off; unreadable counts as off), the start is refused with `agent_disabled` or `experiments_disabled` and no record is written.
2. Use case continues at step 3.

### A2: Too few eligible games

**Trigger:** Fewer than 32 eligible games are available, which only a manual start can meet (step 3)
**Flow:**

1. System runs no shadow game and changes nothing.
2. System completes the evidence record with outcome `insufficient_games`, the number of eligible games and the excluded count per reason (BR-002, BR-003).
3. Use case ends.

### A3: The fit does not improve realism

**Trigger:** The candidate does not meet the BR-006 acceptance rule, or no metric has enough values (step 8)
**Flow:**

1. System keeps the active set.
2. System completes the evidence record with outcome `rejected` and the reason `no_improvement` or `no_metrics`, the per-metric KS distances of all three groups and the noise floor.
3. Use case ends. A rejected calibration is completed, so the next automatic one starts after another N eligible games (step 2).

### A4: A calibration is already running

**Trigger:** A manual or automatic start while a calibration runs (step 2, A1)
**Flow:**

1. System starts no second calibration and writes no record. A manual start is answered with `calibration_running` and the running calibration's id.
2. Use case ends for the refused start; the running calibration continues at its current step.

### A5: The calibration stops before its outcome

**Trigger:** The game journal is unreadable or refuses writes, or the evidence store is broken (BR-008 a); `enabled` or `experiments_enabled` turns off (unreadable counts as off); a validation game has no result after two reruns (A6) (step 3, or any later step). A coordinator that refuses a validation start, for its `shadow_policy` while a real game is live or for its shadow-game capacity, is handled by A6, not here: no policy value blocks every shadow game.
**Flow:**

1. System stops the calibration before any change to the active set. When `enabled` or `experiments_enabled` turns off, the experiment loop stops the calibration in the same tick in which it aborts the experiment games ([UC-043](UC-043.md) A1): the running validation game is force-ended at once, not left to run to its safety cap. The calibration is not in the experiment registry, so the stop is a separate call next to the registry's abort.
2. System completes the evidence record with outcome `aborted` and the reason, in the order of the trigger: `data_unavailable`, `agent_disabled` or `experiments_disabled`, `validation_incomplete`. When the trigger is a broken evidence store or a store write that fails, no record is written or completed (BR-008 a): the calibration stops in memory with a WARN log and a failure count, the active set stays as it is (the empty set for a broken store), and an open record on disk is left for A7 once the store is readable again.
3. Use case ends. An aborted calibration is not completed, so the count stays at or above N; the next automatic start waits as BR-001 says.

### A6: A validation game cannot complete

**Trigger:** A real game preempts a validation shadow game ([UC-043](UC-043.md) A2), the coordinator refuses to start it (its `shadow_policy` while a real game is live, or its shadow-game capacity), or a validation game ends without a usable result ([UC-046](UC-046.md) A9; also when its end snapshot never reaches the calibration) (step 4 or 6). A validation game that ends on the safety cap or by the agent (`timeout`, `agent_ended`, [UC-046](UC-046.md) BR-013) has a usable result (BR-006).
**Flow:**

1. After a preemption or a refused start System waits until no real game runs; then it runs that game again with the same archetype and seed, at most twice.
2. When it still has no result, System stops the calibration as A5 with the reason `validation_incomplete`.
3. Otherwise use case continues at step 4 or step 6, whichever it interrupted.

### A7: Agent restarts during a calibration

**Trigger:** The agent stops (crash, restart, power loss) while a calibration runs (step 3, or any later step)
**Flow:**

1. On start the agent finds the calibration's open record and completes it with outcome `aborted` and the reason `restart`; the next automatic start waits as BR-001 says. When the store is broken (BR-008 a) or that write fails, the record stays open with a WARN log and a failure count; it is completed at the first start with a readable store.
2. The active set is unchanged: an open record never defines it (BR-008).
3. Use case ends.

### A8: Operator rolls back

**Trigger:** The operator runs `scripts/agent-calibrate.sh rollback`, after an accepted calibration (step 8) or while one runs (step 3, or any later step)
**Flow:**

1. A rollback is not a calibration: it works also while `enabled` or `experiments_enabled` is off and runs no shadow game. A running calibration is stopped first and recorded `aborted` with the reason `rollback`.
2. When the active set was not made by an `accepted` record (nothing calibrated yet, or the newest change was already a rollback or a reset), System changes nothing and answers `nothing_to_roll_back`; use case ends. A rollback has one level only.
3. System writes a record with outcome `rolled_back` whose after set is the before set of that `accepted` record (the empty set, i.e. the flag-file archetypes, after the first calibration); that write makes it active (BR-008).
4. Experiments pinned from now on use the restored set. A rollback counts as a completed calibration (BR-007), so the next automatic calibration starts after another N eligible games; the calibration it stopped in step 1 starts no retry wait.
5. Use case ends.

### A9: Operator resets to the baseline

**Trigger:** The device moves to a new venue or environment and the operator runs `scripts/agent-calibrate.sh reset`, between calibrations (step 2) or while one runs (step 3, or any later step)
**Flow:**

1. Like a rollback, a reset is not a calibration: it works also while `enabled` or `experiments_enabled` is off. A running calibration is stopped first and recorded `aborted` with the reason `reset`.
2. System writes a record with outcome `reset` and the empty set as its after set, so the flag-file archetypes are active again (BR-008).
3. From now on only real games journaled after the reset's watermark (BR-007) are eligible: the next calibration starts from the baseline on this device's new games. A rollback never crosses a reset (A8).
4. Use case ends.

## Postconditions

### Success Postconditions

- The candidate set is active for experiments pinned after the calibration; the replaced set is its previous set.
- One evidence record holds the before and after sets with their digests, the games used and excluded, the KS distances, the noise floor and the constants used (BR-007).
- No real-game rule, flag or flag file has changed (C-022).

### Failure Postconditions

- After `insufficient_games`, `rejected` or `aborted`, the active set is unchanged.
- One evidence record names the outcome (`insufficient_games`, `rejected`, `aborted`) and its reason (BR-007).
- After a rollback (A8) the restored set is active and a `rolled_back` record names both sets; after a reset (A9) the flag-file archetypes are active and a `reset` record says so.
- No real-game rule, flag or flag file has changed (C-022).

## Business Rules

### BR-001: Trigger and retry

`calibration.every_n_games` (`agent` set, human-owned, never agent-written, C-034) holds N, read at use time (C-035): variants `off` = 0 (no automatic calibration; manual runs and rollback still work), `50`, `default` = 100, `200`. Only the declared variants are valid, so N is never below 32 except for `off` (BR-004). After an aborted calibration (A5, A7; not one stopped by a rollback or reset) the next automatic start waits 1 hour, so a failing calibration cannot occupy the shadow-game slot back to back. The wait is kept in memory on a monotonic clock, never from stored wall-clock times (the Pi has no real-time clock, so its clock can jump after a power loss); after a restart (A7) it counts from the process start. A calibration is bounded without a deadline of its own: each validation game has the pattern-game safety cap ([UC-046](UC-046.md) BR-013) and at most two reruns (A6).

### BR-002: Eligible real game

A real game (`game_kind` `primary`) is eligible only when all of these hold:

- its mode is `JoustFFA`, the only mode pattern games run (C-021);
- it lasted at least 10 s, by the duration its journal record holds (the agent's `game_duration_seconds` at game end, BR-009) (on the stage Pi the median real game lasts 16 s; shorter games are mostly false starts);
- at least 2 players moved: a player moved when the mean of their `game_player_movement_variance` gauge over the game (1 s samples, as A22 samples it; journaled per player, BR-009) is at least 0.005 g² (a controller lying still stays far below). A player without a mean variance (no 1 s variance sample, for example eliminated before the first one) did not move: it is left out of the mover count and of the dominance check below;
- no player dominates: of the players with a mean variance, the highest is less than 10 times the second highest (the "one person shaking a controller" test pattern);
- it was journaled on this device after the watermark of its newest reset (A9, BR-007) and is not marked as test (BR-003; a `null` mark counts as test);
- its journal record holds these inputs (BR-009); a game without a record is ineligible (BR-003), and a record without a finite duration or a finite `elimination_pace` (the game-level inputs) is excluded with the reason `metrics_missing`; a missing per-player mean is never `metrics_missing` (above). This default is the reviewer's, open to the maintainer's override (#1055).

The reasons, checked in this order, the first failing one counted: `other_mode`, `test_session`, `metrics_missing`, `too_short`, `too_few_moved`, `dominant`. The watermark is applied before them: a game journaled before it is not counted at all.

Agent interventions and the player count are not filtered: a real game is fitted as it was played.

### BR-003: Test session mark

`calibration.test_session` (`agent` set, `on` / `off`, default `off`, human-owned, never agent-written) lets the operator mark a session as test: a real game that ends while it is `on` is ineligible, and so is a real game whose end the agent did not journal (the agent was not running). The operator sets it with `scripts/agent-calibrate.sh test-session on|off`, which writes the stack overlay through the flag service (not through the agent: the agent never writes `agent` flags, C-034) without `persist`, so a flag-service restart returns it to `off`. A game whose journal record holds `null` for the mark (the flag was unreadable at its end) counts as test. `scripts/agent-calibrate.sh status` shows the mark, the eligible count and the excluded count per reason, so a forgotten `on` is visible.

### BR-004: Holdout split

In journal append order (never by end time: the Pi's clock can jump), every 4th eligible game (the 4th, 8th, ...) is in the holdout and the rest is in the fit set; the holdout is never used to fit. A calibration needs at least 32 eligible games: 24 fit games for 3 bands of 8 (BR-005) and 8 holdout games, A22's default `--min-n`. At that minimum one KS distance is noisy, so the rule of BR-006 accepts only large drops; the default N = 100 gives a holdout of 25.

### BR-005: Fit per band

The fit games are split into 3 bands by elimination pace, the journal's `elimination_pace` (eliminations per game minute, never recomputed: a record without it is not eligible, BR-002 `metrics_missing`; low, middle, high; ties in journal append order), each a third of the games, any remainder in the middle band. Each archetype has a fixed band, so its meaning does not swap between calibrations: `calm_long` and `slow_cascade` low; `jittery_novices`, `late_burst` and any other name middle; `close_race` and `quick_cascade` high. Several archetypes share a band; the fit scales each one's own parameters (below), so they keep their shape, stay distinct and are never averaged into one.

Fit method (one ratio step, deterministic): each parameter group is multiplied by one ratio r, the band's median over the archetype's median in its group-A validation games: `base` and `d_base` by the movement-intensity ratio; `amp`, `d_amp` and `burst_h` by the square root of the movement-variance ratio (the mean over players of the per-player mean variance, as the journal measures it); `drift` and `d_drift` by the elimination-pace ratio. A per-slot spread moves with its parameter, so every slot of the archetype moves by the same r and the archetype keeps its shape. `burst_period_s` keeps its value: near-death frequency is not measured (BR-006). A parameter that is 0 stays 0. `d_amp`, the per-slot spread, is what the maintainer called jitter: pattern games add no random variation (C-020). `period_s`, `phase`, `d_phase`, `players`, `stream_rate_hz` and a `trigger_policy` keep their values, because 1 Hz gauges cannot resolve sub-second motion. The ratio, not each field, is clamped: r is reduced so that every slot value stays within the [UC-046](UC-046.md) BR-003 bounds (for example `base + i·d_base` and `amp + i·d_amp` within 0 to 10, every `d_*` within ±1), and the clamp is recorded; the fitted archetype is therefore always valid. A ratio is undefined when either median (the band's or the archetype's group-A median) is 0 or not finite: r = 1 (the parameters keep their values) and the evidence record notes `ratio_undefined`.

### BR-006: Validation and acceptance

Each validation group has max(4, ceil(8 / n)) games per selected archetype, n being the number of selected archetypes (4 games each and 24 per group with the six shipped archetypes, 72 per calibration; 8 games per group for a single archetype such as `quick_cascade`, so a metric can still reach 8 values). Seed group A uses the one-shot runner's seed from the archetype name ([UC-046](UC-046.md) BR-006) plus 0 to 3, seed group B plus 4 to 7. They are shadow games with no experiment arm, marked with the calibration id, one at a time ([UC-046](UC-046.md) BR-010), between the games of any running experiment, never experiment samples. They take the single shadow-game slot one game at a time and yield it between games: when a running experiment wants a pair, the next validation game waits until the registry has spawned it or one registry tick has passed, so a calibration of up to 72 games of up to the safety cap each does not starve experiments. The agent's decide loop runs in validation games as in every shadow game (shadow-default flags): a real game is fitted as played (BR-002), so the shadow games are played the same way. This costs decide calls, and LLM calls when an LLM backend is on, for every validation game.

Metrics (k = 3 at most): `intensity`, `movement_variance` and `elimination_pace`, measured per game as the journal measures them (BR-009), with the same function (`gamejournal.BuildRecord`) on both sides: the holdout's journal records, and for each validation game the record built from the agent's own game-end snapshot of that shadow game. A22 is not run and its numbers are not used (A22 averages intensity also after an elimination and reads the last variance, not the mean). A validation game that ends on the safety cap or by the agent (`timeout`, `agent_ended`) gives usable values: its pace is right-censored, but the same holds for every group. A non-finite value is no value. Each metric counts when it has at least 8 values in the holdout and in each group; k is their number, and k = 0 ends the calibration `rejected` with the reason `no_metrics`. Left out for now, each a follow-up: `activity` and `change` (the agent's 1 s history holds only the last 32 s, so most validation games would truncate and only the fast-dying archetypes would keep a value, a biased subset; needs a whole-game series for the game-end snapshot) and `near_death_rate` (the coordinator's near-death counter has no game id and the agent does not ingest it; needs a per-game gauge and journal `schema_version` 2). Per metric m, against the same holdout:

- paired drop d_m = KS(active, A) − KS(candidate, A);
- A/A difference a_m = KS(active, A) − KS(active, B);
- noise floor σ = the larger of sqrt(mean of a_m²) and 0.05 (one A/A run can come out near 0 by chance).

BR-006 uses the raw KS distances, not A22's verdicts: A22's KS power gate (A22 step 4) needs about 41 games per kind before a verdict is not `insufficient`, while this rule compares two distances against the same holdout and takes its noise from the A/A run. The candidate is accepted when the mean of d_m is greater than 2σ and no single d_m is below −2σ (no metric got clearly worse). The evidence record stores every d_m, a_m and σ. The holdout's sampling error is the same for all three groups, so it cancels in d_m; what remains is the game-to-game variation of the shadow games, which is small because the inputs are deterministic (C-020) and only the seeds differ. The A/A run measures that variation as σ; the 0.05 floor keeps a near-zero σ from accepting noise.

### BR-007: Evidence record

Every calibration writes one evidence record (layout and path: [services.md](../specs/services.md#agent), planned). It is opened at step 3 without an outcome and completed once at the end; an open record never defines the active set. It holds a sequence number `seq` (one more than the newest record's; records are ordered by it, never by wall-clock time), the calibration id, the trigger (`auto`, `manual`), start and end time (informational only), the journal watermark (below), the outcome and its reason (`accepted`; `rejected` with `no_improvement` or `no_metrics`; `insufficient_games`; `aborted` with `data_unavailable`, `agent_disabled`, `experiments_disabled`, `validation_incomplete`, `restart`, `rollback` or `reset`; `rolled_back`; `reset`), the holdout and fit game ids, the excluded count per reason (BR-002, BR-003), the before and after sets with their digests and the flag-file digest of each calibrated name, every d_m, a_m and σ, any clamped ratio and any `ratio_undefined`, and the constants used (BR-008). A rollback and a reset write a record too, with outcome `rolled_back` or `reset`.

A **completed calibration** is a record with outcome `accepted`, `rejected`, `rolled_back` or `reset`. Its **watermark** is the `game_id` of the newest journal record when it completed (empty for an empty journal); step 2, A1 and the A9 eligibility count only the journal records after the watermark of the newest completed calibration (by `seq`), in journal append order. A watermark no longer in the journal (evicted, BR-009) or empty means every journaled record counts. Records are never deleted.

### BR-008: Calibrated set per device, writer and the C-019 amendment

The **calibrated set** is one parameter object per calibrated archetype name. It belongs to one device: it is written only to that device's `agent-experiments` volume, never to git, never copied to another device. The active set is the after set of the newest `accepted`, `rolled_back` or `reset` record; with no such record it is the empty set. A name the active set does not hold uses its flag-file parameters, so the empty set means the flag-file archetypes. An accepted after set is the before set overlaid with the newly fitted names, so a calibration on a narrower selection keeps the other calibrated names. An accepted calibration changes the shadow drivers without a release change, so the release binding of the substrate attestation ([UC-043](UC-043.md) A23, #2541) cannot cover it. v1 fails closed: an experiment pinned with a non-empty calibration id is below the validity bar, whatever the attestation, with the reason `substrate_calibrated`. The pin's calibration id covers only the calibrated entries the pin actually applied: when condition c ignores all of them, the pin's id is empty and a plain attestation covers it again. An unknown id fails closed: every pin written after this feature carries an explicit calibration-id field in its `pattern_pinned` journal facts, present also when empty; facts that are missing or unreadable, or a field that cannot be read, count as calibrated (below the bar, `substrate_calibrated`). The one allowed legacy case is an experiment pinned before this feature: its facts have no field at all, and it was pinned on the flag-file set, so it reads `""`. An attestation grammar bound to a calibration id is a follow-up, once the paired study exists.

The agent is the only writer of records. `scripts/agent-calibrate.sh` (`run`, `rollback`, `reset`, `status`) reaches it under the agent's existing `/experiments` path through envoy (services.md, planned); `test-session on|off` is not an agent call but a flag-service stack overlay (BR-003); a rollback or reset cancels a running calibration through the same call before it writes. Record writes hold one lock in the agent, and a rollback or reset cancels a running calibration under that lock before it writes, so a cancelled calibration can never write `accepted` afterwards.

Every pattern game records the archetype name, its parameter digest and the calibration id (empty for flag-file parameters), so a trace names the exact parameters.

C-019 amendment (TBD-A1, resolved by the maintainer's decision of 2026-11-01), with these conditions:

a. Fail closed: an unreadable, truncated or invalid record ([UC-046](UC-046.md) BR-003 validators, run on load), or a missing volume, falls back to the flag-file archetypes with a WARN, never to a partial set. A store with such a record is broken: the active set is the empty set, and the store refuses every write (run, rollback and reset included, `store_unreadable`), because a new record could otherwise hide a newer unreadable one whose `seq` is unknown. The operator's way out: `scripts/agent-calibrate.sh status` names the unreadable file; the operator moves it aside on the volume and restarts the agent, which then loads the remaining records (A7 completes an open one).
b. Durable atomic write: temporary file, fsync, rename, fsync of the directory.
c. Release edits win: each record stores the flag-file digest of each calibrated name; when a release changes that variant, its calibrated entry is ignored with a WARN log.
d. One writer holding one lock (above), and records are never pruned.
e. Defined rollback: one level, to the before set of the `accepted` record that made the active set (A8); the empty set (flag-file archetypes) is a defined state.
f. The active set (calibration id, digests) is visible in `status` and on the pattern-game traces, so nobody believes the flag file is in force.
g. Realism only: acceptance looks at realism, never at experiment fitness. The A23 validity bar ([UC-043](UC-043.md) A23) treats an experiment pinned on calibrated entries as below the bar (`substrate_calibrated`, above), so no change of the active set can carry an attestation over; a rollback or reset to the flag-file archetypes gives pins with an empty calibration id again. A23 keeps comparing with all real games of its window, not only the games eligible here.

Constants (each a reviewed edit, not a flag, per C-035: an operator does not tune them on stage, and the evidence record stores the values used): minimum duration 10 s; movement floor 0.005 g²; dominance ratio 10; 3 bands of at least 8 fit games; every 4th game in the holdout; max(4, ceil(8 / n)) validation games per archetype per group; acceptance at 2σ with a σ floor of 0.05; retry wait 1 hour; manual N 100 while `calibration.every_n_games` is off.

### BR-009: Game journal

Implemented (#1055 PR 1). At each real game end (`game_kind` `primary`, normalised `real`) the agent appends one record to `<AGENT_EXPERIMENT_DIR>/calibration/real_games.jsonl` on its `agent-experiments` volume ([services.md](../specs/services.md#agent)): `schema_version`, `game_id`, `mode`, `ended_at`, `duration_seconds`, `test_session` (`calibration.test_session` read at the end; `null` when unreadable, which a calibration treats as test), `eliminations`, `history_truncated`, and per player, without a serial (C-009): the mean movement variance and the mean intensity over the game's 1 s samples up to the player's elimination (later samples are left out, as A22 leaves out dead players) with their sample counts, kept across a silence eviction ([UC-041](UC-041.md) BR-007), the last movement variance and whether the player was eliminated. `metrics` holds the A22 metrics measured per game from the agent's game context (BR-006 uses `intensity`, `movement_variance` and `elimination_pace`; the others are journaled for the follow-ups): `intensity` and `movement_variance` (the mean over the players), `elimination_pace` (eliminations per game minute), `activity` and `change` (A22's definition, from the agent's 1 s history, which holds the last 32 s per player: `history_truncated` marks a game where they cover less than the whole game). `near_death_rate` is `null`: the agent does not ingest the coordinator's near-death counter. A metric the agent cannot measure is `null`.

Not journaled: shadow games, games of unknown kind, and games the agent ended on the stale `game_active` backstop ([UC-041](UC-041.md) A4: their telemetry broke, so they are ineligible as unjournaled games, BR-003). A game id is journaled once.

Bounded and durable: the journal keeps the newest 500 records (a constant, about five windows at the default N); one more evicts the oldest. Every append rewrites the file with the durable atomic write of BR-008 condition b, from a single writer off the telemetry ingest path. Fail-soft: a failed write, a full write queue, a game end during shutdown (the writer is joined with a bounded wait) or an unreadable file at start never affects the game or the decide path; it logs `agent.calibration.journal_write_failed` (or `agent.calibration.journal_load_failed`) and counts `agent_calibration_journal_write_failures_total{reason}` ([telemetry.md](../specs/telemetry.md#6-metrics)). A record whose write failed stays in memory and is written with the next one; an unreadable file, or one holding a record with a newer `schema_version` (a downgrade), is never replaced: the journal then refuses writes. Other invalid lines are dropped on the next write.
