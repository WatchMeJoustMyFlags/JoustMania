# Use Case: Recalibrate the Shadow Players from Real Games

## Overview

**Use Case ID:** UC-047
**Use Case Name:** Recalibrate the Shadow Players from Real Games
**Primary Actor:** Agent
**Secondary Actors:** Operator
**Trigger:** Another N eligible real games have ended since the last completed calibration (N = `calibration.every_n_games`, default 100, BR-001), or the operator starts a calibration run by hand
**Goal:** Keep the archetypes that drive shadow games ([UC-046](UC-046.md)) close to how people really play, by fitting their parameters to recent real games and accepting the new parameters only when a holdout shows the shadow games got more realistic, so that experiment verdicts ([UC-043](UC-043.md)) rest on a substrate that resembles real play (#1055, #1017)
**Status:** Draft
**Requirements:** FR-204, FR-205, C-022, C-019, C-020, C-021, C-033, C-034, C-035, C-040

Context: the first realism characterization of the stage Pi ([UC-043](UC-043.md) A22, FR-203, both added by PR #2542) found shadow games matching real games on mean movement intensity, but with about 20 times less movement variance, far fewer deaths and longer games. Many real games on the Pi are test games: one person shakes a controller while the others lie still. This use case removes those games and refits the archetypes to the rest (maintainer idea, 2026-11-01).

Open decision TBD-A1 (blocks implementation, not this spec): C-019 versions archetype parameters by the git history of the flag files, with no separate set files (maintainer decision on #1258). An accepted calibration needs a parameter set outside the flag files (BR-008), because on the Pi a flag file changes only with a release (C-033, C-040). The maintainer decides whether C-019 is amended to allow the calibration record as a second version source. This use case moves to Approved after that decision.

## Preconditions

- **Pre-1:** `enabled` and `experiments_enabled` are on ([UC-043](UC-043.md) Pre-1): calibration runs shadow games, so it needs the same permission as experiments.
- **Pre-2:** The agent's journal volume `agent-experiments` is writable and the metrics store (VictoriaMetrics) is reachable from the agent.
- **Pre-3:** The selection `experiment.mock_archetypes` resolves to valid archetypes ([UC-046](UC-046.md) BR-003); its archetypes are the ones calibrated.

## Main Success Scenario

1. A real game ends. The agent records in its journal the game id and whether `calibration.test_session` was on at that moment (BR-003).
2. System counts the eligible real games (BR-002) that ended since the end of the last completed calibration (outcome `accepted`, `rejected` or `rolled_back`, BR-007). When the count reaches `calibration.every_n_games`, read at that moment, it starts a calibration run with trigger `auto`.
3. System takes the most recent N eligible games (at least 32, BR-004) and splits them by end time: every 4th game goes to the holdout, the others to the fit set (BR-004).
4. System runs validation shadow games with the current parameter set: two games per archetype of the selection, with fixed seeds, with no experiment arm, so no experiment value applies (BR-006).
5. System ranks the archetypes by the death rate per minute of their current-set validation games, divides the fit games into as many bands as there are archetypes by death rate per minute, and gives each archetype the band of the same rank (BR-005).
6. System fits each archetype's parameters to its band (BR-005), keeping the archetype's name, players and stream rate. The result is the candidate set.
7. System runs the same validation shadow games with the candidate set: same archetypes, same seeds, same game flags (BR-006).
8. System compares each set's validation games with the holdout real games using the realism characterization of [UC-043](UC-043.md) A22 (same metrics, KS distance, verdict per metric).
9. The candidate is closer to the holdout than the current set (BR-006). System writes the evidence record with outcome `accepted` (BR-007); that one write makes the candidate the active set and keeps the replaced set as its previous set (BR-008).
10. Experiments declared from now on pin the active set; experiments already running keep the parameters they pinned ([UC-046](UC-046.md) A5).
11. Use case ends.

## Alternative Flows

### A1: Operator starts a calibration by hand

**Trigger:** The operator runs `scripts/agent-calibrate.sh run`, instead of the count reaching N (step 2)
**Flow:**

1. System starts a calibration run with trigger `manual`, whatever the count of step 2.
2. Use case continues at step 3.

### A2: Too few eligible games

**Trigger:** Fewer than 32 eligible real games are available (step 3), possible on a manual run or after a data loss
**Flow:**

1. System runs no shadow game and changes no parameter.
2. System writes the evidence record with outcome `insufficient_games`, the number of eligible games and the count of excluded games per exclusion reason (BR-002, BR-003).
3. Use case ends.

### A3: The fit does not improve realism

**Trigger:** The candidate set is not closer to the holdout than the current set (step 9, BR-006)
**Flow:**

1. System keeps the current set active.
2. System writes the evidence record with outcome `rejected` and the reason: the KS distance per metric for both sets and the metrics that made the candidate fail.
3. Use case ends. The next automatic run starts after another N eligible games (step 2).

### A4: A calibration is already running

**Trigger:** A manual or automatic start while a calibration run is in progress (step 2, A1)
**Flow:**

1. System starts no second run. A manual start is answered with `calibration_running` and the running calibration's id; an automatic start is skipped.
2. The skipped automatic start writes no record: its count stays at or above N, so the next real game end checks again once the running calibration has completed.
3. Use case ends for the refused start; the running calibration continues at its current step.

### A5: Data source unavailable

**Trigger:** The metrics store does not answer or answers with an error (step 2, 3 or 8)
**Flow:**

1. System stops the run before it changes any parameter; shadow games already started finish and are not used.
2. System writes the evidence record with outcome `data_unavailable` and the failing query.
3. Use case ends. The run does not count as completed, so an automatic run is tried again at the next real game end, at most once per hour.

### A6: Kill switch, experiments off or shadow games blocked

**Trigger:** `enabled` or `experiments_enabled` is off, or `shadow_policy` blocks shadow games (step 2, or any later step)
**Flow:**

1. No calibration starts, and no record is written for a start that never happened.
2. A running calibration stops at its next step, before any parameter change; a running validation game is torn down as an experiment game is ([UC-043](UC-043.md) A1). System writes the evidence record with outcome `aborted` and the reason (`agent_disabled`, `experiments_disabled`, `shadow_blocked`).
3. Use case ends.

### A7: A validation game cannot complete

**Trigger:** A real game preempts a validation shadow game ([UC-043](UC-043.md) A2), or a validation game ends without a usable result ([UC-046](UC-046.md) A9) (step 4 or 7)
**Flow:**

1. System runs that game again with the same archetype and seed, at most twice.
2. When the game has a result now, use case continues at step 4 or step 7, whichever it came from.
3. When it still has no result, System stops the run, keeps the current set and writes the evidence record with outcome `aborted` and the reason `validation_incomplete`. Use case ends.

### A8: Agent restarts during a calibration

**Trigger:** The agent stops (crash, restart, power loss) while a calibration runs (step 3, or any later step)
**Flow:**

1. On start the agent finds the run's record without an outcome and completes it with outcome `aborted` and the reason `restart`.
2. The active set is what it was before the run: it changes only with the atomic write of an `accepted` or `rolled_back` record (BR-008), so a stop before that write leaves it unchanged and a stop after it leaves the complete new record.
3. Use case ends.

### A9: Operator rolls back

**Trigger:** The operator runs `scripts/agent-calibrate.sh rollback`, also while `enabled` is off, after an accepted calibration (step 9) or while one runs (step 3, or any later step)
**Flow:**

1. A running calibration is stopped first and recorded `aborted` with the reason `rollback`.
2. Without an active set (the shipped flag-file parameters are in use) System changes nothing and answers `nothing_to_roll_back`; use case ends.
3. System writes an evidence record with outcome `rolled_back`, naming both sets; that one write makes the active set's previous set active again (BR-008). Repeating the rollback walks back further, down to the shipped flag-file parameters (no calibrated set).
4. Experiments declared from now on pin the restored set; running experiments keep theirs. A rollback counts as a completed calibration, so the next automatic run starts only after another N eligible games (step 2).
5. Use case ends.

## Postconditions

### Success Postconditions

- The candidate set is the active set for experiments declared after the calibration; the replaced set is kept as its previous set.
- One evidence record holds the before and after parameters with their digests, the games used and excluded, and the realism comparison (BR-007).
- No real-game rule, flag or flag file has changed (C-022).

### Failure Postconditions

- The active set is unchanged.
- One evidence record names the outcome (`insufficient_games`, `rejected`, `data_unavailable`, `aborted`) and its reason.
- No real-game rule, flag or flag file has changed (C-022).

## Business Rules

### BR-001: Trigger flag

`calibration.every_n_games` (`agent` set, human-owned, never agent-written, C-034) holds N: variants `off` = 0 (no automatic run; manual runs still work), `50`, `default` = 100, `200`. It is read at use time (C-035). After the `off` check, a value below 32 counts as 32 (BR-004). A value below 32 counts as 32 (BR-004).

### BR-002: Eligible real game

A real game (`game_kind` `primary`) is eligible only when all of these hold:

- its mode is `JoustFFA`, the only mode pattern games run (C-021);
- it lasted at least 10 s (on the stage Pi the median real game lasts 16 s; shorter games are mostly false starts);
- at least 2 players moved: a player moved when the variance of their movement intensity over the game is at least 0.005 g² (a controller lying still stays far below);
- no single player dominates: the most active player's movement variance is less than 10 times the second most active player's (the "one person shaking a controller" test pattern);
- it is not a test game (BR-003);
- its duration and per-player movement series are in the metrics store; a game whose series are missing or expired is excluded with the reason `metrics_missing`.

Agent interventions in the real game (shields, music tempo) and the player count are not filtered: a real game is fitted as it was played, with the agent as it ran then. These values change by a reviewed edit of this rule; they are not flags, because nobody tunes them on stage.

### BR-003: Test session mark

`calibration.test_session` (`agent` set, `on` / `off`, default `off`, human-owned, never agent-written, not persisted) lets the operator mark a session as test. A real game that ends while it is `on` is ineligible. The operator sets it with `scripts/agent-calibrate.sh test-session on|off` (a stack overlay; the implementation adds both calibration flags to the mutable-flag registry, flags.md §13); not persisted means a flag-service restart returns it to `off`. `scripts/agent-calibrate.sh status` shows the mark, the eligible count and the excluded count per reason, so a forgotten `on` is visible. A real game whose end the agent did not record (the agent was not running) is ineligible too: unknown counts as test.

### BR-004: Game count and holdout split

A calibration uses the most recent N eligible games (N from BR-001; a manual run uses all eligible games since the last completed calibration, at most 200). It needs at least 32, so that the holdout reaches the 8 games per kind that the realism verdict needs ([UC-043](UC-043.md) A22 step 4). Ordered by end time, every 4th game is in the holdout and the rest is in the fit set. The holdout is never used to fit. Each archetype's band needs at least 4 fit games; with fewer (too many archetypes in the selection for the games) the run ends as A2 with outcome `insufficient_games`.

### BR-005: Fit per archetype

The archetypes stay distinct: each archetype is fitted to its own band of the fit games, never to the average of all of them. Bands split the fit games by death rate per minute into equal-sized groups, one per archetype; the archetype whose current-set validation games die least gets the slowest band. Within its band, each archetype's parameters ([UC-046](UC-046.md) BR-003) are fitted to these targets:

| Parameter | Fitted to (band statistic) |
|---|---|
| `base` | median movement intensity |
| `amp`, `period_s` | median movement variance and the `change` characteristic (decide-contract §14.1) |
| spread between players (`d_base`, `d_amp`, `d_drift`) | the spread of movement intensity and variance between players of one game |
| `burst_h`, `burst_period_s` (spike height and rate) | near-death frequency per player-minute and the height of intensity peaks |
| `drift` | death rate per minute and the change of intensity from the start to the end of a game |

"Jitter" in this use case means the spread between players: pattern games add no random variation (C-020). `players`, `stream_rate_hz`, `phase`, `d_phase` and a `trigger_policy` keep their current values. Every fitted value stays within the BR-003 bounds. The fit is deterministic: the same fit games and current set give the same candidate set. Games with an equal death rate per minute are ordered by end time when the bands are cut.

### BR-006: Validation and acceptance

Each set gets the same validation games: two per archetype of the selection, with two fixed seeds per archetype (the one-shot runner's seed from the archetype name, [UC-046](UC-046.md) BR-006, and that seed plus 1), the same for both sets; with the shipped six archetypes that is 12 games per set, at least the 8 the realism verdict needs. They are shadow games marked with the calibration id, one at a time ([UC-046](UC-046.md) BR-010), never experiment samples. The candidate is closer to the holdout when both hold:

- its mean KS distance to the holdout is lower than the current set's by at least 0.05, averaged over the A22 per-metric rows (not the per-objective rollups) whose verdict is not `insufficient` for either set;
- no metric whose verdict is `similar` for the current set is `divergent` for the candidate.

The comparison uses the A22 metrics, distance and verdict rules on explicit game sets (the holdout's game ids against one set's validation games), not on a time window.

Validation games take the single shadow-game slot between the games of a running experiment; neither pauses the other. A calibration run that has not reached its outcome 2 hours after its start stops with outcome `aborted` and the reason `timeout`, and keeps the current set.

### BR-007: Evidence record

Every calibration run writes one evidence record on the `agent-experiments` volume, also when it fails: the calibration id, the trigger (`auto`, `manual`), start and end time, the outcome (`accepted`, `rejected`, `insufficient_games`, `data_unavailable`, `aborted`, `rolled_back`) and its reason, the game ids of the fit set and the holdout, the count of excluded games per reason (BR-002, BR-003), the before and after parameters per archetype with their digests, and per set the A22 metrics of its validation games against the holdout. The records are kept; a run counts as completed only with outcome `accepted` or `rejected`.

### BR-008: Active set and identity

The active set and its previous sets live with the evidence records on the `agent-experiments` volume. Without an active set the archetypes use the shipped flag-file parameters. With one, an archetype name of `experiment.mock_archetypes` resolves to the active set's parameters for that name; a name the set does not hold keeps its flag-file parameters. The active set is the after set of the newest record with outcome `accepted` or `rolled_back`, so writing that record (one atomic write) is the switch; no separate pointer exists. Every pattern game records the archetype name, the digest of the parameters it ran and the calibration id (empty for flag-file parameters), so a trace names the exact parameters (C-019; see TBD-A1).
