# Use Case: Recalibrate the Shadow Players from Real Games

## Overview

**Use Case ID:** UC-047
**Use Case Name:** Recalibrate the Shadow Players from Real Games
**Primary Actor:** Agent
**Secondary Actors:** Operator
**Trigger:** Another N eligible real games have ended since the last completed calibration (N = `calibration.every_n_games`, default 100, BR-001), or the operator starts a calibration by hand
**Goal:** Keep the archetypes that drive shadow games ([UC-046](UC-046.md)) close to how people really play, by refitting them to recent real games and keeping the result only when a holdout shows the shadow games got more realistic, so that experiment verdicts ([UC-043](UC-043.md)) rest on a substrate that resembles real play (#1055, #1017)
**Status:** Draft
**Requirements:** FR-204, FR-205, C-022, C-019, C-020, C-021, C-033, C-034, C-035, C-040

Context: the first realism characterization of the stage Pi ([UC-043](UC-043.md) A22, FR-203) found shadow games matching real games on mean movement intensity, but with about 20 times less movement variance, far fewer deaths and longer games. Many real games on the Pi are test games: one person shakes a controller while the others lie still. This use case leaves those games out and refits the archetypes to the rest (maintainer idea, 2026-11-01).

TBD-A1 resolved (maintainer decision, 2026-11-01: calibration is device-specific, because different game environments mean different behaviour): the calibrated set belongs to one device and lives in that device's evidence records on its own `agent-experiments` volume. It is never written back to git and never shared between devices; the flag files are only the baseline (C-019 as amended, BR-008). This use case stays Draft until the reworked spec is reviewed.

## Preconditions

- **Pre-1:** `enabled` and `experiments_enabled` are on ([UC-043](UC-043.md) Pre-1): a calibration runs shadow games, so it needs the same permission as experiments.
- **Pre-2:** The agent's volume `agent-experiments` is writable and the metrics store (VictoriaMetrics) is reachable from the agent.
- **Pre-3:** The selection `experiment.mock_archetypes` resolves to valid archetypes ([UC-046](UC-046.md) BR-003); its archetypes are the ones calibrated.

## Main Success Scenario

1. A real game ends. The agent appends the game id and whether `calibration.test_session` was on to its calibration journal (BR-003).
2. System counts the eligible real games (BR-002) that ended on this device since the last completed calibration (BR-007). When the count reaches `calibration.every_n_games`, read at that moment, it starts a calibration with trigger `auto`.
3. System opens the evidence record (no outcome yet, BR-007), takes the most recent N eligible games and splits them by end time: every 4th game goes to the holdout, the others to the fit set (BR-004).
4. System runs the first validation group, the active set with seed group A (BR-006).
5. System splits the fit games into 3 bands by elimination pace and fits each archetype to its band, as ratios against its group-A games (BR-005). The result is the candidate set.
6. System runs the two other validation groups: the active set with seed group B (the A/A run) and the candidate set with seed group A (BR-006).
7. System measures each group against the holdout with the BR-006 metrics and computes the paired KS drop and the A/A noise floor.
8. The candidate meets the acceptance rule (BR-006). System writes the evidence record with outcome `accepted` (BR-007); that one write makes the candidate the active set (BR-008).
9. Experiments pinned from now on use the active set; experiments that have already pinned their archetypes keep them ([UC-046](UC-046.md) A5).
10. Use case ends.

## Alternative Flows

### A1: Operator starts a calibration by hand

**Trigger:** The operator runs `scripts/agent-calibrate.sh run`, instead of the count reaching N (step 2)
**Flow:**

1. System starts a calibration with trigger `manual`, whatever the count. It uses the most recent N eligible games, or all of them when fewer are available.
2. Use case continues at step 3.

### A2: Too few eligible games

**Trigger:** Fewer than 32 eligible games are available, which only a manual start can meet (step 3)
**Flow:**

1. System runs no shadow game and changes nothing.
2. System completes the evidence record with outcome `insufficient_games`, the number of eligible games and the excluded count per reason (BR-002, BR-003).
3. Use case ends.

### A3: The fit does not improve realism

**Trigger:** The candidate does not meet the BR-006 acceptance rule, or no metric has enough values (step 8)
**Flow:**

1. System keeps the active set.
2. System completes the evidence record with outcome `rejected` and the reason `no_improvement` or `no_metrics`, the per-metric KS distances of all three groups and the noise floor.
3. Use case ends. A rejected calibration is completed, so the next automatic one starts after another N eligible games (step 2).

### A4: A calibration is already running

**Trigger:** A manual or automatic start while a calibration runs (step 2, A1)
**Flow:**

1. System starts no second calibration and writes no record. A manual start is answered with `calibration_running` and the running calibration's id.
2. Use case ends for the refused start; the running calibration continues at its current step.

### A5: The calibration stops before its outcome

**Trigger:** The metrics store does not answer or answers with an error, `enabled` or `experiments_enabled` turns off, the operator sets `shadow_policy` to block shadow games (a stack policy, unlike the momentary preemption of A6), a validation game has no result after two reruns (A6) (step 3, or any later step)
**Flow:**

1. System stops the calibration before any change to the active set. A running validation game is torn down as an experiment game is ([UC-043](UC-043.md) A1).
2. System completes the evidence record with outcome `aborted` and the reason, in the order of the trigger: `data_unavailable`, `agent_disabled` or `experiments_disabled`, `shadow_blocked`, `validation_incomplete`.
3. Use case ends. An aborted calibration is not completed, so the count stays at or above N; the next automatic start waits as BR-001 says.

### A6: A validation game cannot complete

**Trigger:** A real game preempts a validation shadow game ([UC-043](UC-043.md) A2), or a validation game ends without a usable result ([UC-046](UC-046.md) A9) (step 4 or 6)
**Flow:**

1. After a preemption System waits until no real game runs; then it runs that game again with the same archetype and seed, at most twice.
2. When it still has no result, System stops the calibration as A5 with the reason `validation_incomplete`.
3. Otherwise use case continues at step 4 or step 6, whichever it interrupted.

### A7: Agent restarts during a calibration

**Trigger:** The agent stops (crash, restart, power loss) while a calibration runs (step 3, or any later step)
**Flow:**

1. On start the agent finds the calibration's open record and completes it with outcome `aborted` and the reason `restart`; the next automatic start waits as BR-001 says.
2. The active set is unchanged: an open record never defines it (BR-008).
3. Use case ends.

### A8: Operator rolls back

**Trigger:** The operator runs `scripts/agent-calibrate.sh rollback`, after an accepted calibration (step 8) or while one runs (step 3, or any later step)
**Flow:**

1. A rollback is not a calibration: it works also while `enabled` or `experiments_enabled` is off and runs no shadow game. A running calibration is stopped first and recorded `aborted` with the reason `rollback`.
2. When the active set was not made by an `accepted` record (nothing calibrated yet, or the newest change was already a rollback or a reset), System changes nothing and answers `nothing_to_roll_back`; use case ends. A rollback has one level only.
3. System writes a record with outcome `rolled_back` whose after set is the before set of that `accepted` record (the empty set, i.e. the flag-file archetypes, after the first calibration); that write makes it active (BR-008).
4. Experiments pinned from now on use the restored set. A rollback counts as a completed calibration (BR-007), so the next automatic calibration starts after another N eligible games; the calibration it stopped in step 1 starts no retry wait.
5. Use case ends.

### A9: Operator resets to the baseline

**Trigger:** The device moves to a new venue or environment and the operator runs `scripts/agent-calibrate.sh reset`, between calibrations (step 2) or while one runs (step 3, or any later step)
**Flow:**

1. Like a rollback, a reset is not a calibration: it works also while `enabled` or `experiments_enabled` is off. A running calibration is stopped first and recorded `aborted` with the reason `reset`.
2. System writes a record with outcome `reset` and the empty set as its after set, so the flag-file archetypes are active again (BR-008).
3. From now on only real games that end after the reset are eligible: the next calibration starts from the baseline on this device's new games. A rollback never crosses a reset (A8).
4. Use case ends.

## Postconditions

### Success Postconditions

- The candidate set is active for experiments pinned after the calibration; the replaced set is its previous set.
- One evidence record holds the before and after sets with their digests, the games used and excluded, the KS distances, the noise floor and the constants used (BR-007).
- No real-game rule, flag or flag file has changed (C-022).

### Failure Postconditions

- After `insufficient_games`, `rejected` or `aborted`, the active set is unchanged.
- One evidence record names the outcome (`insufficient_games`, `rejected`, `aborted`) and its reason (BR-007).
- After a rollback (A8) the restored set is active and a `rolled_back` record names both sets; after a reset (A9) the flag-file archetypes are active and a `reset` record says so.
- No real-game rule, flag or flag file has changed (C-022).

## Business Rules

### BR-001: Trigger and retry

`calibration.every_n_games` (`agent` set, human-owned, never agent-written, C-034) holds N, read at use time (C-035): variants `off` = 0 (no automatic calibration; manual runs and rollback still work), `50`, `default` = 100, `200`. Only the declared variants are valid, so N is never below 32 except for `off` (BR-004). After an aborted calibration (A5, A7; not one stopped by a rollback or reset) the next automatic start waits 1 hour, so a failing calibration cannot occupy the shadow-game slot back to back. A calibration is bounded without a deadline of its own: each validation game has the pattern-game safety cap ([UC-046](UC-046.md) BR-013) and at most two reruns (A6).

### BR-002: Eligible real game

A real game (`game_kind` `primary`) is eligible only when all of these hold:

- its mode is `JoustFFA`, the only mode pattern games run (C-021);
- it lasted at least 10 s, from its `game_duration_seconds` series as [UC-043](UC-043.md) A22 places games (on the stage Pi the median real game lasts 16 s; shorter games are mostly false starts);
- at least 2 players moved: a player moved when the mean of their `game_player_movement_variance` gauge over the game (the 1 Hz samples A22 uses) is at least 0.005 g² (a controller lying still stays far below);
- no player dominates: the highest movement variance is less than 10 times the second highest (the "one person shaking a controller" test pattern);
- it ended on this device after its newest reset (A9) and is not marked as test (BR-003);
- its series are in the metrics store; a game whose series are missing or expired is excluded with the reason `metrics_missing`.

Agent interventions and the player count are not filtered: a real game is fitted as it was played.

### BR-003: Test session mark

`calibration.test_session` (`agent` set, `on` / `off`, default `off`, human-owned, never agent-written) lets the operator mark a session as test: a real game that ends while it is `on` is ineligible, and so is a real game whose end the agent did not journal (the agent was not running). The operator sets it with `scripts/agent-calibrate.sh test-session on|off`, a stack overlay without `persist`, so a flag-service restart returns it to `off`. `scripts/agent-calibrate.sh status` shows the mark, the eligible count and the excluded count per reason, so a forgotten `on` is visible.

### BR-004: Holdout split

Ordered by end time, every 4th eligible game is in the holdout and the rest is in the fit set; the holdout is never used to fit. A calibration needs at least 32 eligible games: 24 fit games for 3 bands of 8 (BR-005) and 8 holdout games, A22's default `--min-n`. At that minimum one KS distance is noisy, so the rule of BR-006 accepts only large drops; the default N = 100 gives a holdout of 25.

### BR-005: Fit per band

The fit games are split into 3 bands by elimination pace, A22's eliminations per game minute (low, middle, high; ties ordered by end time), each a third of the games, any remainder in the middle band. Each archetype has a fixed band, so its meaning does not swap between calibrations: `calm_long` and `slow_cascade` low; `jittery_novices`, `late_burst` and any other name middle; `close_race` and `quick_cascade` high. Several archetypes share a band; the fit scales each one's own parameters (below), so they keep their shape, stay distinct and are never averaged into one.

Fit method (one ratio step, deterministic): each parameter is multiplied by the ratio of the band's median to the archetype's median in its group-A validation games, in this order: `base` by the movement-intensity ratio; `amp`, `d_amp` and `burst_h` by the square root of the movement-variance ratio (variance per player over the game); `drift` and `d_drift` by the elimination-pace ratio; `burst_period_s` by the inverse near-death-frequency ratio. A parameter that is 0 stays 0. `d_amp`, the per-slot spread, is what the maintainer called jitter: pattern games add no random variation (C-020). `period_s`, `phase`, `d_phase`, `players`, `stream_rate_hz` and a `trigger_policy` keep their values, because 1 Hz gauges cannot resolve sub-second motion. A fitted value outside the [UC-046](UC-046.md) BR-003 bounds is clamped to the bound, and the clamp is recorded.

### BR-006: Validation and acceptance

Each validation group has 4 games per selected archetype (24 games per group with the six shipped archetypes; 72 per calibration). Seed group A uses the one-shot runner's seed from the archetype name ([UC-046](UC-046.md) BR-006) plus 0 to 3, seed group B plus 4 to 7. They are shadow games with no experiment arm, marked with the calibration id, one at a time ([UC-046](UC-046.md) BR-010), between the games of any running experiment, never experiment samples.

Metrics: the A22 metrics the fit moves, `intensity`, `movement_variance`, `near_death_rate`, `elimination_pace`, `activity` and `change`, measured per game (per player for intensity and movement variance) as A22 step 3 measures them, so a game A22 leaves out of `near_death_rate` (a shared serial, or a counter reset inside its window, #2543) gives no value for it; each metric counts when it has at least 8 values in the holdout and in each group; k is their number, and k = 0 ends the calibration `rejected` with the reason `no_metrics`. Per metric m, against the same holdout:

- paired drop d_m = KS(active, A) − KS(candidate, A);
- A/A difference a_m = KS(active, A) − KS(active, B);
- noise floor σ = the larger of sqrt(mean of a_m²) and 0.05 (one A/A run can come out near 0 by chance).

BR-006 uses the raw KS distances, not A22's verdicts: A22's KS power gate (A22 step 4) needs about 41 games per kind before a verdict is not `insufficient`, while this rule compares two distances against the same holdout and takes its noise from the A/A run. The candidate is accepted when the mean of d_m is greater than 2σ and no single d_m is below −2σ (no metric got clearly worse). The evidence record stores every d_m, a_m and σ. The holdout's sampling error is the same for all three groups, so it cancels in d_m; what remains is the game-to-game variation of the shadow games, which is small because the inputs are deterministic (C-020) and only the seeds differ. The A/A run measures that variation as σ; the 0.05 floor keeps a near-zero σ from accepting noise.

### BR-007: Evidence record

Every calibration writes one evidence record (layout and path: [services.md](../specs/services.md#agent), planned). It is opened at step 3 without an outcome and completed once at the end; an open record never defines the active set. It holds the calibration id, the trigger (`auto`, `manual`), start and end time, the outcome and its reason (`accepted`; `rejected` with `no_improvement` or `no_metrics`; `insufficient_games`; `aborted` with `data_unavailable`, `agent_disabled`, `experiments_disabled`, `shadow_blocked`, `validation_incomplete`, `restart`, `rollback` or `reset`; `rolled_back`; `reset`), the holdout and fit game ids, the excluded count per reason (BR-002, BR-003), the before and after sets with their digests and the flag-file digest of each calibrated name, every d_m, a_m and σ, any clamped value, and the constants used (BR-008). A rollback and a reset write a record too, with outcome `rolled_back` or `reset`.

A **completed calibration** is a record with outcome `accepted`, `rejected`, `rolled_back` or `reset`; step 2 counts from the end time of the newest one. Records are never deleted.

### BR-008: Calibrated set per device, writer and the C-019 amendment

The **calibrated set** is one parameter object per calibrated archetype name. It belongs to one device: it is written only to that device's `agent-experiments` volume, never to git, never copied to another device. The active set is the after set of the newest `accepted`, `rolled_back` or `reset` record; with no such record it is the empty set. A name the active set does not hold uses its flag-file parameters, so the empty set means the flag-file archetypes. An accepted after set is the before set overlaid with the newly fitted names, so a calibration on a narrower selection keeps the other calibrated names. An accepted calibration changes the shadow drivers without a release change, so it must revisit the release binding of the substrate attestation (UC-043 A23, #2541).

The agent is the only writer of records. `scripts/agent-calibrate.sh` (`run`, `rollback`, `reset`, `status`, `test-session on|off`) reaches it under the agent's existing `/experiments` path through envoy (services.md, planned); a rollback or reset cancels a running calibration through the same call before it writes. Record writes hold one lock in the agent, and a rollback or reset cancels a running calibration under that lock before it writes, so a cancelled calibration can never write `accepted` afterwards.

Every pattern game records the archetype name, its parameter digest and the calibration id (empty for flag-file parameters), so a trace names the exact parameters.

C-019 amendment (TBD-A1, resolved by the maintainer's decision of 2026-11-01), with these conditions:

a. Fail closed: an unreadable, truncated or invalid record ([UC-046](UC-046.md) BR-003 validators, run on load), or a missing volume, falls back to the flag-file archetypes with a WARN, never to a partial set.
b. Durable atomic write: temporary file, fsync, rename, fsync of the directory.
c. Release edits win: each record stores the flag-file digest of each calibrated name; when a release changes that variant, its calibrated entry is ignored with a WARN log.
d. One writer holding one lock (above), and records are never pruned.
e. Defined rollback: one level, to the before set of the `accepted` record that made the active set (A8); the empty set (flag-file archetypes) is a defined state.
f. The active set (calibration id, digests) is visible in `status` and on the pattern-game traces, so nobody believes the flag file is in force.
g. Realism only: acceptance looks at realism, never at experiment fitness; after each change of the active set (accepted or rolled back) the A23 validity bar ([UC-043](UC-043.md) A23) is re-checked before an objective counts as validated again. A23 keeps comparing with all real games of its window, not only the games eligible here.

Constants (each a reviewed edit, not a flag, per C-035: an operator does not tune them on stage, and the evidence record stores the values used): minimum duration 10 s; movement floor 0.005 g²; dominance ratio 10; 3 bands of at least 8 fit games; every 4th game in the holdout; 4 validation games per archetype per group; acceptance at 2σ with a σ floor of 0.05; retry wait 1 hour.
