# Use Case: Identify a Controller

## Overview

**Use Case ID:** UC-004
**Use Case Name:** Identify a Controller
**Primary Actor:** Operator
**Goal:** Find the physical controller that belongs to a controller card on the dashboard
**Status:** Tested
**Requirements:** FR-121

## Preconditions

- The dashboard is open and shows a card for the controller (the controller is connected, UC-002).
- The controller manager and the connect-proxy are running.

## Main Success Scenario

1. Operator presses Identify on the controller's card.
2. System's dashboard calls `IdentifyController` with the card's serial through the connect-proxy.
3. System checks that the controller is connected, is not reserved (BR-004) and is not a player in a running game (BR-003).
4. System flashes the controller's LED white and rumbles it briefly (BR-001), and records the span `controller.identify` with outcome `started` and increments `controller_identify_requests_total{outcome="started"}`.
5. System's dashboard shows "Identifying" on the card until the effect ends; the card's LED circle shows the white flash, since it mirrors the colour written to the LED.
6. System restores the controller's LED colour after the effect (BR-002).

## Alternative Flows

### A1: Controller is not connected

**Trigger:** The serial is unknown or the controller disconnected before the call arrived (step 3)
**Flow:**

1. System refuses the request with outcome `not_connected`; no LED or rumble command is sent.
2. System's dashboard shows "Not connected" on the card.
3. Use case ends.

### A2: Controller is in a running game

**Trigger:** The controller is a player of a game whose gameplay stream is open, alive or dead (step 3)
**Flow:**

1. System refuses the request with outcome `in_game`; the game's LED colours and rumble stay untouched (BR-003).
2. System's dashboard shows "In game" on the card.
3. Use case ends.

### A3: Reserved mock controller

**Trigger:** The serial belongs to a reserved mock controller (a shadow-game or pattern-game controller, UC-002 BR-002) (step 3)
**Flow:**

1. System refuses the request with outcome `reserved` (BR-004).
2. System's dashboard shows "Reserved" on the card.
3. Use case ends.

### A4: Mock controller

**Trigger:** The controller is a lobby mock controller (UC-003) (step 4)
**Flow:**

1. System writes the same LED frames to the mock controller; the rumble has no physical effect.
2. Use case continues at step 5, where the card's LED circle is the only place the flash shows.

### A5: Identify pressed again

**Trigger:** Operator presses Identify while the effect still runs (step 5)
**Flow:**

1. System restarts the effect with a new full duration.
2. Use case continues at step 5.

### A6: Empty serial

**Trigger:** The request carries no serial (step 2)
**Flow:**

1. System refuses the request with outcome `invalid`.
2. Use case ends.

## Postconditions

### Success Postconditions

- The controller shows the same LED colour as before the identify, or the newer base colour the menu set during it.
- One `controller.identify` span and one `controller_identify_requests_total` increment exist per request, whatever the outcome.

### Failure Postconditions

- A refused request changes no LED, no rumble and no game state.

## Business Rules

### BR-001: Identify pattern

The LED flashes white (255, 255, 255) at 2 Hz for `duration_ms` (default 3000 ms when 0 or unset, clamped to 500 to 10000 ms), and the controller rumbles at intensity 150 for the first 500 ms (or the whole effect when it is shorter).

### BR-002: Restore after identify

When the effect ends, the LED shows the controller's current base colour; a base colour the menu sets while the effect runs is stored and shown after it. A controller without a base colour gets back the colour it showed when the first identify started (a repeat press, A5, keeps that colour).

### BR-003: Lobby only

Identify is refused while the controller is listed in an open game gameplay stream (a game coordinator stream configured with player colours), whether the player is alive or dead, because white means warning, respawn or shield there and rumble is a hidden-role signal (UC-022). An identify still running when a game claims the controller (its stream configuration lists it, including a reconnected game stream) is cancelled at once together with its rumble, so the game's colours and countdown are never overlaid. The controller can be identified again once the game's stream closes.

### BR-004: Not for reserved controllers and not an agent action

Reserved mock controllers are refused. Identify is an operator action only: only the `IdentifyController` RPC starts it (a stream `GameEffectCommand` with `GAME_EFFECT_IDENTIFY` is rejected), no flag gates it, the agent cannot call it (C-001, C-005 unaffected), and it identifies a device, not a person (C-009).

### BR-005: A pulse never cuts short an identify

A `GAME_EFFECT_PULSE` (the menu's mode pulse on every lobby controller, [UC-015](UC-015.md) BR-015) that arrives while an identify or a battery display (`GAME_EFFECT_SHOW_BATTERY`) runs on that controller is skipped: the running effect keeps the LED until its end, and a base colour sent with the pulse is stored and shown after it (BR-002). Other effects keep their take-over behaviour (#2105).

### BR-006: Identify from the battery roster - Obsolete (#2132)

Obsolete. The dashboard's separate battery roster ([UC-035](UC-035.md) A5) was removed in #2132; Identify is on the controller card only (main step, BR-001).

The LED and rumble on a real PS Move are verified by hand (no hardware in CI).

### BR-007: The card names the controller (#2399)

The dashboard card's title is the controller's human-readable name (`GameplayData.name`, set by the controller manager's NameManager); the short id (`P` plus the last 4 characters of the serial) is the subtitle, so the operator can match a card to a physical controller. A changed name in the stream updates the title. An empty name falls back to `P<short id>` as the title. The name is written as text, never as HTML. The separate battery roster that once showed names was removed in #2132.

**Code / tests:** `services/dashboard/src/components/ControllerCard.ts`; tests `services/dashboard/src/__tests__/controller-card-name.test.ts`.
