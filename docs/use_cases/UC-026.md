# Use Case: Play Non-Stop Joust

## Overview

**Use Case ID:** UC-026
**Use Case Name:** Play Non-Stop Joust
**Primary Actor:** Player
**Goal:** Die least often before the time limit
**Status:** Implemented
**Requirements:** FR-026, FR-145, FR-172

## Preconditions

- A NonStop game was started with at least two players (UC-010).
- Lobby: selecting NonStop announces the mode by voice (`MENU_VOX_NONSTOP_JOUST`) and shows the pink lobby colour (issue #1276).

## Main Success Scenario

1. System starts the game and counts deaths per player; `score` stays 0 during play.
2. A player whose movement exceeds the threshold dies (`player_death`), the death is counted, and the player respawns after `nonstop.respawn_seconds` (default 3 s) with `nonstop.spawn_protection_seconds` (default 2 s) of protection (`player_respawned`).
3. When `nonstop.time_limit_seconds` is reached, measured from the first gameplay frame after the warm-up, System latches the outcome `completed` (BR-003), computes each score as max(0, base − deaths × penalty) (`nonstop.scoring`, default base 100, penalty 10), picks the highest (ties: fewest deaths), sends the winner rainbow, plays the congratulations voice, publishes `game_winner`, shows the winner for 2 s and publishes `game_ended` (`outcome` `completed`, `winner` = the winner's serial). The gameplay stream stays open until the end-game step is done (UC-030 BR-006).

## Alternative Flows

### A1: Unlimited time

**Trigger:** `nonstop.time_limit_seconds` is 0 (default) (step 3)
**Flow:**

1. The game never ends by itself; an operator ends it (UC-027). No winner is declared (BR-003): no `game_winner`, no rainbow, no congratulations voice; `game_ended` carries `outcome` `force_ended`, `reason` and `winner` `none`.
2. Use case ends.

## Postconditions

### Success Postconditions

- After a time-limit end (step 3) the highest scorer is in the event stream; after a force-end or a stream end (A1, BR-003) `game_ended` carries `winner` `none`. The session is ENDED.

### Failure Postconditions

- `game_error` ends the session.

## Business Rules

### BR-001: Scoring

Score = max(0, base − deaths × penalty), computed once at game end (`nonstop.scoring`, default base 100 and penalty 10; `services/game_coordinator/games/nonstop_joust.py` `_end_game_impl`).

### BR-002: Root-span outcome

NonStop uses the base `run()` and records the game root-span outcome as in UC-020 BR-003: `completed` for a natural end, or `force_ended` with the force-end reason (`game.end_reason`) when force-ended. A force-end after the loop ended does not rewrite the outcome.

### BR-003: Force-end and winner

- A winner (`game_winner`, the winner rainbow, `VOX_CONGRATULATIONS` and the 2 s winner hold) is declared only when the time limit ended the game (step 3) and the latched outcome is not `force_ended` (issues #1343, #1585).
- The outcome is latched when the game loop detects the time limit, before the loop exits. A force-end recorded earlier in the same frame (before the time-limit check) wins: the outcome is `force_ended` and there is no winner. A force-end after the latch (during the 2 s hold or the teardown) keeps the winner and its effects; the hold ends early.
- No winner in every other end: a force-end while the game runs (A1, or before the time limit), and a gameplay stream that the controller manager ends before the time limit. NonStop opens its own gameplay stream in its game loop and does not reconnect it (the base loop's stream recovery does not apply), so a server-side end of that stream ends the game with outcome `completed`, no winner, no error and no effect sent to the finished stream (a shield-end write that the base still attempts fails silently).
- Without a winner, scores are still computed, `player_analytics` reports `winner` false for every player, and `game_ended` carries `winner` `none`, `outcome` and, for `force_ended`, `reason`.
- A respawn or an agent revive (`revive_player`) is refused once the game is no longer RUNNING, the outcome is latched or the gameplay stream is closed: it returns false with no state change and no LED write (issue #1954).
