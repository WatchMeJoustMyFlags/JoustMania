# Use Case: Play Non-Stop Joust

## Overview

**Use Case ID:** UC-026
**Use Case Name:** Play Non-Stop Joust
**Primary Actor:** Player
**Goal:** Die least often before the time limit
**Status:** Tested
**Requirements:** FR-026, FR-145, FR-172

## Preconditions

- A NonStop game was started with at least two players (UC-010).
- Lobby: selecting NonStop announces the mode by voice (`MENU_VOX_NONSTOP_JOUST`) and shows the pink lobby colour (issue #1276).

## Main Success Scenario

1. System starts the game and counts deaths per player; `score` stays 0 during play.
2. A player whose movement exceeds the threshold dies (`player_death`), the death is counted (it is no elimination, BR-004), and the player respawns once `nonstop.respawn_seconds` (default 3 s) of wall-clock time have passed since the death, on the first gameplay frame after that deadline, with `nonstop.spawn_protection_seconds` (default 2 s) of protection (`player_respawned`). The respawn time does not depend on the gameplay frame rate or on how many frames the game loop processes (issue #1963). While the player waits, the controller LED shows the time left: grey above 2 s, yellow above 1 s, green for the last second, with a beep at each colour change. `nonstop.respawn_seconds` = 0 respawns the player on the next gameplay frame (before #1963 a 0 never respawned the player). The game loop processes each frame as it arrives and does not sleep between frames: the controller manager paces the stream (NFR-004).
3. When `nonstop.time_limit_seconds` is reached, measured from the first gameplay frame after the warm-up, System latches the outcome `completed` (BR-003), computes each score as max(0, base − deaths × penalty) (`nonstop.scoring`, default base 100, penalty 10), picks the highest (ties: fewest deaths), sends the winner rainbow, plays the congratulations voice, publishes `game_winner`, shows the winner for 2 s and publishes `player_analytics` for each player (when `analytics.enabled` is on; UC-041 BR-006) and `game_ended` (`outcome` `completed`, `winner` = the winner's serial). The gameplay stream stays open until the end-game step is done (UC-030 BR-006).

## Alternative Flows

### A1: Unlimited time

**Trigger:** `nonstop.time_limit_seconds` is 0 (default) (step 3)
**Flow:**

1. The game never ends by itself; an operator ends it (UC-027). No winner is declared (BR-003): no `game_winner`, no rainbow, no congratulations voice; `game_ended` carries `outcome` `force_ended`, `reason` and `winner` `none`.
2. Use case ends.

### A2: Controller disconnects

**Trigger:** A controller disconnects during the game (step 2), including during the countdown or the EMA warm-up; such a disconnect is handled at the start of the game loop, before the first gameplay frame (issues #1591, #1971)
**Flow:**

1. System counts a death through the normal death path (`player_death`, death effect; no motion involved), as in UC-020 A2. A player who disconnects while waiting to respawn gets no extra death; the pending respawn is cancelled.
2. The player does not respawn for the rest of the game, and an agent revive (`revive_player`) of the player is refused (BR-003). The player stays in the winner ranking with its final score (BR-001). The disconnect is the player's elimination (BR-004).
3. Use case continues at step 2 for the other players.

### A3: Instructions on

**Trigger:** The host has switched spoken instructions on (`game_instructions`, FR-014, UC-012 A3) when the game starts (step 1)
**Flow:**

1. Non-Stop Joust has no instruction recording, so it has no clip: System records `game.instructions` = `no_clip` (UC-020 A5 step 3), plays nothing and does not wait (#2151).
2. Use case continues at step 1.

## Postconditions

### Success Postconditions

- After a time-limit end (step 3) the highest scorer is in the event stream; after a force-end or a stream end (A1, BR-003) `game_ended` carries `winner` `none`. The session is ENDED.

### Failure Postconditions

- `game_error` ends the session.

## Business Rules

### BR-001: Scoring

Score = max(0, base − deaths × penalty), computed once at game end (`nonstop.scoring`, default base 100 and penalty 10; `services/game_coordinator/games/nonstop_joust.py` `_end_game_impl`).

### BR-002: Root-span outcome

NonStop uses the base `run()` and records the game root-span outcome as in UC-020 BR-003: `completed` for a natural end, or `force_ended` with the force-end reason (`game.end_reason`) when force-ended. A force-end after the loop ended does not rewrite the outcome.

### BR-003: Force-end and winner

- A winner (`game_winner`, the winner rainbow, `VOX_CONGRATULATIONS` and the 2 s winner hold) is declared only when the time limit ended the game (step 3) and the latched outcome is not `force_ended` (issues #1343, #1585).
- The outcome is latched when the game loop detects the time limit, before the loop exits. A force-end recorded earlier in the same frame (before the time-limit check) wins: the outcome is `force_ended` and there is no winner. A force-end after the latch (during the 2 s hold or the teardown) keeps the winner and its effects; the hold ends early.
- No winner in every other end: a force-end while the game runs (A1, or before the time limit), and a gameplay stream that the controller manager ends before the time limit. NonStop opens its own gameplay stream in its game loop and does not reconnect it (the base loop's stream recovery does not apply), so a server-side end of that stream ends the game with outcome `completed`, no winner, no error and no effect sent to the finished stream (a shield-end write that the base still attempts fails silently). A gRPC error of that stream ends the game with one `game_error` and no winner, also without a reconnect (`tests/test_nonstop_stream_error.py`, #2025).
- Without a winner, scores are still computed, `player_analytics` reports `winner` false for every player, and `game_ended` carries `winner` `none`, `outcome` and, for `force_ended`, `reason`.
- No kill is taken once the outcome is latched (UC-030 step 9): an `eliminate_player` during the end-game step is refused (`eliminate_refused`, UC-040 A22) and adds no death, so the winner computed from the deaths is the leader at the time limit (#2019).
- A respawn or an agent revive (`revive_player`) is refused once the game is no longer RUNNING, the outcome is latched or the gameplay stream is closed, and for a player whose controller disconnected (A2): it returns false with no state change and no LED write (issues #1954, #1971).

### BR-004: A respawn death is no elimination

A death the player respawns from keeps it in the game (#2524, [UC-041](UC-041.md) BR-008): it sets no `game_player_elimination_order`, and its `player_death` span event carries `death.eliminated` false, so the agent's elimination sequence and elimination fraction leave it out (an `eliminate_player` death respawns too and is no elimination either). The death is still counted (`deaths`, the score, `game_player_deaths_total`, `dead_count`). A disconnect takes the player out for good (A2) and is its elimination: a disconnect death carries `death.eliminated` true and records the player's elimination order; a player who disconnects while waiting to respawn gets its order at the disconnect, once, with no second death and no `player_death`. No order is recorded once the outcome is latched or the game was force-ended (the kill gate, UC-030 step 9).
