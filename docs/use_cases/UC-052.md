**Primary Actor:** Operator
**Goal:** Move chosen controllers to another backend with one HTTP call
**Status:** Implemented

## Preconditions

- The connect-proxy reaches the flag service (`FLAG_SERVICE_URL`).
- A canary that routes any serial to python (`/canary/python`, or `/canary/rust?fraction=N` below 100, whose rest stays on python) needs the python adapter loaded: the opt-in of UC-002 BR-003 (`backend=python_rust`, the `python-hid` profile, controller manager restarted). Otherwise A3.

## Main Success Scenario

1. Operator calls `POST /canary/rust?fraction=N` on the connect-proxy.
2. System changes `bluetooth_backend` through the flag service ([UC-053](UC-053.md) A1): at `fraction` 100 (the default) a stack overlay on the backend's variant; below 100 a stack overlay on the stable counterpart plus a fraction overlay, so `fraction` % of the controller serials resolve the backend and the rest the counterpart. `/canary/python` works the same way; `/canary/status` returns the flag service's view.
3. flagd receives the configuration at once; the controller manager routes the selected controllers to the rust adapter on its next cycle.
4. Operator queries `controller_routing_decisions_total` (VictoriaMetrics / Grafana Explore) and the "Controllers per Backend" panel of the Controllers & Bluetooth dashboard (uid `controller-overview`).
5. Operator calls `POST /canary/rollback`: System clears the stack and the fraction overlay, so every serial resolves the baseline default (`rust` since #1371), and answers with that backend. If the python baseline came from a `/canary/python` stack overlay, the rollback goes to rust, not python.

## Alternative Flows

### A1: Inject a fault (retired)

**Trigger:** None since #1322 (item 11): fault injection was removed (FR-073 Obsolete), with the `/chaos/*` endpoints, the `chaos_fault_type` flag and the adapter wrapper; the operator only canaries a backend (step 1). The ID is kept so it is not reused, and FR-073 (Obsolete) stays linked here.
**Flow:**

1. Use case ends.

### A2: Through envoy

**Trigger:** Operator calls `/canary/*` through the host entry point (port 80) (step 1)
**Flow:**

1. Envoy has no `/canary/` route; the request reaches the dashboard instead (D-B3). Call the connect-proxy from inside the network.
2. Use case ends.

### A3: Python adapter not loaded

**Trigger:** The canary would route serials to python (`/canary/python`, or a fractional `/canary/rust` whose rest is python), and the `backend` flag the flag service serves names no python (the default `rust`, #1371) (step 2)
**Flow:**

1. System answers 409 Conflict naming the `backend` value and the opt-in (UC-002 BR-003) and writes nothing (BR-002). Without this check the controller manager, which has no python adapter, would silently keep those serials on rust (#1402).
2. Use case ends.

## Postconditions

### Success Postconditions

- The chosen controllers use the requested backend.

### Failure Postconditions

- The flag service is unchanged (a refusal keeps its 4xx; python not loaded is 409, A3; the flag service unreachable is 502).

## Business Rules

### BR-001: Manual canary wins

Per-serial `bluetooth_backend` targeting takes precedence over the agent's rollout (UC-050).

### BR-002: A python canary needs the python adapter

Before it writes, a canary that routes serials to python reads the `backend` flag from the flag service and goes on only when its value names `python` (A3). The controller manager reads that flag only at startup, so a value changed after its start passes the check without loading the adapter. A `backend` flag the flag service cannot serve refuses the canary with the flag service's status (fail closed). `/canary/rust` at fraction 100 and `/canary/rollback` need no python adapter.
