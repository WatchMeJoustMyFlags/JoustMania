# Use Case: Ready Up and Start a Game

## Overview

**Use Case ID:** UC-010
**Use Case Name:** Ready Up and Start a Game
**Primary Actor:** Player
**Goal:** Start the selected game with every player who is ready
**Status:** Tested
**Requirements:** FR-010, FR-012, FR-015, FR-027, NFR-005

## Preconditions

- The menu is RUNNING and at least two controllers are CONNECTED (UC-002).
- A game mode is selected (UC-011; default `current_game`, JoustFFA).

## Main Success Scenario

1. Player presses the trigger.
2. System plays a beep, marks the controller READY and lights the LED at full brightness.
3. Other players ready up the same way.
4. System detects that at least two controllers are ready and every connected controller is ready.
5. System waits 0.3 s, stops lobby music and the idle monitor, and asks the game coordinator to start the selected mode as a real game (menu origin) with the ready players, the sensitivity and the mode-specific settings read from the `game` flags.
6. System plays the countdown: three colour phases with beeps (750 ms each by default), then the start sound.
7. The game runs (UC-020 to UC-026).
8. When the game ends, System restores the lobby: all players CONNECTED (un-readied), lobby music on.

## Alternative Flows

### A1: Player un-readies

**Trigger:** A READY player presses Move before every connected controller is ready (step 3)
**Flow:**

1. System returns the controller to CONNECTED (dim LED).
2. Use case continues at step 3.

### A2: Lobby goes idle

**Trigger:** No button press for `idle.timeout_minutes` (default 15) while players wait (step 3)
**Flow:**

1. System turns CONNECTED controllers' LEDs off (IDLE) and lets up to `sentinel.count` highest-battery controllers breathe; READY and ADMIN controllers are untouched.
2. Any button on an idle controller wakes all idle controllers; that press is consumed.
3. Use case continues at step 1.

### A3: Start rejected

**Trigger:** The coordinator rejects the start (a real game already runs, capacity reached) or the roster has fewer than two players (step 5)
**Flow:**

1. System publishes `game_start_cancelled` (roster) or receives `game_start_error`.
2. System returns to the lobby.
3. Use case ends.

### A4: Second trigger press

**Trigger:** A READY player presses the trigger again while everyone is ready (step 4)
**Flow:**

1. System starts the game immediately (same latch prevents a double start).
2. Use case continues at step 5.

### A5: Flag providers not ready

**Trigger:** The game coordinator admits a game (step 5; the same applies to a shadow game the agent starts, UC-043 / UC-046) while one or more OpenFeature providers it reads (domains `system`, `controller`, `game`, `agent`, `user`, `interventions`) is still NOT_READY, i.e. has never synced with flagd, e.g. right after a coordinator restart (#1329)
**Flow:**

1. System waits up to 5 s for those NOT_READY providers to report READY before it creates the game, so no game-start flag is read from a provider that never synced (BR-004). Providers that are READY, STALE or ERROR are not waited on: with the in-process resolver a STALE or ERROR provider (flagd outage after a sync) keeps serving its last-synced flags.
2. When the waited providers are READY, System re-reads the process-wide runtime configuration (`game_loop.update_frequency_hz`, `poll_drop_threshold`, countdown and rainbow durations) in an empty evaluation context, so a shadow or experiment session's targeting never leaks into it. System records the wait on the game root span (`feature_flag.providers_wait_ms`).
3. When the wait runs out, System starts the game anyway. Flags of the domains still NOT_READY resolve to their code defaults. System records a `feature_flag.providers_not_ready` event on the game root span with those domains and logs a warning.
4. If the game was force-ended during the wait (UC-027), System creates no game and the use case ends.
5. Otherwise, use case continues at step 6.

### A6: Start from the dashboard or `ProcessInput`

**Trigger:** A client calls `ProcessInput` with `web_command` `start_game` or with a `button_press` of the trigger (step 3)
**Flow:**

1. System starts the selected mode with the controllers that are READY now, without waiting for every connected controller to be ready.
2. Use case continues at step 5.

## Postconditions

### Success Postconditions

- A real game session exists with the ready players; the menu is in GAME_STARTING until the game ends.

### Failure Postconditions

- No game starts; the lobby stays as it was.

## Business Rules

### BR-001: Minimum players

A game needs at least two players. Per-mode minimums declared in `lib/types.py` are **not** enforced (D-G2).

### BR-002: IDLE and ADMIN block auto start

Controllers in IDLE or ADMIN count as connected but not ready.

### BR-003: `menu_auto_start` boot path

When the menu starts through `menu_auto_start` instead of StartMenu, lobby music and the idle monitor do not run until the first game ends (D-M2). `menu_auto_start` is on by default (`user.json`), so this is the default boot path.

### BR-004: No game reads flags before its providers are ready

The game coordinator creates a game only after every flag provider it reads has synced at least once (no longer NOT_READY), waiting at most 5 s (A5). A wait that fails never blocks the start. A game that starts after the wait ran out records the fallback (`feature_flag.providers_not_ready`) on its root span, so a code-default start is never silent. Waiting on the readiness event is safe from any thread: the provider calls its READY handler on its own thread, and the waiter is woken on its own event loop (`loop.call_soon_threadsafe`, #1250 bug class).
