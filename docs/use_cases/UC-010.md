# Use Case: Ready Up and Start a Game

## Overview

**Use Case ID:** UC-010
**Use Case Name:** Ready Up and Start a Game
**Primary Actor:** Player
**Secondary Actors:** Operator
**Goal:** Start the selected game with every player who is ready
**Status:** Tested
**Requirements:** FR-010, FR-012, FR-015, FR-027, NFR-005

## Preconditions

- The menu is RUNNING (the boot lobby entry has run: the menu reports gRPC health SERVING only after it, or at once when `menu_auto_start` is off, or after the bounded 10 s boot entry timeout or an entry error, #1826) and at least two controllers are CONNECTED (UC-002).
- A game mode is selected (UC-011; default `current_game`, JoustFFA).

## Main Success Scenario

1. Player presses the trigger.
2. System marks the controller READY, lights the LED at full brightness and plays a beep; it does not wait for the beep (BR-012).
3. Other players ready up the same way.
4. System detects that at least two controllers are ready and every connected controller is ready. A STOPPED menu never auto starts (BR-014).
5. System waits 0.3 s, stops lobby music and the idle monitor, and asks the game coordinator to start the selected mode as a real game (menu origin) with the ready players, the sensitivity and the mode-specific settings read from the `game` flags.
6. System plays the countdown: three colour phases with beeps (750 ms each by default), then the start sound.
7. The game runs (UC-020 to UC-026).
8. When the game ends, System restores the lobby: all players CONNECTED (un-readied), lobby music on. A menu the operator stopped during the game stays STOPPED (A11), unless a later `StartMenu` during the game undid the stop (A12).

## Alternative Flows

### A1: Player un-readies

**Trigger:** A READY player presses Move before every connected controller is ready (step 3)
**Flow:**

1. System returns the controller to CONNECTED (dim LED).
2. Use case continues at step 3.

### A2: Lobby goes idle

**Trigger:** No button press for `idle.timeout_minutes` (default 15) while players wait (step 3)
**Flow:**

1. System turns CONNECTED controllers' LEDs off (IDLE) and lets up to `sentinel.count` highest-battery controllers breathe; READY and ADMIN controllers are untouched.
2. Any button on an idle controller wakes all idle controllers; that press is consumed.
3. Use case continues at step 1.

### A3: Start rejected

**Trigger:** The coordinator rejects the start (a real game already runs, capacity reached, the roster is below the mode's minimum), the start stream fails before its first event (the coordinator cannot be reached, or any other failure, #2379), or the roster has fewer players than the selected mode's minimum (BR-001) (step 5)
**Flow:**

1. System publishes `game_start_cancelled` and announces "not enough players" by voice (roster; the event names `game_name`, `player_count` and `minimum_players`), or receives `game_start_error`. When the start stream fails before its first event, System restores the lobby once and then publishes `game_start_cancelled` with `game_name` and a `reason` (also when that restore raises), so a menu-event subscriber learns that the start failed (before #2379 nothing was published): `coordinator_unreachable` when the coordinator could not be reached (gRPC `UNAVAILABLE` or `DEADLINE_EXCEEDED`, a connection error or a timeout), `start_failed` for any other failure (another gRPC status, or a lobby restore after `game_start_error` that itself fails; that restore is not run a second time). A game that started and then lost its stream is not a failed start: no `game_start_cancelled` (A9, A13).
2. System returns to the lobby.
3. Use case ends.

### A4: Second trigger press

**Trigger:** A READY player presses the trigger again while everyone is ready (step 4)
**Flow:**

1. System starts the game immediately (same latch prevents a double start).
2. Use case continues at step 5.

### A5: Flag providers not ready

**Trigger:** The game coordinator admits a game (step 5; the same applies to a shadow game the agent starts, UC-043 / UC-046) while one or more OpenFeature providers it reads (domains `system`, `controller`, `game`, `agent`, `user`, `interventions`) is still NOT_READY, i.e. has never synced with flagd, e.g. right after a coordinator restart (#1329)
**Flow:**

1. System waits up to 5 s for those NOT_READY providers to report READY before it creates the game, so no game-start flag is read from a provider that never synced (BR-004). Providers that are READY, STALE or ERROR are not waited on: with the in-process resolver a STALE or ERROR provider (flagd outage after a sync) keeps serving its last-synced flags.
2. When the waited providers are READY, System re-reads the process-wide runtime configuration (`game_loop.update_frequency_hz`, `poll_drop_threshold`, countdown and rainbow durations) in an empty evaluation context, so a shadow or experiment session's targeting never leaks into it. System records the wait on the game root span (`feature_flag.providers_wait_ms`).
3. When the wait runs out, System starts the game anyway. Flags of the domains still NOT_READY resolve to their code defaults. System records a `feature_flag.providers_not_ready` event on the game root span with those domains and logs a warning.
4. If the game was force-ended during the wait (UC-027), System creates no game and the use case ends.
5. Otherwise, use case continues at step 6.

### A6: Start from the dashboard or `ProcessInput`

**Trigger:** The Operator starts from the dashboard, or a client calls `ProcessInput` with `web_command` `start_game`, or with a `button_press` of the trigger (step 3)
**Flow:**

1. When a `start_game` names a `mode`, System first selects that mode (UC-011 BR-002), unless the start is refused because a game lifecycle is live (A8: nothing changes, not the selection either); an unknown or unimplemented mode is rejected with an error and no game starts.
2. System starts the selected mode with the controllers that are READY now, without waiting for every connected controller to be ready.
3. Use case continues at step 5.

### A7: Start fails after admission

**Trigger:** The coordinator has admitted the game (created its session) and then the start fails (the flag-service registration, the `game_start` publish or the game thread start raises) or the starter's stream is cancelled while the start is still in progress, #1791 (step 5)
**Flow:**

1. System retires the session as a normal end would for its resources (BR-007): the session leaves the registry, the primary slot is freed if it held it, its controllers are released, any flag-service registration is undone and, for a shadow game, its concurrent-shadow slot is freed. No `game_ended` is published, because the game never started; if `game_start` was already published (only the game thread start can fail after it), System publishes `game_start_error` on the game's bus, so primary-bus observers (the dashboard, a reconnected menu) leave Running.
2. A starter that is still connected receives `game_start_error`; a cancelled starter gets no event and the cancel propagates.
3. The menu continues as in A3 (returns to the lobby); the next start is admitted normally.
4. Use case ends.

### A8: Start while a game is starting or running

**Trigger:** A start request (ready auto start, trigger, admin force-start, `ProcessInput` trigger button or web `start_game`) reaches the menu while its game lifecycle is live, that is a game is starting or running (step 5; #2054)
**Flow:**

1. System refuses the start and publishes `game_start_rejected` (`game_name`, `source`, `reason` = `game_active`). The refusal is silent while a game is starting or running, including the short window after the start was scheduled and before the menu leaves the lobby: venue audio is not a reliable cue and the LEDs already show the game.
2. The live game, its event stream and its lifecycle are untouched; the lobby is not restored and no second game is created.
3. System clears the ready latch (A4), so a refused ready or trigger start never leaves the lobby unable to start. The web `start_game` and the `ProcessInput` trigger (`button_press`) answer `success=false`, error `game_active`, like the operator pad's `force_start` and `step_setting` ([UC-015](UC-015.md) A1), and change nothing: a web `start_game` with a `mode` does not select it (A6). Before #2176 both answered `success=true`, so their callers could not see the refusal. The ready, trigger-on-controller and admin force-start paths have no reply.
4. Use case ends.

**Lobby-restart window:** after a game ends, the lifecycle stays live while it restores the lobby (step 8: button monitor, controllers back to CONNECTED, lobby music, idle monitor). Players can ready up again in that window; a start then is refused as above and additionally plays a short beep (`beep_loud`), because the players are back in the lobby. Once the lobby is restored, a trigger press with every player ready starts the next game.

**Recovery with `reset_menu`:** a lifecycle that never finishes would refuse every start. The operator's `reset_menu` (`ProcessInput`) is the recovery (BR-008): it asks the coordinator for the primary game's state, and when no game is starting or running it cancels the stale lifecycle, publishes `game_start_cancelled` (empty) and restores the lobby as in step 8. While a lobby restore is running (this one or a lifecycle's own post-game restore), a further `reset_menu` is ignored and only logged, so it never cancels the restore and no controller is dropped from re-registration. A restore always ends: each step is bounded (BR-010), so a hung controller manager or audio service cannot keep `reset_menu` ignored for good.

### A9: Game stream reconnects after the game ended

**Trigger:** The menu's game event stream breaks after the start was confirmed (BR-006) and the reconnected stream subscribes to the primary bus (step 7; #2063)
**Flow:**

1. Once the coordinator has registered the reconnected subscription (the stream's initial headers, #1613), System asks the coordinator for the primary game's state (`GetGameState`).
2. If the coordinator reports no primary game starting or running, or a different `game_id` than the game the menu followed (the game ended while the stream was down, or the coordinator restarted), System treats the game as ended: it publishes `game_ended` (`game_id` of the followed game, `reason` = `ended_while_disconnected`) and restores the lobby as in step 8 (BR-009).
3. Otherwise the game is still live: System keeps the reconnected stream and the flow continues at step 7 until its terminal event arrives.
4. After step 2, use case ends.

### A10: Operator cancels a game start

**Trigger:** The menu is in GAME_STARTING and no game lifecycle task is live (the start is stuck or was begun by a path that left no task), and the operator sends `reset_menu` (`ProcessInput`) (step 5)
**Flow:**

1. System returns the menu from GAME_STARTING to RUNNING and publishes `game_start_cancelled` (empty).
2. A `reset_menu` in any other state with no live lifecycle (for example RUNNING) changes nothing and publishes nothing. With a live lifecycle task, `reset_menu` follows the recovery rules of A8 and BR-008.
3. Use case ends; the lobby is as before the start request.

### A11: Operator stops and restarts the menu

**Trigger:** The operator (or the game launcher) calls `StopMenu` and later `StartMenu` (any time the lobby is shown, or `StopMenu` while a game is starting or running) (step 1)
**Flow:**

1. `StopMenu` on a running menu sets the menu STOPPED, stops the idle monitor, puts every controller back to CONNECTED (nobody ready, no admin) but keeps the roster of connected controllers, releases the single admin lock (UC-012 BR-004) and publishes `menu_stopped`. Connects and disconnects while the menu is stopped keep updating the roster (UC-002). `StopMenu` on a stopped menu answers `success = false` ("Menu already stopped") and changes nothing.
2. `StartMenu` on a stopped menu outside a game enters the lobby as the boot does (BR-003; during a game see A12): RUNNING, nobody ready, `current_game` restored (UC-011), every controller of the roster CONNECTED again with the restored mode's dim lobby colour (a bounded step, BR-010), lobby music (a bounded step, BR-010: a hung audio service cannot keep `StartMenu` open) and idle monitor started, `menu_started` published. `StartMenu` on a running menu with no live game lifecycle answers `success = false` ("Menu already running") and changes nothing.
3. `StopMenu` while a game is starting or running sticks (#2379): the game is not touched, and when it ends (or its start fails) the lobby restore (step 8) brings back the button monitor, every controller CONNECTED with its dim lobby colour and the lobby music, but leaves the menu STOPPED and does not start the idle monitor; only `StartMenu` makes it RUNNING again (also during the game, A12). The state is read again right before the idle monitor would start, so a `StopMenu` during the restore itself sticks too. A `StopMenu` while the start is being prepared (lobby music and button monitor stopping) aborts the start: no game is requested, the lobby restore runs with the menu left STOPPED. Before #2379 the restore set the menu RUNNING, so the stop was undone.
4. While the menu is STOPPED the button stream stays connected but the menu ignores every button press, so nobody can ready up. A ready auto start already under way when `StopMenu` lands (during its 0.3 s feedback delay or the 0.1 s before the start runs) is dropped (BR-014, #2449); before #2449 such a start set the menu GAME_STARTING and the restore made it RUNNING, so the stop was undone. The auto start (step 4, BR-001) after `StartMenu` therefore still needs every connected controller ready, including the ones that stayed idle across the stop. If the controller manager is unreachable meanwhile, the button stream reconnect clears the roster and the controller manager's connect events fill it again (UC-002); until then nobody is ready, so nothing auto starts. Before #2175 `StopMenu` cleared the roster and no connect event re-filled it, so two of four ready controllers auto started a game (D-M15).
5. Use case ends.

### A12: Operator starts the menu during a game

**Trigger:** The operator (or the game launcher) calls `StartMenu` while the menu's game lifecycle is live: a game is starting or running, or its lobby restore is running (step 5 to step 8; #2449)
**Flow:**

1. System does not enter the lobby mid-game: the game, its event stream and its lifecycle are untouched, and no lobby music, idle monitor or controller re-registration starts. System remembers the request and answers `success = true` whatever the menu state, also inside a restore that already set the menu RUNNING (the live-lifecycle check comes before the "Menu already running" check).
2. When the game ends (or its start fails), the lobby restore (step 8) treats the menu as started: RUNNING with the idle monitor on, as if no `StopMenu` had come (A11 step 3). A start that ends without a game and without a restore (a roster below the minimum, BR-001) leaves the menu RUNNING with the idle monitor too: whenever the lifecycle ends, a menu still in GAME_STARTING is set RUNNING and the idle monitor is started. `StartMenu` and `StopMenu` during the same game: the last one wins, so a `StopMenu` after the `StartMenu` leaves the menu STOPPED after the restore again, and a `StartMenu` after a `StopMenu` during the start preparation lets the start go on.
3. A `StartMenu` that undoes a `StopMenu` during the game publishes `menu_started` at once, as `StopMenu` publishes `menu_stopped` at once. A `StartMenu` during a lifecycle the menu was not stopped for changes nothing (the restore already makes the menu RUNNING) and publishes nothing, but still answers `success = true` (step 1). Before #2449 `StartMenu` during a game entered the lobby mid-game (lobby music, idle monitor, `menu_started`) while the game kept running.
4. Use case ends.

### A13: Coordinator lost after a confirmed start

**Trigger:** The menu's game event stream breaks after the start was confirmed (BR-006) and every reconnect attempt fails (BR-009), so the menu loses the coordinator (step 7; #2450)
**Flow:**

1. System restores the lobby as in step 8 (a menu stopped during the game stays STOPPED, A11).
2. System then publishes `game_ended` with `game_id` of the followed game and `reason` = `coordinator_lost`, so a menu-event subscriber learns that the menu no longer follows the game; it goes out also when that restore raises. No `game_start_cancelled` is published, because the game had started (A3). Before #2450 nothing was published.
3. Use case ends.

## Postconditions

### Success Postconditions

- A real game session exists with the ready players; the menu is in GAME_STARTING until the game ends.

### Failure Postconditions

- No game starts and System returns to the lobby (A3): every player is CONNECTED again (un-readied, lobby LED in the selected mode's colour), lobby music and the idle monitor run (a menu stopped meanwhile stays STOPPED without the idle monitor, A11, unless a later `StartMenu` undid the stop, A12), and the selected mode is unchanged. Un-readying also clears the start latch (A4), so the players can ready up again.

## Business Rules

### BR-001: Minimum players

A game needs at least its mode's minimum number of players (`Games.<mode>.minimum_players`, `lib/types.py`), never fewer than two: two for JoustFFA, Fight Club and NonStop; three for JoustTeams, JoustRandomTeams, Werewolf, Swapper and Tournament; four for Traitor and Zombies. The auto start still fires once at least two players are ready and every connected controller is ready (step 4); the mode's minimum is checked when the start runs (step 5), on every start path: ready auto start, trigger, admin force-start (UC-014 BR-002) and the dashboard or `ProcessInput` start (A6). Below it the menu does not ask the coordinator: it cancels the start (A3), announces "not enough players" by voice (`notenoughplayers`), and the lobby LEDs drop back to dim as every player is un-readied (Failure Postconditions). The coordinator refuses a start below the mode's minimum for every origin, real or shadow, with `game_start_error` / `success=false` and the error `<mode> needs at least <n> players` (`Need at least 2 players` below two), so a direct `StartGame` or agent shadow start cannot bypass the rule (#1862, D-G2). The minimum is checked first: a sub-minimum start is refused with the minimum error even while another game is in progress or the session cap is reached (the `already in progress` error applies only to a roster that meets the minimum).

**Code / tests (BR-001):** `services/menu/servicer.py` (`_run_game_lifecycle`), `services/game_coordinator/servicer.py` (`_start_game_from_config`); tests `services/menu/tests/test_servicer.py` (`TestModeMinimumPlayers`), `services/game_coordinator/tests/test_servicer_sessions.py` (`TestModeMinimumPlayers`).

### BR-002: IDLE and ADMIN block auto start

Controllers in IDLE or ADMIN count as connected but not ready.

### BR-003: `menu_auto_start` boot path

When the menu starts through `menu_auto_start` (on by default, `user.json`) instead of StartMenu, it enters the lobby exactly as StartMenu does: it restores `current_game` (UC-011), starts lobby music (UC-031) and the idle monitor (A2) and publishes `menu_started`. Before it reads `menu_auto_start` and `current_game`, the boot waits up to 5 s for the `user` flag provider to sync; after that it uses the code defaults (on, JoustFFA) (D-M2, #1505).

### BR-004: No game reads flags before its providers are ready

The game coordinator creates a game only after every flag provider it reads has synced at least once (no longer NOT_READY), waiting at most 5 s (A5). A wait that fails never blocks the start. A game that starts after the wait ran out records the fallback (`feature_flag.providers_not_ready`) on its root span, so a code-default start is never silent. Waiting on the readiness event is safe from any thread: the provider calls its READY handler on its own thread, and the waiter is woken on its own event loop (`loop.call_soon_threadsafe`, #1250 bug class).

**Code / tests (BR-004):** `services/game_coordinator/flag_readiness.py`, `game_session.py` (`_run_game_loop_async`), `lib/feature_flags.py` (`wait_for_provider_ready`); tests `services/game_coordinator/tests/test_flag_readiness.py`, `lib/tests/test_feature_flags.py`.

### BR-005: Lobby button map

Buttons of a CONNECTED or READY controller in the lobby (`handlers/connected.py`, `handlers/ready.py`); holding Cross, Circle, Square and Triangle together enters admin mode (UC-012), whose buttons are mapped in UC-012 BR-005.

| Button | CONNECTED | READY |
|--------|-----------|-------|
| Trigger | Mark ready (step 2) | Start at once when every connected controller is ready (A4) |
| Move | No action | Un-ready (A1) |
| Select | Next playable mode (UC-011 A2) | No action |

Select in READY and Move in CONNECTED are ignored.

### BR-006: Start confirmation

The menu starts the real game with `StreamGameEvents(start_config)` (step 5) and treats the first event of that stream as the coordinator's answer: `game_start_error` is a rejected start (A3); any other event confirms the start, after which the menu clears the ready state (players leave READY), and from then on a broken stream is reconnected to the primary bus. Since #1783 the first event is `game_start` (UC-003 BR-003), which the coordinator yields only after the game thread was started, so the confirmation means the same as before, it only arrives before `game_starting`. A reconnected stream subscribes without a `start_config` and gets no replay. Because a terminal event published while the stream was down is lost, the menu checks after every reconnect that its game is still live (A9, BR-009).

**Code / tests (BR-006):** `services/menu/game_lifecycle.py` (`_consume_game_events`, `_handle_first_game_event`); tests `services/menu/tests/test_servicer.py` (`TestConsumeGameEvents::test_game_start_first_confirms_the_start_once`, `TestHandleFirstGameEvent`).

### BR-007: A failed start frees its game

A start that fails or is cancelled after the coordinator admitted the game (A7) never leaves its session behind: the coordinator retires it (`_abort_admitted_session` → `_retire_session`) before it answers, so a failed real start can not lock out the next real game and a failed shadow start does not hold a shadow-cap slot. This applies to every start through `StreamGameEvents(start_config)`, real and shadow alike (D-G21).

**Code / tests (BR-007):** `services/game_coordinator/servicer.py` (`_start_game_from_config`, `_run_admitted_start`, `_abort_admitted_session`); tests `services/game_coordinator/tests/test_servicer_sessions.py` (`TestFailedStartRetiresSession`).

### BR-008: A live game is never replaced by a start request

The menu keeps one game lifecycle task (`_game_lifecycle_task`). A start request while that task is live is refused (A8); a start request never cancels it, so the live game keeps its menu stream. A task that has already finished is simply replaced. The lobby latch (A4) only covers the ready and trigger paths in the lobby: the web `start_game`, the `ProcessInput` trigger and the admin force-start are guarded by this rule.

Only the operator's `reset_menu` cancels a live lifecycle task, and only when the coordinator's `GetGameState` reports no primary game in `STARTING` or `RUNNING`. This recovers a lifecycle that can never finish, for example a reconnected stream whose game check (BR-009) could not reach the coordinator, so the stream was kept although the game had already ended (BR-006: no replay, so no `game_ended` arrives). The lookup fails closed: an error or an unsuccessful answer counts as an active game and the lifecycle is kept. With a game active, `reset_menu` changes nothing. With no live lifecycle, `reset_menu` keeps its earlier behaviour (GAME_STARTING back to RUNNING with `game_start_cancelled`).

**Code / tests (BR-008):** `services/menu/game_lifecycle.py` (`_start_game`, `_reject_start_while_active`, `_restart_lobby`), `services/menu/servicer.py` (`_handle_reset_menu`, `_primary_game_active`); tests `services/menu/tests/test_servicer.py` (`TestStartWhileGameActive`; A10: `TestMenuServicerProcessInput::test_reset_menu_cancels_game_start`, `test_reset_menu_while_running_is_noop`).

### BR-009: A reconnect checks that the followed game still exists

The menu remembers the `game_id` of the game it follows (from the events of its start stream). After a reconnect (BR-006: primary bus, no replay) it waits until the coordinator has registered the subscription, then calls `GetGameState` for the primary game. The game counts as ended when the answer is successful and the primary game is not `STARTING` or `RUNNING`, or its `game_id` differs from the followed one; the lifecycle then publishes `game_ended` (`game_id`, `reason` = `ended_while_disconnected`), restores the lobby and finishes, so the next start is accepted (A8). Checking only after the subscription is registered closes the race: a game that ends later delivers its terminal event on the new stream. An error or unsuccessful answer keeps the reconnected stream, as before this rule; the operator's `reset_menu` stays the recovery for that case (BR-008). A reconnect that fails is retried as before; when every attempt fails the lobby is restored and `game_ended` (`game_id`, `reason` = `coordinator_lost`) is published (A13, #2450). A stream that breaks after the confirmed start is reconnected even when it breaks while delivering events; before #2063 such a break restored the lobby at once although the game kept running, because the confirmation was lost with the broken stream.

**Code / tests (BR-009):** `services/menu/game_lifecycle.py` (`_run_game_event_stream`, `_followed_game_gone`); tests `services/menu/tests/test_servicer.py` (`TestReconnectChecksFollowedGame`).

### BR-010: A lobby restore always ends

Each step of the lobby restore (step 8) has its own time bound of 10 s (`LOBBY_RESTORE_STEP_TIMEOUT_SECONDS`, a code constant: a recovery bound, not a stage knob, so no flag under C-035): starting the button monitor, re-registering the controllers (`state_manager.reset`, which sets their lobby LED colours) and starting the lobby music (also in `StartMenu`, A11, #2195). Waiting for the button stream keeps its own 5 s bound. A step that does not finish in time is cancelled, logged and marked on its span (status ERROR, `menu.restore.timed_out_step`, `menu.restore.deadline_seconds`, event `restore_step_timeout`; telemetry.md §2, #2146), and the restore goes on with the next step; the idle monitor is always started (except for a menu stopped during the game or the restore, which stays STOPPED without it unless a later `StartMenu` came, A12; the state is read right before the start, A11). The restore then ends as usual: the lobby-restart window closes (A8), the lifecycle finishes and the next start or `reset_menu` is accepted. A timed-out re-registration keeps every controller: all are put back to CONNECTED before their LED colours are set, so a controller whose colour was not set is still in the lobby and only shows its old colour. Cancelling the restore from outside (menu stop, shutdown) is not a timeout: it ends the restore at once and is passed on. Before #2072 a hung step kept the restore, and so the window in which `reset_menu` is ignored, open for good.

**Code / tests (BR-010):** `services/menu/game_lifecycle.py` (`_restart_lobby`, `_bounded_restore_step`, `LOBBY_RESTORE_STEP_TIMEOUT_SECONDS`), `services/menu/servicer.py` (`enter_lobby`), `services/menu/state_manager.py` (`reset`); tests `services/menu/tests/test_servicer.py` (`TestLobbyRestoreBounded`).

### BR-011: The browser cannot set the shadow-only start fields

A `StreamGameEvents` request that reaches the coordinator through connect-proxy (the browser side) and carries a `start_config` has `rng_seed`, `experiment_id`, `arm` and `pattern_trigger_policy` cleared before it is forwarded; the rest of the config is forwarded unchanged (#2214). Those fields only subdivide a shadow game (#982) and belong to the agent, which starts its shadow games over gRPC directly (`GAME_ORIGIN_AGENT`) and never through connect-proxy. The dashboard sends no `start_config`. A real game already ignored them in the coordinator's spawn binding; this closes the shadow path.

**Code / tests (BR-011):** `services/connect-proxy/main.go` (`stripShadowOnlyFields`); tests `services/connect-proxy/forwarding_test.go` (`TestProxyStreamGameEventsShadowFields`).

### BR-012: A short tap counts

A press of any lobby button (BR-005: the trigger to ready up, Move to un-ready, Select, and the admin chord buttons) counts when it lasts at least 50 ms, and the System answers it with one press and one release event. A press event needs no hold; hold actions (the admin chord, BR-005, and the force-start hold) keep their hold times (#2312: on the stage Pi a 0.1 s tap mostly failed, a hold of about 1 s worked). No stage of the input path may drop a press that starts and ends between two of its samples:

- rust-hid ORs the button bits of every input report it drains in one pass of its device loop (the other values are the latest report's), so a press and release inside one drain still reports the press; the next drain reports the release. Its input stream keeps at most one waiting sample per controller: a sample the stream has not sent yet is replaced by the newer one with the replaced sample's button bits OR'ed in, so a press is not lost when a lagging reader skips samples (#2372).
- The controller manager's HID stream reader remembers every button it saw down since the previous 100 Hz poll; that poll reports those buttons as pressed and the next poll reports the real state, so its edge detection sends a press and then a release event (the gameplay stream's trigger latch, UC-030 BR-005, is separate and still cleared only per game frame). That reported state is a copy of the real sample: the poll loop treats it as the sample it copies, so it is not counted as a fresh frame (input lag, movement update rate and report-gap statistics; UC-035, #2352).
- The menu changes the state and the LED before it plays the ready beep and does not await the beep (step 2), so a slow audio call never holds back the next button event; the controller events are handled one after another.

Not covered: a press during which rust-hid reads no report at all (its device loop skips a controller while that controller's output writer holds the device, #2313). A discovery pass no longer reopens the open controllers or reads a report from them (UC-002 BR-006, #2314). Python-hid, the opt-in backend (UC-002 BR-003), returns its latest report only. Replacement also cannot keep: a release and re-press (or a double tap) inside one replacement window collapse into one continuous press, so the edge pair is lost; under lag the release arrives one sample after the OR'd sample; and a flush delayed by a device busy in a write (#2313) also drops reports, including a press, that arrived after the `RegisterStream`.

**Code / tests (BR-012):** `services/rust-hid/src/hid.rs` (`read_latest_input`), `services/controller_manager/multiplexer/press_latch.py`, `hid_stream.py` (`_stream_loop`), `hid_service_adapter.py` (`HidServiceAdapter.poll`, shared by the rust and python adapters), `services/menu/handlers/connected.py` (`_handle_trigger`); tests `services/rust-hid/src/hid.rs` (`test_read_latest_input_keeps_a_press_released_within_one_drain`), `services/rust-hid/src/input_slot.rs` (`input_slot`, #2372; test `test_a_replaced_sample_keeps_its_buttons_and_only_the_newest_waits`), `services/rust-hid/src/device_manager.rs` (`test_a_press_in_a_replaced_sample_is_still_delivered`), `services/controller_manager/tests/test_press_latch.py`, `services/menu/tests/test_handlers.py` (`test_ready_does_not_wait_for_the_beep`, `test_a_failing_beep_still_readies`).

### BR-013: Audio never holds the lobby or the game start

Every RPC the menu sends to the audio service (`PlaySound`, `SetVolume`, `PlayMusic`, `StopMusic`) has a deadline of 2 s (`AUDIO_RPC_TIMEOUT_SECONDS`, a code constant: a recovery bound, not a stage knob, so no flag under C-035). Sound effects and voice lines (the ready beep, the mode name on Select, admin and operator-pad value lines, the "not enough players" line, each beep of the failure cue) are sent from a detached task (one shared helper, `run_detached`) and never awaited by the caller, so a slow or hung audio service never holds back the next button event of any controller, a `ProcessInput` command or the game start (#2378; before it, every voice line except the ready beep and the admin "Agent" line was awaited inside the serial button loop with no deadline). The state change, the LED and the published events of a press come first and keep the order of the serial loop; the sound may come late or not at all. The lobby music stays awaited (its stop must reach the audio service before the game's music starts), so a hung audio service delays the game start (step 5) and the lobby restore (step 8) by at most its deadline per call. A failed or timed-out audio RPC is logged and counted in `menu_audio_rpc_failures_total{rpc, reason}` (`reason` = `timeout` / `error`, [telemetry.md §6](../specs/telemetry.md#6-metrics)); the menu goes on without the sound.

**Code / tests (BR-013):** `services/menu/utils/audio.py` (`AudioHelper`, `AUDIO_RPC_TIMEOUT_SECONDS`), `services/menu/utils/detached.py` (`run_detached`), `handlers/connected.py` (`_play_ready_beep_detached`), `handlers/admin.py` (`_play_voice_detached`); tests `services/menu/tests/test_audio_deadlines.py`.

### BR-014: A stopped menu never auto starts

The ready auto start and the trigger start of a READY controller (step 4) fire only on a menu that is not STOPPED. A STOPPED menu ignores button presses (its button stream stays connected), so such a start can only be under way when `StopMenu` lands during the ReadyHandler's 0.3 s feedback delay or during the 0.1 s before the lifecycle runs. The menu state is checked at both points: the start is dropped and logged, no game is requested, no event is published and the ready latch is cleared. `StartMenu` (A11 step 2) re-enables the auto start. Other start paths (admin force-start, which needs a RUNNING menu for admin mode, UC-012 Pre-1; web `start_game`, `ProcessInput` and the operator pad) are not changed by this rule (#2449).

**Code / tests (BR-014):** `services/menu/game_lifecycle.py` (`_ready_start_game`, `_run_game_lifecycle`), `services/menu/menu_setup.py`; tests `services/menu/tests/test_servicer.py` (`TestStoppedMenuNeverAutoStarts`).
