# Use Case: Detect a Player's Death

## Overview

**Use Case ID:** UC-030
**Use Case Name:** Detect a Player's Death
**Primary Actor:** Player
**Goal:** Be eliminated (or warned) exactly when moving the controller too hard, never by surprise
**Status:** Tested
**Requirements:** FR-030, FR-031, FR-032, FR-033, FR-034, NFR-001, NFR-002, NFR-003, NFR-004
**Planned:** FR-160 (#1837, Implemented: A6 and BR-005 shipped in #1865; stays here, not under Requirements, until the hardware check #1465 lets it be Verified, because a Tested use case would derive Verified), FR-161 (#2096, In Progress: A7, BR-008 and BR-009 are implemented in the game coordinator, but `hold` is not yet a variant of `shield.activation`, so no game runs it until its controller feedback ships, UC-040 BR-026)

## Preconditions

- A game is RUNNING and the player is alive and outside any grace or invincibility window.

## Main Success Scenario

1. Player moves the controller.
2. System samples the controller (≈ 1 kHz), keeps the latest state in the controller manager (100 Hz loop) and streams it to the game at the gameplay rate (default 60 Hz).
3. System computes the acceleration magnitude in g (all three axes, gravity included).
4. System smooths it with an exponential moving average (`perception.ema_weight`, default 4: 80 % previous, 20 % new).
5. System computes the effective thresholds for the player's sensitivity (0 to 4): interpolated between the slow-tempo and fast-tempo tables by the game's tempo intensity (UC-031 step 3, BR-005; the music follows the same intensity), divided by the clamped sensitivity × difficulty factor and multiplied by the clamped effective handicap (the handicap composed with the agent's toughness boost and rubberband by maximum and with its soft penalty by minimum, UC-040).
6. The smoothed value exceeds the warning threshold.
7. System warns the player: a white flash and rumble (200 ms each) and a `death_warning` span event; at most once per 0.5 s warning window.
8. The smoothed value exceeds the death threshold.
9. System eliminates the player: plays an explosion, sends the death effect (rumble 1000 ms at 255, distinct from the 200 ms warning rumble; red 300 ms, fade 700 ms; the rumble runs on its own timer and the fade, a lobby reset or the end of the game do not cut it short; a controller disconnect cancels the timer). The LED stays off after the fade by decision (#1832): it saves battery, and the original JoustMania keeps a dead player red through `red_on_kill`, which is deliberately not copied (no such setting). The system also records exactly one `player_death` event on the player span (whatever the mode; telemetry.md §3.2) and increments `game_player_deaths_total{mode, game_kind}` once per death. No kill is taken once the game is force-ended (UC-027 step 3), in any mode: the kill path checks this before the mode's gate, so the kills of the rest of the frame in which the force-end lands count nothing (#2033); the force-end is applied on the game's own loop, so it never lands between a gate check and the bookkeeping after it (UC-027 step 3, #2149). A mode can decline a kill before any of this (its kill gate, checked with the other kill guards; the default gate, kept by Free-for-All, Teams, Random Teams, Traitor, Werewolf, Zombies and NonStop, declines every kill once the game's outcome is latched (the win decided, UC-020 BR-003, or NonStop's time limit, UC-026 BR-003; #2019); Swapper declines every kill once its win is latched, UC-024 BR-004; Tournament takes only a kill of a fighter of the undecided match out of its grace, or of a disconnected player; Fight Club takes only a kill of the defender or the fighter of the round being fought out of its grace, or of a disconnected player still in the game, UC-025 BR-006): a declined kill changes no counter or gauge, plays no explosion, sends no death effect and records no `player_death` event (#1383). The gate is checked again after the explosion, right before the bookkeeping, so a kill whose gate closed while the kill path awaited (shield charge end, explosion; the game was force-ended, the game's outcome was latched or, for Swapper, the game stopped) is declined there: the explosion has played, and a shield charge the player held has already ended with reason `death` (UC-040 A32), but nothing else of the above happens (#1988).
10. System checks the win condition (UC-020 to UC-026).

## Alternative Flows

### A1: In grace or shield

**Trigger:** `now < grace_until` (step 3): the match-start grace or an agent shield, both of which write `grace_until` (UC-040 A16), or the activation of a shield charge (A6, #1837); or an active shield hold (`now < hold_until`, A7, #2096); or a shield end grace window (`now < end_grace_until`, UC-040 BR-033, #2464), which follows a hold that ran out, an instant shield or an activated charge
**Flow:**

1. System resets the player's EMA and skips warning and death checks.
2. Use case ends for this frame. Per-match invincibility (`invincible_until`) is mode-specific and not part of FFA; see UC-025.

### A2: Mode-specific death (moved)

**Trigger:** None in this use case since #1500: a mode that redefines death is mode-specific and documented in its own use case (Zombies conversion and respawn UC-023 steps 3 and 4, Swapper swap UC-024 step 2, Tournament match end UC-025 step 3, NonStop respawn UC-026 step 2). The ID is kept so it is not reused (step 9)
**Flow:**

1. No steps: this flow moved to UC-023 to UC-026 in #1500. The ID is kept so it is not reused.
2. Use case continues at step 10.

### A3: Fixed-threshold roles (moved)

**Trigger:** None in this use case since #1500: fixed role thresholds are mode-specific and documented in their own use cases (werewolves UC-022 A1 step 3, zombies UC-023 BR-002). The ID is kept so it is not reused (step 5)
**Flow:**

1. No steps: this flow moved to UC-022 and UC-023 in #1500. The ID is kept so it is not reused.
2. Use case continues at step 6.

### A4: Below the warning threshold

**Trigger:** The smoothed value stays below the warning threshold (step 6)
**Flow:**

1. Nothing happens for this frame.
2. Use case ends.

### A5: Controller disconnects

**Trigger:** The controller manager reports the player's controller as disconnected in a gameplay frame (step 2)
**Flow:**

1. System eliminates the player through the same path as step 9 (no motion involved) before it evaluates the frame's motion data, and records `player_disconnected` on the player span.
2. Use case continues at step 10.

### A6: Player activates a shield charge

**Trigger:** An alive player who holds a shield charge (UC-040 A30) presses the trigger (BR-005) outside every grace or invincibility window (step 2; #1837, FR-160)
**Flow:**

1. System sets `grace_until = max(grace_until, now + charge seconds)` and drops the charge.
2. System sends `GAME_EFFECT_SHIELD_CHARGE` 0, `GAME_EFFECT_SHIELD` (the charge seconds) and `GAME_EFFECT_SHIELD_SWELL` to the player's controller and plays `shield_up`; the charge's reminder and pre-expiry pulses stop with the charge layer and the swell is the confirmation (UC-040 BR-021, #2094). It publishes `player_shield_charge_ended` (`reason=activated`) and `player_shielded` (`activation=trigger`, `charge_delay_ms`) and records `shield_activated` on the player's span (UC-040 A16, BR-021).
3. System handles the frame as A1: the EMA is reset and the warning and death checks are skipped, also for the motion of this very frame.
4. Use case ends for this frame.

### A7: Player holds the shield (hold mode)

**Trigger:** In a game latched to `hold` (UC-040 BR-019, BR-027; #2096, FR-161), an alive, armed player (BR-005) reads the trigger pressed (BR-008) outside every other grace or invincibility window, while no kill of the player is in progress, with usable energy `min(energy, budget remaining)` of at least the minimum burst (UC-040 BR-024) (step 2)
**Flow:**

1. System starts an activation: `hold_started_at = now` and `hold_until = now + usable energy`; the game keeps a `game.shield_hold` span open for it. `grace_until` is not written. The controller turns white with a light continuous rumble that rises, and a white that dims, as the energy drains (UC-040 BR-026, #2463), sent by the game's outbound task, not awaited in the frame.
2. System handles the frame as A1: the EMA is reset and the warning and death checks are skipped, also for the motion of this very frame. Every following frame with the trigger held is an A1 frame too, until `hold_until`.
3. The first frame that reads the trigger released sets `hold_until = hold_started_at + min(max(held, minimum burst), usable energy)`; a press again before that deadline continues the same activation (BR-008).
4. At `hold_until` the activation ends: System books the cost (`hold_until - hold_started_at`) against the energy and the per-game budget, ends `game.shield_hold` with `shield.hold_outcome` = `released`, `empty` (held until the energy ran out) or `budget_exhausted` (held until the budget ran out), and counts `game_shield_hold_activations_total`. After `empty` or `budget_exhausted` the player must release the trigger before the next activation, and the shield end grace window follows the deadline (UC-040 BR-033, #2464; none after `released`). The first unprotected frame after the activation, or after the window, follows BR-009. The controller's rumble stops and its LED shows the energy left (UC-040 BR-026); after `empty` or `budget_exhausted` the rumble stops cleanly from the top of its ramp (ramp mode, the default, #2463) or, in flat mode, the "empty" pulse plays.
5. Use case ends for this frame.

## Postconditions

### Success Postconditions

- The player is out and every subscriber sees the result in the event stream and telemetry.

### Failure Postconditions

- None: a missed frame is evaluated on the next one.

## Business Rules

### BR-001: Threshold tables

Base thresholds (g) by sensitivity 0 to 4: slow-tempo warning 1.2 / 1.3 / 1.6 / 2.0 / 2.5, slow-tempo death 1.3 / 1.5 / 1.8 / 2.5 / 3.2, fast-tempo warning 1.4 / 1.6 / 1.9 / 2.7 / 2.8, fast-tempo death 1.6 / 1.8 / 2.8 / 3.2 / 3.5 (flag `thresholds`, read at game start).

### BR-002: Downsampling

The gameplay stream sends the latest sample per frame, not the frame's maximum; spikes shorter than a frame can be missed.

### BR-003: Startup guard

A 0.3 s grace applies to all players at game start (it never shortens a longer grace, such as an agent shield, granted before the game loop starts), and about 100 ms of buffered frames prime the EMA. Free-for-All, the modes that use the base `run()`, Werewolf, Zombies, Fight Club and Tournament (their own `run()` calls the warm-up before the base game loop, UC-022 BR-001, UC-023 BR-002, UC-025 A2 and step 1, #1273) run this guard. Fight Club and Tournament run this use case's detection for their two fighters (UC-025 BR-002, #1347, #1882); Tournament keeps its per-match invincibility on top of it (UC-025 step 2). NonStop runs the EMA warm-up of the base `run()` and the 0.3 s grace at the start of its own game loop (UC-026, issue #1591).

### BR-004: Latency

Detection adds at most one frame (16.7 ms at 60 Hz) plus EMA lag; end-to-end latency is not measured (NFR-004); the game-side share is measured (≈ 33 ms at the default weight, `services/game_coordinator/tests/performance/test_game_loop_timing.py`, NFR-004).

Shield hold (A7, #2096; estimates, not measured end to end): from a press to protection, the controller's Bluetooth report interval (not measured), the rust-hid poll (about 1 kHz, at most 1 ms), the controller manager's state loop (100 Hz, at most 10 ms), the wait for the next gameplay frame (at most 16.7 ms at 60 Hz) and the gRPC hop and frame processing (about 1 to 3 ms): about 30 ms worst case plus the report interval, about 47 ms at a 30 Hz stream. The frame in which the press is seen is already protected (A7 step 2). A release is slower: the frame value is "pressed now or since the last frame" (BR-005), so a release just after a frame was built still reads pressed on the next frame, about 45 ms worst case at 60 Hz; the minimum burst (UC-040 BR-024) masks it for short taps. Tests assert frame counts (unit and performance tests); an end-to-end test asserts only the order of events, never a latency bound (NFR-050 allows 1.5 s CI propagation).

### BR-005: Trigger press

- Only the digital trigger is used (the bit the lobby ready uses; not the analogue value). A press is the frame where the trigger reads pressed after a frame that read released.
- A player is armed only after the first released frame seen by the game loop, so a trigger held through the lobby ready, the countdown or the EMA warmup is not a press.
- The press is evaluated before the grace and death checks of the same frame (A6 step 3): the activation wins over a death-crossing frame, because pressing the trigger jolts the controller.
- Presses of a dead player, during the match-start grace, an agent shield or admin invincibility, or without a charge do nothing and are not remembered.
- No time debounce: a press while the shield is active is ignored, so a bouncing press activates at most once.
- Source: `GameplayData.trigger_pressed`, latched by the controller manager as "pressed since the last delivered frame" and cleared per delivered frame, so a short press survives a 15 or 30 Hz stream (services.md, controller-manager notes).

### BR-006: Gameplay stream lifecycle

The game closes its gameplay stream on every end, in every mode: a natural end (after the winner effects; NonStop too: its game loop keeps its own stream open until the end-game step is done, UC-026 step 3, #1932), a force-end, and an error in any phase (#1914). The controller manager then releases the game's controllers at once (Identify, UC-004), not when the game object is garbage-collected. A phase error, or a force-end during an early-stream phase (UC-021 A1), does not open the stream again. An agent `controller_effect` write in flight when the stream closes stops without an error (#1914). An end-of-game effect (the winner rainbow, Swapper's loser colour) on a stream the controller manager has already ended, or that ends under the write, is skipped with a warning in every mode; the game keeps its outcome (UC-020 BR-003, #1956). An LED write from a mode's background task (Fight Club's round timer, Werewolf's reveal, a Zombies respawn timer) on a stream that has ended, or that fails under the write (for example during the game loop's reconnect wait below), is skipped with a warning the same way: the task goes on (the next round is seated or the game ends, the other werewolves are revealed, the zombie respawns), and the reopened stream restores every player's current colour (#2021, #2022).

A stream that dies before or during play is opened again (#1913); a game that is no longer running never reopens:

- **Warm-up** (the modes that run the BR-003 warm-up: the base `run()` modes, Werewolf, Zombies, Fight Club, Tournament): a stream that ends, fails, or delivers no frame for 0.5 s is closed and opened once more, and the warm-up runs once more. A second failure, and a reopen that fails to open (controller manager unavailable), are left to the game loop.
- **Game loop** (the modes on the base game loop: the base `run()` modes, Fight Club, Werewolf, Zombies, Tournament; NonStop runs its own loop): a stream that fails, or ends with a non-OK gRPC status, is closed and opened again after 1 s, 2 s, then 3 s; a game force-ended during that wait opens no new call. After three reconnects in a row without a healthy stream in between the game ends with `game_error` (UC-020 BR-003): the count starts again only once a reopened stream has delivered 60 frames (about 1 s at the default 60 Hz), so a stream that delivers a few frames and fails again still ends the game (#1931). A stream that ends with an OK status ends the loop (#1930). A stream error is an error of the gameplay call (a failed read), or a gRPC error (`AioRpcError`, `InvalidStateError`) raised while a frame is processed; the only gRPC calls a frame makes today are writes on the gameplay call (a death effect, the alive filter). Any other error while the game processes a frame (a mode's kill handler, its win check, a Tournament bracket step) ends the loop at once, without a reconnect, and the game ends with `game_error` (UC-020 BR-003, #2001), except after Tournament's champion latch: the result stands (UC-025 BR-005, D-G34). The controller manager ends the gameplay stream without an error only when the client cancels the call (a half-close does not end it, and the controller manager never closes it OK on its own); a frame that fails ends it with `INTERNAL` (#1930).
- Each reopen (formation drain, UC-021 A1; warm-up; game loop) opens the new call before it closes the old one, and counts once in `game_gameplay_stream_reconnects_total`. An agent `controller_effect` write always goes to the current stream, and a write to a stream that has just closed stops without an error.

### BR-007: Player span lifecycle

Every player lifecycle span ends exactly once on every end of the game, in every mode: a natural end (the mode's end step, or a death, closes it with the mode's own `game_ended` / `player_survived` / `victory` event), a force-end at any phase (after the intro, the countdown or the warm-up, where Fight Club, Werewolf, Zombies and Tournament return from their own `run()` before the end step), and an error in any phase. Tournament's natural end closes them in its end step with `tournament_ended` (the champion's with `is_champion` true). The shared run-end cleanup ends each span still open with `game_ended` (`winner` false; `game.outcome` the latched outcome once the game loop ended, else `force_ended` with `game.end_reason` after a force-end, else `error` after `run()` raised, else `completed`; status ERROR after `run()` raised, else OK), and closes an open per-player `countdown_phase` span and the `players` / `game_cycle` grouping spans with it. A span already ended is not ended again. A failure while ending these spans is logged and neither replaces the run's own error nor skips the session's analytics clear (#1997, telemetry.md §3.2).


### BR-008: Trigger hold

- Hold mode only (a game latched to `hold`, UC-040 BR-019, BR-027). The hold is the level of the digital trigger as the game frame reads it (`GameplayData.trigger_pressed`, BR-005: pressed now or since the last frame), so a tap between two frames reads as one held frame and costs the minimum burst.
- Arming works as BR-005: a trigger held through the lobby ready, the countdown or the EMA warmup does not activate. After an activation ends with `empty` or `budget_exhausted` the player is disarmed until the trigger reads released, so holding on never restarts an activation on a recharge trickle or a grant.
- Holding during another grace or invincibility window (the match-start grace, `grace_until`, `invincible_until`) does not drain: the activation starts on the first frame outside those windows while the trigger is still held.
- A release followed by a press before `hold_until` (inside the minimum-burst tail) continues the same activation: it is the debounce, so a bouncing trigger never pays a second minimum burst for one hold.
- A kill of the player in progress (the kill path awaits its sounds) blocks the activation; a death drops the pool (UC-040 A39).
- A gameplay stream that is opened again (BR-006) forces a release of a held activation at the last frame that read it held, so no drain crosses a reconnect. A gap between frames without a reconnect drains for the gap (it errs towards less shield).
- The frame path does compares only: the energy is a function of time (UC-040 BR-024), the activation, release and end are field writes plus the span, and nothing is awaited for a frame that has no transition. The controller feedback of a transition (UC-040 BR-026) goes to one ordered outbound task per game and is never awaited in the frame: the frame only marks the player, and the task sends the player's state when it runs.
- `hold_until` is part of the effective grace (`max(grace_until, invincible_until, hold_until)`, the #817 composition, amended by #2096): a release never shortens the match-start grace, an agent shield or admin invincibility, because hold never writes `grace_until`.

### BR-009: Release tail

- After an activation ends (A7 step 4), or after a shield end grace window (UC-040 BR-033, #2464) in any mode, the player's EMA holds 0 from the A1 frames. The first unprotected frame therefore primes the EMA with `min(raw sample, effective warning threshold)` and runs no EMA update on it, instead of the plain prime with the raw sample (`_update_ema`): a release jolt on that single frame never kills or warns.
- The following frames update the EMA as step 4, so a sustained hard movement still kills a few frames later (at about 1.6 g warning and 1.8 g death, a constant 2.5 g kills on the third unprotected frame).
- Only after a hold activation or a shield end grace window: the A1 frames of the other graces, and a shield charge or an instant shield without a window (`shield.end_grace_seconds` = 0), keep the plain prime of #757.

### BR-010: Game clock

Every game deadline and duration (the grace and startup guard, warning, shield, shield charge and hold, toughness boost, rubberband, soft penalty, respawn, round and match ends, tempo changes and ramps, game duration) runs on a monotonic clock (#2357), so a wall-clock step (an NTP or real-time-clock sync on a Pi without a hardware clock) neither ends nor extends a running deadline. A time that leaves the coordinator as a timestamp (`until_ms` of `player_shielded`, `expires_ms` of `player_shield_charged`, UC-040) is converted to wall-clock epoch milliseconds when it is sent, because the dashboard compares it with the browser clock.
