# Use Case: Detect a Player's Death

## Overview

**Use Case ID:** UC-030
**Use Case Name:** Detect a Player's Death
**Primary Actor:** Player
**Goal:** Be eliminated (or warned) exactly when moving the controller too hard, never by surprise
**Status:** Implemented
**Requirements:** FR-030, FR-031, FR-032, FR-033, FR-034, NFR-001, NFR-002, NFR-003, NFR-004

## Preconditions

- A game is RUNNING and the player is alive and outside any grace or invincibility window.

## Main Success Scenario

1. Player moves the controller.
2. System samples the controller (≈ 1 kHz), keeps the latest state in the controller manager (100 Hz loop) and streams it to the game at the gameplay rate (default 60 Hz).
3. System computes the acceleration magnitude in g (all three axes, gravity included).
4. System smooths it with an exponential moving average (`perception.ema_weight`, default 4: 80 % previous, 20 % new).
5. System computes the effective thresholds for the player's sensitivity (0 to 4): interpolated between the slow-tempo and fast-tempo tables by the current music tempo, divided by the clamped sensitivity × difficulty factor and multiplied by the clamped effective handicap (the handicap composed with the agent's partial shield and rubberband by maximum and with its soft penalty by minimum, UC-040).
6. The smoothed value exceeds the warning threshold.
7. System warns the player: a white flash and rumble (`effect.warning_flash_ms` / `effect.warning_vibration_ms`, default 200 ms each) and a `death_warning` span event; at most once per 0.5 s warning window.
8. The smoothed value exceeds the death threshold.
9. System eliminates the player: plays an explosion, sends the death effect (`effect.death_rumble_ms` / `effect.death_red_hold_ms` / `effect.death_fade_ms`, default rumble 150 ms, red 300 ms, fade 700 ms), records exactly one `player_death` event on the player span (whatever the mode; telemetry.md §3.2) and increments `game_player_deaths_total`.
10. System checks the win condition (UC-020 to UC-026).

## Alternative Flows

### A1: In grace or invincibility

**Trigger:** `now < max(grace_until, invincible_until)` (step 3)
**Flow:**

1. System resets the player's EMA and skips warning and death checks.
2. Use case ends for this frame.

### A2: Mode-specific death

**Trigger:** The mode redefines death (step 9)
**Flow:**

1. Zombies converts humans, Swapper switches team, NonStop respawns, Tournament ends the match.
2. Use case continues at step 10.

### A3: Fixed-threshold roles

**Trigger:** Player is a zombie or werewolf (step 5)
**Flow:**

1. System uses the role's fixed thresholds (`zombie.thresholds`, `werewolf.thresholds`), ignoring tempo and agent factors.
2. Use case continues at step 6.

### A4: Below the warning threshold

**Trigger:** The smoothed value stays below the warning threshold (step 6)
**Flow:**

1. Nothing happens for this frame.
2. Use case ends.

### A5: Controller disconnects

**Trigger:** The controller manager reports the player's controller as disconnected in a gameplay frame (step 2)
**Flow:**

1. System eliminates the player through the same path as step 9 (no motion involved) before it evaluates the frame's motion data, and records `player_disconnected` on the player span.
2. Use case continues at step 10.

## Postconditions

### Success Postconditions

- The player is out (or converted / respawning) and every subscriber sees the result in the event stream and telemetry.

### Failure Postconditions

- None: a missed frame is evaluated on the next one.

## Business Rules

### BR-001: Threshold tables

Base thresholds (g) by sensitivity 0 to 4: slow-tempo warning 1.2 / 1.3 / 1.6 / 2.0 / 2.5, slow-tempo death 1.3 / 1.5 / 1.8 / 2.5 / 3.2, fast-tempo warning 1.4 / 1.6 / 1.9 / 2.7 / 2.8, fast-tempo death 1.6 / 1.8 / 2.8 / 3.2 / 3.5 (flag `thresholds`, read at game start).

### BR-002: Downsampling

The gameplay stream sends the latest sample per frame, not the frame's maximum; spikes shorter than a frame can be missed.

### BR-003: Startup guard

A 0.3 s grace applies to all players at game start, and about 100 ms of buffered frames prime the EMA.

Known gap: Werewolf, Zombies, Fight Club and Tournament run their own `run()` and skip the EMA priming (Fight Club and Tournament use per-match invincibility instead) (issue #1273, D-G3).

### BR-004: Latency

Detection adds at most one frame (16.7 ms at 60 Hz) plus EMA lag; end-to-end latency is not measured (NFR-004).

Known gap (step 9): `game_player_deaths_total` is defined but never incremented, so the agent's metric-based elimination fallback gets no data (issue #1334).

Known gap (steps 4, 7, A1): Fight Club's own detection path uses a fixed EMA weight of 4, does not reset the EMA during grace and warns on every frame above the warning threshold (issue #1347, D-G9).
