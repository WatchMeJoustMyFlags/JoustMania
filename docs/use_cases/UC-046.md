# Use Case: Run Repeatable Pattern-Driven Shadow Games

## Overview

**Use Case ID:** UC-046
**Use Case Name:** Run Repeatable Pattern-Driven Shadow Games
**Primary Actor:** Operator
**Secondary Actors:** Agent
**Trigger:** A declared experiment reaches its first allocation pass in the experiment registry ([UC-043](UC-043.md)), or the operator runs the replay check on a recorded game
**Goal:** Drive the mock controllers of every shadow experiment game with continuous, parametric motion functions (archetypes; maintainer decision on #1258: experiments are archetype-only), so that players die organically, game length emerges from the parameters, thresholds, tempo and interventions, the verdict has variance between pairs, and any game can be replayed from its trace
**Status:** Tested
**Requirements:** FR-100, FR-101, FR-102, FR-103, FR-104, FR-105, FR-106, FR-107, FR-108, FR-109, FR-110, FR-111, NFR-040, NFR-041, NFR-042, NFR-043, NFR-044, NFR-003, NFR-005, NFR-018, C-005, C-019, C-020, C-021
**Planned:** FR-162 (#2096, Implemented: the simulated trigger policy BR-018, A17 and the deferred promotion of [UC-043](UC-043.md) A17 step 3; stays here, not under Requirements, because a Tested use case would derive Verified)

## Preconditions

- `enabled` and `experiments_enabled` are on ([UC-043](UC-043.md) Pre-1).
- The controller manager runs with the mock adapter.
- `agent.json` defines the archetypes as object variants of `experiment.mock_archetype` (seven ship: six without a trigger policy, all in the default selection, plus `burst_holder`, BR-018) and the selection flag `experiment.mock_archetypes`; step 2 checks the selection (A1, A2, A4).
- The agent's shadow game mode is configured by `SHADOW_GAME_MODE`; step 2 checks that it is `JoustFFA`, the only mode pattern games support in v1 (C-021, A13).
- (retired, #1662) `SimulateMovement` keeps the value it sets. Pattern controllers refuse `SimulateMovement` (BR-004, BR-012), so it does not gate this flow. The ID is kept so it is not reused.

## Main Success Scenario

1. The `agent.json` flag `experiment.mock_archetypes` lists the archetypes experiments run, as comma-separated names; its default variant `all` resolves to every shipped archetype without a trigger policy (`calm_long,slow_cascade,jittery_novices,close_race,late_burst,quick_cascade`; `burst_holder`, BR-018, is selected by name only; `all` is a variant name, not a keyword the agent expands), and the operator may narrow it.
2. In the first allocation pass after the experiment starts (before it spawns any game), the agent reads `experiment.mock_archetypes` and `experiment.max_game_seconds`, resolves every listed archetype to its parameter object (the variant of `experiment.mock_archetype` with that name), validates it, and pins the list (names, parameters, parameter digests) and the safety cap in the experiment journal.
3. For pair p the agent picks archetype p of the pinned list and spawns both arms one after the other: for each arm it reserves one mock controller per player of the archetype, passing the archetype name and parameters, and starts the game with the pair's shared `rng_seed`.
4. The controller manager validates the parameters, binds slot i to the i-th reserved controller, pins the arm's gameplay stream to the archetype's `stream_rate_hz`, and records the installation.
5. For every delivered frame k of a pattern controller, the controller manager reports the acceleration (0, 0, intensity_i(k / r)) in g, with gyro 0.
6. The game coordinator runs its normal death detection (EMA per delivered frame, sensitivity and tempo thresholds, grace); a player dies when its smoothed signal crosses the death threshold.
7. The agent observes the game and decides as usual; the rules engine draws its chaos choices from an RNG seeded by the game's `rng_seed`.
8. The game ends with a winner, with a tie (no winner slot), or as in A3 or A14; each is a sample that counts in the verdict, and the pair is not run again. On removal of each controller the controller manager records its frame count, signal fingerprint and per-second checkpoint fingerprints, and the agent records the elimination order by slot (from the coordinator's death events), the outcome, the replay classification (exact or non-exact) and concludes the fitness sample as in UC-043.
9. Operator replays a recorded game: runs `scripts/pattern-replay-check.sh --against <record>` with the replay record of that game (its `pattern_game_ended` journal event or a saved one-shot record), which runs one shadow game with the recorded archetype and seed (the one-shot runner with `SHADOW_GAME_ARCHETYPE` and `SHADOW_GAME_SEED`); or runs `scripts/pattern-replay-check.sh <archetype> [seed]`, which runs that archetype twice.
10. The script compares the replay with the recorded game and reports, with exit code 0, identical checkpoint fingerprints per slot on their common prefix (the input), an identical elimination order, winner slot and outcome, and an identical sequence of rules decisions.

## Alternative Flows

### A1: Empty selection

**Trigger:** `experiment.mock_archetypes` resolves to no archetype (an empty value, or flagd unreachable so the flag falls back to empty) (step 2)
**Flow:**

1. The agent spawns no game and journals the experiment as discarded with reason `pattern_selection_empty`. Experiments never fall back to random motion or scripted kills.
2. Use case ends.

### A2: Unknown or invalid archetype

**Trigger:** A listed name is not a variant of `experiment.mock_archetype`, or its parameters fail a validation rule of BR-003 (step 2)
**Flow:**

1. The agent spawns no game for the experiment and journals it as discarded with reason `pattern_archetype_invalid` and the failed rules.
2. Use case ends.

### A3: Safety cap reached

**Trigger:** No winner is declared within the pinned `experiment.max_game_seconds` (default 300 s) of wall time after the game started (step 6)
**Flow:**

1. The agent force-ends the game; its outcome is `timeout`. The elimination order holds the players who died so far; there is no winner slot.
2. The game is a valid, right-censored sample (its true length is at least the cap): its fitness is scored from the state at the cap and counts in the paired verdict, and the experiment counts it per arm as a timeout (BR-013). The timeout alone does not make it non-exact.
3. Use case continues at step 8.

### A4: Selection too small

**Trigger:** The pinned list holds fewer distinct archetypes than `verdict_min_pairs`, or names one twice (step 2)
**Flow:**

1. The agent spawns no game and journals the experiment as discarded with reason `pattern_selection_too_small`.
2. Use case ends.

### A5: Flag changes during the experiment

**Trigger:** Operator changes `experiment.mock_archetypes`, an archetype variant or `experiment.max_game_seconds` after the experiment pinned them in its first allocation pass (step 3)
**Flow:**

1. The experiment keeps its pinned archetypes, parameters and cap, also across an agent restart (BR-015); the new values apply to experiments that have not been pinned yet.
2. Use case continues at step 3.

### A6: Every archetype used

**Trigger:** The experiment has spawned one pair per archetype of its pinned list (step 3)
**Flow:**

1. The agent spawns no further pairs for this experiment; when its last game has ended it concludes the experiment with the verdict of the pairs it has (UC-043 step 5).
2. Use case continues at step 8.

### A7: Remote decision backend selected

**Trigger:** `decision.backend` is `jev`, `claude` or `openai` at any decision of the game (step 7)
**Flow:**

1. The agent decides with that backend as usual and marks the game non-exact with reason `remote_backend`.
2. The game still counts as a cohort sample but is excluded from replay comparisons.
3. Use case continues at step 8.

### A8: Another game runs at the same time

**Trigger:** A real game, or a shadow game the agent's experiment registry did not spawn, is live while the pattern game runs (step 6). The registry itself never runs a pattern game next to another of its shadow games (BR-010).
**Flow:**

1. With `shadow_policy=block` no new pattern game starts while a real game runs (the failed start uses up no archetype), and a real start preempts live pattern games (UC-043 A2): the coordinator force-ends them with reason `preempted_by_real_game`. JoustFFA publishes `game_ended` with `outcome=force_ended` and that reason first, and the coordinator publishes `game_force_ended` after it. The agent treats this force-end as aborted, whichever of the two events arrives first (BR-016), and the game is released without a fitness sample and its pair runs again (BR-015); this holds also when the game's telemetry end reaches the agent before the runner's outcome (BR-016, #1405). A rerun after `preempted_by_real_game` does not use up the pair's 3-rerun budget; a separate budget of 10 preemption reruns per pair bounds it (BR-015). A preemption that has begun completes even when the real start is cancelled (UC-043 A2): the agent still gets `game_force_ended` with that reason, and the rerun uses up one of the pair's preemption reruns although no real game runs.
2. Otherwise the pattern game runs and is marked non-exact with reason `concurrent_game`; its input signal stays exact (NFR-040).
3. Use case continues at step 8.

### A9: Game ends without a usable result

**Trigger:** The game ends in `game_error`, is force-ended by someone other than the agent for a reason that is neither a preemption (A8) nor the kill switch (A12) (for example an operator's force-end), or the stream to the coordinator fails, before a winner or the safety cap (step 6)
**Flow:**

1. The experiment releases the game without a fitness sample (UC-043 A12); its replay record carries the outcome `error` (`aborted` for a foreign force-end). The pair runs again, both arms, and the rerun uses up one of the pair's 3 reruns; once they are used up the archetype is skipped (BR-015).
2. Use case continues at step 3.

### A10: Stream frame overrun

**Trigger:** The controller manager falls behind its frame schedule for a pattern stream (step 5)
**Flow:**

1. The controller manager counts the overrun for every controller of that stream; the delivered signal stays identical because it is indexed by frame, not by wall time.
2. The game is marked non-exact with reason `frame_overrun`.
3. Use case continues at step 6.

### A11: Replay differs or is not comparable

**Trigger:** A slot's checkpoint hashes differ on their common prefix, the elimination order or the decision sequence differs, the parameter or flag digests differ, or the recorded game is non-exact (step 10)
**Flow:**

1. The script reports the first difference (slot and second, elimination order, winner slot, outcome or decision index) with exit code 1, or why the games are not comparable (a differing archetype, parameter or flag digest, an unavailable flag digest, or the non-exact reasons of either game) with exit code 2.
2. Use case ends.

### A12: Kill switch

**Trigger:** `enabled` (the kill switch) or `experiments_enabled` turns off (step 3)
**Flow:**

1. A pattern game still in flight is marked non-exact with reason `kill_switch` and force-ended with the reason `pattern_kill_switch` (the coordinator records it as the game's `game.end_reason`); its replay record carries the outcome `aborted`, and it gives no fitness sample.
2. The agent aborts the experiment as in UC-043 A1 and removes its reserved pattern controllers. The aborted experiment is terminal, so the pair does not run again and no rerun is counted (BR-015).
3. Use case ends.

### A13: Unsupported game mode

**Trigger:** The shadow game mode is not `JoustFFA` while `experiment.mock_archetypes` selects archetypes (step 2)
**Flow:**

1. The agent spawns no game and journals the experiment as discarded with reason `pattern_mode_unsupported` (C-021); the one-shot runner refuses the run with the same reason.
2. Use case ends.

### A14: The agent ends the game

**Trigger:** The agent's own `end_game` intervention (UC-040; for example rules-engine rule R7 when `accelerate` dominates) force-ends the pattern game with reason `agent_intervention` before a winner or the safety cap (step 7)
**Flow:**

1. The shadow runner classifies the game as `agent_ended` (BR-016); there is no winner slot, and the elimination order holds the players who died so far.
2. The game is a valid, right-censored sample, like a timeout (BR-013): it ended because of the treatment policy, so dropping it would bias the verdict towards inconclusive. Its fitness is scored from the state at the end and counts in the paired verdict, its pair is not run again, and the experiment reports agent ends per arm next to the timeouts. The agent end alone does not make the game non-exact.
3. Use case continues at step 8.

### A15: Spawn of an arm fails

**Trigger:** Reserving the arm's controllers or starting its game fails: backpressure (a game start already in progress), a block by a real game under `shadow_policy=block`, or another error (step 3)
**Flow:**

1. The agent releases the reservations of the failed arm and rewinds to it; the arm is spawned again on a later tick. The failure uses up no archetype and no rerun budget, and nothing is journaled (BR-015).
2. Use case continues at step 3.

### A16: Replay run gives no record

**Trigger:** The replay run prints no replay record within `PATTERN_REPLAY_TIMEOUT` (default: the effective safety cap `experiment.max_game_seconds` read from the flag service, 300 s when it is unreadable or out of range, plus 120 s start-up margin: 420 s for the default cap, 720 s for `long`, 1920 s for `soak`, so a game that runs to the cap always finishes inside the wait): the one-shot runner refused the run (for example `pattern_mode_unsupported` or an empty selection), the run failed before a game id existed, or the record given to `--against` cannot be read (step 9)
**Flow:**

1. The script reports the failure and exits 3; nothing is compared. A record without an `archetype` (plain or journal-normalised) exits 3 with `record has no archetype`, never 1 ("differs"; D-A24, #1703). A replay run that started a game always prints a record, also when it ended in `error`, `timeout` or `agent_ended`; such a record is compared in step 10.
2. Use case ends.

### A17: Hold experiment without a trigger policy

**Trigger:** An experiment on a hold flag (UC-043 A17) pins archetypes of which at least one has `trigger_policy` `none`, or the shadow game mode (`SHADOW_GAME_MODE`) is not Free-for-All (step 2)
**Flow:**

1. The agent discards the experiment with `pattern_trigger_policy_missing` (naming the archetypes without a policy), or `pattern_mode_unsupported` for the mode, before any game: a pair on such an archetype would be instant against instant (BR-018) and measure "nobody ever shields". An experiment on any other flag pins the same selection and runs.
2. Use case ends.

## Postconditions

### Success Postconditions

- Every pattern game of the experiment ran on a named, pinned archetype, and its archetype name, parameter digest, seed, stream rate, slot mapping, signal and checkpoint hashes, outcome, elimination order and replay classification are on its trace and in the experiment journal.
- A replay of an exact game, run with `decision.backend=rules`, `interventions_enabled` off, one game at a time and 0 frame overruns, has identical per-slot checkpoint hashes on their common prefix (NFR-040), and when it ends with a winner whose deaths are seconds apart, the same elimination order and winner slot (BR-005, NFR-041).

### Failure Postconditions

- Real games never see a pattern controller (reserved controllers are hidden from the lobby).
- A pattern game that ended without a usable result (`aborted`, `error`) contributes no fitness sample, and an experiment that ends without a verdict is journaled with its terminal status and reason.

## Business Rules

### BR-001: Game time

Game time is t = k / r, where k is the index of the frame delivered for that controller on its owning gameplay stream (k = 0 for the first delivered frame) and r is the archetype's pinned `stream_rate_hz`. The owning stream is the first gameplay stream whose explicit filter names the controller (the game's stream, which is also a game stream in the [glossary](../glossary.md) sense of [UC-035](UC-035.md) BR-006: it sends the controllers' colours; an observer stream has neither a filter nor colours); a stream without a filter (the dashboard) never advances k, and when the owning stream ends the next explicit stream continues k. t does not depend on wall-clock time: when the host is loaded, frames arrive later, but frame k always carries intensity(k / r). The controller manager evaluates the function only at frame times. Game time starts when the game's stream opens, before the countdown, not when the game goes live; a mode that opens its stream before its formation or signal phase (Random Teams, [UC-021](UC-021.md) A1; Traitor, [UC-022](UC-022.md) BR-003; about 5 s earlier) starts it before that phase and the instructions clip, so a pattern spike in that window falls into frames the game discards. k advances through the formation, the countdown and warm-up, which the coordinator times by the wall clock, so the frame at which death detection starts varies by a few frames between runs. The checkpoint hashes therefore prove that two runs fed identical signals; the evidence that a replay played out the same is the elimination order, the winner and the decision sequence.

### BR-002: Motion function

Each player i of a pattern game follows

intensity_i(t) = clamp(base_i + drift_i · t + amp_i · sin(2π · (t / period_s + phase_i)) + burst_i(t), 0, 10)

in g. burst_i is a rectangular pulse of height `burst_h` and fixed width 0.2 s (`BURST_WIDTH_S`) that starts every `burst_period_s` seconds: with s = t / `burst_period_s` + phase_i, burst_i(t) = `burst_h` when s ≥ 1 and (s − ⌊s⌋) · `burst_period_s` < 0.2, else 0 (so the first pulse of player i starts at (1 − phase_i) · `burst_period_s`, never at t = 0); `burst_h` = 0 means no bursts. The vector is (0, 0, intensity) along the gravity axis, gyro 0, like today's noise (`services/controller_manager/multiplexer/mock_adapter.py`), and the coordinator uses only the magnitude for deaths (`services/game_coordinator/games/base.py` `_compute_accel_magnitude`).

### BR-003: Archetype and validation

An archetype is one object variant of the `agent.json` flag `experiment.mock_archetype` (flags.md §3.1); its id is the variant name. It holds the players N, `stream_rate_hz` r, the game parameters `base`, `drift`, `amp`, `period_s`, `phase`, `burst_h`, `burst_period_s`, and four per-slot modifiers: player i (slot i, 0..N−1) has base_i = `base` + i · `d_base`, drift_i = `drift` + i · `d_drift`, amp_i = `amp` + i · `d_amp`, phase_i = frac(`phase` + i · `d_phase`). The agent validates it when it pins it and the controller manager when it installs it. It is valid only if:

- every field above is present and a finite number (unknown fields are rejected); the only other field allowed is the optional `trigger_policy` object of BR-018, validated by its own rules there;
- 2 ≤ N ≤ 8 (integer);
- r is 15, 30 or 60 (the variants of `game_loop.update_frequency_hz`, NFR-003);
- 0 ≤ `base`, `amp`, `burst_h` ≤ 10; −1 ≤ `drift`, `d_base`, `d_drift`, `d_amp` ≤ 1 (g/s for drifts, g otherwise); 0 ≤ `phase`, `d_phase` < 1;
- `period_s` > 0; `burst_period_s` > 0 when `burst_h` > 0;
- base_i and amp_i of every slot lie in 0..10.

No rule requires the game to end: game length emerges from the parameters, thresholds, tempo and interventions; `drift` = 0 with peaks under the death threshold gives a game as long as the safety cap allows (BR-013). The output clamp keeps every frame finite and within 0..10 g whatever the drift.

### BR-004: Organic deaths only

A pattern player dies only through the coordinator's normal detection (`services/game_coordinator/games/base.py` `_process_controller_state`). For a pattern controller the controller manager refuses `SimulateMovement` and `SimulateDeath` (FAILED_PRECONDITION) (the scripted `SetAutoGameEnd` kill that skipped it was removed in #1623); the shadow runner sends no movement or kill commands at all: it only runs pattern games, for experiments and for the one-shot runner (`AGENT_SHADOW_GAME`, which refuses to run without an archetype). The mock adapter's random resting motion and the scripted mock RPCs remain only for mock controllers outside experiments: manual and development mocks, the lobby and integration tests, and the demo driver until #1314.

### BR-005: Death predictability

For a given archetype, flag values and pinned stream rate, the signal of every slot is exactly reproducible, and the EMA is updated once per delivered frame, so the frame at which a slot's smoothed signal crosses a constant threshold is deterministic. The effective threshold still moves with the music tempo, and grace windows and shields are timed by the wall clock (`services/game_coordinator/games/base.py` `effective_grace_until`, `_compute_effective_thresholds`); so a death frame is exactly reproducible only when the tempo, countdown and grace timeline also repeats (one game at a time, 0 frame overruns); in practice the live-start frame varies by a few frames (BR-001), so a death moves by a few frames too while the order of deaths stays the same when the deaths are seconds apart. Coordinator wall-clock timing is unchanged.

### BR-006: Slots, seeds and pairs

Slot i is the i-th serial returned by the reservation (roster order), never the serial itself, because mock serials are never reused (`services/controller_manager/multiplexer/mock_adapter.py` `_next_serial`). Pair p of an experiment uses archetype p of the pinned list and the pair seed from `pairSeed(experiment_id, p)` (`services/agent/experiment/registry.go`), so both arms receive identical inputs and an identical game RNG; no jitter is added (C-020). An experiment spawns at most one pair per archetype. A one-shot shadow game uses `SHADOW_GAME_SEED` when set, otherwise the FNV-1a/64 of the archetype name.

### BR-007: Seeded rules chaos

In a pattern game the rules engine uses one chaos RNG per game, a PCG seeded with FNV-1a/64 of (`rng_seed`, `agent.rules`), instead of the time-seeded RNG (`services/agent/decision/rules.go` `newObjectiveRules`). The draws replay in order; the decisions replay when the evaluations happen at the same game moments, which still depends on OTLP ingest timing (measured by NFR-042). If the engine drew chaos rolls before the game was registered as a pattern game (and so before it could be seeded), the game is non-exact with reason `unseeded_draws`. Only pattern games are seeded: every other game keeps the time-seeded RNG, so the rules path and its golden (`services/agent/decision/testdata/rules_path_golden.json`) stay unchanged.

### BR-008: Exact replay

A pattern game is exact only if `decision.backend` was `rules` at every decision of the game, its stream had 0 frame overruns, no other game was live when it started, at any once-per-second check while it ran, or when it ended, the kill switch did not end it, its chaos rolls were all seeded, and its flag digest was available (BR-011). A game counts as live when its telemetry partition reports `game_active` and was updated within the last 10 s; a stale partition (no fresh data, cf. #1020) is ignored. Otherwise the game is non-exact with the reasons `remote_backend`, `frame_overrun`, `concurrent_game`, `kill_switch`, `unseeded_draws`, `flag_digest_unavailable`. A `timeout` outcome alone does not make a game non-exact. The remote backends stay selectable in pattern games; they only exclude the game from exact replays. Non-exact games still count as cohort samples; only exact games enter replay comparisons.

### BR-009: Archetype identity

An archetype is identified by its variant name plus its parameter digest: the SHA-256 (first 16 lowercase hex digits) of the canonical JSON of its parameter object (keys sorted, no whitespace). The flag file's git history versions the variants (C-019); the digest on the trace proves which parameters drove a game even if the variant was edited later.

### BR-010: One shadow game at a time

Every shadow experiment game is a pattern game, and the experiment registry runs them at an effective concurrency of 1 whatever `experiment_shadow_effective_concurrency` says: it spawns a game only when no shadow game is in flight, so the arms of a pair run one after the other and stay exact (BR-008). The cost is throughput: an experiment with P archetypes needs 2·P sequential games (for example 12 games of 20 s to 300 s each for the default selection of 6 archetypes), and several live experiments share the single slot: the registry spawns one arm at a time, taking the experiments in turn.

### BR-011: Flag digest

A pattern game is deterministic only for given flag values. When the agent spawns a pattern arm it computes `pattern.flag_digest`: the SHA-256 (lowercase hex) of the canonical JSON (keys sorted, no whitespace) of the RESOLVED values of the flags that shape a pattern game, evaluated through flagd's OFREP bulk endpoint with the arm's evaluation context (`game_kind=shadow`, `experiment_id`, `arm`; the one-shot runner uses `game_kind=shadow` only). Covered keys, as `<flag set>/<key>`:

- `game/`: `sensitivity`, `thresholds`, `tempo_schedule_mode`, `windows`, `death_grace_period_seconds`, `invincibility_seconds`, `countdown_phase_duration_ms`, `winner_rainbow_duration_ms`, `shadow_policy`, and every key starting with `shield.` (since #2096: the activation mode and the hold values shape a game whose archetype presses the trigger, BR-018; this changed the digest of every pattern game, so a replay recorded before that change is not comparable with one recorded after it);
- `agent/`: `enabled`, `interventions_enabled`, `interventions_allowed`, `objectives`, `perception.ema_weight`, `decision.backend`, `experiment.max_game_seconds`, and every key starting with `policy.` or `fitness.`;
- `interventions/`: every key (the intervention state the game starts with).

The archetype parameters are covered by `pattern.params_digest` (BR-009). Unrelated edits of the flag files (another experiment's targeting, other modes' settings) do not change the digest. When flagd cannot be reached the digest is `unavailable` and the game is non-exact with reason `flag_digest_unavailable` (BR-008; only the exact `unavailable` value, an absent digest is not marked). A replay is comparable only when both games carry the same, available digest; a differing digest is reported as the first difference (A11).

### BR-012: Precedence of motion sources

For a pattern controller the delivered acceleration comes from, in order: an active `SimulateDeath` latch (#926) for its remaining delivered frames, then the pattern intensity_i(k / r). Through the API the latch is unreachable, because the controller manager refuses `SimulateDeath` for a pattern controller (BR-004) and creates every pattern controller fresh, without a latch; the order matters only for a latch set directly on the adapter, which installing a pattern does not clear. A `SimulateMovement` hold never applies to a pattern controller (the controller manager refuses it, BR-004, and the pattern wins over a hold set directly on the adapter). The frame index k advances on every delivered frame of the owning stream, including one that carries the latch, and the signal hash covers the delivered magnitudes.

### BR-013: Safety cap and timeout outcome

The only bound on a pattern game is the safety cap `experiment.max_game_seconds` (default 300 s, 30..3600), read with the archetypes in the experiment's first allocation pass and pinned for the experiment (the one-shot runner reads it at its spawn). A value outside 30..3600 falls back to 300 s with a WARN log and a note on the `pattern_pinned` journal event. At the cap the shadow runner force-ends the game; the outcome is `timeout`. A timeout is a meaningful result (maintainer decision on #1258: the game may simply run too long, and the experiment failed, or succeeded by lasting as long as possible):

- The game is a valid sample. Its fitness is scored like any game's from the state at the cap (duration = the cap, the eliminations and survivors so far), so the experiment's objective decides whether reaching the cap is good or bad: `endurance` (progress = duration / `fitness.endurance.min_session_seconds`, clamped to 1) rewards it, `accelerate` (progress falls to 0 one target past `fitness.accelerate.target_session_seconds`) penalises it. Both terms saturate, so two timed-out arms give a near-zero difference; such a pair still counts.
- The sample is right-censored (the true length is at least the cap): the `pattern_game_ended` journal event carries `outcome=timeout` and `censored=true`. A game the agent's own `end_game` ended (reason `agent_intervention`, A14) is right-censored the same way, with `outcome=agent_ended` and `censored=true`: its fitness is scored from the state at the end and it counts in the verdict.
- The experiment counts timeouts per arm and reports the count and rate per arm in the journal and in its conclusion (the denominator is the arm's pattern games that ended with a sample: `winner`, `tie`, `timeout` or `agent_ended`; aborted and errored games are released and rerun, so they are not counted), and says when one arm timed out clearly more often (a rate difference of at least 0.2 with at least 2 pattern games per arm): that difference is itself a result. It counts `agent_ended` games separately, not as timeouts, and reports their count and rate per arm after the timeouts when at least one game ended that way: an agent end is a treatment decision, not the cap, so it does not enter the timeout rate or its comparison.
- The elimination order lists the players who died so far and the winner slot is −1; the game stays exact unless another BR-008 reason applies, and its pair is not run again.

### BR-014: Elimination order

The elimination order is the order of the coordinator's `player_death` events for the game (JoustFFA publishes one per death with the player's serial), mapped to slots; the winner slot is the slot named by the `game_winner` event, and a `game_tie` leaves the winner slot at −1 (the players who died in the tie are in the order). Both come from the event stream the shadow runner already reads. Only when the stream carried no death events (a dropped stream) does the agent fall back to the delivered-frame counts: among the slots other than the winner, the slot with the fewest delivered frames died first, and without a winner every slot within one second (r frames) of the highest count is a survivor. Survivors are not part of the order. Ties break by slot index.

### BR-015: Pair completion and restart

An archetype counts as used only by pairs whose arms both ended with a sample (a winner, a tie, the safety cap, or the agent's own `end_game` with reason `agent_intervention`, A14). An arm whose spawn fails (backpressure, a block by a real game, an error) uses up nothing: the arm is reserved again on a later tick. An arm released without a sample for any other reason (error, a force-end the agent did not request) makes its whole pair run again, both arms, at most 3 times per pair; after the third rerun the archetype is skipped and the experiment notes it in the journal (`pattern_pair_rerun`, `pattern_archetype_skipped`). A preemption by a real game (`preempted_by_real_game`, A8) also makes the pair run again, but that rerun does not use up the 3-rerun budget: it is journaled as `pattern_pair_rerun_preempted`. As a safety valve against an experiment that real games preempt again and again, each pair has a separate budget of 10 preemption reruns; once it is used up, a further preemption counts against the 3-rerun budget like any other release, so a pair runs at most 1 + 10 + 3 times. The kill switch's `pattern_kill_switch` ends the experiment itself (A12): the experiment is aborted before the game's release arrives, so nothing runs again and no rerun is counted. A stale end (the game's `game_active` series went silent, UC-041 A4) is a failure of the agent's telemetry, not of the game, so it is treated like a preemption: the pair runs again without using up the 3-rerun budget, journaled as `pattern_pair_rerun_stale`, with its own safety valve of 10 stale reruns per pair, after which a further stale end counts against the 3-rerun budget (a pair runs at most 1 + 10 + 10 + 3 times). A pattern experiment that has used or skipped every archetype and has no game in flight concludes in the next allocation pass (A6). When the agent restarts, a rehydrated pattern experiment restores its pin (names, parameters, digests, cap) from its `pattern_pinned` journal event, verifies the digests, restores the rerun counts (budget, preemption and stale) from the journal notes, and resumes at the first pair that has not ended; if the pin cannot be restored (no `pattern_pinned` event, or invalid parameters or digests), the experiment is discarded with reason `pattern_pin_lost`.

### BR-016: Terminal outcome classification

The shadow runner classifies a pattern game from the first terminal event on its stream (`game_ended`, `game_force_ended`, `game_error`) and the outcome JoustFFA freezes into `game_ended` when its game loop ends: `outcome` = `winner`, `tie` or `force_ended`, and for `force_ended` the `reason` (UC-020 BR-003, #1328; telemetry.md §5). JoustFFA publishes `game_ended` from the game thread before the coordinator publishes `game_force_ended`, which comes only after the coordinator has joined the game thread (up to 2 s). So for a force-ended game, `game_ended` usually arrives first. The rules, in order:

- **Kill switch.** After the runner force-ended the game for the kill switch (reason `pattern_kill_switch`, A12), any terminal event is `aborted`, whatever reason it names. The game gives no fitness sample; its experiment is already aborted, so no rerun follows (BR-015).
- **The agent's own `end_game`.** A `game_ended` with `outcome=force_ended`, or a `game_force_ended`, with reason `agent_intervention` is `agent_ended`: a right-censored sample (A14, BR-013), whether or not the runner had also requested a force-end at the cap.
- **Force-end the agent did not request.** A `game_ended` with `outcome=force_ended`, or a `game_force_ended`, when the runner did not force-end the game itself, or when the event names a reason other than the runner's own `shadow_game_timeout` / `pattern_kill_switch`, is `aborted`. The game is released without a fitness sample and its pair runs again (BR-015). With reason `preempted_by_real_game` (A8) the runner reports the release as a preemption, which carries that reason to the experiment so the rerun does not use up the 3-rerun budget; any other foreign reason (for example an operator's force-end) counts against it.
- **Force-end the agent requested at the cap.** After the runner force-ended the game at the safety cap (reason `shadow_game_timeout`), any terminal event without a foreign reason gives `timeout` (BR-013).
- **Error.** `game_error` is `error` (A9).
- **Natural end.** A `game_ended` with any other `outcome` (`winner`, `tie`, or the base `completed`) is a game that ended on its own and is a sample, even when a `game_force_ended` follows: the outcome was frozen before the force-end, so a preemption during the winner celebration does not change it. The record's outcome is `winner`, or `tie` after a `game_tie` (BR-014).
- **No `outcome` field.** A `game_ended` without `outcome` comes from a coordinator older than #1328. The runner waits up to 3 s for a `game_force_ended` (the coordinator's 2 s thread join plus a margin). If one arrives, it is classified by the rules above. If not, or if the stream ends first, the game ended on its own. A current JoustFFA always sends `outcome`, so its natural games are not delayed.

A game is force-ended once (UC-027 BR-003, #1827): when two ends race (the runner's own force end, an operator's ForceEndGame, `end_game`, a preemption), the one that started first sets the reason of both `game_ended` and `game_force_ended`, so the runner may see another caller's reason for a force end it requested and classifies it by the rules above (A8).

Every mode puts `outcome` into `game_ended` (`winner` / `tie` / `force_ended` / `completed`, plus `reason` on a force-end; UC-020 BR-003). Pattern games are JoustFFA-only (C-021), so that is enough here. A future pattern mode must send `outcome` in its `game_ended`, or it gets only the 3 s fallback.

The experiment folds a sample only for a sample outcome (`completed`, that is `winner` / `tie`, `timeout`, `agent_ended`) (#1405). The agent's telemetry game end ([UC-041](UC-041.md)) carries no outcome, so it never folds a sample on its own: the agent folds the game once both the telemetry end and the runner's classification are in, whichever arrives first, and drops the telemetry end of a game the runner classified otherwise. A telemetry end waits for the classification at most `experiment_completed_grace_seconds`, never less than 18 s (the 3 s fallback above, plus the runner's 10 s cleanup RPC, plus a margin), also when the flag is 0 (`off`); with no classification in that window the game is released without a sample (a counting release, BR-015). A telemetry end that arrives while the agent shuts down is neither folded nor kept. A stale end (UC-041 A4) still releases at once; when the runner already reported a preemption, that release keeps the preemption reason (BR-015).

### BR-017: Pattern games are silent

A pattern (shadow) game sends no audio RPC ([UC-031](UC-031.md) BR-006): it must not affect the room, and its intensity and thresholds run without a music track.


### BR-018: Simulated trigger policy (#2096)

- An archetype may carry an optional `trigger_policy` object; without it (or with `{"kind": "none"}`) its controllers never press the trigger. The policy is left out of the canonical JSON when it is `none`, so the parameter digest (BR-009) of an archetype without a policy is unchanged. The forms are:
  - `{"kind": "burst"}`: slot i presses while its burst pulse is on, burst_i(k / r) > 0 (BR-002); valid only with `burst_h` > 0.
  - `{"kind": "threshold", "level": L, "reaction_frames": R, "hold_frames": H}` with 0 ≤ L ≤ 10 (g), R a whole number in 0..60 and H a whole number in 2..120: slot i presses on frame k when some frame j with max(0, k − R − H + 1) ≤ j ≤ k − R has intensity_i(j / r) ≥ L. A press therefore lasts at least two delivered frames, so it survives one coalesced frame.
  - Any other kind, an unknown or missing key, or a value outside its bounds fails validation (BR-003). The agent's validator and the controller manager's validator apply the same rules (shared test cases).
- trigger(k) is a pure function of the archetype and k, like the intensity: the trigger follows intensity_i(k / r), not the delivered value, so a death latch (BR-012) does not change it, and k continues across a reconnect (BR-001) without a repeated or skipped press. The controller manager evaluates it per delivered frame of the owning stream next to the motion function and sets `trigger_pressed` in that frame; an observer stream never sees a press.
- The signal hash folds, for an archetype with a policy only, one byte per frame after the value: 1 when the trigger is pressed, else 0 (telemetry.md §9), so the trigger sequence is part of the replay (BR-008, with the same wall-clock caveat as BR-005 for the hold energy drain); the hash of an archetype without a policy is unchanged.
- The agent sets `StartGameConfig.pattern_trigger_policy` when the archetype it installs has a policy (both from the same pinned archetype). A shadow game honours `trigger` and `hold` only then; otherwise it is instant (UC-040 BR-019). A real start ignores the field.
- `burst_holder` ships with `{"kind": "burst"}`. It is not part of the default selection `all` of `experiment.mock_archetypes`, so running experiments do not change; it is selected by name.
- BR-011 covers every `game/` key starting with `shield.`.
