# Use Case: Run Repeatable Pattern-Driven Shadow Games

## Overview

**Use Case ID:** UC-046
**Use Case Name:** Run Repeatable Pattern-Driven Shadow Games
**Primary Actor:** Operator
**Secondary Actors:** Agent
**Goal:** Drive the mock controllers of shadow experiment games with named, deterministic motion functions instead of random noise, so that players die organically, the verdict has variance between pairs, and any game can be replayed from its trace
**Status:** Draft
**Requirements:** FR-100, FR-101, FR-102, FR-103, FR-104, FR-105, FR-106, FR-107, FR-108, FR-109, FR-110, FR-111, NFR-040, NFR-041, NFR-042, NFR-043, NFR-044, C-019, C-020, C-021

## Preconditions

- `enabled` and `experiments_enabled` are on and an experiment is declared (UC-043).
- The controller manager runs with the mock adapter.
- At least `verdict_min_pairs` (default 5) validated parameter sets are merged under `services/controller_manager/patterns/`.
- The shadow game mode (`SHADOW_GAME_MODE`) is `JoustFFA`, the only mode pattern games support in v1 (C-021).
- `SimulateMovement` keeps the value it sets (fixed separately by #1279, PR #1296).

## Main Success Scenario

1. Operator sets the `agent.json` flag `experiment.mock_pattern_set` to a comma-separated list of parameter set names, for example `ladder_v1,burst_v1,mixed_v1,fade_v1,calm_v1`.
2. When the experiment spawns its first shadow game, the agent reads the flag, resolves every listed set with the controller manager's mock API, and pins the list (names, versions, slot counts) in the experiment journal.
3. For pair p the agent picks set p of the pinned list and spawns both arms: for each arm it reserves one mock controller per slot of the set with the set installed, and starts the game with the pair's shared `rng_seed`.
4. The controller manager validates the set, binds slot i to the i-th reserved controller, pins the arm's gameplay stream to the set's `stream_rate_hz`, and records the installation.
5. For every delivered frame k of a pattern controller, the controller manager reports the acceleration (0, 0, f_i(k / rate)) in g, with gyro 0.
6. The game coordinator runs its normal death detection (EMA per delivered frame, sensitivity and tempo thresholds, grace); a player dies when its smoothed signal crosses the death threshold.
7. The agent observes the game and decides as usual; the rules engine draws its chaos choices from an RNG seeded by the game's `rng_seed`.
8. The game ends with a winner; on removal of each controller the controller manager records its frame count and signal fingerprint, and the agent records the elimination order by slot, the replay classification (exact or non-exact) and concludes the fitness sample as in UC-043.
9. Operator replays a recorded game: runs one shadow game with the set id and seed read from that game's trace (the one-shot runner with `SHADOW_GAME_PATTERN_SET` and `SHADOW_GAME_SEED`), or runs `scripts/pattern-replay-check.sh <set id> [seed]`, which runs that set twice.
10. The system compares the replay with the recorded game and reports identical signal fingerprints per slot, an identical elimination order and an identical sequence of rules decisions.

## Alternative Flows

### A1: Pattern selection off

**Trigger:** `experiment.mock_pattern_set` is `none` (step 2)
**Flow:**

1. The agent spawns shadow games with today's random noise and scripted kills (UC-043).
2. Use case ends.

### A2: Unknown or invalid set

**Trigger:** A listed set name has no file, or the set fails a validation rule of BR-003 (step 2)
**Flow:**

1. The controller manager answers with the failed rules; the agent spawns no game for the experiment.
2. The agent journals the experiment as discarded with reason `pattern_set_invalid` and the failed rules.
3. Use case ends.

### A3: Set never ends a game

**Trigger:** Fewer than N−1 slots of a set reach the terminal level before its `max_game_seconds` (BR-003 V8) (step 2)
**Flow:**

1. The set is rejected and the experiment discarded as in A2; in CI the pull request that adds the set already fails.
2. Use case ends.

### A4: Selection too small

**Trigger:** The pinned list holds fewer distinct sets than `verdict_min_pairs`, or names a set twice (step 2)
**Flow:**

1. The agent spawns no game and journals the experiment as discarded with reason `pattern_selection_too_small`.
2. Use case ends.

### A5: Flag changes during the experiment

**Trigger:** Operator changes `experiment.mock_pattern_set` after the list was pinned (step 3)
**Flow:**

1. The experiment keeps its pinned list; the new value applies to experiments that have not spawned yet.
2. Use case continues at step 3.

### A6: Every set used

**Trigger:** The experiment has spawned one pair per set of its pinned list (step 3)
**Flow:**

1. The agent spawns no further pairs for this experiment; the verdict uses the pairs it has (UC-043 step 5).
2. Use case continues at step 8.

### A7: Remote decision backend selected

**Trigger:** `decision.backend` is `jev`, `claude` or `openai` at any decision of the game (step 7)
**Flow:**

1. The agent decides with that backend as usual and marks the game non-exact with reason `remote_backend`.
2. The game still counts as a cohort sample but is excluded from replay comparisons.
3. Use case continues at step 8.

### A8: Another game runs at the same time

**Trigger:** A real game, or a shadow game the agent's experiment registry did not spawn, is live while the pattern game runs (step 6). The registry itself never runs a pattern game next to another of its shadow games (BR-010).
**Flow:**

1. With `shadow_policy=block` no new pattern game starts while a real game runs, and a real start preempts live pattern games (UC-043 A2); a preempted game is released without a fitness sample.
2. Otherwise the pattern game runs and is marked non-exact with reason `concurrent_game`; its input signal stays exact (NFR-040).
3. Use case continues at step 8.

### A9: Game does not end in time

**Trigger:** Interventions raised the death threshold above the terminal level, or revived players, and no winner is declared within `max_game_seconds` + 15 s (step 6)
**Flow:**

1. The agent force-ends the game; the experiment releases it without a fitness sample and marks it non-exact with reason `no_termination`.
2. Use case continues at step 3.

### A10: Stream frame overrun

**Trigger:** The controller manager falls behind its frame schedule for a pattern stream (step 5)
**Flow:**

1. The controller manager counts the overrun for every controller of that stream; the delivered signal stays identical because it is indexed by frame, not by wall time.
2. The game is marked non-exact with reason `frame_overrun`.
3. Use case continues at step 6.

### A11: Replay differs or is not comparable

**Trigger:** A slot fingerprint, the elimination order or the decision sequence differs, or the recorded game is non-exact (step 10)
**Flow:**

1. The system reports the first difference (slot, elimination position or decision index) or the non-exact reasons of the recorded game.
2. Use case ends.

### A12: Kill switch

**Trigger:** `enabled` or `experiments_enabled` turns off (step 3)
**Flow:**

1. The agent aborts the experiment as in UC-043 A1; reserved pattern controllers are removed.
2. A pattern game still in flight is force-ended, released without a fitness sample and marked non-exact with reason `kill_switch`.
3. Use case ends.

### A13: Unsupported game mode

**Trigger:** The shadow game mode is not `JoustFFA` while `experiment.mock_pattern_set` selects sets (step 2)
**Flow:**

1. The agent spawns no game and journals the experiment as discarded with reason `pattern_mode_unsupported` (C-021); the one-shot runner refuses the run with the same reason.
2. Use case ends.

## Postconditions

### Success Postconditions

- Every pattern game of the experiment ran on a named, pinned parameter set, and its set name, version, seed, stream rate, slot mapping, signal fingerprints, elimination order and replay classification are on its trace and in the experiment journal.
- An exact game replays with identical per-slot signal fingerprints and elimination order.

### Failure Postconditions

- An invalid or too-small selection spawns no pattern game, and the experiment is journaled as discarded with its reason.
- Real games never see a pattern controller (reserved controllers are hidden from the lobby).

## Business Rules

### BR-001: Game time

Game time is t = k / r, where k is the index of the frame delivered for that controller on its gameplay stream (k = 0 for the first delivered frame) and r is the set's pinned `stream_rate_hz`. t does not depend on wall-clock time: when the host is loaded, frames arrive later, but frame k always carries f(k / r). The controller manager evaluates f only at frame times, so f needs no value between frames.

### BR-002: Function family and parameters

Each slot of a set holds an ordered list of segments. A segment starts at `from_s` (seconds of game time; the first segment starts at 0, starts strictly increase) and lasts until the next segment starts; the last segment lasts forever. Inside a segment, τ = t − `from_s` is the local time. A segment holds exactly one function:

- `constant(level)`: f = level.
- `ramp(start, slope)`: f = start + slope · τ.
- `sine(mean, amplitude, period_s, phase)`: f = mean + amplitude · sin(2π · (τ / period_s + phase)), with `phase` in cycles, 0 ≤ phase < 1.

A step sequence is a list of `constant` segments; piecewise-linear keyframes are a list of `ramp` segments. Units: `level`, `start`, `mean`, `amplitude` in g (1 g = 9.81 m/s²); `slope` in g/s; `from_s`, `period_s` in seconds of game time. f is the magnitude of the reported acceleration; the vector is (0, 0, f) along the gravity axis, like today's noise (`services/controller_manager/multiplexer/mock_adapter.py:160-163`), and the coordinator uses only the magnitude for deaths (`services/game_coordinator/games/base.py:1500-1513`). A set file holds `name`, `version`, `description`, `stream_rate_hz`, `max_game_seconds` and `slots` (one list of segments per slot, in slot order). Its id is `<name>_v<version>`, which is also its file name and the flag value.

### BR-003: Validation rules

The controller manager validates a set when it loads it and when it installs it; CI validates every set file on each pull request. A set is valid only if all rules hold (N = number of slots, T = `max_game_seconds`, r = `stream_rate_hz`, K = ⌈T · r⌉):

- V1 Identity: `name` matches `[a-z][a-z0-9_]*`, `version` is an integer ≥ 1, the file name is `<name>_v<version>.json`, `description` holds 1 to 500 characters.
- V2 Slots: 2 ≤ N ≤ 8; every slot has at least one segment.
- V3 Rate: r is 15, 30 or 60 (the variants of `game_loop.update_frequency_hz`, NFR-003).
- V4 Duration: 10 ≤ T ≤ 60 seconds of game time, so T + 15 s stays below the runner's 90 s await (`services/agent/gamerunner/runner.go:120`).
- V5 Finite parameters: every number is finite (no NaN, no infinity); `period_s` > 0; segment starts strictly increase from 0.
- V6 Bounds: 0.0 ≤ f(k / r) ≤ 10.0 g for every slot and every k = 0..K (the mock's death input is about 9.95 g, `services/controller_manager/mock_control_service.py:144-149`). The check is exact because f is used only at frame times.
- V7 Idle prelude: f = 1.0 g at every frame with t < 4.0 s, so the countdown (3 × `countdown_phase_duration_ms`, at most 3 s), the EMA warmup and the 0.3 s start grace (`services/game_coordinator/games/base.py:1208-1236,1415`) see a resting player whatever their frame offset.
- V8 Termination: at least N−1 slots are terminating. A slot is terminating when some frame k_term ≤ K − r (1 s before T) exists with f(k / r) ≥ 4.0 g for every k from k_term to K. 4.0 g is above the highest death threshold of every variant of the `thresholds` flag (3.5 g, `services/flagd/game.json` `fast_max`; the mock's own analysis, `services/controller_manager/mock_control_service.py:31-64`); CI also checks it against every `thresholds` variant.
- V9 Separated death windows: at the default calibration (sensitivity 2, `perception.ema_weight` 4, default `thresholds`, no interventions), a slot's death window is [first frame whose EMA exceeds 1.8 g (slow table), first frame whose EMA exceeds 2.8 g (high-tempo table)], with the EMA primed at f(0) and updated as `services/game_coordinator/games/base.py:1516-1540` does; a window that never reaches 2.8 g ends at K. Sorted by start, every window ends at least 0.5 s (0.5 · r frames) before the next one starts.

### BR-004: Organic deaths only

A pattern player dies only through the coordinator's normal detection (`services/game_coordinator/games/base.py:1779-1854`). For a pattern controller the controller manager refuses `SimulateMovement` and `SimulateDeath`, and `SetAutoGameEnd` is never used; the shadow runner sends no movement or kill commands to a pattern game (it does today, `services/agent/gamerunner/operations.go:322-349`).

### BR-005: Death predictability

For a given parameter set, flag values and pinned stream rate, the signal of every slot is exactly reproducible, and the EMA is updated once per delivered frame, so the frame at which a slot's smoothed signal crosses a constant threshold is deterministic. The effective threshold still moves with the music tempo, and grace windows and shields are timed by the wall clock (`services/game_coordinator/games/base.py:1415,1913-1946`); so a death frame is deterministic within the slot's death window, and exactly reproducible when the tempo and grace timeline also repeats (one game at a time, 0 frame overruns). V9 keeps the windows apart, so the elimination order at the default calibration does not depend on these residuals. Other flag values (for example the sensitivity under test) give another order, deterministic for those values.

### BR-006: Slots, seeds and pairs

Slot i is the i-th serial returned by the reservation (roster order), never the serial itself, because mock serials are never reused (`services/controller_manager/multiplexer/mock_adapter.py:96,287-290`). Pair p of an experiment uses set p of the pinned list and the pair seed from `pairSeed(experiment_id, p)` (`services/agent/experiment/registry.go:934-944`), so both arms receive identical inputs and an identical game RNG; no jitter is added (C-020). An experiment spawns at most one pair per set. A one-shot shadow game uses `SHADOW_GAME_SEED` when set, otherwise the FNV-1a/64 of the set id.

### BR-007: Seeded rules chaos

In a pattern game the rules engine uses one chaos RNG per game, a PCG seeded with FNV-1a/64 of (`rng_seed`, `agent.rules`), instead of the shared time-seeded RNG (`services/agent/decision/rules.go:69-72`). The draws replay in order; the decisions replay when the evaluations happen at the same game moments, which still depends on OTLP ingest timing (measured by NFR-042). Only pattern games are seeded: every other game, including noise experiments with a non-zero `rng_seed`, keeps the time-seeded RNG, so the rules path and its golden (`services/agent/decision/testdata/rules_path_golden.json`) stay unchanged.

### BR-008: Exact replay

A pattern game is exact only if `decision.backend` was `rules` at every decision of the game, its streams had 0 frame overruns, no other game was live at any moment of it, it ended with a winner (not force-ended) and the kill switch did not end it. Otherwise it is non-exact with the reasons `remote_backend`, `frame_overrun`, `concurrent_game`, `no_termination`, `kill_switch`. The remote backends stay selectable in pattern games (the agent acts as usual); they only exclude the game from exact replays. Non-exact games still count as cohort samples; only exact games enter replay comparisons.

### BR-009: Immutable sets

A set file merged to `main` is never edited or deleted (C-019); a change is a new name or version. The agent pins sets by id and version, so a trace always names the exact functions that drove the game.

### BR-010: One pattern game at a time

The experiment registry runs pattern experiments at an effective concurrency of 1 whatever `experiment_shadow_effective_concurrency` says: it spawns an arm of a pattern experiment only when none of its shadow games is in flight, and spawns no other shadow game while a pattern game is in flight. The arms of a pair therefore run one after the other, which keeps them exact (BR-008).

### BR-011: Flag digest

A pattern game is deterministic only for given flag values. When the agent spawns a pattern game it computes `pattern.flag_digest`, the SHA-256 (lowercase hex) of the bytes of `agent.json` followed by the bytes of `game.json` as the agent reads them at that moment (its mounted flag files), and records it with the game. A replay is comparable only when both games carry the same digest; a differing digest is reported as the first difference (A11).

### BR-012: Precedence of motion sources

For a pattern controller the delivered acceleration comes from, in order: an active `SimulateDeath` latch (#926) for its remaining delivered frames, then the pattern f(k / r). A `SimulateMovement` hold never applies to a pattern controller (the controller manager refuses it, BR-004, and the pattern wins over a hold set directly on the adapter). The frame index k advances on every delivered frame, including one that carries the latch, and the signal hash covers the delivered values.
