# Use Case: Run Repeatable Pattern-Driven Shadow Games

## Overview

**Use Case ID:** UC-046
**Use Case Name:** Run Repeatable Pattern-Driven Shadow Games
**Primary Actor:** Operator
**Secondary Actors:** Agent
**Goal:** Drive the mock controllers of shadow experiment games with continuous, parametric motion functions instead of random noise, so that players die organically, game length emerges from the parameters, thresholds, tempo and interventions, the verdict has variance between pairs, and any game can be replayed from its trace
**Status:** Draft
**Requirements:** FR-100, FR-101, FR-102, FR-103, FR-104, FR-105, FR-106, FR-107, FR-108, FR-109, FR-110, FR-111, NFR-040, NFR-041, NFR-042, NFR-043, NFR-044, C-019, C-020, C-021

## Preconditions

- `enabled` and `experiments_enabled` are on and an experiment is declared (UC-043).
- The controller manager runs with the mock adapter.
- `agent.json` defines at least `verdict_min_pairs` (default 5) archetypes as object variants of `experiment.mock_archetype`.
- The shadow game mode (`SHADOW_GAME_MODE`) is `JoustFFA`, the only mode pattern games support in v1 (C-021).
- `SimulateMovement` keeps the value it sets (#1279, PR #1296).

## Main Success Scenario

1. Operator sets the `agent.json` flag `experiment.mock_archetypes` to a comma-separated list of archetype names, for example `calm_long,slow_cascade,jittery_novices,close_race,late_burst`.
2. When the experiment spawns its first shadow game, the agent reads `experiment.mock_archetypes` and `experiment.max_game_seconds`, resolves every listed archetype to its parameter object (the variant of `experiment.mock_archetype` with that name), validates it, and pins the list (names, parameters, parameter digests) and the safety cap in the experiment journal.
3. For pair p the agent picks archetype p of the pinned list and spawns both arms one after the other: for each arm it reserves one mock controller per player of the archetype, passing the archetype name and parameters, and starts the game with the pair's shared `rng_seed`.
4. The controller manager validates the parameters, binds slot i to the i-th reserved controller, pins the arm's gameplay stream to the archetype's `stream_rate_hz`, and records the installation.
5. For every delivered frame k of a pattern controller, the controller manager reports the acceleration (0, 0, intensity_i(k / r)) in g, with gyro 0.
6. The game coordinator runs its normal death detection (EMA per delivered frame, sensitivity and tempo thresholds, grace); a player dies when its smoothed signal crosses the death threshold.
7. The agent observes the game and decides as usual; the rules engine draws its chaos choices from an RNG seeded by the game's `rng_seed`.
8. The game ends with a winner; on removal of each controller the controller manager records its frame count, signal fingerprint and per-second checkpoint fingerprints, and the agent records the elimination order by slot, the outcome, the replay classification (exact or non-exact) and concludes the fitness sample as in UC-043.
9. Operator replays a recorded game: runs one shadow game with the archetype and seed read from that game's trace (the one-shot runner with `SHADOW_GAME_ARCHETYPE` and `SHADOW_GAME_SEED`), or runs `scripts/pattern-replay-check.sh <archetype> [seed]`, which runs that archetype twice.
10. The system compares the replay with the recorded game and reports identical checkpoint fingerprints per slot on their common prefix, an identical elimination order and an identical sequence of rules decisions.

## Alternative Flows

### A1: Pattern selection off

**Trigger:** `experiment.mock_archetypes` is `none` (step 2)
**Flow:**

1. The agent spawns shadow games with today's random noise and scripted kills (UC-043).
2. Use case ends.

### A2: Unknown or invalid archetype

**Trigger:** A listed name is not a variant of `experiment.mock_archetype`, or its parameters fail a validation rule of BR-003 (step 2)
**Flow:**

1. The agent spawns no game for the experiment and journals it as discarded with reason `pattern_archetype_invalid` and the failed rules.
2. Use case ends.

### A3: Safety cap reached

**Trigger:** No winner is declared within the pinned `experiment.max_game_seconds` (default 300 s) of wall time after the game started (step 6)
**Flow:**

1. The agent force-ends the game; its outcome is `timeout`. The elimination order holds the players who died so far; there is no winner slot.
2. The game still yields its fitness sample (BR-013) and is not made non-exact by the timeout alone.
3. Use case continues at step 8.

### A4: Selection too small

**Trigger:** The pinned list holds fewer distinct archetypes than `verdict_min_pairs`, or names one twice (step 2)
**Flow:**

1. The agent spawns no game and journals the experiment as discarded with reason `pattern_selection_too_small`.
2. Use case ends.

### A5: Flag changes during the experiment

**Trigger:** Operator changes `experiment.mock_archetypes`, an archetype variant or `experiment.max_game_seconds` after the experiment pinned them (step 3)
**Flow:**

1. The experiment keeps its pinned archetypes, parameters and cap; the new values apply to experiments that have not spawned yet.
2. Use case continues at step 3.

### A6: Every archetype used

**Trigger:** The experiment has spawned one pair per archetype of its pinned list (step 3)
**Flow:**

1. The agent spawns no further pairs for this experiment; when its last game has ended it concludes the experiment with the verdict of the pairs it has (UC-043 step 5).
2. Use case continues at step 8.

### A7: Remote decision backend selected

**Trigger:** `decision.backend` is `jev`, `claude` or `openai` at any decision of the game (step 7)
**Flow:**

1. The agent decides with that backend as usual and marks the game non-exact with reason `remote_backend`.
2. The game still counts as a cohort sample but is excluded from replay comparisons.
3. Use case continues at step 8.

### A8: Another game runs at the same time

**Trigger:** A real game, or a shadow game the agent's experiment registry did not spawn, is live while the pattern game runs (step 6). The registry itself never runs a pattern game next to another of its shadow games (BR-010).
**Flow:**

1. With `shadow_policy=block` no new pattern game starts while a real game runs, and a real start preempts live pattern games (UC-043 A2); a preempted game is released without a fitness sample.
2. Otherwise the pattern game runs and is marked non-exact with reason `concurrent_game`; its input signal stays exact (NFR-040).
3. Use case continues at step 8.

### A9: Game ends without a usable result

**Trigger:** The game ends in `game_error`, or the stream to the coordinator fails, before a winner or the safety cap (step 6)
**Flow:**

1. The experiment releases the game without a fitness sample (UC-043); its replay record carries the outcome `error`.
2. Use case continues at step 3.

### A10: Stream frame overrun

**Trigger:** The controller manager falls behind its frame schedule for a pattern stream (step 5)
**Flow:**

1. The controller manager counts the overrun for every controller of that stream; the delivered signal stays identical because it is indexed by frame, not by wall time.
2. The game is marked non-exact with reason `frame_overrun`.
3. Use case continues at step 6.

### A11: Replay differs or is not comparable

**Trigger:** A slot's checkpoint hashes differ on their common prefix, the elimination order or the decision sequence differs, the parameter or flag digests differ, or the recorded game is non-exact (step 10)
**Flow:**

1. The system reports the first difference (slot and second, elimination position, decision index or digest) or the non-exact reasons of the recorded game.
2. Use case ends.

### A12: Kill switch

**Trigger:** `enabled` or `experiments_enabled` turns off (step 3)
**Flow:**

1. The agent aborts the experiment as in UC-043 A1; reserved pattern controllers are removed.
2. A pattern game still in flight is force-ended, released without a fitness sample and marked non-exact with reason `kill_switch`.
3. Use case ends.

### A13: Unsupported game mode

**Trigger:** The shadow game mode is not `JoustFFA` while `experiment.mock_archetypes` selects archetypes (step 2)
**Flow:**

1. The agent spawns no game and journals the experiment as discarded with reason `pattern_mode_unsupported` (C-021); the one-shot runner refuses the run with the same reason.
2. Use case ends.

## Postconditions

### Success Postconditions

- Every pattern game of the experiment ran on a named, pinned archetype, and its archetype name, parameter digest, seed, stream rate, slot mapping, signal and checkpoint hashes, outcome, elimination order and replay classification are on its trace and in the experiment journal.
- An exact game replays with identical per-slot checkpoint hashes on their common prefix and an identical elimination order.

### Failure Postconditions

- An invalid or too-small selection spawns no pattern game, and the experiment is journaled as discarded with its reason.
- Real games never see a pattern controller (reserved controllers are hidden from the lobby).

## Business Rules

### BR-001: Game time

Game time is t = k / r, where k is the index of the frame delivered for that controller on its owning gameplay stream (k = 0 for the first delivered frame) and r is the archetype's pinned `stream_rate_hz`. The owning stream is the first gameplay stream whose explicit filter names the controller (the game's stream); a stream without a filter (the dashboard) never advances k, and when the owning stream ends the next explicit stream continues k. t does not depend on wall-clock time: when the host is loaded, frames arrive later, but frame k always carries intensity(k / r). The controller manager evaluates the function only at frame times.

### BR-002: Motion function

Each player i of a pattern game follows

intensity_i(t) = clamp(base_i + drift_i · t + amp_i · sin(2π · (t / period_s + phase_i)) + burst_i(t), 0, 10)

in g. burst_i is a rectangular pulse of height `burst_h` and fixed width 0.2 s (`BURST_WIDTH_S`) that starts every `burst_period_s` seconds: with s = t / `burst_period_s` + phase_i, burst_i(t) = `burst_h` when s ≥ 1 and (s − ⌊s⌋) · `burst_period_s` < 0.2, else 0 (so the first pulse of player i starts at (1 − phase_i) · `burst_period_s`, never at t = 0); `burst_h` = 0 means no bursts. The vector is (0, 0, intensity) along the gravity axis, gyro 0, like today's noise (`services/controller_manager/multiplexer/mock_adapter.py`), and the coordinator uses only the magnitude for deaths (`services/game_coordinator/games/base.py` `_compute_accel_magnitude`).

### BR-003: Archetype and validation

An archetype is one object variant of the `agent.json` flag `experiment.mock_archetype` (flags.md §3.1); its id is the variant name. It holds the players N, `stream_rate_hz` r, the game parameters `base`, `drift`, `amp`, `period_s`, `phase`, `burst_h`, `burst_period_s`, and four per-slot modifiers: player i (slot i, 0..N−1) has base_i = `base` + i · `d_base`, drift_i = `drift` + i · `d_drift`, amp_i = `amp` + i · `d_amp`, phase_i = frac(`phase` + i · `d_phase`). The agent validates it when it pins it and the controller manager when it installs it. It is valid only if:

- every field above is present and a finite number (unknown fields are rejected);
- 2 ≤ N ≤ 8 (integer);
- r is 15, 30 or 60 (the variants of `game_loop.update_frequency_hz`, NFR-003);
- 0 ≤ `base`, `amp`, `burst_h` ≤ 10; −1 ≤ `drift`, `d_base`, `d_drift`, `d_amp` ≤ 1 (g/s for drifts, g otherwise); 0 ≤ `phase`, `d_phase` < 1;
- `period_s` > 0; `burst_period_s` > 0 when `burst_h` > 0;
- base_i and amp_i of every slot lie in 0..10.

No rule requires the game to end: game length emerges from the parameters, thresholds, tempo and interventions; `drift` = 0 with peaks under the death threshold gives a game as long as the safety cap allows (BR-013). The output clamp keeps every frame finite and within 0..10 g whatever the drift.

### BR-004: Organic deaths only

A pattern player dies only through the coordinator's normal detection (`services/game_coordinator/games/base.py` `_process_controller_state`). For a pattern controller the controller manager refuses `SimulateMovement` and `SimulateDeath` (FAILED_PRECONDITION), and `SetAutoGameEnd` never kills it; the shadow runner sends no movement or kill commands to a pattern game.

### BR-005: Death predictability

For a given archetype, flag values and pinned stream rate, the signal of every slot is exactly reproducible, and the EMA is updated once per delivered frame, so the frame at which a slot's smoothed signal crosses a constant threshold is deterministic. The effective threshold still moves with the music tempo, and grace windows and shields are timed by the wall clock (`services/game_coordinator/games/base.py` `effective_grace_until`, `_compute_effective_thresholds`); so a death frame is exactly reproducible when the tempo and grace timeline also repeats (one game at a time, 0 frame overruns). Coordinator wall-clock timing is unchanged.

### BR-006: Slots, seeds and pairs

Slot i is the i-th serial returned by the reservation (roster order), never the serial itself, because mock serials are never reused (`services/controller_manager/multiplexer/mock_adapter.py` `_next_serial`). Pair p of an experiment uses archetype p of the pinned list and the pair seed from `pairSeed(experiment_id, p)` (`services/agent/experiment/registry.go`), so both arms receive identical inputs and an identical game RNG; no jitter is added (C-020). An experiment spawns at most one pair per archetype. A one-shot shadow game uses `SHADOW_GAME_SEED` when set, otherwise the FNV-1a/64 of the archetype name.

### BR-007: Seeded rules chaos

In a pattern game the rules engine uses one chaos RNG per game, a PCG seeded with FNV-1a/64 of (`rng_seed`, `agent.rules`), instead of the time-seeded RNG (`services/agent/decision/rules.go` `newObjectiveRules`). The draws replay in order; the decisions replay when the evaluations happen at the same game moments, which still depends on OTLP ingest timing (measured by NFR-042). Only pattern games are seeded: every other game keeps the time-seeded RNG, so the rules path and its golden (`services/agent/decision/testdata/rules_path_golden.json`) stay unchanged.

### BR-008: Exact replay

A pattern game is exact only if `decision.backend` was `rules` at every decision of the game, its stream had 0 frame overruns, no other game was live at any moment of it, and the kill switch did not end it. Otherwise it is non-exact with the reasons `remote_backend`, `frame_overrun`, `concurrent_game`, `kill_switch`. A `timeout` outcome alone does not make a game non-exact. The remote backends stay selectable in pattern games; they only exclude the game from exact replays. Non-exact games still count as cohort samples; only exact games enter replay comparisons.

### BR-009: Archetype identity

An archetype is identified by its variant name plus its parameter digest: the SHA-256 (first 16 lowercase hex digits) of the canonical JSON of its parameter object (keys sorted, no whitespace). The flag file's git history versions the variants (C-019); the digest on the trace proves which parameters drove a game even if the variant was edited later.

### BR-010: One pattern game at a time

The experiment registry runs pattern experiments at an effective concurrency of 1 whatever `experiment_shadow_effective_concurrency` says: it spawns an arm of a pattern experiment only when no shadow game is in flight, spawns no other shadow game while a pattern game is in flight, and, while a pattern experiment still has archetypes left, spawns no new game for other experiments, so their in-flight games drain and the pattern experiment cannot starve behind them. The arms of a pair therefore run one after the other, which keeps them exact (BR-008).

### BR-011: Flag digest

A pattern game is deterministic only for given flag values. When the agent spawns a pattern game it computes `pattern.flag_digest`, the SHA-256 (lowercase hex) of the bytes of `agent.json` followed by the bytes of `game.json` as the agent reads them at that moment (its mounted flag files), and records it with the game. A replay is comparable only when both games carry the same digest; a differing digest is reported as the first difference (A11).

### BR-012: Precedence of motion sources

For a pattern controller the delivered acceleration comes from, in order: an active `SimulateDeath` latch (#926) for its remaining delivered frames, then the pattern intensity_i(k / r). A `SimulateMovement` hold never applies to a pattern controller (the controller manager refuses it, BR-004, and the pattern wins over a hold set directly on the adapter). The frame index k advances on every delivered frame of the owning stream, including one that carries the latch, and the signal hash covers the delivered magnitudes.

### BR-013: Safety cap and timeout outcome

The only bound on a pattern game is the safety cap `experiment.max_game_seconds` (default 300 s, 30..3600), read with the archetypes at the experiment's first spawn and pinned for the experiment (the one-shot runner reads it at its spawn). At the cap the shadow runner force-ends the game; the outcome is `timeout`. A timeout game is a valid result: its fitness sample counts toward the cohort like a game with a winner, its elimination order lists the players who died so far, its winner slot is −1, and it stays exact unless another BR-008 reason applies.

### BR-014: Elimination order

The elimination order is derived from the replay record: an FFA player stops receiving gameplay frames when the coordinator drops it from the stream's alive filter, so the slot with the fewest delivered frames died first. When the game ended with a winner, the slot with the most frames is the winner and is not part of the order; after a timeout every slot whose frame count is within one second (r frames) of the highest count is a survivor and is not part of the order either. Ties break by slot index.
