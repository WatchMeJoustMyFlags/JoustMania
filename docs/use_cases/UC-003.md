# Use Case: Play with Mock Controllers

## Overview

**Use Case ID:** UC-003
**Use Case Name:** Play with Mock Controllers
**Primary Actor:** Operator
**Goal:** Run and drive the full system without PS Move hardware
**Status:** Tested
**Requirements:** FR-005, FR-006

## Preconditions

- The stack runs with mock controllers (`backend=mock`, e.g. `make up-mock` or `make dry-run`). The controller manager always loads a mock adapter and serves the mock control API on port 50062; `docker-compose.override.yml` publishes that port to the host.

## Main Success Scenario

1. Operator adds mock controllers through the mock control API (AddControllers).
2. System creates controllers with serials `MOCK0000`, `MOCK0001`, ... and connects them (UC-002 from step 3).
3. Operator simulates button presses (SimulateButton) to ready up and start a game (UC-010).
4. Operator simulates movement and deaths (SimulateMovement, SimulateDeath); a simulated movement is held until the operator changes or resets it (BR-002).
5. System plays the game exactly as with hardware, publishing the same events and telemetry.
6. Operator reads LED colours back (GetColor, StreamObservability) to verify feedback.

## Alternative Flows

### A1: Automatic game end (retired)

**Trigger:** None since #1623: `SetAutoGameEnd` was removed from the mock control API (maintainer decision 2026-10-19) because it killed every mock controller except the last-added one, reserved shadow-game controllers and controllers outside the game included (D-C8); tests and the demo end a game with SimulateDeath (step 4) instead. The ID is kept so it is not reused.
**Flow:**

1. `SetAutoGameEnd` is gone (#1623); a game ends with SimulateDeath (step 4).
2. Use case continues at step 5.

### A2: Shadow games

**Trigger:** The agent or a test starts a game with reserved mock controllers (step 3)
**Flow:**

1. System runs the game as a shadow game (UC-043); reserved controllers stay out of the lobby. The starter's event stream receives every event of that game, beginning with `game_start`, which carries the game id (BR-003).
2. Use case ends.

### A3: Reset a controller

**Trigger:** Operator calls ResetController (step 4)
**Flow:**

1. System releases all buttons, clears any death latch and any held movement; the controller reports resting noise again.
2. Use case continues at step 4.

### A4: Disconnect a mock controller

**Trigger:** Operator calls RemoveController for a mock controller (step 4)
**Flow:**

1. System removes the controller from the mock adapter; the controller manager sees it disconnect (UC-002 A1), and a player in a running game is eliminated (UC-020 A2).
2. For a pattern controller the response carries its replay record (UC-046 step 8).
3. An unknown serial fails with a "not found" error and changes nothing.
4. Use case continues at step 4.

### A5: Set an LED colour directly (retired)

**Trigger:** None since #1322: `SetColor` was removed from the mock control API (maintainer decision 2026-10-21); nothing called it. LED colours are still read back with GetColor (step 6), and a test sets one through the adapter. The ID is kept so it is not reused.
**Flow:**

1. `SetColor` is gone (#1322); read colours back with GetColor (step 6).
2. Use case continues at step 6.

### A6: List mock controllers

**Trigger:** Operator (or the agent, for its shadow-game controllers) calls ListMockControllers to find the controllers it added (step 2)
**Flow:**

1. System returns every mock controller's serial and the count, and per controller whether it is reserved and its owner tag; reserved controllers are listed too, so an owner can find and sweep its own controllers by tag.
2. An agent caller leaves this flow here: it starts its shadow game with the listed controllers (A2) or removes the orphans its sweep finds (A4). An operator readies up the listed controllers.
3. Use case continues at step 3.

## Postconditions

### Success Postconditions

- Games run end to end with mock controllers and publish game events, spans and metrics through the same code paths as hardware controllers.

### Failure Postconditions

- The mock API is unreachable from the host when port 50062 is not published.

## Business Rules

### BR-001: Death simulation

SimulateDeath latches an acceleration of about 9.95 g for 2 delivered frames so the game reliably registers it. On a pattern controller SimulateDeath (like SimulateMovement) is refused with FAILED_PRECONDITION (UC-046 BR-004); on an unknown serial it returns `success=false`.

### BR-002: Held movement

SimulateMovement holds the given acceleration on that controller: every poll, and so every streamed gameplay frame, reports exactly that vector until the next SimulateMovement or a ResetController (A3); there is no time limit. A NaN or infinite component is rejected (INVALID_ARGUMENT) and nothing is held. On a pattern controller SimulateMovement is refused with FAILED_PRECONDITION (UC-046 BR-004). SimulateMovement, SimulateButton and ResetController return a "not found" error for an unknown serial and change nothing. A death latch (BR-001) overrides the held value for its frames, after which the held value resumes. A held value feeds the game's death detection like real motion: above the player's death threshold it kills the player, and after each respawn grace it kills them again for as long as it stays held. A dropped frame (Unstable adapter) does not lose the hold, which reappears with the next delivered frame. A controller with no held value reports resting noise (about 1 g with a standard deviation of 0.1 g per axis). The gyroscope always reports noise.

### BR-003: A headless start stream sees its whole game

A game started through `StreamGameEvents` with a `start_config` (the agent's shadow spawns, the test harness, and the menu's real-game start, UC-010 BR-006) streams to its starter every event of that game, beginning with `game_start` (which carries the game id), then `game_starting`, `game_started` and the rest: the coordinator subscribes the starter to the new game's event bus before it publishes `game_start` and before the game thread starts, so no event the game thread publishes early is lost (#1783). The stream yields `game_start` only after the start succeeded (game thread started); a start that fails yields one `game_start_error` event instead and closes the stream, and a failed or client-cancelled start leaves no subscriber on the bus and no session: the coordinator retires the admitted session (UC-010 A7, BR-007). Observers that attach later (zero-arg stream: the primary game; `game_id`: a running game) receive events from the moment they attach, without replay.
