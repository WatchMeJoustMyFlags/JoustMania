# Use Case: Play with Mock Controllers

## Overview

**Use Case ID:** UC-003
**Use Case Name:** Play with Mock Controllers
**Primary Actor:** Operator
**Goal:** Run and drive the full system without PS Move hardware
**Status:** Implemented
**Requirements:** FR-005, FR-006

## Preconditions

- The stack runs with mock controllers (`backend=mock`, e.g. `make up-mock` or `make dry-run`). The controller manager always loads a mock adapter and serves the mock control API on port 50062; `docker-compose.override.yml` publishes that port to the host.

## Main Success Scenario

1. Operator adds mock controllers through the mock control API (AddController / AddControllers).
2. System creates controllers with serials `MOCK0000`, `MOCK0001`, ... (an explicit serial may be passed instead) and connects them (UC-002 from step 3).
3. Operator simulates button presses (SimulateButton) to ready up and start a game (UC-010).
4. Operator simulates movement and deaths (SimulateMovement, SimulateDeath); a simulated movement is held until the operator changes or resets it (BR-002).
5. System plays the game exactly as with hardware, publishing the same events and telemetry.
6. Operator reads LED colours back (GetColor, StreamObservability) to verify feedback.

## Alternative Flows

### A1: Automatic game end

**Trigger:** Operator calls SetAutoGameEnd (step 4)
**Flow:**

1. System kills players after the given duration so the game reaches a winner.
2. Use case continues at step 5.

### A2: Shadow games

**Trigger:** The agent or a test starts a game with reserved mock controllers (step 3)
**Flow:**

1. System runs the game as a shadow game (UC-043); reserved controllers stay out of the lobby.
2. Use case ends.

### A3: Reset a controller

**Trigger:** Operator calls ResetController (step 4)
**Flow:**

1. System releases all buttons, clears any death latch and any held movement; the controller reports resting noise again.
2. Use case continues at step 4.

## Postconditions

### Success Postconditions

- Games run end to end with mock controllers; the agent, telemetry and flags behave as with hardware.

### Failure Postconditions

- The mock API is unreachable from the host when port 50062 is not published.

## Business Rules

### BR-001: Death simulation

SimulateDeath latches an acceleration of about 9.95 g for 2 delivered frames so the game reliably registers it.

### BR-002: Held movement

SimulateMovement holds the given acceleration on that controller: every poll, and so every streamed gameplay frame, reports exactly that vector until the next SimulateMovement or a ResetController (A3); there is no time limit. A NaN or infinite component is rejected (INVALID_ARGUMENT) and nothing is held. A death latch (BR-001) overrides the held value for its frames, after which the held value resumes. A held value feeds the game's death detection like real motion: above the player's death threshold it kills the player, and after each respawn grace it kills them again for as long as it stays held. A simulated disconnect (Unstable or Chaos adapter) drops frames but keeps the hold, which reappears with the next delivered frame. A controller with no held value reports resting noise (about 1 g with a standard deviation of 0.1 g per axis). The gyroscope always reports noise.

Known gap (A1): the auto end kills every mock controller except the last-added one, including reserved shadow-game controllers and controllers that are not in the game (issue #1322: the cleanup removes `SetAutoGameEnd`, so this gap closes by removal rather than a fix).
