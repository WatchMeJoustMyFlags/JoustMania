# Use Case: Force-End a Game

## Overview

**Use Case ID:** UC-027
**Use Case Name:** Force-End a Game
**Primary Actor:** Operator
**Secondary Actors:** Agent (A3)
**Goal:** Stop a running game immediately
**Status:** Tested
**Requirements:** FR-028

Scope: this use case covers Free-for-All and the session machinery (steps 1-5, A1-A4 are mode independent). How the other modes end on a force end is specified in their own use cases (FR-144, FR-145, issues #1343 and #2003, moved out of this use case by #1602): Teams, Random Teams, Traitor, Werewolf, Zombies, Swapper, Fight Club, Tournament and NonStop declare no winner (UC-021 BR-003, UC-022 BR-005, UC-022 BR-004, UC-023 BR-003, UC-024 BR-003, UC-025 BR-003, UC-026 BR-003). JoustFFA declares no winner (#1370).

## Preconditions

- A game session is STARTING or RUNNING.

## Main Success Scenario

1. Operator presses Stop in the dashboard (or calls ForceEndGame with a reason and optionally a game id).
2. System finds the target session (the primary game when no id is given).
3. System stops the game loop, waits up to 2 s for it to finish, sets the session to ENDED and publishes `game_force_ended` with the reason and the game id; no winner is declared (Free-for-All; other modes: see Scope). The game records the outcome `force_ended` with the reason on its root span (`game.outcome`, `game.end_reason`) unless its loop had already ended on a win (#1328); JoustFFA also sends them in `game_ended` (`outcome`, `reason`) and marks survivors `player_survived`, not `victory` (UC-020 A4, BR-003); a force-end that lands before the win is latched, also while the last kill awaits its explosion, publishes no `game_winner` or `game_tie` (UC-020 BR-003, #2020). From the force-end on the game takes no kill, in every mode, also later in the frame the force-end landed in: no death, `player_death` event, death effect or score counts (UC-030 step 9, #2033). The force-end is applied on the game's own loop, the thread that runs the kill path, so it lands either before a kill's gate check (the kill is declined) or after that kill's bookkeeping, never between the check and the count (#2149); the 2 s wait above covers both taking it there and the loop finishing. When the game loop is no longer running (stopped, closed, or its thread ended with the force-end still queued) the force-end is applied at once; a loop that does not take it within the wait keeps it queued and takes it when it runs again, after the rest of the frame it was stuck in and the callbacks queued ahead of it, while the session goes on to ENDED and `game_force_ended`.
4. System retires the session, so a new game can start. Steps 3 and 4 run to completion even when the caller goes away (deadline, disconnect, cancelled RPC, cancelled `end_game`): the session is still set to ENDED, `game_force_ended` is published and the session is retired (#1827).
5. The menu restores the lobby (for the primary game).

## Alternative Flows

### A1: Unknown game id

**Trigger:** No session has the given id (step 2)
**Flow:**

1. System returns `success=false` with an `Unknown game_id` error; nothing changes. A given id never falls back to the primary game.
2. Use case ends.

### A2: No game in progress

**Trigger:** No id is given and no primary game exists, or the target session is not STARTING or RUNNING (step 2)
**Flow:**

1. System returns `success=false` with `No game in progress`; nothing changes.
2. Use case ends.

### A3: Agent ends the game

**Trigger:** The agent applies `end_game` (UC-040) (step 1)
**Flow:**

1. The coordinator force-ends only the session the `end_game` value is addressed to (UC-040 A18, BR-011), with the reason `agent_intervention`, through the same path as ForceEndGame with that game id.
2. Use case continues at step 3.

### A4: Game already ending

**Trigger:** A force end (ForceEndGame, `end_game`) or a real-start preemption ([UC-043](UC-043.md) A2) of the target session is under way (step 2)
**Flow:**

1. System waits for the end under way and returns its result (`success=true` when it ended the game); it logs the second caller's reason at info. The game thread is joined once, the mode is force-ended once and `game_force_ended` is published once, all with the reason of the end that started first; the session is retired once (BR-003, #1827).
2. Use case ends.

## Postconditions

### Success Postconditions

- The session is ENDED and retired; the lobby is available.
- The next game starts and delivers its events normally (BR-002).

### Failure Postconditions

- The session continues.

## Business Rules

### BR-001: Shadow games by id

Shadow games are ended only by explicit game id; an empty id targets the primary game. The agent's `end_game` is always addressed to the game it was decided for, so a shadow game's decision never ends the real game (#1310, PR #1315).

**Code / tests:** `services/game_coordinator/servicer.py` (`ForceEndGame`, `_force_end_current_game`, `_force_end_session`, `_retire_session`), `game_session.py` (`force_end`), `interventions.py` (`_handle_end_game`); tests `services/game_coordinator/tests/test_servicer_sessions.py`, `services/game_coordinator/tests/test_servicer.py`, `services/game_coordinator/tests/test_ffa_uc020.py`, `services/game_coordinator/tests/test_kill_after_latch.py` (step 3, #2020), `services/game_coordinator/tests/test_kill_after_force_end.py` (step 3, no kill after a force-end, #2033), `services/game_coordinator/tests/test_intervention_scoping.py`, `tests/service/test_tc017_parallel_mode_lifecycle.py`, `tests/integration/test_tc013_shadow_alongside_real.py`.

### BR-002: A new game starts normally after a force-ended game

Force-ending a game never leaves the coordinator unable to start or stream the next game. Each game runs on its own event loop, so the event bus that carries game events (the persistent primary bus above all) must work from any loop: the next game publishes its lifecycle events and reaches RUNNING, and stream subscribers receive them without delay, without a coordinator restart (#1300). A force-ended session whose thread ends after the next game started does not reset that game's live `game_players_alive` count: a session zeroes it only while its own game wrote it last (#2244).

**Code / tests:** `services/game_coordinator/event_bus.py`, `metrics.py` (`set_players_alive`, `reset_players_alive_if_owner`); tests `services/game_coordinator/tests/test_event_bus_cross_loop.py`, `services/game_coordinator/tests/test_players_alive_late_session.py`.

### BR-003: One end per session

A session is force-ended at most once. ForceEndGame, the agent's `end_game` and a real-start preemption share one end task per session: a second caller waits for it instead of ending the game again, and the end finishes even when every caller is cancelled. A force end that answers `No game in progress` (A2) logs no error. The session also refuses a second force end while one is under way (`Game is already ending`), unless the mode's own force end raised, which lets a later caller retry (#1827). Known limitation (#1864): if a mode's `force_end` raised and the game thread then ended silently, a retry answers `No game in progress` and no `game_force_ended` is published (unreachable today: no mode overrides `force_end`); if event-loop teardown cancels an end task during its join and the thread never ends, the session answers `Game is already ending` until the process exits (teardown happens only at process exit).

**Code / tests:** `services/game_coordinator/servicer.py` (`_session_ending_task`, `_end_session`, `_force_end_session`, `shutdown`), `game_session.py` (`force_end`, `_force_ending`); tests `services/game_coordinator/tests/test_servicer_sessions.py::TestForceEndOnce`, `services/game_coordinator/tests/test_game_session.py::TestGameSessionForceEnd`; flaky-test pin `test_servicer_sessions.py::TestMultiSession::test_shadow_end_clears_only_its_serials_and_game_state_series`.
