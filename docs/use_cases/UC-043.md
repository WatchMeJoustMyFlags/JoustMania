# Use Case: Run a Shadow Experiment and Promote the Winner

## Overview

**Use Case ID:** UC-043
**Use Case Name:** Run a Shadow Experiment and Promote the Winner
**Primary Actor:** Agent
**Secondary Actors:** Maintainer
**Goal:** Find out in shadow games whether a flag value improves an objective, and promote it only if it does
**Status:** Implemented
**Requirements:** FR-029, FR-055, FR-060, FR-061, FR-062, FR-063, FR-064, FR-065, FR-066, FR-105, FR-106, NFR-018, C-003, C-005, C-007
**Planned:** FR-067 (#964, Open), FR-068 (#1011, Open)

## Preconditions

- `enabled` and `experiments_enabled` are on.
- An experiment is declared (env seed, proposer, thesis or dynamic declarer).

## Main Success Scenario

1. The agent writes the experiment's value for its id and experimental arm through the flag service ([UC-053](UC-053.md) A3); the flag service renders it as targeting that only a non-real game of that experiment and arm resolves (BR-001), and only for flags in the experiment catalog; before writing, the gate asks the flag service for a dry run (`PUT ?dry_run=true`: the flag before and after, rendered under one lock, nothing applied) and refuses a write that would change what a real game resolves, so nothing needs rolling back. Before each pair of shadow games the agent compares the flag service's boot epoch with the one of its write and writes the arm value again after a restart. The arm is also written again after the flag service's idle expiry dropped it (same epoch).
2. Every `experiment_tick_seconds` (default 30) the agent spawns pairs of shadow games (experimental, control) through the coordinator and mock-controller APIs, sharing a seed, with agent origin and reserved mock controllers driven by a pinned motion archetype, one game at a time ([UC-046](UC-046.md)).
3. The coordinator runs them as shadow games with their own game ids (UC-003 A2) and the agent observes them (UC-041).
4. On each game end the agent scores fitness for the objective and adds the sample to the arm. A game the agent ended because its telemetry stopped (UC-041 A4, end reason `stale`) is released without a sample instead.
5. Once at least one seed-matched pair has completed, the agent computes the paired effect d_z = mean / SD of the per-pair fitness differences (SD floored at `verdict_sd_floor`), conclusive from `verdict_min_pairs` (default 5) completed pairs; without completed pairs it falls back to the two-arm Cohen's d, conclusive from `verdict_min_n` (default 8) games per arm. A promote verdict needs the effect threshold (`verdict_effect_threshold`, 0.5) and the raw-effect floor (`verdict_min_raw_effect`, 0.02), and the recent-real baseline anchor may downgrade it to inconclusive.
6. On a promote verdict the agent routes the experiment to the promoter in `code_improvement.mode` (default `issue`).
7. The promoter acts per mode: open an issue, open a PR (or commit locally) for human review, or (autonomous) apply the real default, watch real games and revert on degradation. The autonomous real-default write is blocked while the kill switch (`enabled`) is off: the promotion degrades to a recorded no-op.
8. The agent tears the experiment down and journals intent, events and summary on the `agent-experiments` volume. After an agent restart it rebuilds every live experiment (status, arms, samples) from this journal and resumes it.

## Alternative Flows

### A1: Kill switch or experiments off

**Trigger:** `enabled` or `experiments_enabled` turns off (step 2, or any later step)
**Flow:**

1. The agent aborts every running experiment on the next tick. The one-shot env seed (`AGENT_EXPERIMENTS_ENABLED` bootstrap seed) is not declared again when experiments are switched back on (#1051).
2. Use case continues at step 8.

### A2: Real game starts

**Trigger:** A menu game starts while shadow games run (step 3)
**Flow:**

1. The coordinator preempts live shadow games; with `shadow_policy=block` no new shadow game starts until the real game ends. A preempted game is released without a fitness sample.
2. Use case continues at step 2.

### A3: Inconclusive or discard

**Trigger:** The verdict is discard or inconclusive (step 5)
**Flow:**

1. A significant discard verdict (effect at or below minus the threshold) concludes the experiment at once, without promotion.
2. An inconclusive experiment keeps running until a give-up condition holds, then concludes as a final inconclusive without promotion: `experiment_max_games` (default 50) games in total, every arm past its target N while still inconclusive, or every arm past target N with zero variance. A pattern experiment also concludes once every archetype has been used ([UC-046](UC-046.md) A6).
3. Use case continues at step 8.

### A4: Promotion inert

**Trigger:** The promotion env gates are not set (stock stack) (step 7)
**Flow:**

1. The promoter records a discarded no-op promotion with a reason (D-A6) and returns it as a non-fatal error.
2. Use case continues at step 8.

### A7: Pattern-driven shadow games

**Trigger:** `experiment.mock_archetypes` names archetypes (step 2)
**Flow:**

1. Every experiment runs on archetypes (maintainer decision on #1258): pair p runs archetype p of the pinned list on parametric motion functions with organic deaths, one game at a time; an empty selection discards the experiment ([UC-046](UC-046.md) A1).
2. Use case continues at step 3.

## Planned extensions

Flows with no code on `main` yet. They keep their IDs and do not count toward `Tested` until implemented and moved back to Alternative Flows.

### A5: Validation stage

**Status:** Open (#964, FR-067)
**Trigger:** Promote verdict (step 6)
**Flow:**

1. Re-validate in fresh shadow games before promotion. No code on `main` (the unwired M7-7 validator was removed in #1322).
2. Use case continues at step 7.

### A6: Candidate game code

**Status:** Open (#1011, FR-068)
**Trigger:** An experiment on game logic rather than a flag (step 1)
**Flow:**

1. Run candidate game code instead of a flag value; not on `main`.
2. Use case ends.

## Postconditions

### Success Postconditions

- A verdict is journaled; a promote verdict produced an issue, a PR or (autonomous) a watched real-default change.

### Failure Postconditions

- Real games never saw the experimental variant.

## Business Rules

### BR-001: Shadow-only

`experiment_id`, `arm` and `rng_seed` apply only to shadow sessions; a real start ignores them.

### BR-002: No chaos experiments

The `chaos` objective cannot be experimented on.

### BR-003: Tier 3 needs a human

Issue and PR modes never change a running system; a human merges.
