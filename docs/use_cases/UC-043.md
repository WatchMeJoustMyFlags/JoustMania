# Use Case: Run a Shadow Experiment and Promote the Winner

## Overview

**Use Case ID:** UC-043
**Use Case Name:** Run a Shadow Experiment and Promote the Winner
**Primary Actor:** Agent
**Secondary Actors:** Maintainer, GitHub
**Trigger:** An experiment is declared in the experiment registry: by the experiment seed (the `experiment_seed` flag, #1907), the M7-4 proposer ([UC-042](UC-042.md) step 5), a retro-seeded thesis or the dynamic declarer (BR-002)
**Goal:** Find out in shadow games whether a flag value improves an objective, and promote it only if it does
**Status:** Tested
**Requirements:** FR-029, FR-055, FR-060, FR-061, FR-062, FR-063, FR-064, FR-065, FR-066, FR-105, FR-106, FR-111, NFR-018, C-001, C-002, C-003, C-005, C-007, C-008
**Planned:** FR-067 (#964, Open), FR-068 (#1011, Open), FR-162 (#2096, Implemented: A17 with the deferred `real` write of step 3, PR-7b-2b; stays here, not under Requirements, because a Tested use case would derive Verified before the stage check)

## Preconditions

- `enabled` and `experiments_enabled` are on.
- The experiment loop runs in the agent, with its journal on the `agent-experiments` volume, and the controller manager runs with the mock adapter ([UC-046](UC-046.md)).

## Main Success Scenario

1. The agent starts the experiment: it writes the experiment's value for its id and experimental arm through the invariant gate and the flag service ([UC-053](UC-053.md) A3), only for a flag of the experiment catalog. The gate first asks the flag service for a dry run (the flag before and after, nothing applied) and refuses a write that would change what a real game resolves (BR-001, FR-062), so nothing needs rolling back; the flag service renders the value as targeting that only non-real games of that experiment and arm resolve.
2. Every `experiment_tick_seconds` (default 30) the agent spawns the next shadow game, the next arm of the current pair (experimental, control; one arm at a time, [UC-046](UC-046.md) BR-010; an arm whose spawn failed is spawned again on a later tick, UC-046 A15), through the coordinator and mock-controller APIs (C-005): both arms share the pair's seed and run with agent origin on reserved mock controllers driven by the pair's pinned archetype ([UC-046](UC-046.md)), one game at a time (FR-111). Before each pair the agent checks that its arm value is still on the flag service (A10).
3. The coordinator runs them as shadow games with their own game ids (UC-003 A2) and the agent observes them (UC-041).
4. On each game end that gives a sample ([UC-046](UC-046.md) BR-016) the agent scores fitness for the objective, with the live `fitness.*` thresholds, and adds the sample to the arm.
5. Once at least one seed-matched pair has completed, the agent computes the paired effect d_z = mean / SD of the per-pair fitness differences (SD floored at `verdict_sd_floor`), conclusive from `verdict_min_pairs` (default 5) completed pairs; without completed pairs it falls back to the two-arm Cohen's d, conclusive from `verdict_min_n` (default 8) games per arm. A promote verdict needs an effect of at least `verdict_effect_threshold` (default 0.5, inclusive) and an absolute raw effect of at least `verdict_min_raw_effect` (default 0.02). The recent-real baseline anchor then downgrades a promote verdict to inconclusive when the experimental arm's mean fitness is more than `verdict_anchor_margin` (default 0.02) below the mean fitness of the last 8 real games for the objective; with fewer than 3 such games the anchor is skipped.
6. On a promote verdict the agent routes the experiment to the promoter in `code_improvement.mode` (default `issue`).
7. The promoter acts per mode (BR-003): `issue` opens a GitHub issue; `pr` opens a GitHub PR (target `github`) or makes a local git commit (target `local`); `autonomous` writes the real default and watches the real games that started after the write: once at least 3 of them have fitness, it reverts the default when the mean of the last 5 falls more than 0.05 below the control arm's shadow mean, and with too few games it re-watches every `promotion.rewatch_interval_seconds` (default 60 s) until `promotion.rewatch_timeout_seconds` (default 3600 s; both agent flags read per re-watch since #1788, the compiled defaults apply while a flag is unresolved; the env vars were removed, #1907), after which the default stays. A revert by the re-watch is tried once and journals its one outcome as a `promotion` event on the experiment, reason prefixed `re-watch: `: `reverted`, or `applied` with the failure reason when the revert fails (A9); a re-watch whose promotion the kill switch already reverted (A1) or a newer promotion of the flag replaced writes and journals nothing (#1883). A real game counts from its session start (the game_active 0 to 1 transition); one that started before the write, or whose start is unknown, does not count (#1702). The autonomous write is refused while the kill switch (`enabled`) is off, without a watcher, or within `promotion.revert_cooldown_seconds` (default 600 s, #1788) after a revert of the same flag: the promotion degrades to a recorded no-op. It is also refused when another writer owns the flag's `real` overlay (A19). Fitness is scored against the live `fitness.*` thresholds at game end ([flags.md](../specs/flags.md), #1740), for the shadow arms (step 4) and for the real games the anchor (step 5) and the watch read. The kill switch reverts a written default at once (A1, #1704).
8. The agent tears the experiment down and journals intent, events and summary on the `agent-experiments` volume: a promotion journals its outcome (`applied`, `discarded` or `reverted`), reason and reference, and the experiment ends `done` when the promotion was applied or reverted, `discarded` when it could not act (A4, A9). A `reverted` promotion event can follow the `done` status (kill switch, A1; re-watch, step 7); the dossier decision then reads `reverted` ([UC-035](UC-035.md) A1, #1869). After an agent restart it rebuilds every live experiment (status, arms, pattern pin) from this journal and resumes it (one still `proposed` is aborted, A8; one still `concluded` or `promoting` is ended without a promotion, A15); games that were in flight at the restart are not restored. The final verdict is journaled with the `concluded` decision, so the journal and the promoter read the verdict the experiment concluded on (#2042).

## Alternative Flows

### A1: Kill switch or experiments off

**Trigger:** `enabled` or `experiments_enabled` turns off (step 2, or any later step)
**Flow:**

1. On its next tick the agent aborts every experiment that is not yet terminal (reason `kill-switch: agent disabled` or `experiments_enabled flag off`) and force-ends its in-flight shadow game ([UC-046](UC-046.md) A12). An aborted experiment is not resumed when the flags turn on again, and the experiment seed is not declared again while it stays set: the agent remembers the last value of the experiment seed (the `experiment_seed` flag, [flags.md §3](../specs/flags.md#3-agent)) it acted on (declared, skipped because its flag already had a live experiment, refused, or malformed) and does not act on that value again (#1051, #1907). When the agent reads `off` (`{}`) on any tick, also while the flags are off, it forgets that value, so setting the seed to `off` and back (`agent-dryrun-enable.sh off`, then `on`) declares it again; `off` must stay visible for one `experiment_tick_seconds`. A different value is acted on (A, then B, then A declares A again). An unreadable flag changes nothing ([UC-070](UC-070.md) BR-007).
2. An experiment whose promotion is already running stays `aborted`: the returning promotion does not overwrite the status, and the journal records what the promotion did (outcome, reason, reference). An experiment aborted between its conclusion and the promotion is not promoted. While `enabled` is off (or fails closed), each tick removes every real-default overlay a promotion wrote, whatever its watch state, read from the flag service (writer `promotion`, so also one written before an agent restart; another writer's overlay is not removed: the `DELETE` carries `?if_writer=promotion`, so the flag service clears the overlay only while its writer is still `promotion`, atomically, and a real overlay another writer sets between the agent's read and its `DELETE` stays (A18, #1877)). It stops the re-watch of each promotion and journals a `promotion` event with outcome `reverted` and reason `kill_switch` on its experiment, once per revert (an overlay this agent run did not write has no experiment to journal on and is only logged). A watch or re-watch revert already in flight finishes first: the tick waits for it (at most one flag-service read and delete), so each overlay is reverted once, a failed revert keeps its experiment, and the tick does not log a re-watched promotion as an overlay this run did not write (#1893). A failed revert is journaled once, as a `promotion` event with outcome `applied` and the failure in its reason; an earlier failed watch revert of the same promotion does not count as that event. It is tried again on every tick without a further event, and the next event is the final outcome: `reverted` / `kill_switch` when a retry succeeds. The agent log shows each attempt. A later run of failures for the same promotion (the switch turns on and off again before a retry succeeds) adds no event; a new promotion of the flag journals its own first failure (#1753). A promotion whose flags were read before the tick does not write after it, so the tick's revert is the last real-default write of each promotion it reverted, and no autonomous write happens while `enabled` is off (step 7) (#1704).
3. Use case continues at step 8.

### A2: Real game starts

**Trigger:** A menu game starts while shadow games run (step 3)
**Flow:**

1. The coordinator preempts live shadow games; with `shadow_policy=block` no new shadow game starts until the real game ends (a refused start is a spawn failure, A13). A preempted game is released without a fitness sample and its pair runs again as [UC-046](UC-046.md) BR-015 defines for a preemption. The agent folds a game's sample only once the runner has classified its terminal outcome as a sample (UC-046 BR-016): a game end from telemetry that arrives before that classification waits for it, so a preempted game is never folded, whichever signal arrives first (#1405). A preemption that has begun completes even when the real start is cancelled or fails: the shadow game is force-ended with `preempted_by_real_game` (after its game thread is joined, up to 2 s) and retired, so it leaves the registry and frees its shadow-cap slot; the cancelled start itself is retired per [UC-010](UC-010.md) BR-007. Shadow games the preemption has not reached yet keep running. A second real start while a preemption is under way waits for that preemption instead of force-ending the shadow again. A force end of the shadow under way (ForceEndGame, `end_game`) is waited for the same way: the shadow is then not counted as preempted and its `game_force_ended` carries the force end's reason ([UC-027](UC-027.md) A4, #1827). A shadow game whose force end fails is logged and not counted as preempted; the real start goes ahead, and the shadow is retired once its game has ended, at the next start (#1816).
2. Use case continues at step 2.

### A3: Inconclusive or discard

**Trigger:** The verdict is discard or inconclusive (step 5)
**Flow:**

1. A significant discard verdict (effect at or below minus the threshold) concludes the experiment at once, without promotion.
2. An inconclusive experiment keeps running until a give-up condition holds, then concludes as a final inconclusive without promotion: at least `experiment_max_games` (default 50, capped by the `AGENT_EXPERIMENT_MAX_GAMES` ceiling when set, FR-152 f; 0 = no limit) games in total, or every arm has at least its target N games (the larger of the declared target and `verdict_min_n`) while still inconclusive, with or without variance. It also concludes once every archetype of its pinned list has been used or skipped ([UC-046](UC-046.md) A6).
3. Use case continues at step 8.

### A4: Promotion inert

**Trigger:** The promotion env gates are not set (stock stack) (step 7)
**Flow:**

1. The promoter records a discarded no-op promotion with a reason (D-A6); the journal records the outcome and reason and the experiment ends `discarded`.
2. Use case continues at step 8.

### A7: Archetypes cannot be pinned

**Trigger:** In the experiment's first allocation pass the archetype selection is empty, too small or invalid, or the shadow game mode is not `JoustFFA` (step 2)
**Flow:**

1. The agent spawns no game and discards the experiment without a verdict, with the reason of [UC-046](UC-046.md) A1, A2, A4 or A13; experiments never run on random motion (maintainer decision on #1258).
2. Use case continues at step 8.

### A8: Start fails

**Trigger:** The invariant gate refuses the write, the flag is not in the experiment catalog (`not_experimentable`), or the flag service is unreachable or answers with an error (step 1); or the agent restarts and finds an experiment in its journal that is still `proposed` (its start never succeeded) (step 8)
**Flow:**

1. Nothing is written. The agent aborts the experiment with `start_failed`, whichever declarer declared it (experiment seed, M7-4 proposer ([UC-042](UC-042.md) A4), dynamic declarer, retro thesis), and logs the failure; the start is not tried again. An experiment restored from the journal as `proposed` is aborted with `start_failed` the same way. Only an experiment declared before the restart counts as restored: one this agent declared since it started (for example by the M7-4 proposer, [UC-042](UC-042.md) step 5, while the first enable reads the journal) is left to its declarer and starts normally (#1731). The aborted experiment frees its flag under test and its slot of the concurrent-experiment budget at once.
2. Use case ends.

### A9: Promotion fails

**Trigger:** Opening the issue or PR, or the local commit, fails, or an autonomous revert fails (step 7)
**Flow:**

1. A failed issue, PR or commit is recorded on the promotion span, the log and the experiment journal as outcome `discarded` with the reason, and the experiment ends `discarded`. A failed revert leaves the real default applied; the reason records the failure, no cooldown starts and nothing retries (the kill switch may still revert it later, A1). The re-watch tries the revert once: a failed re-watch revert appends one `promotion` event (`applied`, reason `re-watch: …; revert failed: …`) to the ended experiment's journal and leaves the retry to the kill switch (A1), which journals its own first failure and the final `reverted`. The re-watch's event neither uses up nor is used up by the kill switch's report of a failed revert (#1883).
2. Use case continues at step 8.

### A10: Arm value lost on the flag service

**Trigger:** Before a pair, the flag service's boot epoch differs from the one of the arm write (it restarted), or its idle expiry dropped the arm value (step 2)
**Flow:**

1. The agent writes the arm value again through the gate before it spawns the pair.
2. If that write fails, the agent releases the pair's reservations and spawns nothing this tick; it tries again on the next tick, without a limit.
3. Use case continues at step 2.

### A11: Game ended stale

**Trigger:** The agent ended a shadow game because its telemetry stopped (UC-041 A4, end reason `stale`) (step 4)
**Flow:**

1. The game is released without a fitness sample and its pair runs again as [UC-046](UC-046.md) BR-015 defines for a stale end.
2. Use case continues at step 2.

### A12: Game ends without a usable result

**Trigger:** A shadow game ends in `game_error`, a broken stream or a force-end the agent did not request, other than a real-game preemption (A2) (step 3)
**Flow:**

1. The game is released without a fitness sample and its pair runs again, at most 3 times before the archetype is skipped ([UC-046](UC-046.md) A9, BR-015). This holds also when the game's telemetry end reaches the agent before the runner's outcome: that end waits for the outcome and is dropped (UC-046 BR-016, #1405).
2. Use case continues at step 2.

### A13: Spawn fails

**Trigger:** Starting a shadow game fails: backpressure, a block by a real game under `shadow_policy=block`, or another error (step 2)
**Flow:**

1. The agent releases the pair's reservations; the arm is tried again on a later tick and uses up no rerun budget ([UC-046](UC-046.md) A15, BR-015).
2. Use case continues at step 2.

### A14: GITHUB_API_URL is not key-safe

**Trigger:** The agent routes a promote verdict to the promoter with target `github` (step 6), and the GitHub API address is not `https`, or plain `http` to a loopback host, or carries credentials, a query or a fragment (C-016, #1886)
**Flow:**

1. The agent builds no GitHub client at start and promotions use the no-op client, as for a missing credential. It logs one WARN with the reason (`malformed` or `cleartext_remote`), never the address, and the GitHub credential is sent nowhere.
2. A client that is built follows no redirect: a redirect from the API host is the response, so the credential never reaches another host.
3. The promotion records what it would do and fails as in A9.
4. Use case continues at step 8.

### A15: Restart during a conclusion

**Trigger:** The agent restarts and finds an experiment in its journal that is still `concluded` or `promoting` (step 8): the agent stopped hard (crash, kill, power loss) after the conclusion and before the teardown. A graceful stop aborts it instead (`agent shutdown`).
**Flow:**

1. A restored experiment is never promoted, whatever its verdict: its in-flight games are lost and its evidence predates the restart, so a promote verdict has to be earned again by a new experiment with fresh games (#2042).
2. A `concluded` experiment ends `discarded` with the reason `concluded before restart: <outcome>; not promoted`, where `<outcome>` is the verdict outcome in its journal (`unknown` without one).
3. A `promoting` experiment whose journal holds a `promotion` event after its last `concluded` decision ends from that event, `done` when it is `applied`, `reverted` or `deferred` (A17; a hold-key write still `deferred` is then journaled `discarded: lost_at_restart`, and a revert still `revert_pending` is re-queued, A17 step 3) and `discarded` otherwise, and the promoter is not called again. A `concluded` experiment with such an event (a journal written before BR-007) ends the same way.
4. A `promoting` experiment without such an event is aborted with `promotion_interrupted`, and the agent logs a WARN with its flag key; the promoter is not called again. What the promotion did is unknown: an issue or PR may exist, and a real default it wrote stays unwatched until the kill switch removes it (A1, [UC-045](UC-045.md) step 5) or a maintainer does.
5. Like A8, ending a restored experiment strips its targeting and frees its flag under test and its slot of the concurrent-experiment budget at once; it needs only the local journal and the targeting strip. A journal that cannot be loaded is logged and skipped, and the other experiments are still restored.
6. Use case continues at step 8.

### A16: Operator enables the dry-run

**Trigger:** The operator wants the experiment loop to run on a `make dry-run` stack, where both live gates are off in the fail-closed baseline (step 1)
**Flow:**

1. Operator runs `scripts/agent-dryrun-enable.sh on`. System sets, through the flag service (`scripts/flags.sh`, writer `operator`, never a flag file), the `experiment_seed` flag of the agent set to `windows_frantic` first, then `enabled` and `experiments_enabled` to `on`, so the first enabled tick already sees the seed. Nothing is persisted.
2. `scripts/agent-dryrun-enable.sh status` shows `enabled`, `experiments_enabled`, `experiment_seed` and `decision.backend`; `off` clears the three overlays so the fail-closed baseline returns (A1). A usage error exits 2. The change is live: the agent needs no restart.
3. Use case continues at step 2.

### A17: Experiment on a hold flag (#2096)

**Trigger:** A declarer or the proposer picks a hold flag of the experiment catalog (UC-040 BR-024 to BR-027; flags.md §4, §13.3) (step 1)
**Flow:**

1. The hold flags are the eight keys `shield.activation`, `shield.energy_max_seconds`, `shield.energy_budget_seconds`, `shield.energy_initial_seconds`, `shield.recharge_per_second`, `shield.min_burst_seconds`, `shield.hold_rumble_intensity` and `shield.empty_pulse_ms`; the charge cue flags and `shield.charge_expiry_seconds` are not in the catalog (C-034). The dynamic declarer and the proposer's flag vocabulary offer a hold flag only when the archetypes `experiment.mock_archetypes` resolves to all press the trigger (UC-046 BR-018) and the shadow game mode is Free-for-All. `shield.activation` is offered only while games do not already resolve `hold`, and its experimental value is always `hold`: the registry refuses to declare any other value, so a proposer cannot experiment its way out of hold. A hold sub-parameter is offered only while games resolve `hold` for `shield.activation`. "Resolve" is the flag's effective default, which real games and shadow games outside an arm both read (a stage overlay, else an admin (pad-persisted) overlay, else the `real` overlay, else the baseline; none of the eight keys has baseline targeting). A failed read offers no hold flag.
2. At the experiment's pin (its first allocation pass) the agent discards it with `pattern_trigger_policy_missing` when any pinned archetype has no trigger policy (UC-046 A17), with `hold_not_real_default` when a sub-parameter's `shield.activation` no longer resolves `hold`, and with `hold_already_default` when a `shield.activation` experiment finds `hold` already resolved. A running sub-parameter experiment is checked again at every tick and discarded with `hold_not_real_default` once `shield.activation` leaves `hold`; a running `shield.activation` experiment is discarded with `hold_already_default` once `hold` is resolved. A failed read keeps the experiment (pinning waits for the next tick): a transient error is no evidence.
3. A promotion writes a `real` overlay that the next game latches (UC-040 BR-027); a running game keeps its values. An operator's stage overlay (or a pad-persisted admin value, #2218) outranks the `real` overlay, so a promotion is inert while an operator value is set. The flag service refuses a `real` write of a hold key with `409 real_game_live` while any registered game scope has a `game_kind` other than `shadow` (fails closed; flags.md §13, `real_write: no_live_real_game`) and refuses `ttl_seconds` on it; a shadow game does not block it. The agent defers the write until no real game runs (#2096 PR-7b-2b). An autonomous promotion of a hold key while a real game is live returns outcome `deferred` (reason `real game running; real write waits for game end`), and the experiment ends `done`. "Live" is first the agent's telemetry prefilter (a `game_active` partition of kind `real` or without a kind, updated in the last 10 s), then the flag service's registered games (`GET /games`: any game whose kind is not exactly `shadow`); a missing probe or a failed read counts as live (fail closed). The flag service's `409 real_game_live` on the write is authoritative and also gives `deferred`. The deferred write waits in memory, one entry per flag. The experiment loop checks the queue every 2 s; at the first check with no real game live the agent writes the value with the promotion's original kill-switch epoch, watches it as in step 7, and journals `applied` (or `reverted`) on the experiment. A `409 real_game_live` at that write keeps the entry waiting. The mode is read again right before each write, and a mode other than `autonomous` there keeps the entry waiting; the remaining gap is a flip away and back between that read and the write. A newer promotion of the same flag replaces the waiting one, which is journaled `discarded` with reason `superseded`. An entry older than 24 h is journaled `discarded` with reason `deferred_expired` (its baseline is stale). A kill switch (A1, [UC-045](UC-045.md)), two consecutive checks that find `code_improvement.mode` other than `autonomous` (or the agent disabled; a single such check only skips the writes, because a flagd sync flap reads the fail-closed `issue`), a post-revert cooldown of the flag, a failed write or a graceful shutdown drops the entry, journaled `discarded` with reason `kill_switch`, `mode_changed`, the cooldown reason, the error or `shutdown`. A crash loses the queued write and nothing is written (fail safe); at the next start (the experiment loop's first enabled tick) the agent journals `discarded` with reason `lost_at_restart` on each `done` experiment whose last promotion event is still `deferred` (A15). While a write waits, its flag counts as under test: no declarer, proposer or seed declares an experiment on it ([UC-042](UC-042.md) A11 reason `flag_under_test`). The agent's own watch and re-watch reverts of a hold key are deferred the same way: while a real game is live the revert waits and runs at the first check with no real game live, journaled `reverted` on the experiment. It is journaled write-ahead: a promotion event `applied` with the reason `revert deferred until no real game runs` and `revert_pending` (the watch's own promotion result, or a re-watch event). A graceful shutdown runs a waiting revert when no real game is live and otherwise leaves it unrun; after a restart or a crash the agent re-queues every revert whose experiment's last promotion event has `revert_pending`, and runs it only while the flag's promotion overlay still holds that experiment's value (its intent's experimental value, which is what it promoted): when the overlay is gone, holds another value or a newer promotion of this run owns the flag, the revert is not run and a promotion event without `revert_pending` (outcome `applied`, the reason) clears the pending state. A waiting revert that another revert or a newer promotion of the flag replaces gets the same clearing event. A failed probe read counts as live, and a failed overlay read keeps the restored revert waiting; both are counted in `agent_promotion_probe_errors_total` (`source`) and logged at most once a minute per source. A revert the re-watch confirms after the shutdown began is not queued; its write-ahead event re-queues it at the next start. The agent checks the flag service's registered games right before the revert and then sends a guarded `DELETE` (`?unless_real_game=true`, #2236): the flag service refuses it with `409 real_game_live` under its registration lock while a non-shadow game is registered, so a real game that registers between the read and the `DELETE` still blocks the revert. On that 409 the revert keeps waiting (nothing was cleared, nothing new is journaled: the write-ahead event already holds it) and runs at a later check with no real game live. Only the kill switch reverts at any time, through its own path (a `DELETE` without `?unless_real_game`, which the flag service never refuses while a game runs; like every revert of the agent it carries `?if_writer=promotion`, A18); its revert applies from the next game, and it drops a waiting revert because it reverts the overlay itself and journals that. Issue and PR modes are unchanged, and a promotion of a flag that is not a hold key is written at once. The gauges `agent_promotion_deferred_pending` and `agent_promotion_deferred_oldest_seconds` show the queue (telemetry.md §6); the dossier's decision reads `deferred` while the write waits and `discarded` when it was dropped ([UC-035](UC-035.md) step 1). The agent logs a WARN at startup when the real-game probe is not wired, because every hold-key promotion would then wait forever.
4. Use case continues at step 2.

### A18: Another writer owns the real overlay at revert (#1877)

**Trigger:** A real overlay of another writer replaced the promotion's overlay between the agent's read of the overlay and its revert `DELETE` (step 7, A1, A17 step 3)
**Flow:**

1. Every revert of the agent (watch, re-watch, deferred, restored after a restart, kill switch) sends `DELETE /game/{flag}?game_kind=real&if_writer=promotion` (services.md §7.2, flags.md §13). The flag service compares the stored real overlay's writer with `if_writer` and clears it only when they are equal, under the same lock as every write, so no write can land between the compare and the delete. The informational `writer` label is never compared (D11).
2. On `412 writer_mismatch` nothing was cleared: the other writer owns the real default now. The agent drops the revert (it is not retried and no longer waits in the deferred queue), logs one WARN (`revert dropped: another writer owns the real overlay now`), stamps the post-revert cooldown and treats the revert as done, as when its read finds no promotion overlay. The journal records it like a revert whose read found no promotion overlay: outcome `reverted` (reason `kill_switch` for the kill switch; `kill_switch; superseded by another writer` when the `412` dropped it, so the journal and dashboard tell it from a real clear).
3. A guarded revert (`?unless_real_game=true`, A17 step 3) that meets a live real game gets `409 real_game_live` first and keeps waiting; the writer is compared only when the clear would otherwise succeed. The kill switch is never blocked from clearing an overlay the agent wrote: every promotion overlay carries writer `promotion`.
4. Use case continues at step 8.

### A19: Another writer owns the real overlay at promotion (#2260)

**Trigger:** An autonomous promotion write (step 7, or a deferred write of A17 step 3) finds a `real` overlay that a writer other than the promotion set (a script, a maintainer using the flag-service API)
**Flow:**

1. Every promotion write of the agent sends `PUT /game/{flag}?if_writer_in=promotion,` with scope `game_kind: "real"` (services.md §7.2, flags.md §13). The flag service writes the overlay only when the stored real overlay's writer is `promotion` (a previous promotion of the agent) or no real overlay is present, compared and written under the same lock as every write, so no other write can land between the compare and the write.
2. On `412 writer_mismatch` nothing was written: the other writer owns the real default. The agent does not promote: the promotion is journaled with outcome `discarded` and the reason `real_overlay_owned_by_another_writer`, the experiment ends `discarded` (step 8), and nothing is retried. **Recommendation (#2276):** the refused result is not lost: the experiment's `experiment.progress` snapshots (UC-035 step 4) carry the winning value as `experiment.recommendation.flag` / `.value` / `.owner` (the intent's flag and experimental value, and the writer that owns the real overlay, `unknown` when it could not be read), so the Experiments tab shows "would promote <flag>=<value>; real value owned by <writer>". On the synchronous path the terminal snapshot carries it; on a deferred write refused after the experiment ended, a snapshot with trigger `recommendation` is emitted, also after an agent restart (built from the journal). It carries `experiment.end_reason` too, so the reason line stays; the value attribute is cut at 512 bytes. The proposer and the seed declarer do not skip a flag whose real overlay another writer owns: shadow games get their own values through targeting, so a shadow experiment on it is still valid evidence and only the final promotion is refused. The recommendation lives in the span; the journal event keeps the owner (`foreign_owner`), and a rehydrated live experiment restores it from there. A snapshot of an experiment that was finished before a restart is only emitted when a later refusal arrives. No post-revert cooldown starts (nothing was reverted); a later promotion of the flag sends the same precondition and is refused the same way while the other writer's overlay stays. A waiting write of the deferred queue (A17 step 3) that meets the `412` is dropped from the queue and journaled with the same outcome and reason on its experiment, which already ended `done` (as for the other drop reasons of A17 step 3).
3. A hold key's write that meets a live real game gets `409 real_game_live` first and is deferred as in A17 step 3; the writer is compared only when the write would otherwise succeed. The kill switch (A1, [UC-045](UC-045.md)) is unaffected: it never writes, and every overlay the agent writes still carries writer `promotion` (A18).
4. Use case continues at step 8.

### A20: Graceful stop during an experiment (#2332)

**Trigger:** The agent's graceful stop begins (SIGTERM; the experiment loop's run context is cancelled) while an experiment runs, a game end is still folding or a game-end proposer is still running (step 4)
**Flow:**

1. From the moment the stop begins, the experiment registry declares and starts no experiment: a declare or start from any declarer (the experiment seed, the dynamic declarer, a retro-seeded thesis or the M7-4 proposer, [UC-042](UC-042.md) step 5) is refused with `agent shutting down: no new experiment`, writes no targeting and creates no journal. A proposal refused this way is recorded as blocked (UC-042), and an experiment declared but not yet started when the stop began is aborted (`agent shutdown`, or `start_failed` when its start is refused). The refusal is decided under the registry lock that the shutdown teardown also takes, so an experiment declared before the stop is in the teardown's set and none is declared after it.
2. A game end that lands after the stop began still folds its sample into the arm and journals it, and the verdict is evaluated and journaled as usual (step 5). When that verdict concludes `promote`, the agent does not call the promoter: no issue, PR or real-default write is made while the agent goes down. The promotion is journaled as a `promotion` event with outcome `discarded` and reason `shutdown` (the reason a deferred write dropped at shutdown gets, A17 step 3), and the experiment ends `discarded` (step 8). It is not promoted at the next start either: as in A15, a promote verdict from before the stop has to be earned again by a new experiment. A promotion that was already running when the stop began finishes and journals what it did (BR-007).
3. The shutdown teardown then aborts every experiment that is still live (`agent shutdown`), as before. The kill switch (A1, [UC-045](UC-045.md)) is unaffected: it still reverts the agent's promotions while `enabled` is off.
4. Use case ends.

## Postconditions

### Success Postconditions

- The experiment is concluded with a verdict in its journal (intent, events, summary) and torn down: its arm value is removed from the flag service.
- A promote verdict was routed in `code_improvement.mode`: an issue, a PR or a local commit for human review, a watched autonomous real default, or a recorded no-op promotion (A4).

### Failure Postconditions

- No real game resolved the experimental value, and no real default changed without a promote verdict.

## Business Rules

### BR-001: Shadow-only

`experiment_id`, `arm` and `rng_seed` apply only to shadow sessions; a real start ignores them.

### BR-002: No chaos experiments

The `chaos` objective has no fitness function: the registry refuses to declare an experiment on it, whichever declarer asks, so no such experiment reaches step 1. No declarer asks for it: the experiment seed treats `chaos` (or any unknown objective) as malformed and declares nothing (#1907); the M7-4 proposer uses `balanced`, the dynamic declarer the `experiment_dynamic_objective` flag (`balanced`, `endurance` or `accelerate`; an empty, unknown or unreadable value, `chaos` included, falls back to `balanced`, #1907), and a retro thesis `accelerate` or `endurance` from the suggestion's emphasis, else the objective its flag selector chose.

### BR-003: Proposals need a human

Issue and PR modes are proposals (C-007): they never change a running system, and a maintainer reviews and merges them. Only `autonomous` mode changes a real default, as a tier 2 change after shadow validation (C-003, FR-065).

### BR-004: Shadow games are silent

A shadow game never calls the audio service (no music, tempo, volume or sound RPC; [UC-031](UC-031.md) BR-006), so an experiment arm next to a real game does not take over its music. The arm's tempo schedule and thresholds still run (UC-031 BR-005).

### BR-005: An experiment on the pacing windows overrides the agent's pacing lever

When the experiment sets `windows`, the experimental arm's games keep the experiment's windows: a `pacing_profile` intervention there resolves the experiment's value (UC-040 BR-018), and when that value differs from the requested preset the coordinator applies nothing and records it as blocked `experiment_override` ([UC-040](UC-040.md) A22). A preset whose windows equal the experiment's is applied, since it changes nothing. The control arm has no experiment value, so the coordinator would still let the lever move its windows; the agent therefore does not decide `pacing_profile` in either arm of an experiment on `windows`, nor any other lever of the experiment's flag (UC-040 A40, BR-028, #1975), so the arms stay comparable and no budget goes to blocked interventions. A game started before the experiment's value was written begins with the baseline windows and then blocks the lever as well, so it keeps the baseline; arm games are normally spawned after the write (#1970).

### BR-006: An experiment concludes at most once

An experiment is concluded once: one `experiment.concluded` log line, one concluded decision in its journal, one targeting strip, one terminal notice and, for a promote verdict, one promotion. Two paths can reach the conclusion at the same time (the end of the last game and the allocation pass of UC-046 A6, or the end of both arms' games); the second finds the experiment no longer `proposed` or `running` and returns its current status without concluding it again (#2034). This also holds across an agent restart: an experiment restored as `concluded` or `promoting` is ended without a second conclusion or promotion (A15, #2042).

### BR-007: A promotion acts only after it is journaled

The promoter is called only for a `concluded` experiment, and only after its `promoting` decision is durable in the experiment journal. If that write fails, nothing is promoted: the agent journals a `promotion` event with outcome `discarded` and the reason `promotion not journaled: <error>` (when the journal still accepts it) and the experiment ends `discarded`. A summary rewrite that fails after the event line is durable does not count as a failed write. A restart therefore never finds a promotion that acted without a `promoting` decision in the journal (A15, #2042).


### BR-008: Every catalog flag is described

Every flag an experiment may change (a `game` registry row with scope `experiment+arm`, flags.md §13.3) carries a one-line `description` in game terms; the flag service refuses to start without it (flags.md §13, #2345). A flag added to the catalog therefore reaches the M7-4 proposer with its meaning ([UC-042](UC-042.md) BR-008). The declarers that pick from the catalog without a model (experiment seed, dynamic declarer, retro thesis) do not read it. Tests: `services/flag-service/registry/description_test.go`.
