# Use Case: Decide an In-Game Intervention

## Overview

**Use Case ID:** UC-040
**Use Case Name:** Decide an In-Game Intervention
**Primary Actor:** Agent
**Secondary Actors:** Model API, Player
**Goal:** Nudge a running game toward the active objectives with a bounded, reversible intervention
**Trigger:** A telemetry batch updates a game's context (UC-041) while the game is active and at least one player is fresh (sent a signal within `lifecycle.player_ttl_seconds`, default 5 s); a context that fails this evaluation gate is not evaluated and nothing is recorded
**Status:** Implemented
**Requirements:** FR-043, FR-044, FR-046, FR-047, FR-048, FR-049, FR-050, FR-051, FR-052, FR-053, FR-054, FR-069, NFR-010, NFR-011, NFR-012, NFR-013, NFR-015, NFR-050, C-002, C-004, C-018

## Preconditions

- The agent observes the game and holds one context per game id (UC-041).
- The game coordinator registered the game with the flag service, so the game has a scope there ([UC-053](UC-053.md)).

## Main Success Scenario

1. System reads the live flag snapshot (objectives, policy, `decision.*`) and finds the kill switch `enabled` on (A28); this scenario follows a remote backend (rules: A1).
2. System sees `decision.backend` = jev (the main in-game backend), claude (the manual backup) or openai, and the backend is available (jev: `JEV_API_KEY`; claude: key + model; openai: key + model + base URL).
3. System checks that no remote call is in flight for this game, that the game kind is eligible (`llm.eligible_game_kinds`, default `real_only`: real games only), that the allow-list offers at least one intervention besides `noop` (BR-005), that `decision.min_interval_ms` (default 3 s) has passed and that the global budget (`llm.max_requests_per_minute`, default 6) has room.
4. System builds the state (narrative, players, digest) and the FFA questions: which intervention (noop or an allowed type), which target, what magnitude (questions, answers and validation: [decide-contract.md](../specs/decide-contract.md)).
5. System calls the backend asynchronously with `decision.<backend>.timeout_ms` (claude 5000 ms, jev and openai 2500 ms by default); the game keeps running.
6. The backend answers; System parses and validates the answers strictly.
7. System re-reads the live flags: the kill switch is still on and `decision.backend` is unchanged.
8. System checks the answers for consistency (not invalid) and that the intervention is not `noop`.
9. The `ffa.intervention` confidence is at least the answering backend's act threshold, read now (#1287): for jev `decision.jev.act_confidence_threshold` (default 0.6; variant `inherit` uses the global), for claude and openai `decision.act_confidence_threshold` (default 0.8). Outcome `act`; the span records the effective threshold and its source (`jev` / `global`).
10. System re-reads the current context: it exists, the game is still active and the target (if any) is still present.
11. System runs the permission chain: allow-list, battery threshold, per-game weighted rate limit.
12. System writes the intervention to the flag service for this game (`interventions` set, scoped to the game id, and to the player's serial for a per-player intervention; a one-shot intervention is appended to the game's event list) ([UC-053](UC-053.md)); the write is gated by `interventions_enabled` (A11) and can fail (A27).
13. The game coordinator picks up the flag change, re-checks the allow-list, the mode's capabilities, battery and its global backstop, and applies the intervention through the game's own code (e.g. tempo change, shield, elimination; a partial shield lasts at most 30 s and its boost is clamped to 1.0 to 2.0), publishing `agent_intervention`; after an applied HARD-class intervention it pulses the targeted controller (or every active player for a game-wide intervention) magenta unless `agent_intervention_cue` is off (#818); a player-targeted intervention is also recorded as an event on that player's span carrying `player.serial` and `player.name`. A one-shot intervention applies once, and only in the game whose event list holds it (BR-006). `end_game` ends only the game it was decided for (BR-011), and a per-player grant (`grant_shield`, `partial_shield`, `soft_penalty`) applies once per decision, to the player it targets (BR-012). The intervention's side effect runs on the game's own event loop (BR-018, A26).
14. System records `agent.decide`, `chat {model}`, `agent.decision` and `agent.action` spans (a player-targeted decision names the player with `player.serial` and, when known and the game is not a shadow game, `player.name`) and later measures the effect of each dispatched decision (`agent.intervention.effect`, correlated by that decision's own `decision.intervention_id`; a cycle has no id), all inside the game's trace (BR-013). Today only a decision of the rules engine's own cycle (A1) is measured: a decision that lands on the remote path, including its rules fallback, carries no fitness baseline, so it gets no effect span and no id (known bug #1699). The rationale on the spans is truncated to 256 runes. Interventions a player can perceive give feedback in the game: an audio cue plays a real sound (BR-007), and a shield plays a sound and shows on the player's LED and on the dashboard (A16, A17).

## Alternative Flows

### A1: Rules backend (default)

**Trigger:** `decision.backend` is `rules` (step 2)
**Flow:**

1. System ranks rule candidates by objective weight × urgency × fitness pressure and emits up to two decisions per evaluation (at most one evaluation per second).
2. System records the rules answers as the first emitted decision (intervention and target, even one the allow-list will block), with `outcome=act`.
3. If the ranking emitted nothing, System records no span and counts the cycle in `agent_evaluations_total{outcome=idle}`; use case ends.
4. Otherwise use case continues at step 11 (no confidence routing).

### A2: Remote timeout, error or invalid answer → rules fallback

**Trigger:** The call times out, fails (HTTP error including 429) or the answer fails validation (step 5 or 6)
**Flow:**

1. After the kill-switch and backend checks (step 7), System records `outcome=fallback` with `fallback_reason` = timeout, error or invalid_answer.
2. System lets the rules engine decide on the **current** context. If the context is gone or the game has ended, nothing is decided and the span carries `outcome=fallback` **with** `discarded_reason` = `stale_context` or `game_ended`, and use case ends; it also ends when the rules emit nothing.
3. Otherwise use case continues at step 11.

### A3: Backend unavailable, ineligible or over budget → rules now

**Trigger:** Unknown backend, missing key / model, no re-validation source, ineligible game kind or exhausted budget (step 2 or 3)
**Flow:**

1. After the in-flight check (A4), System checks in this order: the backend (`unknown_backend`, `backend_unavailable`; `async_not_wired` when the loop has no context provider to re-validate a late answer, which the shipped agent always wires, so only a hand-built loop in a test produces it), the game kind (`llm_not_eligible`), then the allow-list (A14), the cadence (A4) and the budget (`llm_budget_exhausted`). So an unknown, unavailable or ineligible backend falls back to rules even when the allow-list is empty; the allow-list then blocks their decisions (A10).
2. System records `outcome=fallback` with the reason (`unknown_backend`, `backend_unavailable`, `async_not_wired`, `llm_not_eligible`, `llm_budget_exhausted`) on the cycle's `agent.decide` span and counts it in `agent_llm_gated_total{reason}`. When the rules emit nothing in that cycle, only the configuration fallbacks (`unknown_backend`, `backend_unavailable`, `async_not_wired`) still emit the span, at most one per reason per `decision.throttle_seconds`; `llm_not_eligible` and `llm_budget_exhausted` are then counted only. A game entering or changing a configuration fallback logs a WARN `agent.decide.backend_misconfigured`, and an INFO when it clears.
3. Rules decide in the same cycle (A1); when they emit nothing, use case ends.
4. Otherwise use case continues at step 11.

### A4: Cadence or in-flight gate

**Trigger:** A call is in flight for this game or the minimum interval has not passed (step 3)
**Flow:**

1. System makes no decision this cycle (rules stay quiet; not a fallback) and records no span. A call in flight is not counted; an unmet interval counts `agent_llm_gated_total{reason=decide_interval}` and logs `agent.decide.cadence_wait` at debug level.
2. Use case ends.

### A5: Low confidence → held

**Trigger:** Confidence below the threshold (step 9)
**Flow:**

1. System records `outcome=held` and does nothing. The context is not checked first, so a low-confidence answer that lands after the game ended is `held`, not `discarded`.
2. Use case ends.

### A6: Kill switch mid-flight → discarded

**Trigger:** `enabled` was turned off while the call was in flight (step 7, the first check on landing)
**Flow:**

1. System records `outcome=discarded`, `discarded_reason=kill_switch`; neither the answer nor a rules fallback acts. When the call had failed or timed out, the span also carries its `decide.fallback_reason`.
2. Use case ends.

### A7: Situation changed → discarded

**Trigger:** The backend changed (step 7), or, for an answer that would act, the context is missing, the game ended or the target is gone (step 10)
**Flow:**

1. System records `outcome=discarded` with `backend_changed` (step 7) or `stale_context`, `game_ended`, `target_gone` (step 10).
2. Use case ends.

### A8: Inconsistent answers → invalid

**Trigger:** E.g. `noop` with a target, or a player intervention without a target (step 8)
**Flow:**

1. System records `outcome=invalid` with `invalid_reason`; no action and no fallback.
2. Use case ends.

### A9: Noop

**Trigger:** The backend chose `noop` (step 8)
**Flow:**

1. System records `outcome=noop`.
2. Use case ends.

### A10: Blocked

**Trigger:** Not allowed, battery below `policy.battery_threshold` or rate limit reached (step 11)
**Flow:**

1. System records the decision as blocked with the reason on `agent.decision` and as `decide.blocked` / `decide.block_reason` on `agent.decide`; the outcome stays `act`; nothing is written. A scarce budget is spent in rank order (A20, BR-014); a repeat the budget already refused emits no new `agent.decision` span (A21).
2. Use case ends.

### A11: Actuation gate off

**Trigger:** `interventions_enabled` is off (step 12)
**Flow:**

1. Nothing is written and no write is counted; the decision has already charged the per-game budget and its `agent.action` span is recorded. `agent_interventions_applied_total` still increments for the gated no-op: this is the logged discrepancy D-A9, a known bug (#1681), not required behaviour.
2. Use case ends.

### A12: Noul questions

**Trigger:** A request contains a `noul` (yes/no, P(yes)) question (shipped in PR #1261). Today that is only the internal `jev.gate` noul the Jev backend asks every stage-1 round ([decide-contract.md §3.1](../specs/decide-contract.md), A13); the FFA questions of step 4 hold no noul (step 4)
**Flow:**

1. Jev answers it natively (confidence \|2p − 1\|); the rules engine answers a noul with 0.5 at confidence 0. Claude and OpenAI support no noul: they would reject such a request before any network call (`invalid_answer`, then rules decide as in A2), but no caller sends them one today.
2. Use case continues at step 6.

### A13: Two-stage Jev round (gated)

**Trigger:** `decision.backend` is jev (step 5; PR #1265, gate #1281)
**Flow:**

1. System's first Jev call asks the gate noul "Does the game need an intervention right now?" and `ffa.intervention` without `noop` in the same call.
2. System synthesises the `ffa.intervention` answer as `{noop: 1 − p_yes, Jev's pick: p_yes, others: 0}`, so its confidence is p_yes when acting, and records Jev's real p_yes and distribution on the stage-1 span.
3. If p_yes ≤ 0.5 the answer is `noop` and no second call is made; use case continues at step 6 (then A9).
4. Otherwise, if the chosen intervention needs a target or a magnitude, System makes a second Jev call conditioned on it (target among alive players described by suitability; magnitude levels of that intervention only, no neutral level, the most likely level wins with ties going to the gentler level; for two-way levers Go picks the direction from the danger signals and Jev picks the strength).
5. Both calls share the `decision.jev.timeout_ms` deadline; a stage-2 failure fails the whole round (A2).
6. Use case continues at step 6; at step 9 p_yes is compared with Jev's own `decision.jev.act_confidence_threshold` (default `gate` 0.6, calibrated for p_yes: collapsing and near-threshold act, calm and dragging are noop; A5 when below). With the `inherit` variant the global `decision.act_confidence_threshold` applies instead (default 0.8 holds every calibrated state).

### A14: No interventions allowed → no remote call

**Trigger:** The effective allow-list is empty: `interventions_allowed` resolves to `none` (or to a list that holds only `noop` or empty ids, e.g. `probe`), so `noop` would be the only `ffa.intervention` option, while a remote backend is selected, available and the game kind eligible (step 3; #1298). On the rules backend, and when A3's backend or eligibility fallback applies first, this flow does not apply: the rules run and the allow-list blocks what they emit (A10).
**Flow:**

1. System makes no remote call: no Jev, Claude or OpenAI request is built or sent, and neither the cadence (`decision.min_interval_ms`) nor the global budget (`llm.max_requests_per_minute`) is charged.
2. System does not run the rules engine either (nothing it could emit would pass the allow-list) and records no fallback and no `agent.decide` span.
3. System increments `agent_llm_gated_total{reason=no_interventions_allowed}` and writes a debug log `agent.decide.no_interventions_allowed` only when the game enters or leaves this state.
4. As soon as the allow-list offers an intervention again, the next cycle continues at step 3.

### A15: One-shot interventions of an earlier game

**Trigger:** A game starts after one-shot interventions (`audio_cue`, `controller_effect`, `eliminate_player`, `revive_player`, `end_game`) were applied in an earlier game, and a later flag change makes the coordinator re-evaluate during the new game (step 13)
**Flow:**

1. The earlier game's event list was dropped with its scope when that game ended ([UC-053](UC-053.md) BR-003); the new game is registered with an empty event list.
2. On the re-evaluation the new game's list holds no event, so nothing is applied and no `agent_intervention` is published.
3. An event appended for the new game has the next sequence number and is applied once. Use case continues at step 13.

### A16: Shield feedback for the player

**Trigger:** The coordinator grants or extends a `grant_shield` or `partial_shield` for a player (step 13; #1301)
**Flow:**

1. System sends the player's controller a `GAME_EFFECT_SHIELD` (`grant_shield`) or `GAME_EFFECT_PARTIAL_SHIELD` (`partial_shield`) with `duration_ms` = the remaining protection; the controller manager renders the LED schedule itself (BR-008, BR-009).
2. System plays the shield sound `shield_up` (full volume for `grant_shield`, half volume for `partial_shield`) (BR-007).
3. System publishes the game event `player_shielded` (`serial`, `kind` = `full` or `partial`, `seconds`, `until_ms`) and records the span event `shield_feedback` on the player's span.
4. The dashboard tile of the player shows the live LED colour and a shield badge counting down to `until_ms`.
5. When the protection ends, the controller restores the player's current base colour.
6. Use case continues at step 14.

### A17: Shield feedback ends early

**Trigger:** The shielded player dies, wins (winner rainbow), disconnects, or the game ends while the shield of A16 runs (step 13)
**Flow:**

1. On death or the winner rainbow the controller manager ends the shield layer before that effect starts; on game end System sends `GAME_EFFECT_SHIELD` with `duration_ms=0` to every player with a full or partial shield still running, before the winner effects; this ends both shield layers (BR-010).
2. The controller manager cancels the shield renderer (no task is left) and shows the death effect, the rainbow or, at game end, the current base colour; the dashboard clears the badge on `player_death`, `game_ended` and `game_force_ended`.
3. Use case continues at step 14.

### A18: `end_game` evaluated in another game

**Trigger:** The agent writes `end_game` for one game while other games are live, real or shadow (step 13; #1310)
**Flow:**

1. The agent appends `end_game` to the event list of the game whose decision loop decided it. It refuses to write an intervention whose game id is empty or is not a coordinator game id (`game_…`), such as the `session-<n>` id of the partition for unlabeled signals, and records the refusal as a failed write (`agent_intervention_writes_total{result=error}`, `agent.action` span error), with no flag-service call and no retry (#1323, #1651).
2. The flag service renders the event list on that game's id only; every other live game resolves its own list, so it sees no new event: no force-end, no `agent_intervention` event, no backstop budget used.
3. The addressed game is force-ended through the same path as `ForceEndGame` for that `game_id`, real or shadow. Use case continues at step 14.

### A19: Per-player grant from an earlier decision or game

**Trigger:** A per-player grant flag (`shield_seconds`, `partial_shield_seconds`, `soft_penalty_action`) holds the grant of an earlier decision for player A, and the agent grants player B, or a new game starts (step 13; #1313)
**Flow:**

1. The agent writes each grant for (game, player); the flag service gives every write a fresh generated variant, so one decision is one change for one player, even when the value repeats.
2. On every re-evaluation the coordinator applies a grant only to a player whose resolved variant or value changed since the last read in this game and is not neutral. Player A's unchanged grant is not applied again when B is granted.
3. A new game starts with no grant: the earlier game's grants were dropped with its scope ([UC-053](UC-053.md) BR-003).
4. Use case continues at step 13 for player B only.

### A20: Scarce intervention budget

**Trigger:** The per-game budget (`policy.max_interventions_per_minute`) cannot admit every decision of the cycle (step 11; #1326)
**Flow:**

1. System offers the cycle's decisions to the rate limit in rank order (BR-014).
2. The first decision that passes the allow-list and battery checks but does not fit the remaining budget ends admission for the cycle: it and every lower-ranked decision of the cycle are blocked with `rate_limit` and charge nothing, so a cheaper, lower-ranked decision never spends the budget ahead of it. A decision that costs more than the whole budget can never fit and does not end admission.
3. A `send_controller_effect` decision is admitted only if the protective reserve is still free after charging it (BR-015). When it is not, it is blocked with `rate_limit` and the lower-ranked decisions are still offered.
4. Blocked decisions are recorded as in A10. Use case continues at step 12.

### A21: Decision the budget already refused

**Trigger:** A decision with the same intervention and target was already blocked with `rate_limit`, and the budget has not changed since: nothing was admitted and nothing left the 60 s window (step 11; #1326)
**Flow:**

1. System blocks it with `rate_limit` again and records it in the cycle's layer state and in `agent_decisions_total{blocked="true",block_reason="rate_limit"}`, and logs `agent.decision_rate_limit_repeat` at debug level.
2. System emits no `agent.decision` / `agent.action` span, no `agent.decision_blocked` warning and no narrative-timeline entry for the repeat. The cycle's `agent.decide` span still reports `decide.blocked=true` / `decide.block_reason=rate_limit`. The dashboard Agent tab therefore takes its blocked tallies (total, by intervention, by reason) from `agent_decisions_total{blocked="true"}` over its 10-minute window, not from the warning lines; it falls back to counting the warning lines only when VictoriaMetrics is unreachable or has no samples. The timeline keeps the first refusal per budget state.
3. Once the budget changes, the next refusal of that decision is recorded in full again (A10).
4. Use case ends.

### A22: Coordinator blocks the intervention

**Trigger:** The coordinator's re-check fails for an intervention the agent dispatched (step 13)
**Flow:**

1. The coordinator does not apply it and publishes `agent_intervention` with `blocked=true` and the reason: `not_allowed` (not in its allow-list), `mode_unsupported` (the mode's capability matrix denies it, e.g. `revive_player` in FFA), `low_battery`, `rate_limited` (global backstop) or `handler_error` (the handler failed). The agent's spans still read `act`, not blocked. While the allow-list the coordinator holds is older than the intervention (after a flagd reconnect, [UC-053](UC-053.md) A9 step 4), the intervention is deferred rather than checked, and checked once the allow-list catches up, so a stale allow-list never blocks or applies it.
2. Use case ends.

### A23: Probe mode

**Trigger:** The agent runs with `AGENT_PROBE_DECISIONS=true`, which replaces the rules engine with the probe engine, and the rules engine decides: on the rules backend (A1) or in a rules fallback (A2, A3). While a remote backend is selected, available and eligible, an allow-list of only `noop` (`probe`) leads to A14 instead: no remote call, no rules, so no probe decision (step 1)
**Flow:**

1. The probe engine emits one synthetic `noop` decision at most every 5 s and nothing else; there are no rules answers, so the cycle records no `agent.decide` span.
2. The `noop` passes the allow-list only when the list names `noop`, as the `probe` variant of `interventions_allowed` does (otherwise it is blocked `not_allowed`, A10); it then charges the per-game budget like a medium intervention (1.0), and the decision is recorded on `agent.decision` and `agent.action` spans.
3. The writer treats it as a successful write that changes no flag and calls no flag service; `agent_interventions_applied_total{action=noop}` increments. The whole decide and act path is exercised without a game effect.
4. Use case ends.

### A24: Per-player levels return to neutral

**Trigger:** During a game, a player whose `player_sensitivity_factor` or `player_handicap_factor` resolved to a non-neutral value resolves to neutral again because the agent cleared the player's value, including the last such player (step 13; #1317)
**Flow:**

1. The coordinator reads the player's level as neutral where its baseline for this game holds a non-neutral level.
2. The coordinator dispatches the neutral value as a revert: it resets that player's factor to neutral (1.0) without the permission chain or the backstop, so a kill switch or an exhausted budget can never leave the factor stuck (BR-017). Players whose level changed to another non-neutral value in the same read go through the permission chain (step 13).
3. A later non-neutral value for any player is a change again and is applied (step 13).
4. Use case continues at step 14.

### A25: A game ends and its per-player values are dropped

**Trigger:** A game ends, real or shadow, after per-player interventions were written for it (step 12; #1323)
**Flow:**

1. The game coordinator reports the end to the flag service ([UC-053](UC-053.md) step 7).
2. The flag service drops every value and event list of that game, including every per-player entry, and pushes the configuration once (BR-016).
3. The game's players resolve the neutral value in no other game: a serial belongs to one game, and other live games' values are untouched, so nothing is dispatched for them.
4. Use case ends.

### A26: Intervention side effect runs on the owning game's event loop

**Trigger:** The coordinator applies or reverts an intervention for a live game, real or shadow (step 13; #1250)
**Flow:**

1. The coordinator detects the change, updates the game's last-applied state and runs the enforcement chain on its own event loop, as in step 13 (BR-006, BR-012).
2. It hands the intervention's effect (the handler, a revert, the on-device agent cue) to that game's dispatcher, which runs it on the event loop of the game's own thread, where the game's audio and controller-manager clients and its gameplay stream were created (BR-018).
3. Effects for one game run one at a time, in the order the coordinator decided them: an effect starts only after the previous one has finished. Each game, real or shadow, uses its own loop.
4. The coordinator waits for the effect at most 5 s without blocking its own loop. An effect that has started is never cancelled, so it is never left half-applied.
5. If the effect did not complete, the coordinator logs a warning, counts it in `game_intervention_dispatch_failures_total{type,reason}`, records the outcome on the apply's `agent_intervention` event and goes on with the next flag and game. Not started because the game's loop is closed, not running or stopped first: skipped for good, blocked with `block_reason=game_loop_unavailable`. Not started within 5 s (queued behind a slow effect of the same game): skipped for good, blocked with `game_loop_timeout`. Started but not finished within 5 s: left to finish on the game loop, outcome unknown, recorded as not blocked with `block_reason=game_loop_late` and no agent cue. The on-device agent cue is best-effort: it is not sent for `end_game` (the game has just ended) or when `agent_intervention_cue` is off, and a cue that cannot run is only logged at debug level, not counted.
6. Use case continues at step 14.

### A27: The intervention write fails

**Trigger:** The flag service cannot be reached, does not answer within 500 ms, or refuses the write (503, an unknown game, any other non-success status) (step 12)
**Flow:**

1. System does not retry, except once after 100 ms when the flag service answers that the game is not live yet (`game_not_live`).
2. System counts `agent_intervention_writes_total{result=error}`, logs `agent.action_write_failed` (ERROR) and `agent.apply_failed`, and marks the `agent.action` span as an error; `agent_interventions_applied_total` does not increment. A refused game id (A18) is recorded the same way, without a flag-service call.
3. The decision has already charged the per-game budget and is recorded as dispatched; nothing reaches the game, so the game continues unchanged.
4. Use case ends.

### A28: Kill switch off at the start of a cycle

**Trigger:** `enabled` is off when System reads the flag snapshot, or flagd cannot be read, which resolves it to off (step 1)
**Flow:**

1. System decides nothing and calls no backend; it records a throttled `agent.disabled` span with the flags in effect ([UC-045](UC-045.md)).
2. Use case ends.

### A29: Agent shuts down while a remote call is in flight

**Trigger:** The agent receives SIGTERM or SIGINT while a remote decide call is in flight (step 5)
**Flow:**

1. The shutdown cancels the call; an answer that lands after the cancellation is dropped as well.
2. System records `outcome=discarded`, `discarded_reason=shutdown` on the `agent.decide` span; there is no rules fallback and no action. The agent waits for in-flight calls before it flushes its spans.
3. Use case ends.

## Postconditions

### Success Postconditions

- The intervention is written for the deciding game only, the game coordinator has applied it through the game's own code, and its decision is recorded in the game's trace (`agent.decision`, `agent.action`).

### Failure Postconditions

- The game was never paused or slowed by the agent (BR-001), no other game was changed (BR-002), and nothing was written to the flag service outside the allow-list, the per-game budget and the actuation gate (BR-004, FR-051).

## Business Rules

### BR-001: The game never waits

Remote calls are asynchronous; nothing in the game coordinator waits for the agent.

### BR-002: Interventions are game-scoped

Every intervention is written for the game whose decision loop decided it and resolves only in that game (FR-069, FR-136, [UC-053](UC-053.md)); a decision without a coordinator game id is not written.

### BR-003: Backend roles

See [C-018](../requirements.md#constraints).

### BR-004: Double enforcement

The allow-list is checked by the agent and again by the coordinator; the coordinator also enforces a global backstop (default 60 per minute).

### BR-005: No paid call without a possible action

A remote decide call is made only when the effective allow-list (deduplicated, empty ids and `noop` dropped, as for the `ffa.intervention` options) holds at least one intervention; otherwise the call could only answer `noop` (A14, NFR-011). The check sits before cadence and budget are charged. An answer already in flight when `interventions_allowed` flips to `none` is still blocked at landing by the live allow-list (`not_allowed`, A10). This covers in-game decide calls only: the post-game retro and the experiment proposer are governed by the kill switch and the LLM budget, not by the allow-list.

### BR-006: A one-shot intervention fires once, only in its game

A one-shot intervention is an event in its game's event list (FR-137, [UC-053](UC-053.md) BR-006). The coordinator applies, in order, every event with a sequence number above the last one it applied for that game and flag, exactly once; a game starts with an empty list, so an event of an earlier game, or from before a coordinator restart, is never applied in a new game (#1299). Fail closed on flagd errors: a read that returns an evaluation error applies nothing and does not move the last applied sequence number. A new, non-empty epoch (a flag-service restart) restarts the count. State flags are not affected: a game converges on its current value.

### BR-007: Every intervention sound resolves

Every sound id an intervention plays exists in the audio registry. The writer default `agent_cue` (`play_audio_cue`) and the shield sound `shield_up` are registry **aliases**: `agent_cue` plays the lobby ready ping (`Joust/sounds/beep_loud.ogg`, the sound a controller makes when it readies in the lobby), `shield_up` plays the Commander power-up sting (`Commander/sounds/power_ready.ogg`; an alias names an exact asset path). The audio service logs a WARNING for any sound id that is not in the registry (#1301).

### BR-008: Shield LED schedule

For `GAME_EFFECT_SHIELD` with duration T: the LED shows the shield colour (white, as in spawn protection) and its brightness falls linearly from 100 % to 30 % over the first T − 1 s; in the last 1 s it blinks at 4 Hz between full shield colour and off; at T it shows the player's current base colour. A shield of 1 s or less blinks for its whole duration. The controller manager renders the schedule at its effect rate (20 Hz) as a pure function of the time since the grant; the coordinator sends one command per grant, not a colour stream.

### BR-009: Partial shield is the weaker variant

For `GAME_EFFECT_PARTIAL_SHIELD` with duration T: the shield colour breathes slowly (0.5 Hz) between 10 % and 50 % brightness until the last 1 s, then blinks at 4 Hz between 50 % and off, then restores the base colour.

### BR-010: Feedback follows the protection, never the other way round

Feedback starts only when the grant changes the protection: a grant that extends the shield restarts the LED schedule with the new remaining time; a grant that is kept (the effective grace, `max(agent shield, admin invincibility)` per #817, already lasts longer) sends no feedback. The shield sound plays only on the transition from unprotected to protected; an extension restarts the LED silently. The LED effect, the sound and the `player_shielded` event are sent independently: one failing never skips the others. Feedback never changes `grace_until`, `invincible_until` or the partial-shield boost, and a feedback failure never fails the intervention; the coordinator keeps no timer or task for it.

On the controller the shield is a persistent **layer**, not a replaceable effect:

- Effects that do not touch the LED (rumble) neither end nor hide the shield.
- Short LED effects (death warning flash, agent pulse / flash, battery display) are drawn over the shield; when they end, the shield schedule continues at the point it has reached by then.
- A new base colour (a team or colour change during the game) does not end the shield; it is the colour shown when the shield ends.
- Death, the winner rainbow, a disconnect and `GAME_EFFECT_SHIELD` with `duration_ms=0` (game end) end the shield, the full and the partial layer alike.
- A full and a partial shield can be active together; the full one is shown, and when it ends while the partial one is still active the partial schedule continues. `GAME_EFFECT_PARTIAL_SHIELD` with `duration_ms=0` ends only the partial layer.

### BR-011: `end_game` ends only the game it was decided for

`end_game` is an event in the deciding game's event list. The coordinator force-ends only the session whose list holds it; it never resolves "the current game" or "the primary game" on the agent's behalf. A shadow game's decision can therefore never end the real game, and a real game's decision never ends a shadow. The agent never writes an intervention without a coordinator game id (#1310).

### BR-012: A per-player grant applies once per decision

The per-player grant flags `shield_seconds`, `partial_shield_seconds` and `soft_penalty_action` are one-shot, time-boxed effects. Each write gets a fresh variant from the flag service; the coordinator change-detects grants per player on the resolved variant and value within the game and dispatches one intervention per changed player with `target` = that serial, so the battery guard and the backstop apply per grant. Fail closed: a per-player read that returns an evaluation error does not move that player's last-seen grant. The coordinator sees what flagd serves after each push: two grants to the same player pushed in one configuration collapse to the later one, which is applied once (#1323). A cleared grant resolves to the neutral value, which is never applied. The level flags `player_sensitivity_factor` and `player_handicap_factor` are not grants: re-applying an unchanged factor is a no-op (BR-017).

### BR-013: Agent spans sit under the game cycle

The agent's in-game spans belong to the running game cycle. `agent.signal_received` (and so the rules-path `agent.decide`, `agent.decision` and `agent.action` under it) and the remote path's async `agent.decide` are remote children of the coordinator's `game_cycle` span. The agent learns that span's id from the `game_cycle_span_id` label (UC-041 BR-004). When it is not known, the parent is `gameplay_phase`, then the game root span; with no game ids at all the span is its own root. Each `agent.decision` keeps its Link to the game root in every case, and the spans keep their backdated start times and their `link.kind=fire_cycle` Link.

Each `agent.intervention.effect` span is a direct child of the `agent.decision` that dispatched the intervention: one span per evaluated fitness signal, backdated to dispatch time and ended after the follow-up window, with no effect span parenting another (#1325). The effect span outlives its decision by design (the window is 20 s); a child that ends after its parent is valid in OTel and keeps the cause one click away, whereas a `game_cycle` parent with a Link would hide the cause behind a Link and still end after `game_cycle` when the game ends inside the window.

### BR-014: A scarce budget goes to the highest-ranked decision

Within one cycle, decisions reach the per-game weighted rate limit in rank order (rules: the engine's score order; remote: the single answer). Admission stops at the first decision that passes the allow-list and battery checks but does not fit the remaining budget, unless its cost exceeds the whole budget: every lower-ranked decision of that cycle is blocked with `rate_limit` and charges nothing (A20). A decision the budget refused is reported in full once per budget state (the state changes when an intervention is admitted or one leaves the 60 s window); repeats in between are counted and logged at debug level but emit no `agent.decision` span (A21). When the budget covers every decision of the cycle nothing changes: every decision is admitted in rank order, so the rules ranking and the rules path golden are unchanged.

### BR-015: Nudges keep a reserve for protective interventions

A `send_controller_effect` decision (R8 statue nudge, R9 random effect, or a remote answer) is admitted only when the window still has room for one medium intervention (1.0, the cost of `grant_shield` and `adjust_player_sensitivity`) after charging it. The reserve does not apply when `chaos` is the strictly dominant objective weight (the decision's weights, else the `objectives` flag): then the operator asked for chaos and a nudge is the most valuable decision. It also does not apply when `interventions_allowed` permits no protective intervention (`grant_shield`, `partial_shield`, `adjust_player_sensitivity`, `set_player_handicap`; e.g. the shipped `ambient`): nothing could use the reserve, so nudges may spend the whole budget. With the default budget of 2 and a protective intervention allowed, nudges spend at most 1.0 per minute (two nudges) and a shield or handicap finds 1.0 free; with `conservative` (1) no nudge applies unless chaos dominates.

Accepted limit: only `send_controller_effect` keeps the reserve. The other soft interventions, `play_audio_cue` and `adjust_volume` (also 0.5), do not, so they can still take the last 0.5 or 1.0 before a shield fires in a later cycle. In the same cycle BR-014 still ranks them below a higher-ranked shield. Today R2's calming cue is the only rule that emits one, and only early in an endurance session.

Why a reserve and not a new rule priority or a per-player cooldown (#1326): under the stage objectives `balanced_focused` (balanced 0.7, chaos 0.1) R8 scores at most 0.1 × 1.0 = 0.1, the `minScore` floor, while R3 (handicap) and R4 (shield) score 0.7 × urgency, so the ranking already puts shield and handicap first. The starvation came from cost: a 0.5 nudge fits a half-free budget that a 1.0 shield does not, so nudges took every freed half slot. A fixed priority would override the operator's weights under `chaos_focused`, and a per-player cooldown does not bound six statue players, who are six different targets.

### BR-016: Per-player entries live only as long as their game

Per-player values exist only in a live game's scope on the flag service, so the rendered configuration and flagd's evaluation cost grow with the games currently running, not with the history of games. When the game ends the flag service drops every value of the game in one push (A25, [UC-053](UC-053.md) BR-003); a game scope older than 1 h is dropped as well (UC-053 A11). No agent-side pruning is needed.

### BR-017: Per-player levels belong to one game

A game starts with neutral factors: a level is written for one game and dropped with it (BR-016), so a new game never inherits an earlier game's level. During the game the coordinator dispatches a level change only for the players whose resolved level differs from the last read in this game (alive players that pass the battery guard); a player whose level moves to neutral is reset to neutral (A24). The reset is a revert to neutral: it runs without the permission chain and does not count against the backstop. Fail closed: a per-player read that returns an evaluation error is ignored and never moves the last-seen level.

### BR-018: Intervention side effects run on the owning game's event loop

Each game runs on its own thread and event loop, and its gRPC clients (audio, controller manager) and gameplay stream belong to that loop; awaiting them from another loop fails with "attached to a different loop" (#1250). The coordinator therefore keeps change detection, baselines and the enforcement chain on its own loop, and runs every intervention side effect (apply handler, revert handler, agent cue) on the loop of the game it was evaluated for, one at a time in decision order per game. `end_game` is the exception: it ends the session through the servicer's force-end path on the coordinator's loop, because that path joins the game's thread, and it sends no agent cue. The coordinator waits at most 5 s per effect and never blocks its own loop or deadlocks. An effect that has not started by then, or whose game loop is closed or stopping, is never applied (`game_loop_unavailable` / `game_loop_timeout`, recorded as blocked). An effect that has started is never cancelled, because cancelling it midway could leave the game half-changed; if it is still running at 5 s its outcome is unknown (`game_loop_late`, not recorded as blocked). Each such case is logged and counted (A26).

Accepted limit: the wait is per game but sequential across games. A game whose loop is stuck delays the interventions of the games evaluated after it in the same pass by up to 5 s per pending effect (head-of-line delay); its own later effects are skipped as `game_loop_timeout`. A stuck shadow game can therefore delay the real game's interventions, but never block or corrupt them.
