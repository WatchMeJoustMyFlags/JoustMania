# Use Case: Decide an In-Game Intervention

## Overview

**Use Case ID:** UC-040
**Use Case Name:** Decide an In-Game Intervention
**Primary Actor:** Agent
**Secondary Actors:** Model API, Player
**Goal:** Nudge a running game toward the active objectives with a bounded, reversible intervention
**Trigger:** A telemetry batch updates a game's context (UC-041) while the game is active and at least one player is fresh; the [glossary](../glossary.md) owns the definitions of **Fresh player** and **Evaluation gate** (a context that fails the gate is not evaluated and nothing is recorded)
**Status:** Tested
**Requirements:** FR-043, FR-044, FR-046, FR-047, FR-048, FR-049, FR-050, FR-051, FR-052, FR-053, FR-054, FR-069, NFR-010, NFR-011, NFR-012, NFR-013, NFR-015, NFR-050, C-002, C-004, C-018
**Planned:** FR-160 (#1837, Implemented: shipped in PRs #1865, #1871, #1873, #1874; stays here, not under Requirements, until the hardware check #1465 lets it be Verified, because a Tested use case would derive Verified), FR-161 and FR-162 (#2096, In Progress: the game coordinator's pool, grants, refusals and latch (A36, A37 step 2, A38, A39, BR-024, BR-025, BR-027), the `hold` variant of `shield.activation`, the controller feedback (BR-026), the dashboard bar (UC-035 BR-008) and the agent's view and ledger checks (step 4, A37 step 1; the coordinator's hold gauges) are implemented; `shield_energy_full` (A38 step 3) is a later PR of #2096; FR-162 is Implemented: the experiment catalog and the deferred promotion, UC-043 A17)

## Preconditions

- The agent observes the game and holds one context per game id (UC-041).
- The game coordinator registered the game with the flag service, so the game has a scope there ([UC-053](UC-053.md)).

## Main Success Scenario

1. System reads the live flag snapshot (objectives, policy, `decision.*`) and finds the kill switch `enabled` on (A28); this scenario follows a remote backend (rules: A1). The agent evaluates flags without a resolver cache, so a flip is seen on the next read ([flags.md §1.3](../specs/flags.md#13-reload-semantics), #1715); this applies to every flag read in this use case (steps 1 and 7, A6, A7, A28).
2. System sees `decision.backend` = jev (the main in-game backend), claude (the manual backup) or openai, and the backend is available (jev: `JEV_API_KEY`; claude: key + model; openai: key + model + base URL).
3. System checks that no remote call is in flight for this game, that the game kind is eligible (`llm.eligible_game_kinds`, default `real_only`: real games only), that the allow-list offers at least one intervention besides `noop` (BR-005), that `decision.min_interval_ms` (default 3 s) has passed since the previous call of this game started and `decision.min_gap_after_answer_ms` (default 1 s) since it ended (an answer, a timeout or a failure ends a call, #2123), and that the global budget (`llm.max_requests_per_minute`, default 6) has room.
4. System builds the state (narrative, players with the danger signals, `shielded` and `shield_charged`, and in a hold game the energy fields instead of `shield_charged` (#2096), `shield_limited` for a player the agent would refuse another shield on the cap, the cooldown or the hold pool or budget, and the per-player factors the agent already applied (#2066; [decide-contract.md](../specs/decide-contract.md) §1.2), digest) and the FFA questions: which intervention (noop or an allowed type), which target, what magnitude (questions, answers and validation: [decide-contract.md](../specs/decide-contract.md)).
5. System calls the backend asynchronously with `decision.<backend>.timeout_ms` (claude 5000 ms, jev and openai 2500 ms by default); the game keeps running.
6. The backend answers; System parses and validates the answers strictly.
7. System re-reads the live flags (step 1 caveat): the kill switch is still on and `decision.backend` is unchanged.
8. System checks the answers for consistency (not invalid) and that the intervention is not `noop`.
9. The `ffa.intervention` confidence is at least the answering backend's act threshold, read now (#1287): for jev `decision.jev.act_confidence_threshold` (default 0.6; variant `inherit` uses the global), for claude and openai `decision.act_confidence_threshold` (default 0.8). Outcome `act`; the span records the effective threshold and its source (`jev` / `global`).
10. System re-reads the current context: it exists, the game is still active, the target (if any) is still present, and the state the request was built on is not older than `decision.max_state_age_ms` (#2123).
11. System runs the permission chain: allow-list, battery threshold, the experiment-flag check (a lever of the flag under test in an experiment game: A40, BR-028), the already-applied check (a state or level intervention only, when suppression is on: A35, BR-023), the shield ledger (a targeted `grant_shield` only: A31, A33), per-game weighted rate limit.
12. System writes the intervention to the flag service for this game (`interventions` set, scoped to the game id, and to the player's serial for a per-player intervention; a one-shot intervention is appended to the game's event list) ([UC-053](UC-053.md)); the write is gated by `interventions_enabled` (A11) and can fail (A27).
13. The game coordinator picks up the flag change, re-checks the allow-list, the mode's capabilities, battery and its global backstop, and applies the intervention through the game's own code (e.g. tempo change, shield (in trigger mode, Free-for-All only, a shield charge the player activates, A30; in hold mode, energy added to the player's pool, A36), elimination; a toughness boost lasts at most 30 s and its boost is clamped to 1.0 to 2.0), publishing `agent_intervention`; after an applied HARD-class intervention it pulses the targeted controller (or every active player for a game-wide intervention) unless `agent_intervention_cue` is off (#818; the pulse is magenta (255,0,192), the colour of the helped cue, #2426); a player-targeted intervention is also recorded as an event on that player's span carrying `player.serial` and `player.name`. A one-shot intervention applies once, and only in the game whose event list holds it (BR-006). `end_game` ends only the game it was decided for (BR-011), and a per-player grant (`grant_shield`, `toughness_boost`, `soft_penalty`) applies once per decision, to the player it targets (BR-012). The intervention's side effect runs on the game's own event loop (BR-018, A26). A `grant_shield` is also limited per player per game by a cap and a cooldown (BR-022, A34). An applied `grant_shield` first pulses the helped controller magenta (255,0,192), before the shield colour (A42, BR-031); once the game is ending a `grant_shield` is refused `game_ending` (A42 step 3).
14. System records `agent.decide`, `chat {model}`, `agent.decision` and `agent.action` spans (a player-targeted decision names the player with `player.serial` and, when known and the game is not a shadow game, `player.name`) and later measures the effect of each dispatched decision (`agent.intervention.effect`, correlated by that decision's own `decision.intervention_id`; a cycle has no id), all inside the game's trace (BR-013). This holds on every path: a decision that lands on the remote path, including its rules fallback, takes its fitness baseline from the current context at landing (#1699). Only a written decision is measured: a gated no-op (A11) or a failed write (A27) gets no effect span and no id. The rationale on the spans keeps its first 256 runes and appends `...` when longer. Interventions a player can perceive give feedback in the game: an audio cue plays a real sound (BR-007), and a shield plays a sound and shows on the player's LED and on the dashboard (A16, A17).

## Alternative Flows

### A1: Rules backend (default)

**Trigger:** `decision.backend` is `rules` (step 2)
**Flow:**

1. System ranks rule candidates by objective weight × urgency × fitness pressure and emits up to two decisions per evaluation (at most one evaluation per second).
2. System records the rules answers as the first emitted decision (intervention and target, even one the allow-list will block), with `outcome=act`.
3. If the ranking emitted nothing, System records no span and counts the cycle in `agent_evaluations_total{outcome=idle}`; use case ends.
4. Otherwise use case continues at step 11 (no confidence routing).

### A2: Remote timeout, error or invalid answer → rules fallback

**Trigger:** The call times out, fails (HTTP error including 429) or the answer fails validation (step 5 or 6)
**Flow:**

1. After the kill-switch and backend checks (step 7), System records `outcome=fallback` with `fallback_reason` = timeout, error or invalid_answer.
2. System lets the rules engine decide on the **current** context. If the context is gone or the game has ended, nothing is decided and the span carries `outcome=fallback` **with** `discarded_reason` = `stale_context` or `game_ended`, and use case ends; it also ends when the rules emit nothing.
3. Otherwise use case continues at step 11.

### A3: Backend unavailable, ineligible or over budget → rules now

**Trigger:** Unknown backend, missing key / model, no re-validation source, ineligible game kind or exhausted budget (step 2 or 3)
**Flow:**

1. After the in-flight check (A4), System checks in this order: the backend (`unknown_backend`, `backend_unavailable`; `async_not_wired` when the loop has no context provider to re-validate a late answer, which the shipped agent always wires, so only a hand-built loop in a test produces it), the game kind (`llm_not_eligible`), then the allow-list (A14), the cadence (A4) and the budget (`llm_budget_exhausted`). So an unknown, unavailable or ineligible backend falls back to rules even when the allow-list is empty; the allow-list then blocks their decisions (A10).
2. System records `outcome=fallback` with the reason (`unknown_backend`, `backend_unavailable`, `async_not_wired`, `llm_not_eligible`, `llm_budget_exhausted`) on the cycle's `agent.decide` span and counts it in `agent_llm_gated_total{reason}`. When the rules emit nothing in that cycle, only the configuration fallbacks (`unknown_backend`, `backend_unavailable`, `async_not_wired`) still emit the span, at most one per reason per `decision.throttle_seconds`; `llm_not_eligible` and `llm_budget_exhausted` are then counted only. A game entering or changing a configuration fallback logs a WARN `agent.decide.backend_misconfigured`, and an INFO when it clears.
3. Rules decide in the same cycle (A1); when they emit nothing, use case ends.
4. Otherwise use case continues at step 11.

### A4: Cadence or in-flight gate

**Trigger:** A call is in flight for this game, the minimum interval has not passed since the previous call started, or the gap has not passed since it ended (step 3)
**Flow:**

1. System makes no decision this cycle (rules stay quiet; not a fallback) and records no span. A call in flight is not counted; an unmet interval or gap counts `agent_llm_gated_total{reason=decide_interval}` and logs `agent.decide.cadence_wait` at debug level. The gap clock starts when the previous call returns, whatever its outcome: an answer, a timeout or a failure, before the answer is checked or acted on (#2123). Two calls of one game are never in flight together.
2. Use case ends.

### A5: Low confidence → held

**Trigger:** Confidence below the threshold (step 9)
**Flow:**

1. System records `outcome=held` and does nothing. The context is not checked first, so a low-confidence answer that lands after the game ended is `held`, not `discarded`.
2. Use case ends.

### A6: Kill switch mid-flight → discarded

**Trigger:** `enabled` was turned off while the call was in flight (step 7, the first check on landing)
**Flow:**

1. System records `outcome=discarded`, `discarded_reason=kill_switch`; neither the answer nor a rules fallback acts. When the call had failed or timed out, the span also carries its `decide.fallback_reason`.
2. Use case ends.

### A7: Situation changed → discarded

**Trigger:** The backend changed (step 7), or, for an answer that would act, the context is missing, the game ended, the target is gone or the state the request was built on is older than `decision.max_state_age_ms` (default 10 s, #2123) (step 10)
**Flow:**

1. System records `outcome=discarded` with `backend_changed` (step 7) or `stale_context`, `game_ended`, `target_gone`, `state_too_old` (step 10), and counts it in `agent_decide_discarded_total{reason}` (every remote `agent.decide` span that carries a `discarded_reason` is counted, #2123).
2. Use case ends.

### A8: Inconsistent answers → invalid

**Trigger:** E.g. `noop` with a target, or a player intervention without a target (step 8)
**Flow:**

1. System records `outcome=invalid` with `invalid_reason`; no action and no fallback.
2. Use case ends.

### A9: Noop

**Trigger:** The backend chose `noop` (step 8)
**Flow:**

1. System records `outcome=noop`.
2. Use case ends.

### A10: Blocked

**Trigger:** Not allowed, battery below `policy.battery_threshold`, refused by the shield ledger (`already_charged`, A31; `shield_cap_reached` or `shield_cooldown`, A33), the same value already applied (`already_applied`, A35) or rate limit reached (step 11)
**Flow:**

1. System records the decision as blocked with the reason on `agent.decision` and as `decide.blocked` / `decide.block_reason` on `agent.decide`; the outcome stays `act`; nothing is written. A scarce budget is spent in rank order (A20, BR-014); a repeat the budget already refused emits no new `agent.decision` span (A21).
2. Use case ends.

### A11: Actuation gate off

**Trigger:** `interventions_enabled` is off (step 12)
**Flow:**

1. Nothing is written and no write is counted; the decision has already charged the per-game budget and its `agent.action` span is recorded. `agent_interventions_applied_total` does not increment: it counts only interventions that were written (#1681). The decision gets no effect sample and no `decision.intervention_id`.
2. System records the drop on the `agent.decision` and `agent.action` spans as `decision.applied=false` with `decision.not_applied_reason=write_gate_off` (a written decision carries `decision.applied=true`; a failed write A27 carries `decision.applied=false` with `write_failed`), so the dashboard shows `not applied: write gate off (interventions_enabled)` and never `allowed` for a write that did not happen (#2093). Behaviour is unchanged: only the record differs.
3. Use case ends.

### A12: Noul questions

**Trigger:** A request contains a `noul` (yes/no, P(yes)) question (shipped in PR #1261). Today that is only the internal `jev.gate` noul the Jev backend asks every stage-1 round ([decide-contract.md §3.1](../specs/decide-contract.md), A13); the FFA questions of step 4 hold no noul (step 4)
**Flow:**

1. Jev answers it natively (confidence \|2p − 1\|); the rules engine answers a noul with 0.5 at confidence 0. Claude and OpenAI support no noul: they would reject such a request before any network call (`invalid_answer`, then rules decide as in A2), but no caller sends them one today.
2. Use case continues at step 6.

### A13: Two-stage Jev round (gated)

**Trigger:** `decision.backend` is jev (step 5; PR #1265, gate #1281)
**Flow:**

1. System's first Jev call asks the gate noul "Does the game need an intervention right now?" and `ffa.intervention` without `noop` in the same call.
2. System synthesises the `ffa.intervention` answer as `{noop: 1 − p_yes, Jev's pick: p_yes, others: 0}`, so its confidence is p_yes when acting, and records Jev's real p_yes and distribution on the stage-1 span.
3. If p_yes ≤ 0.5 the answer is `noop` and no second call is made; use case continues at step 6 (then A9).
4. Otherwise, if the chosen intervention needs a target or a magnitude, System makes a second Jev call conditioned on it (target among alive players described by suitability; magnitude levels of that intervention only, no neutral level, the most likely level wins with ties going to the gentler level; for two-way levers Go picks the direction from the danger signals and Jev picks the strength).
5. Both calls share the `decision.jev.timeout_ms` deadline; a stage-2 failure fails the whole round (A2).
6. Use case continues at step 6; at step 9 p_yes is compared with Jev's own `decision.jev.act_confidence_threshold` (default `gate` 0.6, calibrated for p_yes: collapsing and near-threshold act, calm and dragging are noop; A5 when below). With the `inherit` variant the global `decision.act_confidence_threshold` applies instead (default 0.8 holds every calibrated state).

### A14: No interventions allowed → no remote call

**Trigger:** The effective allow-list is empty: `interventions_allowed` resolves to `none` (or to a list that holds only `noop` or empty ids, e.g. `probe`; or, in an experiment game, only levers of the flag under test, A40 step 5, #2251), so `noop` would be the only `ffa.intervention` option, while a remote backend is selected, available and the game kind eligible (step 3; #1298). On the rules backend, and when A3's backend or eligibility fallback applies first, this flow does not apply: the rules run and the allow-list blocks what they emit (A10).
**Flow:**

1. System makes no remote call: no Jev, Claude or OpenAI request is built or sent, and neither the cadence (`decision.min_interval_ms`) nor the global budget (`llm.max_requests_per_minute`) is charged.
2. System does not run the rules engine either (nothing it could emit would pass the allow-list) and records no fallback and no `agent.decide` span.
3. System increments `agent_llm_gated_total{reason=no_interventions_allowed}` and writes a debug log `agent.decide.no_interventions_allowed` only when the game enters or leaves this state.
4. As soon as the allow-list offers an intervention again, the next cycle continues at step 3.

### A15: One-shot interventions of an earlier game

**Trigger:** A game starts after one-shot interventions (`audio_cue`, `controller_effect`, `eliminate_player`, `revive_player`, `end_game`) were applied in an earlier game, and a later flag change makes the coordinator re-evaluate during the new game (step 13)
**Flow:**

1. The earlier game's event list was dropped with its scope when that game ended ([UC-053](UC-053.md) BR-003); the new game is registered with an empty event list.
2. On the re-evaluation the new game's list holds no event, so nothing is applied and no `agent_intervention` is published.
3. An event appended for the new game has the next sequence number and is applied once. Use case continues at step 13.

### A16: Shield feedback for the player

*In trigger mode (#1837) the feedback is the charge of A30 and the activation of UC-030 A6.*

**Trigger:** The coordinator grants or extends a `grant_shield` or `toughness_boost` for a player (step 13; #1301)
**Flow:**

1. For a `grant_shield`, System first sends the helped cue (A42, BR-031). System sends the player's controller a `GAME_EFFECT_SHIELD` (`grant_shield`) or `GAME_EFFECT_TOUGHNESS_BOOST` (`toughness_boost`) with `duration_ms` = the remaining protection; the controller manager renders the LED schedule itself (BR-008, BR-009). For a `GAME_EFFECT_SHIELD` it also gives an "ending soon" double pulse about 1 s before the protection ends (BR-021, #2094).
2. System plays the shield sound `shield_up` (full volume for `grant_shield`, half volume for `toughness_boost`) (BR-007).
3. System publishes the game event `player_shielded` (`serial`, `kind` = `full` or `toughness_boost`, `seconds`, `until_ms`; the dashboard also renders the pre-#1838 kind `partial` as the toughness boost badge, so an older coordinator never shows as an immune full shield) and records the span event `shield_feedback` on the player's span.
4. The dashboard tile of the player shows the live LED colour and a shield badge counting down the event's `seconds` from the browser's monotonic receipt time (`performance.now()`, #2387); `until_ms` is never compared with the browser clock, so a Pi/browser clock skew (a Pi without an RTC) neither hides nor prolongs the badge. An event without a usable `seconds` falls back to `until_ms` against the browser clock.
5. When the protection ends, the controller restores the player's current base colour.
6. Use case continues at step 14.

### A17: Shield feedback ends early

*A held shield charge (#1837) ends the same way, A32.*

**Trigger:** The shielded player dies, wins (winner rainbow), disconnects, or the game ends while the shield of A16 runs (step 13)
**Flow:**

1. On death or the winner rainbow the controller manager ends the shield layer before that effect starts; on game end System sends `GAME_EFFECT_SHIELD` with `duration_ms=0` to every player with a full shield or a toughness boost still running, before the winner effects; this ends both shield layers (BR-010).
2. The controller manager cancels the shield renderer (no task is left) and shows the death effect, the rainbow or, at game end, the current base colour; the dashboard clears the badge on `player_death`, `game_ended` and `game_force_ended`.
3. Use case continues at step 14.

### A18: `end_game` evaluated in another game

**Trigger:** The agent writes `end_game` for one game while other games are live, real or shadow (step 13; #1310)
**Flow:**

1. The agent appends `end_game` to the event list of the game whose decision loop decided it. Without a coordinator game id it writes nothing (BR-002).
2. The flag service renders the event list on that game's id only; every other live game resolves its own list, so it sees no new event: no force-end, no `agent_intervention` event, no backstop budget used.
3. The addressed game is force-ended through the same path as `ForceEndGame` for that `game_id`, real or shadow. An `end_game` for a game whose end is already under way waits for that end and publishes no second `game_force_ended` (the intervention itself is still recorded as `agent_intervention`) ([UC-027](UC-027.md) A4, #1827). Use case continues at step 14.

### A19: Per-player grant from an earlier decision or game

**Trigger:** A per-player grant flag (`shield_seconds`, `toughness_boost_seconds`, `soft_penalty_action`) holds the grant of an earlier decision for player A, and the agent grants player B, or a new game starts (step 13; #1313)
**Flow:**

1. The agent writes each grant for (game, player); the flag service gives every write a fresh generated variant, so one decision is one change for one player, even when the value repeats.
2. On every re-evaluation the coordinator applies a grant only to a player whose resolved variant or value changed since the last read in this game and is not neutral. Player A's unchanged grant is not applied again when B is granted.
3. A new game starts with no grant: the earlier game's grants were dropped with its scope ([UC-053](UC-053.md) BR-003).
4. Use case continues at step 13 for player B only.

### A20: Scarce intervention budget

**Trigger:** The per-game budget (`policy.max_interventions_per_minute`) cannot admit every decision of the cycle (step 11; #1326)
**Flow:**

1. System offers the cycle's decisions to the rate limit in rank order (BR-014).
2. The first decision that passes the allow-list and battery checks but does not fit the remaining budget ends admission for the cycle: it and every lower-ranked decision of the cycle are blocked with `rate_limit` and charge nothing, so a cheaper, lower-ranked decision never spends the budget ahead of it. A decision that costs more than the whole budget can never fit and does not end admission.
3. A `send_controller_effect` decision is admitted only if the protective reserve is still free after charging it (BR-015). When it is not, it is blocked with `rate_limit` and the lower-ranked decisions are still offered.
4. Blocked decisions are recorded as in A10. Use case continues at step 12.

### A21: Decision the budget already refused

**Trigger:** A decision with the same intervention and target was already blocked with `rate_limit`, and the budget has not changed since: nothing was admitted and nothing left the 60 s window (step 11; #1326)
**Flow:**

1. System blocks it with `rate_limit` again and records it in the cycle's layer state and in `agent_decisions_total{blocked="true",block_reason="rate_limit"}`, and logs `agent.decision_rate_limit_repeat` at debug level.
2. System emits no `agent.decision` / `agent.action` span, no `agent.decision_blocked` warning and no narrative-timeline entry for the repeat. The cycle's `agent.decide` span still reports `decide.blocked=true` / `decide.block_reason=rate_limit`. The dashboard Agent tab therefore takes its blocked tallies (total, by intervention, by reason) from `agent_decisions_total{blocked="true"}` over its 10-minute window, not from the warning lines; when VictoriaMetrics is unreachable it shows them as `n/a`, and with no samples as zero (#2059). The timeline keeps the first refusal per budget state.
3. Once the budget changes, the next refusal of that decision is recorded in full again (A10).
4. Use case ends.

### A22: Coordinator blocks the intervention

**Trigger:** The coordinator's re-check fails for an intervention the agent dispatched (step 13)
**Flow:**

1. The coordinator does not apply it and publishes `agent_intervention` with `blocked=true` and the reason: `not_allowed` (not in its allow-list), `mode_unsupported` (the mode's capability matrix denies it, e.g. `revive_player` in FFA), `low_battery`, `rate_limited` (global backstop) or `handler_error` (the handler failed). `already_charged` (a `grant_shield` to a player who holds a shield charge, A31; #1837). `shield_pool_full` and `shield_budget_exhausted` (a `grant_shield` in a hold game that could add nothing, A37; nothing applied, the backstop reservation is refunded, not counted against BR-022; #2096). `shield_cap_reached` and `shield_cooldown` (a `grant_shield` refused by the shield limits per player per game, A34, BR-022; nothing applied, the backstop reservation is refunded; #2044). `revive_refused` (the mode refused a `revive_player`: the game is decided or not running, or the player is unknown or already alive; the handler applies nothing, the backstop reservation is refunded; #1948, UC-023 BR-004, UC-026 BR-003). `eliminate_refused` (an `eliminate_player` that killed nobody: the player is unknown or already dead, a kill of the same player is in flight, the game is force-ended (every mode, UC-030 step 9, #2033; the force-end is applied on the game's loop, so an `eliminate_player` there is either counted before it or refused, #2149), or the mode declined the kill (UC-030 step 9, e.g. every mode with the default kill gate once the game's outcome is latched, #2019, Swapper once its win is latched, UC-024 BR-004, Tournament for a waiting player, a fighter in grace, between matches or after the champion is latched, or Fight Club for a waiting player, a combatant in its invincibility, between rounds or after the winner is latched, UC-025 BR-006); the handler applies nothing, the backstop reservation is refunded; #1383). `experiment_override` (a `pacing_profile` in an experimental-arm shadow game whose experiment sets `windows` to a value other than the requested preset: the experiment's windows stay, the handler applies nothing and the backstop reservation is refunded; a preset whose value equals the experiment's is applied; a failed flag read on either side is a flag error, never an override, and the handler applies what it read, as before; [UC-043](UC-043.md) BR-005, #1970). The agent's spans still read `act`, not blocked. While the allow-list the coordinator holds is older than the intervention (after a flagd reconnect, [UC-053](UC-053.md) A9 step 4), the intervention is deferred rather than checked, and checked once the allow-list catches up, so a stale allow-list never blocks or applies it.
2. Use case ends.

### A23: Probe mode

**Trigger:** The flag `decision.probe_decisions` is on (agent set, default off; read every decision cycle, so a flip changes the next cycle; off while flagd cannot resolve it, no env fallback; #1810, #1907), which replaces the rules engine with the probe engine for that cycle (never in a pattern game, UC-046), and the rules engine decides: on the rules backend (A1) or in a rules fallback (A2, A3). While a remote backend is selected, available and eligible, an allow-list of only `noop` (`probe`) leads to A14 instead: no remote call, no rules, so no probe decision (step 1)
**Flow:**

1. The probe engine emits one synthetic `noop` decision at most every 5 s and nothing else; there are no rules answers, so the cycle records no `agent.decide` span.
2. The `noop` passes the allow-list only when the list names `noop`, as the `probe` variant of `interventions_allowed` does (otherwise it is blocked `not_allowed`, A10); it then charges the per-game budget like a medium intervention (1.0), and the decision is recorded on `agent.decision` and `agent.action` spans.
3. The writer treats it as a successful write that changes no flag and calls no flag service; `agent_interventions_applied_total{action=noop}` increments. The whole decide and act path is exercised without a game effect.
4. Use case ends.

### A24: Per-player levels return to neutral

2. 2. The flag service drops every value and event list of that game, including every per-player entry, and pushes the configuration once (BR-016).

### A26: Intervention side effect runs on the owning game's event loop

**Trigger:** The coordinator applies or reverts an intervention for a live game, real or shadow (step 13; #1250)
**Flow:**

1. The coordinator detects the change, updates the game's last-applied state and runs the enforcement chain on its own event loop, as in step 13 (BR-006, BR-012).
2. It hands the intervention's effect (the handler, a revert, the on-device agent cue) to that game's dispatcher, which runs it on the event loop of the game's own thread, where the game's audio and controller-manager clients and its gameplay stream were created (BR-018).
3. Effects for one game run one at a time, in the order the coordinator decided them: an effect starts only after the previous one has finished. Each game, real or shadow, uses its own loop.
4. The coordinator waits for the effect at most 5 s without blocking its own loop. An effect that has started is never cancelled, so it is never left half-applied.
5. If the effect did not complete, the coordinator logs a warning, counts it in `game_intervention_dispatch_failures_total{type,reason}`, records the outcome on the apply's `agent_intervention` event and goes on with the next flag and game. Not started because the game's loop is closed, not running or stopped first: skipped for good, blocked with `block_reason=game_loop_unavailable`. Not started within 5 s (queued behind a slow effect of the same game): skipped for good, blocked with `game_loop_timeout`. Started but not finished within 5 s: left to finish on the game loop, outcome unknown, recorded as not blocked with `block_reason=game_loop_late` and no agent cue. The on-device agent cue is best-effort: it is not sent for `end_game` (the game has just ended) or when `agent_intervention_cue` is off, and a cue that cannot run is only logged at debug level, not counted.
6. Use case continues at step 14.

### A30: Shield charge granted

**Trigger:** A `grant_shield` is applied while the game's activation mode is `trigger` (BR-019) and the player holds no charge (step 13; #1837, FR-160)
**Flow:**

2. System sends `GAME_EFFECT_SHIELD_CHARGE` to the player's controller with a bounded `duration_ms` and re-sends it while the charge is held (BR-021). The controller breathes the player's colour and plays the charge rumble pattern: a grant pattern, a reminder pulse every few seconds while the charge is held, and a double pulse shortly before it expires (BR-021, #2094).
3. System publishes the game event `player_shield_charged` (`serial`, `seconds`, `expires_ms`, `"0"` = never), records the span event `shield_charge_granted` on the player's span and starts the span `game.shield_charge`.

### A31: Grant to a player who holds a charge

**Trigger:** A `grant_shield` targets a player who already holds a shield charge (step 13; BR-020)
**Flow:**

1. In trigger mode only (BR-019), the agent gives a player at most one shield charge per window: it blocks a `grant_shield` as `already_charged` when its own charge ledger holds a grant to that player in this game. Trigger mode for the agent means a Free-for-All game (`game.mode` `FFA`), a real game, and `shield.activation` resolving to `trigger` for this game when the agent reads it from the `game` flag set with `gameId` and `game_kind=real`. The coordinator's grant read carries the game's context as well (BR-018), but targeting on these two flags may use only `gameId` and `game_kind` (flags.md §4), and the agent reads them only for a real game, so both resolve the same value. A `hold` read follows the coordinator's latch (BR-019, BR-027): the agent remembers, per game, the first mode it read (for at most 1 h; an unreadable read records nothing), and it makes that first read when it first sees the game (its first signal, a few seconds after the start), not at its first `grant_shield` decision, and a later `hold` read in a game it first read as `trigger` stays trigger, so a flip to `hold` mid-game does not make the ledger inert while the coordinator keeps the game in trigger mode. A game the agent first reads as `hold` is a hold game: the ledger never applies in it, also to a later `trigger` read (fail open; the hold checks are A37). The window is `min(shield.charge_expiry_seconds, 20 s)` (20 s when the expiry is 0) plus 2 s for the write to reach the coordinator, so at most 22 s. The block comes before the rate limit: no budget is charged, nothing is written and the coordinator sees nothing. Fail open: any other mode, an unknown mode, a shadow game, or a `game` flag set the agent cannot read means no block, and the coordinator decides (step 2). The ledger is the agent's own record, in memory only, so within the window it also refuses a grant the coordinator would accept (BR-020) and it is lost when the agent restarts (step 2). The ledger mechanics (reserve, release, repeats, warnings) are in [decide-contract.md](../specs/decide-contract.md) §4.5 step 4. The decide state marks a player `shield_charged` while the ledger would refuse a `grant_shield` to them at the moment the state is built, so a remote backend sees the refusal before it spends a call (NFR-011). The rules engine drops a `grant_shield` candidate whose target is `shield_charged` before ranking, without moving to another player. The window is a pacing rule: an activation, an expiry or a death does not end it early (#1870). After an operator flips `shield.activation` from `trigger` to `instant` mid-game, or while the `game` flag set cannot be read (the refusal then fails open, but the state marker and R4 read the ledger directly), entries written before that point stay live for up to 22 s: the state still says `shield_charged`, R4 skips that player and an instant `grant_shield` to them does not count as `shielded`, although the ledger no longer refuses. This errs towards fewer shields.
2. If a write goes out anyway (the ledger missed it, for example after an agent restart), the coordinator applies nothing, sends no feedback and publishes `agent_intervention` with `blocked=true`, `block_reason=already_charged` (A22). The backstop reservation it made for the write is refunded. The agent's own tally still counts that write as applied; the coordinator's `game_interventions_total{blocked="true", block_reason="already_charged"}` is the truth (#1778).
3. Use case ends.

The controller stops breathing and its charge rumble pattern stops at once, a pulse in progress included (BR-021): on expiry, death and game end the coordinator sends `GAME_EFFECT_SHIELD_CHARGE` with `duration_ms` 0 and stops re-sending it; a disconnected controller drops its layers and pattern in the controller manager. At game end a running shield is ended separately by `GAME_EFFECT_SHIELD` 0 (A17), so a charge holder with no running shield gets only `GAME_EFFECT_SHIELD_CHARGE` 0.

### A33: Agent refuses a shield on the cap or the cooldown

**Trigger:** The agent decides a `grant_shield` (rules, rules fallback or a remote answer) for a player it already gave the per-game shield cap, whose last agent shield ended less than the cooldown ago, or to whom another grant is still being written (step 11; BR-022, #2044)
**Flow:**

1. System reads `policy.max_shields_per_player_per_game` and `policy.shield_cooldown_seconds` (`agent` flag set, flags.md §3) with the cycle's live flags; a read error or a negative value gives the default (3 / 15 s), 0 means unlimited / off.
2. The shield ledger, after the allow-list and battery and, in trigger mode, after `already_charged` (A31), refuses the grant `shield_cap_reached` when the player's agent shields in this game (written plus in flight) reached the cap, else `shield_cooldown` while now is before the end of the last one (write + granted seconds + 2 s) plus the cooldown, or while another grant to the player is in flight. The refusal comes before the rate limit: no budget is charged, rank-order admission continues, nothing is written. The ledger mechanics are in [decide-contract.md](../specs/decide-contract.md) §4.5 step 4.
3. System records the decision as blocked with that reason (A10); `agent.decide` carries `decide.blocked` / `decide.block_reason` on the remote path. A repeat with the same reason is quiet: it only counts in `agent_decisions_total` and logs `agent.decision_shield_cap_reached_repeat` / `agent.decision_shield_cooldown_repeat` at debug level (as A21).
4. The rules engine drops a `grant_shield` candidate to such a player before ranking, so R4 does not take a decision slot every second for a refused shield. The player is then not one of R4's candidates, and R4 may shield another candidate instead (A41). From the same ledger snapshot the decide state marks the player `shield_limited` (step 4), so a remote backend sees the refusal before it spends a call (NFR-011; #2066).
5. A grant the agent did not write (rate-limit block, gated write A11, failed write A27) does not count and starts no cooldown. A new game starts with no shields counted.
6. Use case ends.

### A34: Coordinator refuses a shield on the cap or the cooldown

### A35: The same value is already applied

**Trigger:** The agent decides a state or level intervention (BR-023) whose target and value equal the last one it wrote to this game, within the last 30 s (step 11; #2046)
**Flow:**

1. After the allow-list and battery, and before the shield ledger and the rate limit, the agent compares the decision with its applied-value record for this game, keyed by intervention and target: the value is compared as a number when it parses as one, else as the trimmed string. An empty value matches only an empty value.
2. On a match the agent blocks the decision `already_applied`: nothing is written, no budget is charged, rank-order admission continues (BR-014) and no effect is measured. `agent.decision` carries `decision.blocked=true`, `decision.block_reason=already_applied`; `agent.decide` carries `decide.blocked` / `decide.block_reason` and its outcome stays `act` (or `fallback`).
3. The first suppression per recorded value is emitted with its spans, an info log `agent.decision_already_applied` (not the `agent.decision_blocked` warning) and a narrative-timeline entry that reads "already in place", not "blocked". A repeat only counts in `agent_decisions_total` and logs `agent.decision_already_applied_repeat` at debug level (as A21).
4. The rules engine drops a candidate whose value is already applied before ranking, so it does not take a decision slot every second; it may rank another intervention instead, and that may be a stronger one (for example a `grant_shield` for the same near-threshold player). Shields stay bounded by the cap and cooldown of BR-022 (A33). The decide state carries the per-player factor the agent already applied when it is not neutral (`sensitivity_factor=0.80`, step 4), so a remote backend sees the help is in place (#2066).
5. The record holds only values the agent wrote (`applied=true`). While a write to the key is in flight the check finds no match, since a different value may land last. A failed write (A27) or two writes to the same key in flight at once delete the entry, a gated write (A11) leaves it as it was, an entry whose target is no longer among the game's players is dropped, and an entry expires 30 s after its write, so the value is written again. A new game starts with an empty record.
6. Use case ends.

### A36: Shield energy granted (hold mode)

**Trigger:** A `grant_shield` is applied in a game latched to `hold` (BR-019, BR-027) to a living player whose pool has room and whose budget is not used up (step 13; #2096, FR-161)
**Flow:**

1. After the alive check, the pool checks (A37) and the shield limits (BR-022, A34), System adds `min(seconds, min(cap, budget remaining) - energy)` to the player's energy (BR-024). `grace_until` is not touched: the player is protected only while holding the trigger (UC-030 A7).
2. During an active hold the added energy moves the running deadline (`hold_until`) out; in the minimum-burst tail of a release it only adds to the pool.
3. System records `shield_energy_granted` (`shield.seconds_requested`, `shield.seconds_added`, `shield.energy_s`) on the player's span and, when the pool reaches full (`min(cap, budget remaining)`), `shield_energy_full` (`shield.energy_source` = `agent`). The grant counts against BR-022 (it added more than 0) and its cooldown runs from the grant (grant time + the requested seconds, also when a partial top-up added fewer: the conservative choice), as in trigger mode.
4. Feedback (BR-026): the coordinator sends the player's new energy (`GAME_EFFECT_SHIELD_ENERGY`, or `GAME_EFFECT_SHIELD_HOLD` with the new end during a hold); the controller plays the #2094 grant pattern when the grant fills the pool and a single pulse for a partial top-up, and its LED shows the new level. The dashboard bar (UC-035 BR-008) follows the `player_shield_energy` event with `source` = `agent`.
5. Use case continues at step 14.

### A37: Grant into a full pool or an exhausted budget

**Trigger:** A `grant_shield` in a hold game targets a living player whose energy is already at `min(cap, budget remaining)` (less than 0.05 s of room), or whose budget remaining is below the minimum burst (step 11 or step 13; BR-024, #2096)
**Flow:**

Agent side (#2096; [decide-contract.md](../specs/decide-contract.md) §4.5 step 4): the agent's shield ledger blocks the grant `shield_budget_exhausted` (budget remaining below the minimum burst) or `shield_pool_full` (energy plus the seconds of the agent's grants in flight at least `min(cap, budget remaining)` minus 0.5 s) from the coordinator's hold gauges (the decide-state values), in a game whose `game_shield_activation_mode` says `hold`, before the rate limit, after the allow-list and battery and before the cap and cooldown. Repeats are quiet (as A21: `agent.decision_shield_pool_full_repeat`, `agent.decision_shield_budget_exhausted_repeat` at debug level).

### A38: Passive recharge

**Trigger:** `shield.recharge_per_second` is above 0 in a hold game while a player lives and no activation runs (step 13; BR-025, #2096)
**Flow:**

2. The coordinator keeps no timer: the energy is computed from the time when it is read (an activation, a grant, a death, the game end).

Reaching full gives the #2094 grant pattern once: the controller manager detects it from the level, rate and full level of the last `GAME_EFFECT_SHIELD_ENERGY` (BR-026), so the coordinator sends nothing for a recharge. 5. Use case ends.

### A39: Shield energy ends

**Trigger:** An activation runs out (empty or budget used up) while held, the player dies or disconnects, or the game ends (step 13; BR-024, #2096)
**Flow:**

### A41: The rules shield the candidate with the fewest shields (catch-up)

**Trigger:** R4 (shield a struggling player while the field shrinks, step 2) proposes a `grant_shield` (step 11; rules, rules fallback; BR-030, #2395)
**Flow:**

1. Once per ranking the rules engine reads the agent's shield grants per player in this game from the shield ledger (`Loop.ShieldGrants`: the `grant_shield` writes plus the ones in flight; a grant refused by the agent or not written does not count).
2. After the first elimination (the elimination path; before it, R4's candidates are the players in sustained danger, A43) R4 proposes a `grant_shield` for every struggling player, each with its own urgency (from that player's skill and the elimination fraction). A struggling player is alive, has a skill level strictly below the mean skill of the alive players with a skill level, and is not the strongest of them. So the strongest alive player (R3's outlier, the stronger player of a duel) never gets a catch-up shield, and an even field has no struggling player.
3. The rules' filters drop the candidates the agent would refuse: the no-shield filter (A31, A33, A37: charged, at the cap, in the cooldown or, in a hold game, full or out of budget), the battery policy, and the minimum score. The struggling players left are R4's candidates; a player who is not a candidate (not struggling, too strong for the minimum score, filtered, without a skill level, dead) never holds the others back and is never shielded in their place.
4. Among the candidates R4 keeps one: the player with the fewest agent shields in this game; on a tie the weakest, then the lower serial. The kept candidate takes the best R4 candidate's score and place among the other rules' candidates (the rotation picks the target, not the priority). So the rules keep shielding while any candidate is left, spread the shields over the candidates, and never emit fewer shields than shielding the weakest candidate would.
5. When a weaker candidate was passed over, the decision's reason reads `catch-up: shield the player with the fewest agent shields (skill …, n shields) while the field shrinks` and its fitness carries `shield_grants`, so the narrative and `agent.decision` show why this player was chosen.
6. The count is per game: the ledger belongs to the game's Loop, so a new game starts at 0 and a shadow game counts only its own grants. It is in memory: an agent restart starts again at 0. The cap, the cooldown, the pool checks, the rate limit and the kill switch (BR-022, BR-014, BR-024, C-034) apply as before; the choice never allows a shield they refuse.
7. A remote backend picks its own target; this flow binds the rules engine (the default backend and every rules fallback). Binding a remote backend's target to the rotation is deferred (#2395 review); the cap, the cooldown and the other gates bound it as before. Use case continues at step 11 (the permission chain).

**Trigger:** The coordinator applies a `grant_shield` for a player, in any shield mode (step 13; BR-031, #2395)
**Flow:**

1. After the grant is in place (instant mode: the protection, A16; trigger mode: the stored charge, A30; hold mode: the energy added to the pool, A36), System sends the player's controller a `GAME_EFFECT_PULSE` in magenta (255,0,192), 500 ms at speed 4 (two pulses), on the game's gameplay stream.

5. Use case continues at step 14.

### A43: The rules shield a player in sustained danger before the first elimination

**Trigger:** No player of the game has been eliminated yet, and an alive player's movement has stayed near the death threshold for several consecutive readings (step 2; rules, rules fallback; BR-032, #2461)
**Flow:**

1. Each ranking, while `policy.shield_danger_enabled` is on (the default; `off` skips this flow, A41 is unaffected), the game has no elimination and at least two alive players, R4 reads each alive player's movement track (the per-player samples of UC-041, about one per second, each the player's `game_player_accel_magnitude` reading of that second) and the session's death-threshold track (`game_effective_death_threshold`; the threshold in force at each sample, else the last one observed).
2. A player is in sustained danger when the newest `policy.shield_danger_samples` readings (default 3) are each at or above `policy.shield_danger_ratio` (default 0.85, the `near_threshold` cut-off of the danger signals) of the death threshold in force then, the readings are consecutive (no gap longer than 2.5 s between two of them, and the whole window at most `policy.shield_danger_samples` × 2.5 s long) and the newest value is at most 3 s older than the game's context. A reading equal to the one before it counts once, and the newest value's age is taken from the first reading of its run of equal readings: the coordinator's gauge is re-exported with its last value, so a frozen value keeps arriving with a fresh time and must not look fresh. One reading over the level (a single warning spike) is never enough.
3. Fail closed: a player with fewer readings, a reading below the level, a gap, a stale newest reading, no known positive death threshold, or a value that is not a finite number is not in sustained danger, and R4 proposes nothing for them. So after an agent restart (the tracks are in memory), or for a player whose readings stopped or froze, there is no danger shield until fresh readings build up again.
4. R4 proposes a `grant_shield` for every player in sustained danger, with urgency = the lowest reading / threshold ratio of the window, at most 1. The skill level is not needed: the danger, not the skill, makes the player a candidate. The decision's reason reads `shield a player in sustained danger (n readings at or above r of the death threshold) before the first elimination` and its fitness carries `danger_ratio` (the urgency) and `danger_samples` (n).
5. These candidates go through exactly what the struggling players of A41 go through: the no-shield filter (A31, A33, A37), the battery policy, the minimum score, and the rotation that keeps one, the fewest agent shields first (A41 step 4, BR-030; a player without a skill level sorts after the skilled ones on a tie). When the rotation passes over the weakest candidate, the reason reads `catch-up: shield the player in sustained danger with the fewest agent shields (n shields) before the first elimination` and the fitness carries `shield_grants`. The permission chain (step 11: allow-list, battery, experiment flag, shield ledger with the cap and the cooldown, rate limit), the actuation gate and the coordinator's checks (A34, A37) apply unchanged.
6. From the first elimination on, R4 uses only the elimination path of A41 (the struggling players, unchanged), so a game of three or more players decides after its first elimination exactly as before. In a duel the first elimination ends the game, so A43 is the only way the rules shield in a two-player game.
7. A remote backend reads the same danger signals in its state (step 4) and picks its own target; this flow binds the rules engine. Use case continues at step 11.

## Postconditions

### Success Postconditions

- The intervention is written for the deciding game only, the game coordinator has applied it through the game's own code, and its decision is recorded in the game's trace (`agent.decision`, `agent.action`).

### Failure Postconditions

- The game was never paused or slowed by the agent (BR-001), no other game was changed (BR-002), and nothing was written to the flag service outside the allow-list, the per-game budget and the actuation gate (BR-004, FR-051).

## Business Rules

### BR-001: The game never waits

Remote calls are asynchronous; nothing in the game coordinator waits for the agent.

### BR-002: Interventions are game-scoped

Every intervention is written for the game whose decision loop decided it and resolves only in that game (FR-069, FR-136, [UC-053](UC-053.md)); a decision without a coordinator game id is not written. This rule is the owner. The writer refuses an intervention whose game id is empty or is not a coordinator game id (`game_…`), such as the `session-<n>` id of the partition for unlabeled signals ([UC-041](UC-041.md) A5), and records the refusal as a failed write (`agent_intervention_writes_total{result=error}`, `agent.action` span error), with no flag-service call and no retry (#1323, #1651).

### BR-003: Backend roles

See [C-018](../requirements.md#constraints).

### BR-004: Double enforcement

The allow-list is checked by the agent and again by the coordinator; the coordinator also enforces a global backstop (default 60 per minute), and it caps and paces the agent's shields per player per game whoever wrote them (BR-022, A34).

### BR-005: No paid call without a possible action

A remote decide call is made only when the effective allow-list (deduplicated, empty ids and `noop` dropped, as for the `ffa.intervention` options) holds at least one intervention; otherwise the call could only answer `noop` (A14, NFR-011). The check sits before cadence and budget are charged. An answer already in flight when `interventions_allowed` flips to `none` is still blocked at landing by the live allow-list (`not_allowed`, A10). This covers in-game decide calls only: the post-game retro and the experiment proposer are governed by the kill switch and the LLM budget, not by the allow-list.

### BR-006: A one-shot intervention fires once, only in its game

A one-shot intervention is an event in its game's event list (FR-137, [UC-053](UC-053.md) BR-006). The coordinator applies, in order, every event with a sequence number above the last one it applied for that game and flag, exactly once; a game starts with an empty list, so an event of an earlier game, or from before a coordinator restart, is never applied in a new game (#1299). Fail closed on flagd errors: a read that returns an evaluation error applies nothing and does not move the last applied sequence number. A new, non-empty epoch (a flag-service restart) restarts the count. State flags are not affected: a game converges on its current value.

### BR-007: Every intervention sound resolves

Every sound id an intervention plays exists in the audio registry. The writer default `agent_cue` (`play_audio_cue`) and the shield sound `shield_up` are registry **aliases**: `agent_cue` plays the lobby ready ping (`Joust/sounds/beep_loud.ogg`, the sound a controller makes when it readies in the lobby), `shield_up` plays the Commander power-up sting (`Commander/sounds/power_ready.ogg`; an alias names an exact asset path). The audio service logs a WARNING for any sound id that is not in the registry (#1301).

### BR-008: Shield LED schedule

For `GAME_EFFECT_SHIELD` with duration T: the LED shows the shield colour (white, as in spawn protection) and its brightness falls linearly from 100 % to 30 % over the first T − 1 s; in the last 1 s it blinks at 4 Hz between full shield colour and off; at T it shows the player's current base colour. A shield of 1 s or less blinks for its whole duration. The controller manager renders the schedule at its effect rate (20 Hz) as a pure function of the time since the grant; the coordinator sends one command per grant, not a colour stream.

### BR-009: Toughness boost is the weaker variant

For `GAME_EFFECT_TOUGHNESS_BOOST` with duration T: the shield colour breathes slowly (0.5 Hz) between 10 % and 50 % brightness until the last 1 s, then blinks at 4 Hz between 50 % and off, then restores the base colour.

### BR-010: Feedback follows the protection, never the other way round

Feedback starts only when the grant changes the protection: a grant that extends the shield restarts the LED schedule with the new remaining time; a grant that is kept (the effective grace, `max(agent shield, admin invincibility)` per #817, already lasts longer) sends no feedback. The shield sound plays only on the transition from unprotected to protected; an extension restarts the LED silently. The LED effect, the sound and the `player_shielded` event are sent independently: one failing never skips the others. Feedback never changes `grace_until`, `invincible_until` or the toughness boost factor, and a feedback failure never fails the intervention; the coordinator keeps no timer or task for it.

On the controller the shield is a persistent **layer**, not a replaceable effect:

- Effects that do not touch the LED (rumble) neither end nor hide the shield.
- Short LED effects (death warning flash, agent pulse / flash, battery display) are drawn over the shield; when they end, the shield schedule continues at the point it has reached by then.
- A new base colour (a team or colour change during the game) does not end the shield; it is the colour shown when the shield ends.
- Death, the winner rainbow, a disconnect and `GAME_EFFECT_SHIELD` with `duration_ms=0` (game end) end the shield, the full and the toughness boost layer alike.
- A full shield and a toughness boost can be active together; the full one is shown, and when it ends while the toughness boost is still active its schedule continues. `GAME_EFFECT_TOUGHNESS_BOOST` with `duration_ms=0` ends only the toughness boost layer.

### BR-011: `end_game` ends only the game it was decided for

`end_game` is an event in the deciding game's event list. The coordinator force-ends only the session whose list holds it; it never resolves "the current game" or "the primary game" on the agent's behalf. A shadow game's decision can therefore never end the real game, and a real game's decision never ends a shadow. The agent never writes an intervention without a coordinator game id (BR-002, #1310).

### BR-012: A per-player grant applies once per decision

The per-player grant flags `shield_seconds`, `toughness_boost_seconds` and `soft_penalty_action` are one-shot, time-boxed effects. Each write gets a fresh variant from the flag service; the coordinator change-detects grants per player on the resolved variant and value within the game and dispatches one intervention per changed player with `target` = that serial, so the battery guard and the backstop apply per grant. Fail closed: a per-player read that returns an evaluation error does not move that player's last-seen grant. The coordinator sees what flagd serves after each push: two grants to the same player pushed in one configuration collapse to the later one, which is applied once (#1323). A cleared grant resolves to the neutral value, which is never applied. The level flags `player_sensitivity_factor` and `player_handicap_factor` are not grants: re-applying an unchanged factor is a no-op (BR-017).

### BR-013: Agent spans sit under the game cycle

The agent's in-game spans belong to the running game cycle. `agent.signal_received` (and so the rules-path `agent.decide`, `agent.decision` and `agent.action` under it) and the remote path's async `agent.decide` are remote children of the coordinator's `game_cycle` span. The agent learns that span's id from the `game_cycle_span_id` label (UC-041 BR-004). When it is not known, the parent is `gameplay_phase`, then the game root span; with no game ids at all the span is its own root. Each `agent.decision` keeps its Link to the game root in every case, and the spans keep their backdated start times and their `link.kind=fire_cycle` Link.

Each `agent.intervention.effect` span is a direct child of the `agent.decision` that dispatched the intervention: one span per evaluated fitness signal, backdated to dispatch time and ended after the follow-up window, with no effect span parenting another (#1325). The effect span outlives its decision by design (the window is 20 s); a child that ends after its parent is valid in OTel and keeps the cause one click away, whereas a `game_cycle` parent with a Link would hide the cause behind a Link and still end after `game_cycle` when the game ends inside the window.

### BR-014: A scarce budget goes to the highest-ranked decision

Within one cycle, decisions reach the per-game weighted rate limit in rank order (rules: the engine's score order; remote: the single answer). Admission stops at the first decision that passes the allow-list and battery checks but does not fit the remaining budget, unless its cost exceeds the whole budget: every lower-ranked decision of that cycle is blocked with `rate_limit` and charges nothing (A20). A decision the budget refused is reported in full once per budget state (the state changes when an intervention is admitted or one leaves the 60 s window); repeats in between are counted and logged at debug level but emit no `agent.decision` span (A21). When the budget covers every decision of the cycle nothing changes: every decision is admitted in rank order, so the rules ranking and the rules path golden are unchanged.

### BR-015: Nudges keep a reserve for protective interventions

A `send_controller_effect` decision (R8 statue nudge, R9 random effect, or a remote answer) is admitted only when the window still has room for one medium intervention (1.0, the cost of `grant_shield` and `adjust_player_sensitivity`) after charging it. The reserve does not apply when `chaos` is the strictly dominant objective weight (the decision's weights, else the `objectives` flag): then the operator asked for chaos and a nudge is the most valuable decision. It also does not apply when `interventions_allowed` permits no protective intervention (`grant_shield`, `toughness_boost`, `adjust_player_sensitivity`, `set_player_handicap`; e.g. the shipped `ambient`): nothing could use the reserve, so nudges may spend the whole budget. With the default budget of 2 and a protective intervention allowed, nudges spend at most 1.0 per minute (two nudges) and a shield or handicap finds 1.0 free; with `conservative` (1) no nudge applies unless chaos dominates.

Accepted limit: only `send_controller_effect` keeps the reserve. The other soft interventions, `play_audio_cue` and `adjust_volume` (also 0.5), do not, so they can still take the last 0.5 or 1.0 before a shield fires in a later cycle. In the same cycle BR-014 still ranks them below a higher-ranked shield. Today R2's calming cue is the only rule that emits one, and only early in an endurance session.

Why a reserve and not a new rule priority or a per-player cooldown (#1326): under the stage objectives `balanced_focused` (balanced 0.7, chaos 0.1) R8 scores at most 0.1 × 1.0 = 0.1, the `minScore` floor, while R3 (handicap) and R4 (shield) score 0.7 × urgency, so the ranking already puts shield and handicap first. The starvation came from cost: a 0.5 nudge fits a half-free budget that a 1.0 shield does not, so nudges took every freed half slot. A fixed priority would override the operator's weights under `chaos_focused`, and a per-player cooldown does not bound six statue players, who are six different targets.

### BR-016: Per-player entries live only as long as their game

Per-player values exist only in a live game's scope on the flag service, so the rendered configuration and flagd's evaluation cost grow with the games currently running, not with the history of games. When the game ends the flag service drops every value of the game in one push (A25, [UC-053](UC-053.md) BR-003); a game scope older than 1 h is dropped as well (UC-053 A11). No agent-side pruning is needed.

### BR-017: Per-player levels belong to one game

A game starts with neutral factors: a level is written for one game and dropped with it (BR-016), so a new game never inherits an earlier game's level. During the game the coordinator dispatches a level change only for the players whose resolved level differs from the last read in this game (alive players that pass the battery guard); a player whose level moves to neutral is reset to neutral (A24). The reset is a revert to neutral: it runs without the permission chain and does not count against the backstop. Fail closed: a per-player read that returns an evaluation error is ignored and never moves the last-seen level.

### BR-018: Intervention side effects run on the owning game's event loop

Each game runs on its own thread and event loop, and its gRPC clients (audio, controller manager) and gameplay stream belong to that loop; awaiting them from another loop fails with "attached to a different loop" (#1250). The coordinator therefore keeps change detection, baselines and the enforcement chain on its own loop, and runs every intervention side effect (apply handler, revert handler, agent cue) on the loop of the game it was evaluated for, one at a time in decision order per game. `end_game` is the exception: it ends the session through the servicer's force-end path on the coordinator's loop, because that path joins the game's thread, and it sends no agent cue. The coordinator waits at most 5 s per effect and never blocks its own loop or deadlocks. An effect that has not started by then, or whose game loop is closed or stopping, is never applied (`game_loop_unavailable` / `game_loop_timeout`, recorded as blocked). An effect that has started is never cancelled, because cancelling it midway could leave the game half-changed; if it is still running at 5 s its outcome is unknown (`game_loop_late`, not recorded as blocked). Each such case is logged and counted (A26). A side effect's flag reads see the evaluation context of the game it runs for (game mode, controller count, sensitivity, `game_kind`, and experiment and arm for an experiment game), set around the effect on the game's loop and restored after it; before the game's run starts, that is its session kind and experiment. A key the read passes itself still wins (#1970). So in an experimental-arm shadow game an experiment value on a flag a handler reads resolves there too, and a real or non-experiment shadow game resolves as before. The flags handlers read are declared in `handler_flag_reads.py` and checked by a contract test and a census test (flags.md §1.2, #1872).

Accepted limit: the wait is per game but sequential across games. A game whose loop is stuck delays the interventions of the games evaluated after it in the same pass by up to 5 s per pending effect (head-of-line delay); its own later effects are skipped as `game_loop_timeout`. A stuck shadow game can therefore delay the real game's interventions, but never block or corrupt them.

### BR-019: Shield activation mode

- The `game` flag `shield.activation` (`instant` | `trigger` | `hold`; `hold` with its controller feedback, BR-026, #2096) is read at each `grant_shield` in instant and trigger games; a malformed value gives `instant`. A game whose flag resolves to `hold` at the start of its game loop or at its first `grant_shield`, whichever comes first, is latched to hold for its whole life (BR-027); a `hold` read mid-game in a game that was not latched to hold resolves to the mode that game read at that latch (`instant` or `trigger`): a flip to `hold` never changes the mode of a running game. The stack default is `trigger` (#1837, PR-5), which only Free-for-All honours; every other mode and every shadow game stays `instant`. The code fallback and the CI baseline stay `instant`. Rollback: set the flagd `defaultVariant` back to `instant`, live. `hold` is not the default; an operator selects it (a stage overlay, flags.md §13.3), and since FR-162 the agent may experiment toward it in shadow games and promote it (UC-043 A17). A promotion of `shield.activation` never lands mid-game, although trigger and instant games read the flag per grant: the agent writes the `real` value only while no real game runs (the flag service refuses it otherwise, UC-043 A17 step 3).
- `trigger` and `hold` apply to Free-for-All only (an allow-list). Every other mode, including Fight Club, Zombies (the trigger is the weapon), Traitor and Werewolf (UC-022: rumble is the hidden-role signal), is always `instant` whatever the flag says.
- A shadow game is `instant` unless its pattern controllers press the trigger by themselves: it honours `trigger` and `hold` (including the hold latch, BR-027) only when its start carries `pattern_trigger_policy`, which the agent sets when the installed archetype declares a `trigger_policy` (UC-046 BR-018, #2096), so an experiment on `shield.activation` can compare trigger against hold, not instant against hold. The coordinator binds the field only to a shadow session, like `rng_seed`: a real (menu-origin) start that carries it ignores it. The Free-for-All allow-list applies to shadow games too. Nothing in this changes how a real game reads the flag. Whether a shadow game plays sound or rumble is governed by #1846, not by this rule.
- A flip applies to the next grant. A held charge stays activatable in either mode, and an `instant` grant to a player who holds a charge applies the shield at once and leaves the charge alone.
- The agent never writes `shield.activation` or `shield.charge_expiry_seconds` stack-wide (C-034); they are human flags (stage overlay, flags.md §13.3). Since FR-162 (#2096 PR-7b-2a), `shield.activation` and the seven hold parameters are experiment+arm and `real` values the agent may write under UC-043 A17; `shield.charge_expiry_seconds` and the #2094 cue flags stay human-only (C-034).

### BR-020: One charge per player

- Trigger mode only (a hold game has a pool instead, BR-024). A player holds at most one charge. The coordinator refuses a `grant_shield` while a charge is held as `already_charged` (A31); it is authoritative. A grant while a shield is active and no charge is held is accepted by the coordinator: the charge then waits under the active shield. The agent's ledger (A31 step 1) allows at most one agent charge per player per window, so it may refuse such a grant within its window.
- The granted seconds become the shield duration at activation. The expiry is fixed at grant time, so a flag flip never changes a held charge.
- Death, disconnect (a death in every mode, UC-020 A2), game end and expiry discard the charge. A respawn never restores it. `eliminate_player` still eliminates a player who holds a charge or an active shield.
- The coordinator keeps no timer for the charge: it checks the expiry in the frame path, only for players that hold one.

### BR-021: Charge and activation feedback

- Charge layer (`GAME_EFFECT_SHIELD_CHARGE`): the player's current base colour breathing between 60 % and 100 % at 0.5 Hz, rendered at 5 to 10 Hz (or only on a visible change) to spare the battery. It is the lowest-priority shield layer: the full shield and the toughness boost draw over it. Short LED effects overlay it.
- `duration_ms` is capped at 120 s. While a charge is held the coordinator re-sends the command before it runs out, which also covers an expiry of `never` (0). The controller manager ends the shield layers, charge and active `SHIELD` alike, of a game stream's controllers when that stream closes (serials snapshotted before the stream is released), so a coordinator crash leaves no breathing controller in the lobby. After a mid-game coordinator reconnect the coordinator re-sends `GAME_EFFECT_SHIELD_CHARGE` for every held charge, and `GAME_EFFECT_SHIELD` and `GAME_EFFECT_TOUGHNESS_BOOST` with the time left for every running shield and toughness boost; the cleanup is delayed about 7 s (longer than the coordinator's 1, 2, 3 s reconnect backoff) and cancelled when a new game stream claims the serial, so the re-send finds the layers intact.
- Charge rumble pattern (#2094; it replaced the single 100 ms tick at intensity 120 of #1837, which players moving in a game did not feel), run by the controller manager per charge layer, so the coordinator sends nothing extra and its frame path is unchanged:
  - Grant: when a charge layer starts (not when a re-send extends it), 3 pulses of `shield.charge_rumble_pulse_ms` (default 150 ms) at `shield.charge_rumble_intensity` (default 255) with 100 ms gaps.
  - Reminder: one such pulse every `shield.charge_reminder_seconds` (default 5 s, counted from the grant) while the charge is held; 0 turns the reminders off.
  - Pre-expiry: a double pulse (two pulses, 100 ms gap) `shield.charge_pre_expiry_seconds` (default 3 s, at most 8 s) before the charge layer ends; the last cue, no reminder after it. The layer's end is the expiry: the coordinator sends the time to expiry, capped at 120 s, and re-sends 10 s before a cap that is not the expiry, so an expiry of `never` (0) or one more than 120 s ahead never gives the pulse early. A charge shorter than the grant pattern plus the lead gets no pre-expiry pulse. 0 turns it off.
  - The four flags are read when the charge layer starts and fixed for that charge (flags.md §4). Intensity 0 turns the whole pattern off.
  - A charge pulse plays only when the rumble slot is free: while another rumble runs (the warning, the death rumble, the swell, an agent `RUMBLE`), a cue waits up to 1 s for the slot and is skipped if it is still taken. Any later rumble replaces a running charge pulse. The pattern stops at once, a pulse in progress included, when the charge layer ends: activation (`GAME_EFFECT_SHIELD_CHARGE` 0), expiry, death, game end, stream close or disconnect.
- Shield ending soon (#2094): an active shield (a `GAME_EFFECT_SHIELD` layer: an instant shield or an activated charge) gives a double pulse (2 x 150 ms at 255, 100 ms gap) `shield.ending_rumble_seconds` (default 1 s, 0 to 3, 0 = off) before its layer ends, so the player knows the protection is about to end. The lead is read each time the layer starts or restarts; a restart (a re-grant or a re-send after a reconnect) moves the pulse to the new end. A shield no longer than the lead gets no pulse. The toughness boost (not a protection) gets none. Same rules as the charge pulses: only in a free rumble slot (waits up to 1 s), any later rumble replaces it, and it stops at once when the shield layer ends early: death, game end (`GAME_EFFECT_SHIELD` 0), stream close or disconnect.
- Activation swell (`GAME_EFFECT_SHIELD_SWELL`): a rumble ramping 0, 180, 0 over 600 ms. It is a rumble only: it neither ends nor hides an LED layer.
- The charge pulses, the ending pulse and the swell are distinct from the death warning (200 ms flat) and the death rumble (1000 ms at 255). Any later rumble (warning, death, agent `RUMBLE`) replaces a running charge pulse, ending pulse or swell; the death rumble is never shortened.
- `GAME_EFFECT_SHIELD_CHARGE` with `duration_ms=0` ends only the charge layer; `GAME_EFFECT_SHIELD` 0 ends every shield layer.

### BR-022: Shields per player per game are capped and paced

- Two operator flags in the `agent` set bound the agent's shields per player per game: `policy.max_shields_per_player_per_game` (default 3, 0 = unlimited) and `policy.shield_cooldown_seconds` (default 15 s, 0 = off). The agent never writes them (C-034). A read error or a negative value gives the default, so the limits stay on. They carry no targeting, so every reader resolves the same value.
- Count: the agent shields applied to that player (by serial) in this game. An instant grant that moved the player's shield counts, in trigger mode a stored charge counts, and in hold mode a grant that added energy counts, a partial add included (A36); a refusal for a full pool or a used-up budget does not (A37). A kept grant (the player's protection already lasts longer, step 13) and a refused grant do not count. A revive does not reset the count; the next game starts at 0.
- Cooldown: a grant is refused while now is before the end of the player's last agent shield plus the cooldown. The end is the shield's own (grant time + requested seconds), never `grace_until`, which other graces share. In trigger and hold mode the cooldown runs from the grant: charge stored (or energy added) + the requested seconds (a partial top-up in hold mode still books the full requested cooldown), whenever the player uses it. The flag is read at each grant and added to the stored end, so a flip applies to the next grant.
- With a cooldown set, a running agent shield is never extended (the cooldown refuses it); cooldown 0 restores extend-not-shorten (#817).
- The coordinator is the authority (A34). The agent enforces the same limits first (A33), so a refused shield costs no budget and is not written. The agent's count is an upper bound of the coordinator's: it counts every write it made, also one the coordinator refused (`already_charged` after an agent restart, a dead target, the mode, its own cooldown) or kept, so the agent errs towards fewer shields, never more. Its ledger is in memory: an agent restart, or a game whose Loop was evicted, starts again at 0, and the coordinator's count still holds.

### BR-023: An intervention that cannot change the game is not written

- Only state and level interventions are suppressed (the `state` and `level` kinds of flags.md §13.1): `adjust_music_tempo`, `adjust_volume`, `adjust_global_sensitivity`, `adjust_global_difficulty`, `set_pacing_profile`, `ramp_tempo`, `auto_rubberband`, `adjust_player_sensitivity`, `set_player_handicap`. The coordinator acts on these only when the value changes, so writing the same value again changes nothing in the game. A grant (`grant_shield`, `toughness_boost`, `soft_penalty`) or an event (`eliminate_player`, `revive_player`, `send_controller_effect`, `play_audio_cue`, `end_game`) is never suppressed: each write is a new grant or a new event.
- The agent compares against its own record of what it wrote, not against the flag service. A value lost on the flag-service side (a restart, UC-053 A9; a player dropped on re-registration, UC-053 A13; an operator clearing it) is re-asserted within the 30 s TTL. The TTL is a constant, not a tunable (C-035).
- Dropping an already-applied candidate frees a ranking slot, so the rules may pick a stronger intervention in its place (a `grant_shield` for the same player, R4). Every shield stays bounded by BR-022 (per-player cap and cooldown).
- Suppression is switched on by the agent's wiring (`Loop.SetSuppressReapplied`); a loop without it, such as the rules golden harness, writes every decision as before.


### BR-024: Shield energy pool and budget (hold mode)

- Each player of a hold game has a pool of shield energy in seconds. Cap `shield.energy_max_seconds` (default 5, 1 to 10). Budget `shield.energy_budget_seconds` (default 15, 3 to 30): the active shield time actually used per player per game, summed over every activation, whatever filled the pool. Minimum burst `shield.min_burst_seconds` (default 0.3, 0.1 to 1). Starting energy `shield.energy_initial_seconds` (default 0, 0 to 5), clamped to the cap and the budget. All are `game` flags latched at the start of the game loop or at the first `grant_shield`, whichever comes first (BR-027, flags.md §4).
- One activation costs `max(held, minimum burst)` and never more than the usable energy at its start, `min(energy, budget remaining)`; the protection lasts exactly the cost. An activation needs a usable energy of at least the minimum burst, so a remainder below it never buys a full burst.
- The energy shown and stored is clamped to the budget remaining, so it never shows energy that cannot be used. Once the budget remaining is below the minimum burst the shield cannot activate again in that game, and grants (A37) and recharge (A38) add nothing.
- Bound: total protected time per player per game ≤ budget; contiguous protection ≤ `min(budget remaining, energy at the start + grants landing during the hold)`.

### BR-025: Energy sources

- Agent grants add energy (A36); passive recharge, `shield.recharge_per_second` (default 0 = off, at most 0.5), adds energy while no activation runs (A38). The pool never fills by itself otherwise.
- Recharge is pure game balance: it counts against the budget only when spent and never against BR-022.

### BR-026: Hold feedback

- The controller shows the shield energy on the LED and as rumble, so the player knows it without looking (LED is the primary feedback; audio only reinforces). Two shield layers of the controller manager carry it ([services.md](../specs/services.md) §4 and §6 "LED states"): `GAME_EFFECT_SHIELD_ENERGY`, the idle pool, and `GAME_EFFECT_SHIELD_HOLD`, the running activation, which draws over it.
- LED states. Each idle state uses the player's current base colour; none uses red or off (death), and only the active state uses white (protected, as every shield, BR-008):
  - empty (usable energy below the minimum burst, so the shield cannot activate; also once the budget is used up): the base colour, steady, as in a game without a shield;
  - low (usable, below a third of the cap): the base colour breathing from 100 % down to 20 % at 1 Hz;
  - charged (from a third of the cap up to below full): the base colour breathing 60 % to 100 % at 0.5 Hz, the look of a held charge in trigger mode (BR-021);
  - full (the energy at `min(cap, budget remaining)`): the base colour breathing towards white, between the base colour and a 50 % white blend at 0.5 Hz;
  - active (held): white, its brightness following the energy left, from 100 % at a full cap down to 30 %; the last second blinks at 4 Hz, as a shield does (BR-008).
  The controller computes the idle level from the last command (energy, recharge rate, full level), so a recharge moves the LED through the states with no further command.
- Rumble:
  - active: a light continuous rumble, `shield.hold_rumble_intensity` (default 70), kept as a background level that the controller manager restores after every one-shot rumble (warning, cue pulses, swell); it stops when the activation ends. Death ends every shield layer and the background level with it, also when no layer is left (#2462), so the death rumble keeps the motor and stops at 0;
  - ending soon: the #2094 double pulse `shield.ending_rumble_seconds` before the energy runs out while held (the existing flag, no new one); a grant during the hold moves it;
  - empty: one pulse of `shield.empty_pulse_ms` (default 400) at the cue intensity when an activation ends because the energy or the budget ran out;
  - full: the #2094 grant pattern (3 pulses) when a grant fills the pool, or when the recharge fills it (detected by the controller from the recharge rate, once per fill); a partial top-up by a grant gives a single pulse. A pool that starts the game with energy (`shield.energy_initial_seconds`) plays no pattern at game start; the LED shows it.
  - Every cue pulse follows the slot rules of BR-021: it waits up to 1 s for a busy rumble slot and is skipped after that; death and the warning keep the slot.
- Sound only reinforces: `shield_up` plays on an activation at most once per 2 s per player, so a bouncing or mashed trigger never queues sound RPCs.
- The coordinator latches the cue values with the hold values (BR-027): `shield.charge_rumble_intensity`, `shield.charge_rumble_pulse_ms`, `shield.ending_rumble_seconds`, `shield.hold_rumble_intensity` and `shield.empty_pulse_ms`. It ships them with each command, so the controller plays what the game latched; the controller manager falls back to its own read when they are absent.
- One ordered outbound task per hold game sends the commands; the frame path only marks the player and never awaits (UC-030 BR-008). The game's gameplay stream carries one write at a time (grpc allows one write in flight per call): the task, the frame path's warning and death effects, the intervention handlers and the end-of-game effects all write through one lock per call, so a frame waits at most for the one write in flight, as long as its own write takes (the agent cue to several players writes one pulse after the other, never a batch ahead of a frame). A write that started is never cancelled, because cancelling a grpc write ends the whole call: a cancel of the writer (the game end stopping the task) leaves its write to finish, and the next write waits for it. After the game end the task is stopped for good: a late grant or re-send sends nothing after `SHIELD` 0. The task sends the player's state at the time it runs, so changes between two sends coalesce:
  - the start of the game loop: `SHIELD_ENERGY` for every player;
  - an activation: `SHIELD_HOLD` with the energy left;
  - the end of an activation: `SHIELD_HOLD` 0, then `SHIELD_ENERGY` (with the empty pulse after `empty` or `budget_exhausted`);
  - a grant: `SHIELD_ENERGY` with the full or top-up cue, or, during a hold, `SHIELD_HOLD` with the new end and the cue;
  - a release inside the minimum-burst tail sends nothing; a dead or disconnected player gets nothing (the death effect and the disconnect end the layers);
  - after a mid-game reconnect the state of every living player is sent again (BR-021).
- A hold activation does not publish `player_shielded`, so the dashboard's shield badge never shows a protection a release already ended; the energy bar reads `player_shield_energy` (UC-035 BR-008).
- Whether the default hold rumble is felt on a moving controller is a stage check on the Pi (#1465) before `hold` becomes a default.

### BR-027: Hold parameters are latched per game

- `shield.activation` (when it resolves to `hold`) and every hold and cue parameter are read once, at the start of the game loop or at the first `grant_shield`, whichever comes first, in the game's flag context (the read sees the experiment arm, as `windows` does), and are fixed for that game.
- A stage overlay, an experiment write or a promotion (and a kill-switch revert of a promotion, UC-045) applies from the next game; a running game keeps its values. A promotion of a hold key is written only while no real game runs (UC-043 A17). A game not latched to hold keeps reading `shield.activation` per grant (BR-019), but a `hold` read there gives the mode it read at the latch, so a flip to `hold` never changes the mode of a running game.
- The game carries the latched values in telemetry (`game.shield_hold` span and the `game_shield_hold_setting` per-game gauge), the decide state and the retro (UC-042 BR-007).

### BR-028: The agent does not move the flag under test

- In a game that belongs to an experiment on flag X, in either arm, the agent does not decide a lever that changes the game value X sets (A40, #1975). Otherwise the control arm, which has no experiment value, would get the lever's value and the comparison would be confounded, and every such decision in the experimental arm would be blocked `experiment_override` by the coordinator (A22, UC-043 BR-005), spending budget on nothing.
- The levers and the experiment flag each one changes are a static map (`decision.ExperimentLevers`): `set_pacing_profile` changes `windows` (the handler swaps the game's music windows) and `adjust_global_sensitivity` changes `sensitivity` (the handler replaces the game's sensitivity level). A factor on top of the sensitivity (`adjust_player_sensitivity`, `set_player_handicap`, `adjust_global_difficulty`) does not replace the value and is not in the map.
- The game's experiment comes from the agent's experiment registry; an experiment it does not know skips nothing. A remote backend is not offered these levers in such a game (A40 step 5, #2251). The skip is an agent-side filter, not a safety gate: the kill switch and every fail-closed gate are unchanged (C-034).

### BR-029: The agent's shield length is the `default` variant of `shield_seconds`

- A `grant_shield` that carries no value (every rules decision, a remote answer without a magnitude) is written with the value of the variant named `default` of the `interventions` flag `shield_seconds` (5 s in the baseline; #2395). The flag's `defaultVariant` stays `none` (0): it is what a player the agent never granted resolves. A remote answer's magnitude (3 to 10 s) is kept.
- The agent reads it at use time, through the flag service (`GET /interventions/shield_seconds`), when it runs the permission chain for a grant the allow-list permits; one read serves the whole agent for at most 1 s. It stamps the value on the decision before the shield ledger, so the ledger's cooldown end and in-flight seconds (BR-022, A33, A37) and the write use the same length.
- Fail closed: a read that fails or times out (200 ms), a missing variant, or a value that is not a number from 3 to 10 (the `grant_shield` magnitude bounds, so the recorded answer is the written length) gives 5 s, the length before #2395, and logs `agent.shield_seconds_unreadable` (at most every 30 s). No new flag (C-035). The flag service reads its baseline file at start, so an edited variant applies after a flag-service restart.
- The rules record's `ffa.magnitude` answer reports the stamped length (decide contract §2.1), so `decide.answers` on the `agent.decide` span and the decision's value agree.

### BR-030: Shields go to the candidate with the fewest shields

- The rules engine spreads its shields: among R4's candidates (the struggling players that the filters and the minimum score leave: alive, with a skill level strictly below the mean of the alive players with a skill level, and never the strongest alive player; before the first elimination the players in sustained danger instead, A43, BR-032), it shields the one with the fewest agent shields in this game, the weakest on a tie (A41, #2395). A player who is not a candidate never holds the others back, and the kept candidate takes the best R4 candidate's score and place, so the rotation never gives fewer shields than shielding the weakest candidate would. The per-player cap and cooldown (BR-022), the charge and pool checks (BR-020, BR-024), the budget (BR-014, BR-015) and the kill switch and fail-closed gates still apply on top; the rotation only chooses the target and never allows a shield the other rules refuse.
- The count is the shield ledger's (A33): per game, in memory, written plus in flight. A shadow game and a real game never share it.

### BR-031: An agent shield is visible to the room

- Every applied `grant_shield` pulses the helped controller magenta (255,0,192) before the shield colour (A42, #2395), so a shield reads as the agent helping a struggling player, not as chance. The #818 "agent acted" cue for HARD-class interventions is the same magenta (#2426), so both read as the agent acting; the two are told apart by what they target (the helped controller before its shield, versus the intervention's target or every active player).
- The cue is told apart by its timing, not by its colour alone: a short pulse (two pulses in 500 ms) on the one helped controller, just before that controller's shield appears (the white shield in instant mode, the player's base colour breathing in trigger and hold mode). Magenta can match a player's own colour: it is the second team colour in the team modes (`teams_base.py` `TEAM_COLORS`, so every game with two or more teams has a magenta team), and close to the hue of the last players in a Free-for-All of 8 or more ([services.md](../specs/services.md) palettes).
- `grant_shield` is written only by the agent (the `shield_seconds` flag, W1, [flags.md](../specs/flags.md) §13.1), so every grant the coordinator applies is an agent grant. Admin invincibility (`invincible_until`), a player's own hold activation and the activation of a charge are not grants and get no cue.
- The LED is the cue (LED is the primary feedback); no voice line is added. The cue is not behind `agent_intervention_cue`: that toggle mutes the #818 operator cue of HARD-class interventions, and `grant_shield` is MEDIUM-class, so the two cues never both fire for one grant.
- A cue pulse may cut a running 200 ms warning flash short in trigger and hold mode (the overlay takes over the LED); the warning rumble still plays, and the next warning flashes again.

### BR-032: Danger shields need sustained danger and pass every shield gate

- Before the first elimination R4 shields a player only on a sustained near-threshold signal: `policy.shield_danger_samples` consecutive readings at or above `policy.shield_danger_ratio` of the death threshold, the newest value at most 3 s old counted from when it was last new (A43, #2461). Missing, stale, frozen or non-finite data gives no danger shield (fail closed).
- `policy.shield_danger_enabled` = `off` switches the danger shield off on its own; the elimination path (A41) and the allow-list are unaffected. A missing or unreadable value reads `on`.
- The three flags are in the `agent` set, human-owned: the agent never writes them (C-034). The agent clamps the ratio and the count at use time, read with the cycle's live flags: the ratio to 0.7 to 1.0 and the readings to 2 to 10, so no flag value lets one reading trigger a shield; a missing, unreadable, non-positive or non-finite value gives the default (0.85 / 3).
- A danger shield is an R4 `grant_shield` like any other: the rotation (BR-030), the shield length (BR-029), the cap and the cooldown (BR-022), the charge and pool checks (BR-020, BR-024), the budget (BR-014, BR-015), the kill switch and every fail-closed gate apply unchanged. It only adds candidates before the first elimination, when the elimination path has none.

### BR-033: A group shield is all or nothing and shadow-first (draft, #2467)

- Draft: the rules are final in the PR that adds the coordinator handler (the flows are written there, #2467 PR 3). Today the flags exist and nothing reads or writes them.
- A group shield covers 2 to `policy.group_grant.max_targets` alive players with one decision. It is applied to all of them or to none (the flows follow in PR 3); every target passes the same per-target checks as a single `grant_shield` (BR-022 cap and cooldown, BR-020 and BR-024 charge, pool and budget), and each target counts as one shield for those limits.
- It costs one intervention in the rate limit and is not a protective lever (BR-015). At most `policy.group_grant.max_per_game` group shields per game, checked by the agent and again by the coordinator.
- It needs `policy.group_grant.enabled` = `on`, and in a real game also `policy.group_grant.real_games` = `on`; a game of unknown kind counts as real. A missing or unreadable flag reads off (fail closed). The four flags carry no targeting: the agent and the coordinator read them in different contexts and must see one value (`test_group_grant_flags_carry_no_targeting`).
- The event `interventions/group_shield` carries `{"serials":"A,B,C","seconds":"5"}`; the flag service checks the payload (`serial_set`, `float 1 10`, flags.md §13.1). No `interventions_allowed` variant names `grant_group_shield` yet (`test_allow_list_variants_only_name_coordinator_types`), so the agent offers and writes nothing.
