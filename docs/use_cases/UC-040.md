# Use Case: Decide an In-Game Intervention

## Overview

**Use Case ID:** UC-040
**Use Case Name:** Decide an In-Game Intervention
**Primary Actor:** Agent
**Goal:** Nudge a running game toward the active objectives with a bounded, reversible intervention
**Status:** Implemented
**Requirements:** FR-043, FR-044, FR-046, FR-047, FR-048, FR-049, FR-050, FR-051, FR-052, FR-053, FR-054, NFR-010, NFR-011, NFR-012, NFR-013, NFR-015, C-002, C-004
**Planned:** FR-069 (#1269, Open)

## Preconditions

- The agent observes the game (UC-041) and the gate holds: the game is active and at least one player is fresh.
- `enabled` is on.
- Contract details: [decide-contract.md](../specs/decide-contract.md).

## Main Success Scenario (remote backend)

1. System reads the live flag snapshot (objectives, policy, `decision.*`).
2. System sees `decision.backend` = jev (the main in-game backend), claude (the manual backup) or openai, and the backend is available (jev: `JEV_API_KEY`; claude: key + model; openai: key + model + base URL).
3. System checks that no remote call is in flight for this game, that the game kind is eligible (`llm.eligible_game_kinds`, default real), that the allow-list offers at least one intervention besides `noop` (BR-005), that `decision.min_interval_ms` (default 3 s) has passed and that the global budget (`llm.max_requests_per_minute`, default 6) has room.
4. System builds the state (narrative, players, digest) and the FFA questions: which intervention (noop or an allowed type), which target, what magnitude.
5. System calls the backend asynchronously with `decision.<backend>.timeout_ms` (claude 5000 ms, jev and openai 2500 ms by default); the game keeps running.
6. The backend answers; System parses and validates the answers strictly.
7. System re-reads the live flags: the kill switch is still on and `decision.backend` is unchanged.
8. System checks the answers for consistency (not invalid) and that the intervention is not `noop`.
9. The `ffa.intervention` confidence is at least the answering backend's act threshold, read now (#1287): for jev `decision.jev.act_confidence_threshold` (default 0.6; variant `inherit` uses the global), for claude and openai `decision.act_confidence_threshold` (default 0.8). Outcome `act`; the span records the effective threshold and its source (`jev` / `global`).
10. System re-reads the current context: it exists, the game is still active and the target (if any) is still present.
11. System runs the permission chain: allow-list, battery threshold, per-game weighted rate limit.
12. System writes the intervention into `interventions.json` (the write is gated by `interventions_enabled`).
13. The game coordinator picks up the flag change, re-checks the allow-list, the mode's capabilities, battery and its global backstop, and applies the intervention through the game's own code (e.g. tempo change, shield, elimination), publishing `agent_intervention`; a player-targeted intervention is also recorded as an event on that player's span carrying `player.serial` and `player.name`. An edge intervention applies once, and only in a game during which its nonce changed (BR-006).
14. System records `agent.decide`, `chat {model}`, `agent.decision` and `agent.action` spans (a player-targeted decision names the player with `player.serial` and, when known and the game is not a shadow game, `player.name`) and later measures the intervention's effect (`agent.intervention.effect`).

Interventions a player can perceive give feedback in the game: an audio cue plays a real sound (BR-007), and a shield plays a sound and shows on the player's LED and on the dashboard (A16, A17).

## Alternative Flows

### A1: Rules backend (default)

**Trigger:** `decision.backend` is `rules` (step 2)
**Flow:**

1. System ranks rule candidates by objective weight × urgency × fitness pressure and emits up to two decisions per evaluation (at most one evaluation per second).
2. System records the rules answers as the first emitted decision (intervention and target, even one the allow-list will block), with `outcome=act`. A cycle in which the ranking emitted nothing records no `agent.decide` span.
3. Use case continues at step 11 (no confidence routing).

### A2: Remote timeout, error or invalid answer → rules fallback

**Trigger:** The call times out, fails (HTTP error including 429) or the answer fails validation (steps 5 to 6)
**Flow:**

1. After the kill-switch and backend checks (step 7), System records `outcome=fallback` with `fallback_reason` = timeout, error or invalid_answer.
2. System lets the rules engine decide on the **current** context. If the context is gone or the game has ended, nothing is decided and the span carries `outcome=fallback` **with** `discarded_reason` = `stale_context` or `game_ended`.
3. Use case continues at step 11.

### A3: Backend unavailable, ineligible or over budget → rules now

**Trigger:** Unknown backend, missing key / model, ineligible game kind or exhausted budget (steps 2 to 3)
**Flow:**

1. System records `outcome=fallback` with the reason (`unknown_backend`, `backend_unavailable`, `async_not_wired`, `llm_not_eligible`, `llm_budget_exhausted`).
2. Rules decide in the same cycle (A1).

### A4: Cadence or in-flight gate

**Trigger:** A call is in flight for this game or the minimum interval has not passed (step 3)
**Flow:**

1. System makes no decision this cycle (rules stay quiet; not a fallback).

### A5: Low confidence → held

**Trigger:** Confidence below the threshold (step 9)
**Flow:**

1. System records `outcome=held` and does nothing. The context is not checked first, so a low-confidence answer that lands after the game ended is `held`, not `discarded`.

### A6: Kill switch mid-flight → discarded

**Trigger:** `enabled` was turned off while the call was in flight (step 7, the first check on landing)
**Flow:**

1. System records `outcome=discarded`, `discarded_reason=kill_switch`; neither the answer nor a rules fallback acts.

### A7: Situation changed → discarded

**Trigger:** The backend changed (step 7), or, for an answer that would act, the context is missing, the game ended or the target is gone (step 10)
**Flow:**

1. System records `outcome=discarded` with `backend_changed` (step 7) or `stale_context`, `game_ended`, `target_gone` (step 10).

### A8: Inconsistent answers → invalid

**Trigger:** E.g. `noop` with a target, or a player intervention without a target (step 8)
**Flow:**

1. System records `outcome=invalid` with `invalid_reason`; no action and no fallback.

### A9: Noop

**Trigger:** The backend chose `noop` (step 8)
**Flow:**

1. System records `outcome=noop`.

### A10: Blocked

**Trigger:** Not allowed, battery below `policy.battery_threshold` or rate limit reached (step 11)
**Flow:**

1. System records the decision as blocked with the reason on `agent.decision` and as `decide.blocked` / `decide.block_reason` on `agent.decide`; the outcome stays `act`; nothing is written.
2. Use case ends.

### A11: Actuation gate off

**Trigger:** `interventions_enabled` is off (step 12)
**Flow:**

1. Nothing is written (the applied counter still increments, D-A9).

### A12: Noul questions

**Trigger:** A request contains a `noul` (yes/no, P(yes)) question (shipped in PR #1261; no caller-level FFA question is a noul; the Jev backend asks the internal `jev.gate` noul every stage-1 round, see [decide-contract.md §3.1](../specs/decide-contract.md))
**Flow:**

1. Jev answers it natively (confidence \|2p − 1\|); rules answer 0.5 at confidence 0.
2. Claude and openai reject the request before any network call (`invalid_answer`), so rules decide (A2).

### A13: Two-stage Jev round (gated)

**Trigger:** `decision.backend` is jev (step 5; PR #1265, gate #1281)
**Flow:**

1. System's first Jev call asks the gate noul "Does the game need an intervention right now?" and `ffa.intervention` without `noop` in the same call.
2. System synthesises the `ffa.intervention` answer as `{noop: 1 − p_yes, Jev's pick: p_yes, others: 0}`, so its confidence is p_yes when acting, and records Jev's real p_yes and distribution on the stage-1 span.
3. If p_yes ≤ 0.5 the answer is `noop` and no second call is made; use case continues at step 6 (then A9).
4. Otherwise, if the chosen intervention needs a target or a magnitude, System makes a second Jev call conditioned on it (target among alive players described by suitability; magnitude levels of that intervention only, no neutral level, the most likely level wins with ties going to the gentler level; for two-way levers Go picks the direction from the danger signals and Jev picks the strength).
5. Both calls share the `decision.jev.timeout_ms` deadline; a stage-2 failure fails the whole round (A2).
6. Use case continues at step 6; at step 9 p_yes is compared with Jev's own `decision.jev.act_confidence_threshold` (default `gate` 0.6, calibrated for p_yes: collapsing and near-threshold act, calm and dragging are noop; A5 when below). With the `inherit` variant the global `decision.act_confidence_threshold` applies instead (default 0.8 holds every calibrated state).

### A14: No interventions allowed → no remote call

**Trigger:** The effective allow-list is empty: `interventions_allowed` resolves to `none` (or to a list that holds only `noop` or empty ids, e.g. `probe`), so `noop` would be the only `ffa.intervention` option (step 3; #1298)
**Flow:**

1. System makes no remote call: no Jev, Claude or OpenAI request is built or sent, and neither the cadence (`decision.min_interval_ms`) nor the global budget (`llm.max_requests_per_minute`) is charged.
2. System does not run the rules engine either (nothing it could emit would pass the allow-list) and records no fallback and no `agent.decide` span.
3. System increments `agent_llm_gated_total{reason=no_interventions_allowed}` and writes a debug log `agent.decide.no_interventions_allowed` only when the game enters or leaves this state.
4. As soon as the allow-list offers an intervention again, the next cycle continues at step 3.

### A15: Edge value left over from an earlier game

**Trigger:** A game starts while an edge flag (`audio_cue`, `controller_effect`, `eliminate_player`, `revive_player`, `end_game`) still holds the last `<nonce>:<payload>` written for an earlier game, and a later flag change (any flagd file) makes the coordinator re-evaluate during the new game (step 13)
**Flow:**

1. At game start, before the game runs, the coordinator records each edge flag's current nonce as that game's baseline without applying it (real and shadow games alike).
2. On the re-evaluation the nonce equals the baseline, so nothing is applied and no `agent_intervention` is published.
3. A new nonce written during the game differs from the baseline, so it is applied once. Use case continues at step 13.

### A16: Shield feedback for the player

**Trigger:** The coordinator grants or extends a `grant_shield` or `partial_shield` for a player (step 13; #1301)
**Flow:**

1. System plays the shield sound `shield_up` (full volume for `grant_shield`, half volume for `partial_shield`) (BR-007).
2. System sends the player's controller a `GAME_EFFECT_SHIELD` (`grant_shield`) or `GAME_EFFECT_PARTIAL_SHIELD` (`partial_shield`) with `duration_ms` = the remaining protection; the controller manager renders the LED schedule itself (BR-008, BR-009).
3. System publishes the game event `player_shielded` (`serial`, `kind` = `full` or `partial`, `seconds`, `until_ms`) and records the span event `shield_feedback` on the player's span.
4. The dashboard tile of the player shows the live LED colour and a shield badge counting down to `until_ms`.
5. When the protection ends, the controller restores the player's current base colour.
6. Use case continues at step 14.

### A17: Shield feedback ends early

**Trigger:** The shielded player dies, the game ends, or a new base colour is set while the shield effect of A16 runs (step 13)
**Flow:**

1. On death the death effect replaces the shield effect; on game end System sends the shield effect with `duration_ms=0` to every player with shield feedback still running, before the winner effects (BR-010).
2. The controller manager cancels the shield effect task and restores the base colour; the dashboard clears the badge on `player_death`, `game_ended` and `game_force_ended`.
3. Use case continues at step 14.

## Postconditions

### Success Postconditions

- The intervention is live in the game and auditable from the trace.

### Failure Postconditions

- The game continues unchanged; the reason is on the `agent.decide` / `agent.decision` span.

## Business Rules

### BR-001: The game never waits

Remote calls are asynchronous; nothing in the game coordinator waits for the agent.

### BR-002: Interventions are not game-scoped yet

See [D-A2](../specs-inventory.md#46-agent-d-a) (FR-069, #1269).

### BR-003: Backend roles

See [C-018](../requirements.md#constraints).

### BR-004: Double enforcement

The allow-list is checked by the agent and again by the coordinator; the coordinator also enforces a global backstop (default 60 per minute).

### BR-005: No paid call without a possible action

A remote decide call is made only when the effective allow-list (deduplicated, empty ids and `noop` dropped, as for the `ffa.intervention` options) holds at least one intervention; otherwise the call could only answer `noop` (A14, NFR-011). The check sits before cadence and budget are charged. An answer already in flight when `interventions_allowed` flips to `none` is still blocked at landing by the live allow-list (`not_allowed`, A10). This covers in-game decide calls only: the post-game retro and the experiment proposer are governed by the kill switch and the LLM budget, not by the allow-list.

### BR-006: An edge intervention fires only in the game that saw it change

An edge flag's value present when a game starts is treated as already consumed for that game: the coordinator seeds the game's nonce baseline from the current flag values at game start and applies an edge intervention only when its nonce changes during that game, at most once per nonce. A stale `end_game`, `eliminate_player` or `audio_cue` from an earlier game, or from before a coordinator restart, is never replayed into a new game (#1299). A live game with no baseline (never primed) is primed on first evaluation, also without applying. Fail closed on flagd errors: a read that returns an evaluation error never moves the baseline, and a baseline that could not be read at game start adopts the next good value without applying it. State flags are not affected: a game converges on their current value.

### BR-007: Every intervention sound resolves

Every sound id an intervention plays exists in the audio registry. The writer default `agent_cue` (`play_audio_cue`) and the shield sound `shield_up` are registry **aliases**: `agent_cue` plays the lobby ready ping (`beep_loud`, the sound a controller makes when it joins the lobby), `shield_up` plays `power_ready` (Commander). The audio service logs a WARNING for any sound id that is not in the registry (#1301).

### BR-008: Shield LED schedule

For `GAME_EFFECT_SHIELD` with duration T: the LED shows the shield colour (white, as in spawn protection) and its brightness falls linearly from 100 % to 30 % over the first T − 1 s; in the last 1 s it blinks at 4 Hz between full shield colour and off; at T it shows the player's current base colour. A shield of 1 s or less blinks for its whole duration. The controller manager renders the schedule at its effect rate (20 Hz); the coordinator sends one command per grant, not a colour stream.

### BR-009: Partial shield is the weaker variant

For `GAME_EFFECT_PARTIAL_SHIELD` with duration T: the shield colour breathes slowly (0.5 Hz) between 10 % and 50 % brightness until the last 1 s, then blinks at 4 Hz between 50 % and off, then restores the base colour.

### BR-010: Feedback follows the protection, never the other way round

Feedback starts only when the grant changes the protection: a grant that extends the shield restarts the effect with the new remaining time; a grant that is kept (the effective grace, `max(agent shield, admin invincibility)` per #817, already lasts longer) sends no feedback. Death, game end and a new base colour end the effect; the coordinator keeps no timer or task for it. Feedback never changes `grace_until`, `invincible_until` or the partial-shield boost, and a feedback failure never fails the intervention.
