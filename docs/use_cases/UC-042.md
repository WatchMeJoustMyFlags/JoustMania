# Use Case: Review a Game and Propose Experiments

## Overview

**Use Case ID:** UC-042
**Use Case Name:** Review a Game and Propose Experiments
**Primary Actor:** Agent
**Goal:** Learn from a finished game and turn the lesson into an experiment
**Status:** Implemented
**Requirements:** FR-056, FR-057, FR-058, NFR-011, C-009

## Preconditions

- A game ended (UC-041 step 7).
- `AGENT_INFERENCE_BACKEND` is `claude` with `ANTHROPIC_API_KEY` set for model-backed output; otherwise the stub backend is used (capture only, no proposals).

## Main Success Scenario

1. The agent runs one retro per game: while `enabled` is on, for an eligible game kind (default real only) and with budget left, it asks the model for a session assessment, suggestions and a focus.
2. The agent records the retro on an `agent.llm.retro` span (prompt fingerprint, response fields).
3. The agent builds a game summary and adds its game-level aggregates to the in-memory cross-game window: a real game to the real-game window, a shadow game to its experiment's linked set (BR-004, BR-005).
4. If `enabled` and `experiments_enabled` are on, `code_improvement.min_interval_seconds` (default 300 s) has passed, the game kind is in `llm.eligible_game_kinds` and the shared budget has a slot, the proposer asks the model for one experiment: a flag of the experiment catalog (the `game` flags whose registry row allows an experiment arm, flags.md §13.3), a value and a rationale. The prompt carries the rendered `PRIOR GAMES` block: the real-game window and, for a shadow game, its own experiment's linked set as a separate section (BR-005, BR-006).
5. The agent gives the proposal its own experiment id (`prop_<hex>`) and submits it to the experiment gate, which writes the experiment-arm value through the flag service (UC-043, [UC-053](UC-053.md) A3).

## Alternative Flows

### A1: Shadow game

**Trigger:** The game was a shadow game (step 1)
**Flow:**

1. The retro is capture-only (no model call); with a real backend it records `agent_llm_gated_total{reason=llm_not_eligible}`.
2. With a real backend, the proposer makes no model call either; it records `agent_llm_gated_total{reason=llm_not_eligible}` and tries again at the next game end.
3. Use case continues at step 3.

### A2: Budget exhausted or no backend

**Trigger:** No budget or stub backend (step 1 or 4)
**Flow:**

1. With the stub backend, the retro is recorded without inference (capture-only span) and the proposer proposes nothing.
2. With a real backend and no budget left, the retro is gated: no prompt, no span, only `agent_llm_gated_total{reason=llm_budget_exhausted}` and the log `agent.llm.retro_gated`. The proposer records the same metric and tries again at the next game end. The stub never takes a budget slot.
3. Use case continues at step 3.

### A3: Retro-seeded theses

**Trigger:** `AGENT_EXPERIMENT_PROPOSER_ENABLED=true` (step 2)
**Flow:**

1. Retro suggestions are forwarded to the experiment loop's thesis proposer (subordinate to `experiments_enabled` and the kill switch).
2. Use case continues at step 3.

### A4: Gate rejects the proposal

**Trigger:** Unknown flag, non-game target, default changed, not shadow-scoped, real resolution changed (step 5)
**Flow:**

1. Nothing is written; the rejection reason is on the `code_improvement.proposed` span.
2. Use case ends.

### A5: Agent or experiments switched off

**Trigger:** `enabled` or `experiments_enabled` is off at game end (steps 1, 4), or is switched off while the model call runs (step 4)
**Flow:**

1. With `enabled` off the retro is capture-only (`inference.fallback_reason=agent_disabled`, no model call, no budget slot).
2. The proposer does nothing: no model call, no budget slot, no experiment write (outcome `disabled`, reason `agent_disabled` / `experiments_disabled`).
3. If the flag flipped during the model call, the proposal is dropped before the experiment gate; the reason is on the `code_improvement.propose_attempt` span.
4. Use case ends.

## Postconditions

### Success Postconditions

- A retro span exists (unless the budget was exhausted, A2); possibly an experiment-arm value on the flag service.

### Failure Postconditions

- No proposal; the game is unaffected.

## Business Rules

### BR-001: Shared budget

The global per-minute model budget (`llm.max_requests_per_minute`, NFR-011) is shared by in-game decisions, the retro and the proposer.

### BR-002: Proposer obeys the kill switch and the budget

The M7-4 proposer runs only while `enabled` and `experiments_enabled` are both on, read at each game end (`enabled` fails closed when flagd is unreachable; `experiments_enabled` falls back to `AGENT_EXPERIMENTS_ENABLED`, as in the experiment loop). A real model call draws from the same shared budget as the retro and in-game decisions (BR-001, NFR-011). Resolved D-A5 (PR #1284).

### BR-003: Engine flag is informational

`code_improvement.engine` is recorded only; `AGENT_INFERENCE_BACKEND` selects the backend.

### BR-004: Cross-game window holds no controller identity

A controller is not a person, not even across games: the same controller in the next game may be held by someone else ([C-009](../requirements.md)). Anything that crosses a game boundary (the cross-game window and the `PRIOR GAMES` prompt block built from it) holds game-level aggregates only:

- mode, player count, duration;
- outcome type, derived from the survivor count because the agent sees no end reason: `winner` (one survivor), `tie` (no survivor) or `multiple_survivors` (a force-end or a team win). A force-end that leaves exactly one survivor therefore renders as `winner`;
- death rate (eliminations / players) and near-death rate (share of players with an observed closest call who survived with a closest call of at least 0.8 × the death threshold);
- interventions by type: dispatched and blocked counts and the mean measured effect (intensity and active-player delta).

Eliminations come from the game's full elimination sequence and intervention counts from the game's full per-type tally, not from the 64-entry game timeline, which can lose early events; the mean effects use the interventions still on the timeline. No serial, display name, dominance holder, intervention target or per-player arc is stored in the window or rendered into the block; the summary's per-controller fields are dropped when the game is recorded. Per-player detail stays allowed within a single game (the retro of the game just played, steps 1 and 2). The window lives in agent-process memory only and is lost on restart; no per-game summary file is written. Decided on #1368.

### BR-005: Real and shadow history never mix

- **Real games** feed one real-game window of at most 20 games; the oldest is evicted.
- **Shadow games** feed only the linked set of their experiment, keyed by `experiment_id` (the link UC-043 gives its games; each entry keeps its arm). A linked set holds at most 20 games and is evicted when the experiment is torn down (done, discarded or aborted). The window remembers the last 64 torn-down experiments and drops a game of one of them that ends late. At most 64 linked sets are held (`MaxLinkedSets`); past that the oldest set is evicted. A shadow game with no experiment has no linked set and is dropped.
- A real game's prompt sees the real-game window only. A shadow game's prompt sees the real-game window plus its own experiment's linked set, rendered as a separate, labelled section; it never sees another experiment's games. A linked set reaches a prompt only when the proposer runs for a shadow game, which with a real backend needs `shadow` in `llm.eligible_game_kinds` (A1).

### BR-006: Pattern-driven players are exempt, keyed by archetype

Pattern-driven synthetic controllers (UC-046) have no person behind them: the player is the generating function. Inside its experiment's linked set, a pattern game may contribute per-player rows (elimination place, win, survival), keyed by archetype name, params digest and slot, never by serial. A pattern game's outcome uses the pattern-game vocabulary (`winner`, `tie`, `timeout`, `aborted`, `error`; UC-046). Rows come only from the pattern game's replay record, which lists pattern controllers only; in a game that also has other controllers, only the pattern controllers contribute rows, and the others stay aggregate-only (BR-004). The experiment journal's `pattern_game_ended` event carries no serial. Exemption: the per-game pattern telemetry (`pattern.slot_serials` on the game's spawn event, UC-046 and [telemetry.md](../specs/telemetry.md)) keeps the mock serials of that one game for replay and log correlation; mock serials are never reused, it is not cross-game memory and it never enters a prompt.
