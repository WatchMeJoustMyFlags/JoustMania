# Use Case: Review a Game and Propose Experiments

## Overview

**Use Case ID:** UC-042
**Use Case Name:** Review a Game and Propose Experiments
**Primary Actor:** Agent
**Secondary Actors:** Model API
**Trigger:** The agent ends a game (UC-041 step 7)
**Goal:** Learn from a finished game and turn the lesson into an experiment
**Status:** Tested
**Requirements:** FR-042, FR-056, FR-057, FR-058, FR-066, NFR-011, C-009, C-016, C-018
**Planned:** FR-162 (#2096, Implemented: the hold keys in the experiment catalog and the proposer vocabulary, [UC-043](UC-043.md) A17, and the game summary's hold values, BR-007; stays here, not under Requirements, because a Tested use case would derive Verified)

## Preconditions

- The agent observes games (UC-041).
- Its inference backend is chosen per use (once per retro, once per propose cycle) by the `inference.backend` flag (`stub` default or `claude`; `stub` while flagd cannot resolve the flag, no env fallback, #1810, #1907): `claude` takes effect when the flag says so and `ANTHROPIC_API_KEY` is set and `AGENT_INFERENCE_BASE_URL` is valid (the Model API, C-016, C-018); otherwise the stub backend, which makes no model call. The key is the egress ceiling: the flag alone cannot send anything anywhere new. The M7-4 proposer additionally needs its gate open (Pre-3 / BR-002), so the flag alone never switches on model-chosen experiments.

## Main Success Scenario

1. The agent runs one retro per game: with `enabled` on, the game kind in `llm.eligible_game_kinds` (default `real_only`: real games only) and a slot of the shared budget (BR-001), it asks the Model API for a session assessment, suggestions and a focus. The prompt states the game's intervention counts split as the game summary splits them: applied (written) and blocked by a gate (permission chain or actuation gate), so a fully gated game reads `0 applied, N blocked by a gate`, never `N interventions` (entity model GAME_SUMMARY, #1771).
2. The agent records the retro on an `agent.llm.retro` span (prompt fingerprint `llm.retro.system_sha256`, response fields).
3. The agent builds a game summary (with `interventions_applied` and `interventions_blocked`, logged on `agent.game.summary_built`) and adds its game-level aggregates to the in-memory cross-game window: a real game to the real-game window, a shadow game to its experiment's linked set (BR-004, BR-005). This step reads no flag.
4. With `enabled`, `experiments_enabled` and the proposer gate on (BR-002), at most once per `code_improvement.min_interval_seconds` (default 300 s), for a game kind in `llm.eligible_game_kinds` and with a budget slot, the proposer asks the Model API for one experiment: a flag of the experiment catalog (the `game` flags whose registry row allows an experiment arm, flags.md §13.3) that the shadow game's mode reads ([UC-043](UC-043.md) BR-009, #2392), a value and a rationale. The prompt lists each catalog flag with its registry description, its declared variants and its range (BR-008). The prompt carries the rendered `PRIOR GAMES` block: the real-game window and, for a shadow game, its own experiment's linked set as a separate section (BR-005, BR-006).
5. The agent declares the proposal as an experiment of the experiment registry (its own `exp_<hex>` id, arms experimental and control, hypothesis = the rationale, objective `balanced`, target N = `verdict_min_n` games per arm) and starts it: the experiment-arm value is written through the invariant gate and the flag service as in [UC-043](UC-043.md) step 1 (dry run first, nothing applied on a refusal), so the experiment's shadow games read it.

## Alternative Flows

### A1: Game kind not eligible for a model retro

**Trigger:** A real backend is wired and the game kind is not in `llm.eligible_game_kinds` (step 1): with the default `real_only` a shadow game, with `none` every game; an empty kind is never eligible. The kill switch is checked first: with `enabled` off A8 applies instead, and no `llm_not_eligible` is counted
**Flow:**

1. The retro makes no model call and takes no budget slot; its span is capture-only (`inference.used=none`, `inference.fallback_reason=llm_not_eligible`) and the agent counts `agent_llm_gated_total{reason=llm_not_eligible}`.
2. Use case continues at step 2.

### A2: Retro budget exhausted or stub backend

**Trigger:** The stub backend is wired, or a real backend finds the shared budget full (step 1)
**Flow:**

1. With the stub backend the retro is capture-only (`inference.fallback_reason=no_backend_available`), whatever `enabled` and the game kind say; the stub never takes a budget slot. Use case continues at step 2.
2. With a real backend and no budget slot the retro is gated: no prompt, no span, only `agent_llm_gated_total{reason=llm_budget_exhausted}` and the log `agent.llm.retro_gated`. Use case continues at step 3.

### A3: Retro-seeded theses

**Trigger:** The proposer gate is open (`AGENT_EXPERIMENT_PROPOSER_ENABLED=true` and `experiment_proposer_enabled` on, BR-002) and a model retro returned suggestions (step 2)
**Flow:**

1. The agent forwards the suggestions to the experiment loop's thesis proposer. On its next tick, and only while `experiments_enabled` and `enabled` are on, the thesis proposer declares at most one experiment from them, under the same concurrent-experiment budget as A11.
2. Use case continues at step 3.

### A4: Gate rejects the proposal

**Trigger:** Starting the declared experiment fails at the invariant gate (step 5): unknown flag, non-game target, default changed, not shadow-scoped, real resolution changed, an unexpected new variant, a dry-run refusal such as `out_of_bounds`, `flag_read_only` or `malformed`, or the flag service is unreachable or answers with an error (`read_error`, `write_simulation_error`)
**Flow:**

1. The agent aborts the just-declared experiment with reason `start_failed`; no experiment-arm value is written and the journal holds the declaration and the abort.
2. The rejection reason is on the gate's `code_improvement.proposed` span (`blocked=true`) and on the attempt span (`code_improvement.outcome=blocked`).
3. Use case ends.

### A5: Agent or experiments switched off for the proposer

**Trigger:** `enabled`, `experiments_enabled` or the proposer gate is off when the proposer runs (step 4), or turns off while its model call runs (step 4)
**Flow:**

1. Off at the start: the proposer makes no model call, takes no budget slot and writes nothing; its outcome is `disabled` with reason `agent_disabled`, `experiments_disabled` or `proposer_disabled` (debug log, no span).
2. Off during the call: the agent drops the proposal before the invariant gate; the attempt span records outcome `disabled` and the reason.
3. Use case ends.

### A6: Game ended stale

**Trigger:** The game ended with end reason `stale`, because its telemetry stopped (UC-041 A4) (step 1)
**Flow:**

1. The agent runs no retro, builds no summary, adds nothing to the cross-game window and runs no proposer for this game; only the stale end is counted (`agent_game_end_stale_total`).
2. Use case ends.

### A7: Proposer not admitted

**Trigger:** The cadence floor has not passed, the game kind is not in `llm.eligible_game_kinds`, the budget is full, or the stub backend is wired (step 4)
**Flow:**

1. Cadence floor not passed: outcome `gated`, no model call (debug log).
2. Not eligible or budget full: outcome `llm_gated` with reason `llm_not_eligible` or `llm_budget_exhausted`, counted in `agent_llm_gated_total{reason}`; the cadence floor is not used up, so the next game end may try again.
3. Stub backend: the attempt span records outcome `no_backend`; the cadence floor is used up.
4. Use case ends.

### A8: Agent switched off for the retro

**Trigger:** A real backend is wired and `enabled` is off at the game end (step 1)
**Flow:**

1. The retro makes no model call and takes no budget slot; its span is capture-only with `inference.fallback_reason=agent_disabled`.
2. Use case continues at step 2.

### A9: Retro model call fails

**Trigger:** The retro's model call errors or times out, or its reply cannot be decoded (step 1)
**Flow:**

1. The span is still recorded with error status, `llm.retro.parse_ok=false` and the error type (`invalid_output` for an undecodable reply, `timeout`, ...); the budget slot stays used and no suggestions are forwarded (no A3).
2. Use case continues at step 3.

### A10: Proposer model call fails

**Trigger:** The proposer's model call errors or times out, or its reply cannot be decoded or names a flag outside the experiment catalog (step 4)
**Flow:**

1. Nothing is declared or written. The attempt span records outcome `no_backend` for a failed call, `undecodable` for an unusable reply; the cadence floor and the budget slot stay used.
2. Use case ends.

### A11: Declaration refused

**Trigger:** The flag is already under test, the concurrent-experiment budget is full (live experiments at the smaller of the registry capacity and `experiment_dynamic_max_concurrent`, default 3, capped by the `AGENT_EXPERIMENT_DYNAMIC_MAX_CONCURRENT` ceiling when set, FR-152 e), or no experiment loop runs (step 5)
**Flow:**

1. Nothing is declared or written; the attempt span records outcome `blocked` with reason `flag_under_test` (also for a hold key whose deferred promotion still waits, [UC-043](UC-043.md) A17 step 3), `no_capacity` or `no_experiment_loop`.
2. Use case ends.

## Postconditions

### Success Postconditions

- The game's retro is on an `agent.llm.retro` span (with the model's assessment when a model call succeeded; capture-only in A1, A8 and on the stub backend, error status in A9; no span when gated, A2), and the game's aggregates are in the cross-game window.
- The proposed experiment is declared and running in the experiment registry, and its experiment-arm value is on the flag service, resolved only by that experiment's shadow games of the experimental arm.

### Failure Postconditions

- No flag value that a real game resolves was changed, and no experiment-arm value of this proposal remains on the flag service.

## Business Rules

### BR-001: Shared budget

The global per-minute model budget (`llm.max_requests_per_minute`, NFR-011) is shared by in-game decisions, the retro and the proposer.

### BR-002: Proposer obeys the kill switch and the budget

The M7-4 proposer runs only while `enabled`, `experiments_enabled` and the proposer gate are on, read at each game end and again after the model call, before the experiment write. The proposer gate (#1810, [FR-152](../requirements.md) d, C-034) is the operator's `AGENT_EXPERIMENT_PROPOSER_ENABLED=true` AND the `experiment_proposer_enabled` flag; unset env is closed and an unresolved flag reads off. The same gate opens the retro-seeded thesis proposer (A3), so a real text backend alone never switches on model-chosen experiments. See [FR-042](../requirements.md), FR-066; a flip of any flag reaches the agent on its next read ([flags.md §1.3](../specs/flags.md#13-reload-semantics)). `enabled` and `experiments_enabled` both fail closed when flagd is unreachable (no env fallback since #1907), as in the experiment loop. A real model call draws from the same shared budget as the retro and in-game decisions (BR-001, NFR-011). The retro reads only `enabled` (A8), never `experiments_enabled`. This rule is the owner; [UC-045](UC-045.md) BR-002 cites it. Resolved D-A5 (PR #1284).

### BR-003: Engine flag is informational

**Status:** Obsolete (#1810). `code_improvement.engine` was retired (D-A10); the `inference.backend` flag selects the backend.

### BR-004: Cross-game window holds no controller identity

A controller is not a person, not even across games: the same controller in the next game may be held by someone else ([C-009](../requirements.md)). Anything that crosses a game boundary (the cross-game window and the `PRIOR GAMES` prompt block built from it) holds game-level aggregates only:

- mode, player count, duration;
- outcome type, derived from the survivor count because the agent sees no end reason: `winner` (one survivor), `tie` (no survivor), `multiple_survivors` (a force-end or a team win) or `unknown` (no players seen). A force-end that leaves exactly one survivor therefore renders as `winner`;
- death rate (eliminations / players) and near-death rate (share of players with an observed closest call who survived with a closest call of at least 0.8 × the death threshold);
- interventions by type: applied and blocked counts, split as the game summary splits them (applied = written; blocked = refused by the permission chain or turned into a no-op by `interventions_enabled`; a failed write in neither), and the mean measured effect (intensity and active-player delta). The `PRIOR GAMES` block renders them as `applied=N blocked=M`, so a game whose dispatched decisions were all gated no-ops reads `applied=0` (#1778).

Eliminations come from the game's full elimination sequence and intervention counts from the game's full per-type tally, not from the 64-entry game timeline, which can lose early events; the mean effects use the interventions still on the timeline. No serial, display name, dominance holder, intervention target or per-player arc is stored in the window or rendered into the block; the summary's per-controller fields are dropped when the game is recorded. Per-player detail stays allowed within a single game (the retro of the game just played, steps 1 and 2). The window lives in agent-process memory only and is lost on restart; no per-game summary file is written. Decided on #1368.

### BR-005: Real and shadow history never mix

- **Real games** feed one real-game window of at most 20 games; the oldest is evicted.
- **Shadow games** feed only the linked set of their experiment, keyed by `experiment_id` (the link UC-043 gives its games; each entry keeps its arm). A linked set holds at most 20 games and is evicted when the experiment is torn down (done, discarded or aborted). The window remembers the last 64 torn-down experiments and drops a game of one of them that ends late. At most 64 linked sets are held (`MaxLinkedSets`); past that the oldest set is evicted. A shadow game with no experiment has no linked set and is dropped.
- A real game's prompt sees the real-game window only. A shadow game's prompt sees the real-game window plus its own experiment's linked set, rendered as a separate, labelled section; it never sees another experiment's games. A linked set reaches a prompt only when the proposer runs for a shadow game, which with a real backend needs `shadow` in `llm.eligible_game_kinds` (variant `real_and_shadow`, A1, A7).

### BR-006: Pattern-driven players are exempt, keyed by archetype

Pattern-driven synthetic controllers (UC-046) have no person behind them: the player is the generating function. Inside its experiment's linked set, a pattern game may contribute per-player rows (elimination place, win, survival), keyed by archetype name, params digest and slot, never by serial. A pattern game's outcome uses the pattern-game vocabulary (`winner`, `tie`, `timeout`, `agent_ended`, `aborted`, `error`; [UC-046](UC-046.md) BR-016). Rows come only from the pattern game's replay record, which lists pattern controllers only; in a game that also has other controllers, only the pattern controllers contribute rows, and the others stay aggregate-only (BR-004). The experiment journal's `pattern_game_ended` event carries no serial. Exemption: the per-game pattern telemetry (`pattern.slot_serials` on the game's spawn event, UC-046 and [telemetry.md](../specs/telemetry.md)) keeps the mock serials of that one game for replay and log correlation; mock serials are never reused, it is not cross-game memory and it never enters a prompt.


### BR-007: Hold values in the retro (#2096)

The game summary of a hold game (UC-040 BR-024, BR-027) carries the latched values (`shield.activation`, the cap, budget, starting energy, recharge rate, minimum burst and the cue values; `shield_hold`) and per player the energy granted, recharged and used, the activations and the empties (`player_arcs[].shield_totals`, as of the last export before the game ended), so the retro and the proposer can reason about whether the next game needs a change. The retro prompt shows both; a game that is not a hold game has neither. Source: the coordinator's `game_shield_hold_setting` and `game_player_shield_stats` gauges ([telemetry.md](../specs/telemetry.md) §6). Tests: `services/agent/gamesummary/summary_hold_uc042_test.go`, `services/agent/llm/retro_hold_uc042_test.go`.

### BR-008: The proposer sees what each catalog flag does (#2345)

The proposer prompt lists every flag of the experiment catalog it offers as one line: the key, the registry row's `description` (what the flag does in game terms), the declared variants the row allows with their values (an object value by its kind only) and the numeric range, all read from the flag service's `GET /game` in the same read that sets the vocabulary ([flags.md §13](../specs/flags.md#13-mutable-flag-registry), [services.md](../specs/services.md)). The flag service refuses to start when a catalog row has no description, or one longer than 120 characters or over more than one line; the agent cuts a description to 120 characters, folds it to one line and shows at most ten variants, so the prompt stays bounded whatever the service serves. A flag without a description shows its key and what it has. Only the proposer prompt changes: the rules path and the decide prompts do not show descriptions.
