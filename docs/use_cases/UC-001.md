# Use Case: Pair a Controller over USB

## Overview

**Use Case ID:** UC-001
**Use Case Name:** Pair a Controller over USB
**Primary Actor:** Player
**Goal:** Make a new PS Move controller known to the Pi's Bluetooth adapter so it can connect wirelessly
**Status:** Implemented
**Requirements:** FR-001, FR-124, FR-125, NFR-007, NFR-025, C-011, C-012

## Preconditions

- The stack is running with the pairing daemon (host network, privileged) and at least one Bluetooth adapter.
- The controller is a supported PS Move motion controller, ZCM1 or ZCM2 (BR-006).

## Main Success Scenario

1. Player plugs the controller into a USB port of the Pi.
2. System detects the controller on its next USB poll (every `pairing.poll_interval`, default 10 s); only PS Move motion controllers are detected (BR-006).
3. System picks the least-loaded Bluetooth adapter (BR-001).
4. System writes the adapter's address into the controller through the pairing backend that the `bluetooth_backend` flag selects (BR-003; default `rust`, the rust-hid PairingService).
5. System marks the controller as trusted in BlueZ on the selected adapter (BR-007). For a controller BlueZ already knows on that adapter nothing is restarted and no adapter is power-cycled (BR-005); a controller BlueZ does not know there takes A7.
6. System logs that the player can unplug the controller and press the PS button.
7. Player unplugs the controller.

## Alternative Flows

### A1: Controller already paired this session

**Trigger:** The serial was verified earlier in this daemon session, or it was unpaired while plugged in and has not left USB since (UC-005 A8) (step 2)
**Flow:**

1. System skips pairing.
2. Use case ends.

### A2: Trust step fails

**Trigger:** Marking the controller as trusted on the selected adapter fails, also after one retry, e.g. because BlueZ has no device object for it there (BR-007) (step 5)
**Flow:**

1. System logs the failure as non-fatal and keeps the pairing.
2. Use case continues at step 6.

### A3: Unknown backend value

**Trigger:** `bluetooth_backend` resolves to a value that is not one of its variants (`python`, `rust`, `unstable`), e.g. an empty string or a typo (step 4)
**Flow:**

1. System logs a warning and uses the rust-hid backend, the stack's default (BR-003).
2. Use case continues at step 5.

### A4: Controller already known to BlueZ

**Trigger:** The controller is in BlueZ's device list but was not verified in this daemon session, e.g. after a daemon restart (step 2)
**Flow:**

1. System pairs it again, to the adapter that is least loaded now; this can move the controller to another adapter (then A5).
2. Use case continues at step 3.

### A5: Controller registered on another adapter

**Trigger:** The pairing succeeded and BlueZ still holds a registration of the controller's address on an adapter other than the selected one, e.g. after A4 moved it (step 4)
**Flow:**

1. System removes those registrations (BR-004) before it marks the controller as trusted.
2. Use case continues at step 5.

### A6: A game is running

**Trigger:** A real or shadow game is running while the controller is plugged in (step 1)
**Flow:**

1. System pairs the controller as in steps 2 to 5; pairing does not wait for the game to end (BR-005).
2. With `pairing.bluez_restart_mode` = `when_idle` (default), a Bluetooth service restart that BR-005 calls for (A7) is deferred while the real (primary) game is starting, running or ending, or while its state cannot be read; the daemon runs it on a later poll once that game is idle or ended, so no player of a real game is eliminated by the pairing. Shadow games never defer it.
3. With `never` nothing is restarted, so every controller connected over Bluetooth stays connected.
4. Use case continues at step 6.

### A7: Controller BlueZ does not know on the selected adapter

**Trigger:** After the pairing (step 4), BlueZ has no registration of the controller on the selected adapter, e.g. a controller it has never seen (step 5)
**Flow:**

1. System writes a BlueZ device record for the controller under that adapter's storage, marked trusted (BR-008).
2. System has bluetoothd load the record by restarting it as `pairing.bluez_restart_mode` allows (BR-005): with `when_idle` (default) at once when no real game is starting, running or ending, otherwise on the first poll after that game (A6); with `never` not at all, so the controller cannot connect until bluetoothd restarts for another reason.
3. After each restart, System registers the pairing agent again (BR-005).
4. Use case continues at step 5; when the restart is deferred, the trust step fails (A2) and the record's own trust applies once bluetoothd loads it.

### A8: Device record cannot be written

**Trigger:** The record of A7 cannot be written: the controller's product id is not a supported PS Move (BR-006, e.g. an older rust-hid that does not report it), BlueZ keeps no storage directory for the selected adapter, or the write fails, in A7 (step 5)
**Flow:**

1. System logs an error with the reason and requests no restart for it.
2. Use case continues at step 5; the pairing is kept, and the controller likely cannot connect until it is paired again.

## Postconditions

### Success Postconditions

- The controller stores the Pi adapter's address and is trusted by BlueZ on the selected adapter, or, after A7, has a trusted device record there that bluetoothd loads at its next restart.
- `psmove_pairing_success_total` is incremented.
- With `pairing.bluez_restart_mode` `when_idle` or `never`, every controller that was connected over Bluetooth during a real game is still connected (BR-005).

### Failure Postconditions

- The controller is not paired; `psmove_pairing_failed_total` is incremented and the next poll retries.

## Business Rules

### BR-001: Adapter load balancing

New controllers go to the least-loaded adapter. Load is the number of devices BlueZ knows on that adapter (paired or connected, PS Move or not), not only the connected ones; ties go to the lowest adapter address. About 7 controllers per adapter is the recommended hardware limit (C-011); the daemon does not enforce it. A controller already known to BlueZ is paired again in each daemon session and can move to another adapter (A4); its registration on the previous adapter is then removed (A5, BR-004), so each controller counts on one adapter only.

### BR-002: No LED feedback

The pairing daemon gives no LED feedback during pairing (see D-C4 in [specs-inventory](../specs-inventory.md#45-controllers-pairing-leds-d-c)).

### BR-003: Every backend variant has a pairing backend

The pairing daemon maps each `bluetooth_backend` variant to a defined pairing backend (#1320): `rust` → the rust-hid PairingService; `python` → the in-process hidapi backend; `unstable` → the in-process hidapi backend too (`unstable` is the controller manager's fault-injecting wrapper around the python I/O path; pairing is a one-shot USB write with nothing to inject). Any other value, and an unreachable flagd, select `rust`, the default backend that every stack ships (UC-002 BR-003).

### BR-004: Stale registrations are removed on re-pair

After a successful pairing (step 4) the daemon removes every registration of the controller's address on the other adapters, through BlueZ (`Adapter1.RemoveDevice`) for present adapters and by deleting `/var/lib/bluetooth/<adapter>/<address>` for registrations BlueZ has not loaded (as in UC-005 BR-002). The address comes from the controller on USB, so the address alone identifies it; no other device is touched, and the registration on the selected adapter is kept. A failed removal is logged and does not fail the pairing.

### BR-005: Pairing does not disconnect other controllers

Restarting the Bluetooth service (`bluetooth.service` / bluetoothd) powers every adapter off and drops every connected controller, which eliminates every player of a running game (#1446). It also ends the `bluetoothctl` agent session (#632), so after every restart the daemon registers the pairing agent again. A restart is needed only after a new BlueZ device record was written (A7, BR-008): bluetoothd reads its storage only at start. Whether pairing restarts it is set by the flag `pairing.bluez_restart_mode` (system domain, read at use time; an unknown value or unreachable flagd means `never`, fail closed):

- `when_idle` (default, #1466): bluetoothd is restarted only after a pairing wrote a new BlueZ device record (or one written earlier is not loaded yet), and only while no real (primary) game is starting, running or ending. A restart outside a real game still drops the controllers connected in the lobby; their players press PS again. It happens only when a controller new to that adapter is paired. The daemon reads the primary game's state from the game coordinator's `GetGameState` (empty `game_id`) through envoy's Connect route (`http://localhost/joustmania.game_coordinator.GameCoordinatorService/GetGameState`, env `GAME_STATE_URL`), so it needs no gRPC port of its own; shadow games are not the primary game and never defer it. An unreadable state counts as a running game (fail closed): the restart waits and is retried on each USB poll; the poll runs it under the pairing lock, so it never interleaves with a pairing or an unpair.
- `never`: pairing never restarts bluetoothd and never powers an adapter off or on. Registration removal (BR-004, `Adapter1.RemoveDevice`) and trust (`Device1.Trusted` on the selected adapter, BR-007) take effect in the running bluetoothd, but a record written by A7 is not loaded, so a controller new to that adapter cannot connect until bluetoothd restarts for another reason.
- `always`: the pre-#1446 behaviour: bluetoothd is restarted after every successful pairing, during games too. Diagnostics only.

Why a record and a restart: BlueZ refuses an incoming HID connection from a device it does not know (`profiles/input/server.c`; PS Move is not in its sixaxis cable-pairing table), and only a running bluetoothd's own pairing creates one; a PS Move paired over USB never pairs over Bluetooth. psmoveapi, used before #610, wrote the record and restarted bluetoothd for the same reason. Whether `Adapter1.ConnectDevice` or a power cycle of only the selected adapter could avoid the restart needs hardware (#1465).

### BR-006: Only PS Move motion controllers are paired

The pairing daemon and both HID backends (rust-hid, python_hid) enumerate only Sony's vendor id `054C` with product id `03D5` (ZCM1, PS3 era) or `0C5E` (ZCM2, PS4 era) (C-012). Product id `042F` is the PS Move Navigation controller: it has no light, no motion sensors and no trigger, so it cannot play; it is never enumerated, paired or opened as a player controller (#1442), and the registration reset (C-011) leaves it alone too.

### BR-007: Trust lands on the selected adapter

The trust step sets `Device1.Trusted` through BlueZ's D-Bus API on the device object of the adapter the controller was just paired to (`/org/bluez/<hci>/dev_<address>`). It does not use `bluetoothctl trust`, which acts on bluetoothctl's default adapter and, with several adapters, can trust the copy on another adapter or fail (#1445). No other adapter's registration is trusted or changed by the trust step. If BlueZ has no device object for the address on the selected adapter, the trust fails (A2); it is retried once, except when BlueZ answers that the object does not exist.

### BR-008: Device record for a controller BlueZ does not know

When BlueZ has no registration of the controller on the selected adapter (A7), the daemon writes the record that psmoveapi wrote before #610 (#1466):

- `/var/lib/bluetooth/<adapter>/<controller>/info`: `[General]` `Name=Motion Controller`, `Class=0x002508`, `SupportedTechnologies=BR/EDR;`, `Trusted=true`, `Blocked=false`, `Services=` the HID service UUID `00001124-0000-1000-8000-00805f9b34fb`; `[DeviceID]` `Source=1`, `Vendor=1356` (`054C`), `Product=` the product id read over USB (`03D5` ZCM1 or `0C5E` ZCM2), `Version=1`.
- `/var/lib/bluetooth/<adapter>/cache/<controller>`: the PS Move's HID SDP record under `[ServiceRecords]` (handle `0x00010000`), which BlueZ needs to set up the HID connection because the controller is never queried over Bluetooth before it connects.

Only PS Moves get a record (product id `03D5` or `0C5E`, BR-006), only under an adapter directory BlueZ already keeps, and only for the address read from the controller on USB. An existing `info` or cache file is never overwritten: it may hold BlueZ's own pairing data, such as a ZCM2 link key. A record that exists but is not loaded yet still asks for the restart (BR-005). Files are created with mode 0600 in directories with mode 0700, as BlueZ does. Once bluetoothd has loaded it, the record is an ordinary BlueZ registration, which unpair (UC-005) and the registration reset remove through BlueZ.

Hardware verification pending (#1465): a never-seen ZCM1 and ZCM2 connect after unplug and PS with the default `when_idle`.
