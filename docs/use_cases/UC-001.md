# Use Case: Pair a Controller over USB

## Overview

**Use Case ID:** UC-001
**Use Case Name:** Pair a Controller over USB
**Primary Actor:** Player
**Goal:** Make a new PS Move controller known to the Pi's Bluetooth adapter so it can connect wirelessly
**Status:** Tested
**Requirements:** FR-001, FR-009, FR-124, FR-125, NFR-007, NFR-025, C-011, C-012

## Preconditions

- The stack is running with the pairing daemon (host network, privileged) and at least one Bluetooth adapter.
- The controller is a supported PS Move motion controller, ZCM1 or ZCM2 (BR-006).

## Main Success Scenario

1. Player plugs the controller into a USB port of the Pi.
2. System detects the controller on its next USB poll (every `pairing.poll_interval`, default 10 s); only PS Move motion controllers are detected (BR-006). System pulses the LED of every detected controller it is about to pair until its pairing ends (BR-010).
3. System picks the least-loaded Bluetooth adapter (BR-001).
4. System writes the adapter's address into the controller through the pairing backend that the `bluetooth_backend` flag selects (BR-003; default `rust`, the rust-hid PairingService).
5. System marks the controller as trusted in BlueZ on the selected adapter (BR-007). For a controller BlueZ already knows on that adapter nothing is restarted and no adapter is power-cycled (BR-005); a controller BlueZ does not know there takes A7.
6. System flashes the controller's LED green (BR-010) and logs that the player can unplug the controller and press the PS button.
7. Player unplugs the controller.

## Alternative Flows

### A1: Controller already paired this session

**Trigger:** The serial was verified earlier in this daemon session, or it was unpaired while plugged in and has not left USB since (UC-005 A8) (step 2). A controller whose device record waits for a restart (A7) or could not be written (A8) counts as verified only until it leaves USB.
**Flow:**

1. System skips pairing and shows no LED cue for it.
2. Use case ends.

### A2: Trust step fails

**Trigger:** Marking the controller as trusted on the selected adapter fails, also after one retry, e.g. because BlueZ has no device object for it there (BR-007) (step 5)
**Flow:**

1. System logs the failure as non-fatal and keeps the pairing.
2. Use case continues at step 6.

### A3: Unknown backend value

**Trigger:** `bluetooth_backend` resolves to a value that is not one of its variants (`python`, `rust`, `unstable`), e.g. an empty string or a typo (step 4)
**Flow:**

1. System logs a warning and uses the rust-hid backend, the stack's default (BR-003).
2. Use case continues at step 5.

### A4: Controller already known to BlueZ

**Trigger:** The controller is in BlueZ's device list but was not verified in this daemon session, e.g. after a daemon restart (step 2)
**Flow:**

1. System pairs it again, to the adapter that is least loaded now; this can move the controller to another adapter (then A5).
2. Use case continues at step 3.

### A5: Controller registered on another adapter

**Trigger:** The pairing succeeded and BlueZ still holds a registration of the controller's address on an adapter other than the selected one, e.g. after A4 moved it (step 4)
**Flow:**

1. System removes those registrations (BR-004) before it marks the controller as trusted.
2. Use case continues at step 5.

### A6: A game is running

**Trigger:** A real or shadow game is running while the controller is plugged in (step 1)
**Flow:**

1. System pairs the controller as in steps 2 to 5; pairing does not wait for the game to end (BR-005).
2. With `pairing.bluez_restart_mode` = `when_idle` (default), a Bluetooth service restart that BR-005 calls for (A7) is deferred while the real (primary) game is starting, running or ending, or while its state cannot be read; the daemon runs it on a later poll once that game is idle or ended, so no player of a real game is eliminated by the pairing. Shadow games never defer it.
3. With `never` nothing is restarted, so every controller connected over Bluetooth stays connected.
4. Use case continues at step 6.

### A7: Controller BlueZ does not know on the selected adapter

**Trigger:** After the pairing (step 4), BlueZ keeps no registration of the controller on the selected adapter (no device there that is paired, bonded or trusted; a temporary or discovered device does not count), e.g. a controller it has never seen (step 5)
**Flow:**

1. System writes a BlueZ device record for the controller under that adapter's storage, marked trusted (BR-008).
2. System has bluetoothd load the record by restarting it once, as `pairing.bluez_restart_mode` allows (BR-005): with `when_idle` (default) at the end of the first poll at which, for `pairing.restart_quiet_period` (default 20 s), no PS Move still to be paired has been on USB and none was paired, and no real game is starting, running or ending, so pairing a stack of controllers one after the other costs one restart (#2091); a game that is busy then delays it to the first poll after that game (A6); with `never` not at all, so the controller cannot connect until bluetoothd restarts for another reason. Just before the restart, System writes again any of the waiting records that has disappeared (BR-008). A restart that fails stays pending with its records and is tried again on a later poll (BR-005).
3. After each restart, System registers the pairing agent again (BR-005, BR-009).
4. Use case continues at step 5, which runs before the restart: the trust step finds no device object (A2) and the record's own trust applies once bluetoothd loads it. While the restart is deferred or after it failed, unplugging and plugging the controller in again pairs it again (it is no longer skipped as verified, A1), which writes a lost record again.

### A8: Device record cannot be written

**Trigger:** The record of A7 cannot be written: the controller's product id is not a supported PS Move (BR-006, e.g. an older rust-hid that does not report it), BlueZ keeps no storage directory for the selected adapter, an existing `info` file there is empty or unreadable, or the write fails, in A7 (step 5)
**Flow:**

1. System logs an error with the reason, shows the red LED cue on the controller (BR-010) and requests no restart for it. For an empty or unreadable `info` file the error names the file and tells the operator to delete it (and the controller's cache file, if any) and then plug the controller in again; System never overwrites or deletes it itself (BR-008).
2. Use case continues at step 5; the pairing is kept, and the controller likely cannot connect until it is paired again. Unplugging and plugging it in again pairs it again (A1), which writes the record once the cause is gone, e.g. after the operator deleted the unusable `info` file.

## Postconditions

### Success Postconditions

- The controller stores the Pi adapter's address and is trusted by BlueZ on the selected adapter, or, after A7, has a trusted device record there that bluetoothd loads at its next restart.
- `psmove_pairing_success_total` is incremented.
- With `pairing.bluez_restart_mode` `when_idle` or `never`, every controller that was connected over Bluetooth during a real game is still connected (BR-005).

### Failure Postconditions

- The controller is not paired; `psmove_pairing_failed_total` is incremented, its LED shows red until the next poll retries (pulse again) or it is unplugged (BR-010).

## Business Rules

### BR-001: Adapter load balancing

New controllers go to the least-loaded adapter. Load is the number of devices BlueZ knows on that adapter (paired or connected, PS Move or not), not only the connected ones; ties go to the lowest adapter address. About 7 controllers per adapter is the recommended hardware limit (C-011); the daemon does not enforce it. A controller already known to BlueZ is paired again in each daemon session and can move to another adapter (A4); its registration on the previous adapter is then removed (A5, BR-004), so each controller counts on one adapter only.

### BR-002: No LED feedback

**Status:** Obsolete, superseded by BR-010 (#2091).

The pairing daemon gave no LED feedback during pairing (see D-C4 in [specs-inventory](../specs-inventory.md#45-controllers-pairing-leds-d-c)).

### BR-003: Every backend variant has a pairing backend

The pairing daemon maps each `bluetooth_backend` variant to a defined pairing backend (#1320): `rust` → the rust-hid PairingService; `python` → the in-process hidapi backend; `unstable` → the in-process hidapi backend too (`unstable` is the controller manager's fault-injecting wrapper around the python I/O path; pairing is a one-shot USB write with nothing to inject). Any other value, and an unreachable flagd, select `rust`, the default backend that every stack ships (UC-002 BR-003).

### BR-004: Stale registrations are removed on re-pair

After a successful pairing (step 4) the daemon removes every registration of the controller's address on the other adapters, through BlueZ (`Adapter1.RemoveDevice`) for present adapters and by deleting `/var/lib/bluetooth/<adapter>/<address>` for registrations BlueZ has not loaded (as in UC-005 BR-002). The address comes from the controller on USB, so the address alone identifies it; no other device is touched, and the registration on the selected adapter is kept. A failed removal is logged and does not fail the pairing.

### BR-005: Pairing does not disconnect other controllers

Restarting the Bluetooth service (`bluetooth.service` / bluetoothd) powers every adapter off and drops every connected controller, which eliminates every player of a running game (#1446). It also ends the `bluetoothctl` agent session (#632), so after every restart the daemon registers the pairing agent again (BR-009). When systemd refuses the restart (`RestartUnit` returns an error), bluetoothd keeps running with its agent session, and the agent is not registered again. A restart is needed only after a new BlueZ device record was written (A7, BR-008): bluetoothd reads its storage only at start. Whether pairing restarts it is set by the flag `pairing.bluez_restart_mode` (system domain, read at use time; an unknown value or unreachable flagd means `never`, fail closed):

- `when_idle` (default, #1466): bluetoothd is restarted only after a pairing wrote a new BlueZ device record (or one written earlier is not loaded yet), only once, for `pairing.restart_quiet_period` seconds (system domain, read at use time, default 20; `0` restarts at the end of the pairing poll as before #2091; a negative value, an unknown value or an unreachable flagd mean 20), no PS Move still to be paired has been on USB and none was paired, and only while no real (primary) game is starting, running or ending. The quiet period is measured from the later of the last USB poll that listed a PS Move not yet paired this session and the last successful pairing (a poll whose listing failed keeps the previous value), so a host who pairs a stack of controllers one after the other, unplugging each before plugging in the next, gets one restart after the last one (#2091); a restart that waits for a controller that is already unplugged runs at the next idle poll once that time has passed. A controller paired this session and left plugged in (e.g. charging) holds the restart only until the quiet period after its pairing has passed, never until it is unplugged; one that is not yet paired (e.g. waiting for a replug after an unpair, UC-005 A8) holds it while it stays on USB. The quiet period is checked before the game state; a restart it allows still waits for the real game (A6). A restart outside a real game still drops the controllers connected in the lobby; their players press PS again. It happens only when a controller new to that adapter is paired. The daemon reads the primary game's state from the game coordinator's `GetGameState` (empty `game_id`) through envoy's Connect route (`http://localhost/joustmania.game_coordinator.GameCoordinatorService/GetGameState`, env `GAME_STATE_URL`), so it needs no gRPC port of its own; shadow games are not the primary game and never defer it. An unreadable state counts as a running game (fail closed): the restart waits and is retried on each USB poll; the poll runs it under the pairing lock, so it never interleaves with a pairing or an unpair. A poll tries a pending restart also when listing the USB controllers fails (e.g. rust-hid is down), but not while the daemon shuts down. A restart that fails (e.g. systemd refuses it) keeps its records and is tried again, at most once per poll, after 10 s, 30 s, 60 s and then every 5 minutes until one succeeds (each attempt also waits for the USB quiet period); the first failure is logged as an error, the following ones as warnings (#1490). The state is read just before the restart, not atomically with it: a game that starts in the short window between that read and systemd's `RestartUnit` (well under a second, while the countdown is still running) is not protected.
- `never`: pairing never restarts bluetoothd and never powers an adapter off or on. Registration removal (BR-004, `Adapter1.RemoveDevice`) and trust (`Device1.Trusted` on the selected adapter, BR-007) take effect in the running bluetoothd, but a record written by A7 is not loaded, so a controller new to that adapter cannot connect until bluetoothd restarts for another reason.
- `always`: the pre-#1446 behaviour: bluetoothd is restarted after the pairings of a USB poll, during games too. Diagnostics only.

However many controllers a poll pairs, it restarts bluetoothd at most once, after all of them; with `when_idle` and a quiet period above 0, one restart covers every pairing until USB has been quiet (#2091).

Why a record and a restart: BlueZ refuses an incoming HID connection from a device it does not know (`profiles/input/server.c`; PS Move is not in its sixaxis cable-pairing table), and only a running bluetoothd's own pairing creates one; a PS Move paired over USB never pairs over Bluetooth. psmoveapi, used before #610, wrote the record and restarted bluetoothd for the same reason. Whether `Adapter1.ConnectDevice` or a power cycle of only the selected adapter could avoid the restart needs hardware (#1465).

### BR-006: Only PS Move motion controllers are paired

The pairing daemon and both HID backends (rust-hid, python_hid) enumerate only Sony's vendor id `054C` with product id `03D5` (ZCM1, PS3 era) or `0C5E` (ZCM2, PS4 era) (C-012). Product id `042F` is the PS Move Navigation controller: it has no light, no motion sensors and no trigger, so it cannot play; it is never enumerated, paired or opened as a player controller (#1442), and the registration reset (C-011) leaves it alone too.

### BR-007: Trust lands on the selected adapter

The trust step sets `Device1.Trusted` through BlueZ's D-Bus API on the device object of the adapter the controller was just paired to (`/org/bluez/<hci>/dev_<address>`). It does not use `bluetoothctl trust`, which acts on bluetoothctl's default adapter and, with several adapters, can trust the copy on another adapter or fail (#1445). No other adapter's registration is trusted or changed by the trust step. If BlueZ has no device object for the address on the selected adapter, the trust fails (A2); it is retried once, except when BlueZ answers that the object does not exist.

### BR-008: Device record for a controller BlueZ does not know

When BlueZ has no registration of the controller on the selected adapter (A7), the daemon writes the record that psmoveapi wrote before #610 (#1466):

- `/var/lib/bluetooth/<adapter>/<controller>/info`: `[General]` `Name=Motion Controller`, `Class=0x002508`, `SupportedTechnologies=BR/EDR;`, `Trusted=true`, `Blocked=false`, `Services=` the HID service UUID `00001124-0000-1000-8000-00805f9b34fb`; `[DeviceID]` `Source=1`, `Vendor=1356` (`054C`), `Product=` the product id read over USB (`03D5` ZCM1 or `0C5E` ZCM2), `Version=1`.
- `/var/lib/bluetooth/<adapter>/cache/<controller>`: the PS Move's HID SDP record under `[ServiceRecords]` (handle `0x00010000`), which BlueZ needs to set up the HID connection because the controller is never queried over Bluetooth before it connects.

Only PS Moves get a record (product id `03D5` or `0C5E`, BR-006), only under an adapter directory BlueZ already keeps, and only for the address read from the controller on USB. An existing `info` or cache file is never overwritten: it may hold BlueZ's own pairing data, such as a ZCM2 link key. A valid record that exists but is not loaded yet still asks for the restart (BR-005); an empty or unreadable `info` asks for none (A8) and is not repaired: the daemon cannot tell its own files from BlueZ's (its writes are atomic, so it never leaves an empty or partial `info` itself), so only the operator deletes it. Each file is written to a temporary file in the same directory, flushed to disk and then linked to its name, so a failed write leaves no partial file and no directory the write created. A record waiting for a deferred restart can be deleted by bluetoothd before it loads it (e.g. when a temporary device of that address expires); it is written again just before the restart. Files are created with mode 0600 in directories with mode 0700, as BlueZ does. Once bluetoothd has loaded it, the record is an ordinary BlueZ registration, which unpair (UC-005) and the registration reset remove through BlueZ.

Hardware verification pending (#1465): a never-seen ZCM1 and ZCM2 connect after unplug and PS with the default `when_idle`.

### BR-009: The pairing agent answers only for controllers paired over USB

The pairing daemon is BlueZ's default pairing agent: it exports an `org.bluez.Agent1` object (`/org/joustmania/pairing_agent`, capability `KeyboardOnly`) on the system bus and registers it at start and again after each bluetoothd restart (BR-005). It calls `AgentManager1.RegisterAgent` and only after BlueZ replied `RequestDefaultAgent`; requested earlier, BlueZ has no agent to make default (#1492). Registration counts as done when BlueZ confirmed both calls; an agent BlueZ still knows (`AlreadyExists`) is made default again. A refusal, no reply within 5 s or an unreachable system bus is logged as an error (the same failure again only at debug level) and the daemon keeps running without a confirmed agent. It registers the agent again: after its own bluetoothd restart (BR-005); when `org.bluez` gets a new owner on the system bus (`NameOwnerChanged`: bluetoothd restarted or crashed outside the daemon); and on every Bluetooth monitor cycle (`pairing.bt_monitor_interval`, default 5 s) while BlueZ has not confirmed the agent on the daemon's current bus connection, which covers a bluetoothd that was not up at daemon start and a reconnected bus (where the agent is exported and the owner watch set up again). No `bluetoothctl` process is involved (it replaced a `bluetoothctl` session that never answered its prompts), so no agent output can back up and stall (#1477).

The agent answers a request only for a controller whose address was paired over USB in this daemon session (step 4 succeeded) and has not been unpaired since (UC-005): a PIN code request with `0000`, a passkey request with `0`, and a passkey confirmation, pairing authorization or service authorization by accepting it. Re-pairing after a replug (A1, A7, A8) does not remove a controller from this set; an unpair does. Every request from any other device, including a controller paired before the daemon started, is refused with `org.bluez.Error.Rejected` and logged at INFO with the device address. A controller that connects with its BlueZ trust alone (BR-007, BR-008) sends the agent no request.

Hardware verification pending (#1465): a controller that asks for a PIN or a confirmation pairs through the agent after USB pairing, and a device not paired over USB is refused.

### BR-010: LED cue on the controller on USB

The pairing daemon drives the LED of a PS Move on USB while it pairs it (#2091; supersedes BR-002), because the LED is the primary feedback channel at a venue:

- **Pulse:** a slow white pulse (about 2 s per cycle) on every controller that a poll lists and is about to pair (not on one it skips, A1), from the start of that poll until its pairing ends.
- **Paired:** three short green flashes (about 1.5 s), then off, once step 4 succeeded and the trust step ran (a failed trust is not a failure, A2). This tells the host to unplug it.
- **Failed:** steady red when the pairing fails (no adapter, the backend write fails) or its device record cannot be written (A8); it stays red until the next poll retries (pulse again) or the controller leaves USB.

The daemon writes the PS Move output report `0x06` (LED colour, no rumble) to the controller's USB HID node itself, whichever backend `bluetooth_backend` selects (BR-003): the node is the `device_path` the backend listed, and the daemon runs privileged with `/dev`. A cue belongs to one controller (serial) at one HID node: it ends when that controller is no longer listed on USB at that node, so a node number another controller takes over between two polls never carries the old cue. Writes to one node run one at a time and only for the latest cue: a frame of an ended cue never lands after the next cue started. The daemon ends every cue when it shuts down. An LED write that fails (e.g. the controller was unplugged) ends that cue silently and never fails the pairing. A controller BlueZ already knows and that is on USB and connected over Bluetooth at the same time may show the controller manager's colour over the cue. Hardware verification pending (#1465): the cue shows on a ZCM1 and a ZCM2 on USB.

There is no announcement after the batched restart (BR-005): the pairing daemon has no announce path to the menu or audio service, so the lobby's players notice the dropped connection and press PS again.
