# Use Case: Change a Runtime Flag through the Flag Service

## Overview

**Use Case ID:** UC-053
**Use Case Name:** Change a Runtime Flag through the Flag Service
**Primary Actor:** Agent
**Secondary Actors:** Operator, Presenter, Host
**Goal:** Change a runtime-mutable flag, for one game, one player or the whole stack, with one request to the flag service that every OpenFeature client sees, without writing a flag file
**Status:** Tested
**Requirements:** FR-130, FR-131, FR-132, FR-133, FR-134, FR-135, FR-136, FR-137, FR-138, FR-139, NFR-050, NFR-051, NFR-052, NFR-053, C-030, C-031, C-032, C-033

## Preconditions

- The flag service has loaded the baseline flag files (`services/flagd/<set>.json`, or `services/flagd/ci/<set>.json` in the CI and demo stacks) and the persisted admin settings, and serves them to flagd as its gRPC sync source.
- flagd is connected to the flag service and serves every OpenFeature client unchanged (in-process resolvers on the sync port: Python, Go since #1713, Rust since #1713), each selecting its flag set by `flagSetId`.

## Main Success Scenario

1. The game coordinator registers a game with the flag service before the game runs: game id, game kind, the serials of its players, the experiment id and arm of a shadow experiment game, and its own instance id. A coordinator without `FLAG_SERVICE_URL` skips every lifecycle call (registration, end, reconcile).
2. The agent decides an intervention for that game ([UC-040](UC-040.md)) and sends it to the flag service as a value for one flag of one flag set with its scope, for example "`shield_seconds` in set `interventions` = 5 for game G, serial S".
3. The flag service checks the request against the mutable-flag registry and the game scope: the flag is runtime-mutable, the value lies within its bounds, the scope fits the flag, game G is live and flagd has an open sync stream.
4. The flag service records the value in game G's scope in memory and renders the configuration again: the value appears as targeting on the game id (and the serial, for a per-player flag) and resolves for no other game.
5. The flag service pushes the new configuration to flagd over the sync stream and records the write as a `flagservice.write` span and in `flagservice_writes_total{result="ok"}`. A sync stream carries every served flag set (empty selector) or the one set its `flagSetId=<set>` selector names; any other selector, or a set the flag service does not serve, is refused with `INVALID_ARGUMENT` and counted in `flagservice_sync_rejected_total`. The sync service's `GetMetadata` call is not implemented (`UNIMPLEMENTED`).
6. flagd serves the new value; the game coordinator's in-process resolver receives the configuration change and applies the intervention in game G only.
7. When game G ends, the game coordinator reports the end; the flag service drops the game's scope, renders the configuration again without it and pushes it, so nothing of game G is left for the next game. The coordinator reports the end as soon as the game ends on its own (win, tie, error), or after a force end or preemption has stopped it, normally once per game (#1847); the periodic reconcile every 15 s (A9 step 3) is only the backstop for a lost report.

## Alternative Flows

### A1: Operator or presenter changes a stack-wide flag

**Trigger:** The presenter runs a stage script (`scripts/talk-stage.sh`, `scripts/agent-backend.sh`), the operator sends a request to the flag service, or the agent writes a value of its own that is not for one game: the rollout stage (`rollout/current_controller_count`, [UC-050](UC-050.md)) as a stack overlay, or a promoted default (FR-138) as the `real` overlay, which replaces the flag's default (below a stack overlay and a persisted admin value) for every reader that no experiment-arm rule matches (step 2)
**Flow:**

1. The script, operator or agent sends a value without a game scope, for example "`decision.backend` in set `agent` = `jev`".
2. The flag service checks the registry and bounds, substitutes the flag's default in memory (baseline targeting still applies), pushes the configuration and records the write span.
3. The value lasts until its writer clears it, its optional time-to-live runs out or the flag service restarts; the flag file is unchanged.
4. Use case continues at step 6.

### A2: Host changes a setting in admin mode

**Trigger:** The host changes sensitivity, team count, force-all-start, the game mode or the allowed interventions on a controller ([UC-012](UC-012.md), [UC-013](UC-013.md)) (step 2)
**Flow:**

1. The menu sends the setting as a stack-wide value.
2. The flag service checks the registry and bounds, substitutes the flag's default in memory, and writes the setting to its own state file because the menu asks for persistence and the registry allows it for the flag.
3. The setting holds across restarts of the flag service; the baseline flag file is unchanged.
4. Use case continues at step 6.

### A3: Experiment loop sets an arm value

**Trigger:** The agent's experiment loop starts an experiment ([UC-043](UC-043.md)) (step 2)
**Flow:**

1. The agent sends "flag F = value V for experiment E, arm A".
2. The flag service renders the value as targeting that matches only `game_kind` other than `real` together with experiment E and arm A.
3. When the experiment is torn down the agent clears the arm values, and the flag service drops them. Arm values the agent never clears are dropped by the flag service once 2 h (`FLAG_SERVICE_EXPERIMENT_IDLE`) have passed since the later of the last arm write and the last registered game carrying the experiment id, with a warning and a `flagservice_experiments_expired_total` increment.
4. Use case ends.

### A4: One-shot intervention

**Trigger:** The agent decides `end_game`, `eliminate_player`, `revive_player`, `audio_cue` or `controller_effect` (step 2)
**Flow:**

1. The agent appends an event to the flag for game G, the player's serial in the event's payload.
2. The flag service adds the event with the game's next sequence number to the game's event list (the last 16 events) and pushes the configuration.
3. The game coordinator applies, in order, every event of game G with a sequence number above the last one it applied.
4. When the oldest event it reads is newer than the last applied sequence number + 1, more than 16 events arrived between two reads and the older ones are lost. The coordinator applies the events it still reads, logs a warning naming the flag, the game and the missing sequence range, and counts `game_intervention_event_gaps_total{flag}`; the lost events are not replayed.
5. Use case continues at step 7.

### A5: Flag not runtime-mutable or value out of bounds

**Trigger:** The flag set or flag is unknown, the flag has no registry entry, the value is not an allowed variant or lies outside the flag's bounds, the scope does not fit the flag, the serial is not a player of the game, or the flag set is still served from its file source (step 3)
**Flow:**

1. The flag service rejects the request (`404 unknown_flag_set`, `404 unknown_flag`, `422 flag_read_only`, `422 out_of_bounds`, `422 serial_not_in_game`, `409 set_not_served`, `409 real_game_live` (a `real` write of a flag marked `real_write: no_live_real_game` while a real game is registered, flags.md §13, #2096) or `400 malformed`).
2. The configuration is unchanged; the write span and `flagservice_writes_total{result="rejected"}` record the reason.
3. Use case ends.

### A6: Game not live

**Trigger:** The request names a game id that is not registered or has ended (step 3), including a game whose registration (step 1) or coordinator reconcile (A10) was refused with `409 too_many_games` because 64 game scopes (`FLAG_SERVICE_MAX_GAMES`) are live; a reconcile over the cap is refused whole
**Flow:**

1. The flag service rejects the request with `409 game_not_live`.
2. The agent retries once after 100 ms, which covers a registration that is still in flight; a second rejection is recorded and nothing is written, so a late decision for an ended game never reaches the next game.
3. Use case ends.

### A7: flagd not connected

**Trigger:** flagd has no open sync stream to the flag service (step 3)
**Flow:**

1. The flag service rejects the flag write with `503 no_sync_stream`: a value flagd cannot see is never reported as written. Game registration and game end are exempt, so the coordinator keeps registering games while flagd reconnects.
2. The writer records the failure (fail closed); the game keeps playing on flagd's last snapshot.
3. Use case ends.

### A8: Flag service unreachable

**Trigger:** The writer cannot reach the flag service, or the request times out after 500 ms (step 2)
**Flow:**

1. The writer records the write as failed (fail closed) and does not retry the same decision; the game keeps playing. The menu's admin writer re-reads the flag once after a timeout before it reports: a write the flag service applied after the deadline counts as applied ([UC-013](UC-013.md) A3, #2095).
2. flagd keeps serving its last snapshot and retries the sync stream; OpenFeature clients keep their values.
3. Use case ends.

### A9: Flag service restarts

**Trigger:** The flag service process restarts while a game is registered (step 4)
**Flow:**

1. The flag service loads the baseline flag files and the persisted admin settings again with a new epoch; every other value and every game scope is gone.
2. flagd reconnects and receives the new configuration.
3. The game coordinator sees the new boot epoch (it reads `GET /healthz` every 2 s and reconciles every 15 s regardless) and registers its live games again, so writes for a running game are accepted again; interventions written before the restart are not restored, and the new, non-empty epoch tells the coordinator to restart its event sequence count. A failed read never resets the count, so no event is replayed.
4. The coordinator's flag sets reconnect one by one, in no fixed order, so for a few seconds the `interventions` set it holds can be newer than its `interventions_allowed` allow-list (`agent` set). The flag service stamps every `interventions` flag and `interventions_allowed` with its epoch and snapshot version (`snapshotEpoch`, `snapshotVersion` flag metadata); the coordinator defers an intervention, neither applying nor blocking it, while the allow-list it holds has another epoch, an older version or no stamp, and re-evaluates it when the `agent` set catches up. An intervention written during the reconnect is therefore applied once if the current allow-list permits it and blocked `not_allowed` if not; a stale allow-list, wider or narrower, never decides it (#1552). A deferral that lasts longer than 5 s is logged as a warning and shows in `game_intervention_deferral_age_seconds`, and the flag service refuses to start when it would serve `interventions` without `agent`.
5. Use case continues at step 2.

### A10: Game coordinator restarts

**Trigger:** A game coordinator restarts while its games are registered (step 6)
**Flow:**

1. On start the coordinator reports its set of live games (empty after a restart) with its instance id.
2. The flag service drops every game scope of that instance that is not in the set and pushes the configuration; games of other coordinator instances are untouched. A set that would take the live scopes over `FLAG_SERVICE_MAX_GAMES` (64) is refused whole with `409 too_many_games` and changes nothing.
3. Use case ends.

### A11: Game end never reported

**Trigger:** A game scope has not been seen for the maximum game age of 1 h: no registration and no reconcile entry named it (step 7)
**Flow:**

1. The flag service drops the scope (the age counts from the last registration or reconcile, not the first one, so a running game the coordinator keeps reconciling every 15 s never expires, #2217), logs the expiry and counts it in `flagservice_game_scopes_expired_total`.
2. Use case ends.

### A13: Game registered again with a different player list

**Trigger:** A game id that is already live is registered again (PUT `/games/{gameId}`), for example by the reconcile of A9 or A10, and the new serials omit a player (including an empty list) (step 1)
**Flow:**

1. The flag service updates the stored game record and keeps its original registration time (`registered_at`, for display) and refreshes its last-seen time (`last_seen_at`), from which the 1 h age of A11 counts.
2. For every serial the earlier registration listed and the new one does not, the flag service drops that player's per-player values in the game, renders the configuration again and pushes it. A player who left the game keeps no value.
3. Values for the whole game, its event lists and the values of players still listed are kept. A registration that lists the same serials changes no value and pushes nothing.
4. Use case ends.

### A12: State file corrupt or unreadable

**Trigger:** At start or restart the flag service's admin state file does not parse, has an unsupported version, or cannot be read (step 4)
**Flow:**

1. A file that does not parse or has an unsupported version is moved aside to `<file>.corrupt-<unix ts>`, or left in place (and logged) if the rename fails; at most 3 such copies are kept (the oldest are deleted). The flag service logs it, counts it in `flagservice_admin_state_corrupt_total` and starts from the baseline without admin values; the next persisted write creates a new state file.
2. A file that cannot be read (permissions, I/O error) is left untouched and is not moved aside: the flag service starts, applies admin writes in memory only, reports them as not persisted and counts each in `flagservice_admin_persist_errors_total` until its next start.
3. Use case continues at step 2.

## Postconditions

### Success Postconditions

- flagd serves the new value to the readers it was written for, and to no other game or player.
- The write is recorded as a `flagservice.write` span naming the flag, value, scope, game id and serial, and in `flagservice_writes_total{flag_set,flag,op,result,reason}`.
- After the game ends, no flag resolves differently because of that game.
- No baseline flag file has changed.

### Failure Postconditions

- The configuration flagd serves is unchanged and the rejection or failure is recorded with its reason.
- The game keeps playing.

## Business Rules

### BR-001: Only registry flags change at runtime

A flag changes at runtime only if the mutable-flag registry declares it ([flags.md §13](../specs/flags.md#13-mutable-flag-registry)); every other flag is the read-only baseline from the flag files and changes only with a reviewed file change and a restart of the flag service.

### BR-002: Validation, not authorization

A write is checked only against the registry (mutable flag, value in bounds, scope fits), the game scope (game registered) and the sync stream (flagd connected). There are no writer roles or credentials: this is a local party game, and authorization is out of scope by decision. The ownership model (C-008) holds because each writer's code writes only its own flags.

### BR-003: Game-scoped values die with the game

An intervention is always written for one registered game and resolves only in that game. When the game ends, the flag service drops its scope; the next game starts from the baseline, so no per-game baseline of consumed values is needed.

### BR-004: Only admin settings persist

The flag service writes no database and never writes the baseline flag files. It persists only admin settings: a write that asks for persistence, of a flag the registry marks as an admin setting, goes to its own state file (one per stack); everything else, including a stage script's or a test's value of the same flag, is gone after a restart. Durable changes to the baseline go through a reviewed file change (C-007) or a promotion PR.

### BR-005: Every write is audited

Every accepted or rejected write is a `flagservice.write` span with the flag key, value, scope, `game.id` and `player.serial` when given and the caller's informational writer label, and a `flagservice_writes_total{flag_set,flag,op,result,reason}` increment.

### BR-006: One-shot interventions are per-game event lists

An `end_game`, `eliminate_player`, `revive_player`, `audio_cue` or `controller_effect` intervention is an event appended to a per-game list (`{"epoch","seq","events"}`, the last 16 events) rendered on the game id only, with the serial in the event's payload. A game scope starts with an empty list, so the coordinator applies every event of its game exactly once and never one from an earlier game.

### BR-007: Evaluation stays on stock flagd

The flag service is a sync source only. Every OpenFeature client keeps resolving through flagd with its existing resolver, port and `flagSetId` selector.
