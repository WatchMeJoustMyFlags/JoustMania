# Use Case: Change a Runtime Flag through the Flag Service

## Overview

**Use Case ID:** UC-053
**Use Case Name:** Change a Runtime Flag through the Flag Service
**Primary Actor:** Agent
**Secondary Actors:** Operator, Presenter, Host
**Goal:** Change a runtime-mutable flag, for one game, one player or the whole stack, with one typed request that every OpenFeature client sees, without writing a flag file
**Status:** Draft
**Requirements:** NFR-050, NFR-051, NFR-052, NFR-053, C-030, C-031, C-032, C-033
**Planned:** FR-120 (#1408, Open), FR-121 (#1408, Open), FR-122 (#1409, Open), FR-123 (#1409, Open), FR-124 (#1410, Open), FR-125 (#1410, Open), FR-126 (#1410, Open), FR-127 (#1410, Open), FR-128 (#1415, Open), FR-129 (#1409, Open)

## Preconditions

- The flag service has loaded the baseline flag files (`services/flagd/*.json`, or `services/flagd/ci/*.json` in the CI and demo stacks) and serves them to flagd as its gRPC sync source.
- flagd is connected to the flag service and serves every OpenFeature client unchanged (Python in-process resolver, Go and Rust RPC resolvers).
- The writer holds a writer role (`coordinator` for the game lifecycle; `agent`, `experiment`, `promotion`, `admin`, `operator`, `stage`, `test` for writes) that the flag service accepts.

## Main Success Scenario

1. The game coordinator registers a game with the flag service when it admits the game: game id, game kind, the serials of its players, and the experiment id and arm of a shadow experiment game.
2. The agent decides an intervention for that game ([UC-040](UC-040.md)) and sends the typed request for it to the flag service, for example "grant a 5 s shield to serial S in game G, decision D".
3. The flag service checks the request against the mutable-flag registry: the flag is runtime-mutable, the writer role may change it, the value lies within the flag's bounds and the game is live.
4. The flag service records the value in the game's scope in memory and renders the flag set again: the value appears as targeting on the game id (and the serial, for a player-targeted flag) and resolves for no other game.
5. The flag service pushes the new flag set snapshot to flagd over the sync stream and records the write as an `flagservice.write` span and in `flagservice_writes_total{result="ok"}`.
6. flagd serves the new value; the game coordinator's in-process resolver receives the configuration change and applies the intervention in game G only.
7. When game G ends, the game coordinator reports the end; the flag service drops the game's scope, renders the flag set again without it and pushes the snapshot, so nothing of game G is left for the next game.

## Alternative Flows

### A1: Operator or presenter changes a stack-wide flag

**Trigger:** The presenter runs a stage script (`scripts/talk-stage.sh`, `scripts/agent-backend.sh`) or the operator calls the flag service's operator API (step 2)
**Flow:**

1. The script sends a typed request, for example "set the decision backend to `jev`", with writer role `stage` or `operator`.
2. The flag service checks role and bounds, overlays the value on the baseline in memory, pushes the snapshot and records the write span.
3. The overlay lasts until the next stage reset, the next restart of the flag service or an explicit reset of that flag; the flag file is unchanged.
4. Use case continues at step 6.

### A2: Host changes a setting in admin mode

**Trigger:** The host changes sensitivity, team count, force-all-start or the allowed interventions on a controller ([UC-012](UC-012.md), [UC-013](UC-013.md)) (step 2)
**Flow:**

1. The menu sends the typed admin request with writer role `admin`.
2. The flag service checks role and bounds, overlays the value in memory and pushes the snapshot.
3. The setting holds until the flag service restarts; a restart returns to the value in the baseline flag file.
4. Use case continues at step 6.

### A3: Experiment loop sets an arm value

**Trigger:** The agent's experiment loop starts an experiment ([UC-043](UC-043.md)) (step 2)
**Flow:**

1. The agent sends "set flag F to value V for experiment E, arm A" with writer role `experiment`.
2. The flag service renders the value as targeting that matches only `game_kind` other than `real` together with experiment E and arm A, and rejects the request if the value could reach a real game.
3. When the experiment is torn down the agent clears the arm values, and the flag service drops them.
4. Use case ends.

### A4: Unauthorized writer or immutable flag

**Trigger:** The writer role may not change the flag, or the flag is not runtime-mutable (step 3)
**Flow:**

1. The flag service rejects the request with `PERMISSION_DENIED` and the reason `role_not_allowed` or `flag_read_only`.
2. The flag set is unchanged; the write span and `flagservice_writes_total{result="rejected"}` record the reason.
3. The use case ends.

### A5: Value out of bounds

**Trigger:** The value is not an allowed variant or lies outside the flag's numeric bounds (step 3)
**Flow:**

1. The flag service rejects the request with `INVALID_ARGUMENT` and the reason `out_of_bounds`.
2. The flag set is unchanged and the rejection is recorded.
3. The use case ends.

### A6: Game not live

**Trigger:** The request names a game id that is not registered or has ended (step 3)
**Flow:**

1. The flag service rejects the request with `FAILED_PRECONDITION` and the reason `game_not_live`.
2. Nothing is written, so a late decision for an ended game never reaches the next game.
3. The use case ends.

### A7: Flag service unreachable

**Trigger:** The writer cannot reach the flag service, or the request times out after 500 ms (step 2)
**Flow:**

1. The writer records the write as failed (fail closed) and does not retry the same decision; the game keeps playing.
2. flagd keeps serving its last snapshot and retries the sync stream with backoff; OpenFeature clients keep their values.
3. The use case ends.

### A8: Flag service restarts

**Trigger:** The flag service process restarts while a game is registered (step 4)
**Flow:**

1. The flag service loads the baseline flag files again; every overlay and every game scope is gone.
2. flagd reconnects and receives the baseline snapshot.
3. The game coordinator registers its live games again on reconnect; interventions written before the restart are not restored.
4. Use case continues at step 2.

### A9: Game coordinator restarts

**Trigger:** The game coordinator restarts while games are registered (step 6)
**Flow:**

1. On start the game coordinator reports its set of live games (empty after a restart).
2. The flag service drops every game scope that is not in that set and pushes the snapshot.
3. Use case ends.

### A10: Game end never reported

**Trigger:** A game scope is older than the maximum game age (step 7)
**Flow:**

1. The flag service drops the scope, logs the expiry and counts it in `flagservice_game_scopes_expired_total`.
2. Use case ends.

## Postconditions

### Success Postconditions

- flagd serves the new value to the readers it was written for, and to no other game or player.
- The write is recorded as a span and a metric naming the flag, value, writer role, game id and serial.
- After the game ends, no flag resolves differently because of that game.
- No flag file has changed.

### Failure Postconditions

- The flag set flagd serves is unchanged and the rejection or failure is recorded with its reason.
- The game keeps playing.

## Business Rules

### BR-001: Only registry flags change at runtime

A flag changes at runtime only if the mutable-flag registry declares it ([flags.md §13](../specs/flags.md#13-mutable-flag-registry)); every other flag is the read-only baseline from the flag files and changes only with a committed file change and a restart of the flag service.

### BR-002: A writer role writes only its own flags

Each registry entry lists the writer roles allowed to change it. The agent writes interventions, `current_controller_count` and experiment arm values; it never writes a human-owned setting, the `user` set or the agent's own governance flags (C-008, [OWNERSHIP_MODEL.md](../OWNERSHIP_MODEL.md) §1).

### BR-003: Game-scoped values die with the game

An intervention is always written for one registered game and resolves only in that game. When the game ends, the flag service drops its scope; the next game starts from the baseline, so no per-game baseline of consumed values is needed.

### BR-004: The flag service never persists

The flag service writes no file and no database. A restart returns to the baseline flag files; durable changes go through a committed file change (tier 3, C-007) or a promotion PR.

### BR-005: Evaluation stays on stock flagd

The flag service is a sync source only. Every OpenFeature client keeps resolving through flagd with its existing resolver, port and flag-set selector.

### BR-006: One-shot interventions carry a per-game sequence

An `end_game`, `eliminate_player`, `revive_player`, `audio_cue` or `controller_effect` intervention is written as the next value of a per-game sequence (`<seq>:<payload>`), scoped to its game and, when it names a player, to that serial. A game scope starts with no value, so the coordinator applies every sequence change it sees during the game and never replays a value from an earlier game.

### BR-007: Every write is audited

Every accepted or rejected write is an `flagservice.write` span with the flag key, value, writer role, `game.id` and `player.serial` when given, and a `flagservice_writes_total{flag_set,flag,role,result}` increment.
