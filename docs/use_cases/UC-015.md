# Use Case: Operate the Game with the Operator Pad

## Overview

**Use Case ID:** UC-015
**Use Case Name:** Operate the Game with the Operator Pad
**Primary Actor:** Host
**Goal:** Start and end games, pick the mode, change the lobby settings (the shield mode included), stop or resume the agent and set the volume from one USB macro pad (8 keys and a knob), without a controller in admin mode and without a laptop
**Trigger:** Host presses, holds or turns a key of the pad
**Status:** Implemented
**Requirements:** FR-190, FR-191, FR-192, FR-193, FR-194, FR-195, FR-196, FR-197, FR-198, FR-199, NFR-009

The key layout is BR-011 (an action fires on release, except where noted).

Work in progress (#2050; remove this paragraph after the hardware check of #2050 PR8): this use case is the spec for phase 1 of the operator pad, the key mapping only. There is no display yet (the OLED is phase 2), so every result is a voice line, a sound or a controller LED cue. The menu side is built (#2050 PR3: the `ProcessInput` commands `force_start`, `step_setting`, `agent_switch`, `set_backend`; #2050 PR4: `GetMenuStatus`, `lifecycle_generation` and the `stale` check of A5); the pad service code is in `services/operator_pad/` (#2050 PR6: gestures, actions, device, status reads, telemetry) and deploys as the `operator-pad` image under the `operator-pad` compose profile (#2050 PR7; on the Pi `COMPOSE_PROFILES=operator-pad` in `.env.local`, [UC-060](UC-060.md)); it reads the `operator` flag set (#2087; a key flagd cannot resolve falls back to its code default). The integration test of steps 2 and 3 is `tests/integration/test_uc015_k1_start.py`; only the check on the Pi hardware is still pending (#2050 PR8); FR-190 to FR-195 are Implemented, not Verified: they stay so until then. The pad is an optional service (`operator-pad` compose profile, [services.md](../specs/services.md) §2): a stack without it behaves exactly as before.

This use case includes the rules of [UC-011](UC-011.md) (mode), [UC-012](UC-012.md) (settings), [UC-013](UC-013.md) (agent level), [UC-014](UC-014.md) (force-start) and [UC-027](UC-027.md) (force-end) by reference; it does not copy them. Where the pad differs, a business rule below says so.

## Preconditions

- **Pre-1:** The `operator-pad` service runs, the pad is plugged in and the service holds an exclusive grab of its input devices (BR-014: which nodes count as the pad), and the `operator_pad.enabled` kill flag is on (default on, [flags.md](../specs/flags.md) §10a): with it off the pad ignores every key, drops gestures in progress and sends nothing.
- **Pre-2:** The pad firmware sends the fixed key codes (K1 = F13, K2 = F14, K3 to K8 = F18 to F23, knob press = F15, knob turn A = F16 and B = F17; the `operator_pad.keymap` default). The pad is a Vial keyboard (`cb00:1337`) whose events arrive on its main keyboard interface. Knob direction A is counter-clockwise (left) and B is clockwise (right); B raises the volume or steps a setting forward. Physical layout: 8 keys plus the knob press at the top right; top row K1, K2 and the knob; middle row K3 to K5; bottom row K6 to K8. All tap and hold timing happens on the host. The keys by F key code: BR-016.
- **Pre-3:** The menu is RUNNING (UC-010 Pre-conditions). The pad sends its commands to the menu only; it writes no flag itself (BR-001).

## Main Success Scenario

1. Host taps K1 in the lobby.
2. System (the pad service) reads `GetMenuStatus` and, when `lifecycle_live` is false, asks the menu to start through `ProcessInput` `start_game` (the menu's A8 guard, [UC-010](UC-010.md) A8, still refuses while a game is starting or running: `success=false`, `game_active`, BR-012).
3. System starts the game as in [UC-010](UC-010.md) step 5 onwards; a game that starts is announced by the usual countdown.
4. Host holds K1 and turns the knob: System steps the selected mode ([UC-011](UC-011.md) steps 2 to 5, `step_setting` option `current_game`), one voice line for the mode when K1 is released (the [UC-011](UC-011.md) voice map) and a short pulse of the mode's colour on every lobby controller (BR-015); a turn marks K1 as used, so the release does not start a game (BR-007). While K1 is held, the pad speaks the mode the release would select and the lobby controllers pulse its colour (live preview, BR-017, `preview_setting`); nothing is selected before the release.
5. Host holds K2, K5 or K3 and turns the knob: System steps the setting by the turns counted while the key was down in one `step_setting` call (`steps=n`, BR-005) when the key is released (the agent level and the backend included); the new value is announced (UC-012 voices) and written as the same persisted admin value as the controller does ([UC-053](UC-053.md) A2). K2 (sensitivity) and K5 (teams) have the knob ladder **automatic**, then the values (BR-018): `automatic` clears the persisted value, so the flag file's default or an agent promotion applies again, and the knob starts at the operator's value, or where the setting stands now when there is none (BR-018), so "up" means more. While the key is held, the pad speaks the label once and then the value the release would commit (live preview, BR-017); nothing is written before the release.
6. Host holds K3 for 1 s: System stops the agent (BR-002) or resumes it (BR-003), the direction taken from the status read when K3 went down (BR-013), and plays a distinct voice line for each direction.
7. Host holds K4 for 1.5 s and releases: System force-ends the primary game ([UC-027](UC-027.md) steps 1 to 5) or, in the lobby, force-starts ([UC-014](UC-014.md) steps 3 to 5, with the roster of BR-008).
8. Host turns the knob: System sets the master volume (BR-006) and plays a short sound at the new level; Host presses the knob: System mutes or unmutes.
9. Host holds K6 and turns the knob in the lobby: System steps the operator's shield mode (`shield.activation`; knob ladder automatic, instant, trigger, hold) by the turns counted while K6 was down in one `step_setting` call when K6 is released (BR-005, BR-018): a mode is written persisted, `automatic` clears the operator value; the menu says the result and shows it on every lobby controller (BR-018). While K6 is held, the pad speaks "Shield mode" once and then the mode the release would commit, and the lobby controllers pulse that mode's colour (live preview, BR-017); nothing is written before the release.

## Alternative Flows

### A1: A game is starting or running

**Trigger:** a lobby-only command arrives while the menu's game lifecycle is live (step 2, 4, 5, 7 or 9; #2054)
**Flow:**

1. System refuses in the menu, not only in the pad. The new pad commands `force_start`, `step_setting` (`sensitivity`, `num_teams`, `game_instructions`, `force_all_start`, the mode with K1 + knob and the shield mode with K6 + knob, BR-018) and `preview_setting` return `success=false`, error `game_active`, and change nothing (a refused `preview_setting` shows no pulse). The web `start_game` refuses with `success=false`, `game_active` too, besides its `game_start_rejected` event ([UC-010](UC-010.md) A8; before #2176 it answered `success=true`); the dashboard's `select_game` keeps its answer (UC-011 A1). The pad refuses a K1 tap itself when the status it read at the press shows `lifecycle_live`; when a game starts after that read, the menu's guard answers `game_active` and the pad plays the refusal cue.
2. System plays the refusal cue (BR-009) once per refused gesture.
3. Use case ends. Not refused while a game runs: the volume (BR-006), the agent switch and level (BR-002 to BR-004), the backend (BR-004) and force-end (step 7).

### A2: Admin mode is open

**Trigger:** a pad command that writes a setting or starts a game arrives while a controller is in admin mode ([UC-012](UC-012.md)) (step 2 or 5)
**Flow:**

1. The last write wins; no lock is taken. A pad `force_start` first closes the admin session (`abandon_session`, reason `operator_pad_start`) so the admin lock and its span end; the admin controller is not added to the roster (BR-008).
2. Use case continues at step 2 (a start) or step 5 (a setting).

### A3: Flag service down or refusing

**Trigger:** a write of the pad command fails: the flag service does not answer within the writer's 500 ms deadline ([UC-053](UC-053.md) A8, NFR-052) or refuses (`503 no_sync_stream`, [UC-053](UC-053.md) A7) (step 5)
**Flow:**

1. System fails closed: it does not retry and does not queue the command (BR-010). `ProcessInput` returns `success=false` with the error `flag_service_unavailable`; a kill that wrote only one of its two keys returns `partial:<key>` with the key that failed, and a kill whose two writes both failed returns `failed` (BR-002); a resume returns `partial:<key>` with the first key in its write order that failed when at least one of its writes succeeded, and `failed` when all failed (BR-003); every other failed write returns `flag_service_unavailable`. A write that timed out is re-read once from the flag service before it counts (as [UC-013](UC-013.md) A3, #2095): when the flag service now serves the written variant, the write succeeded. One exception: a `current_game` step whose persisted write fails still succeeds, because the selection takes effect in menu memory (the next start uses it) and only its survival across a menu restart is lost.
2. System plays the failure cue (BR-009: two loud beeps), distinct from the success voice lines and from every level cue, and records a span and a metric.
3. Use case ends; the host sees nothing change and retries by hand. The last resort to stop the agent is `docker stop joustmania-agent` (talk runbook).

### A4: Device missing or unknown keys

**Trigger:** the pad is not plugged in, is unplugged mid-use, or sends a key code outside the table (step 1; Pre-1, Pre-2)
**Flow:**

1. System rescans for the device (hotplug) and never fails the other services; the menu, the dashboard and the controllers work as before. A rescan waits the rescan interval after every detach, so a node that fails right after the attach never makes a busy loop. A read of any node that fails for any reason counts as the device gone (detach, rescan), never as a pad that stays attached and reads nothing.
2. System resets every gesture in progress when the device disappears (a key held at the time never fires), and also when the kernel reports lost input events (`SYN_DROPPED`): a key whose release may have been lost never turns a later tap into a hold.
3. System ignores an unknown key code and counts it; after a firmware reset that leaves only unknown codes it logs a warning and plays one cue (BR-009).
4. Use case ends.

### A5: Stale state on K4

**Trigger:** the game state changed between the press and the release of K4 (step 7): a game ended during a lobby hold, or one started during an end hold
**Flow:**

1. System reads the menu status (`GetMenuStatus`, [services.md](../specs/services.md) §3.1) when K4 goes down and again on release. When the `lifecycle_generation` or the state class (lobby / live) differs, the pad cancels the gesture, sends nothing and plays the cancel cue (BR-009).
2. For `force_start` the pad sends `expected_generation` with the generation it captured when K4 went down (not the one read on release), so the menu is the authority over the whole hold; the menu refuses a mismatch with `success=false`, error `stale`, so any other caller is protected too.
3. Use case ends; the host repeats the gesture if still wanted.

### A6: Pad locked

**Trigger:** Host held K8 for 3 s (step 1; BR-011)
**Flow:**

1. System toggles the lock, says "Pad locked" or "Pad unlocked" (BR-009; no display yet) and sets the pad's Scroll Lock LED while locked.
2. While locked the pad sends nothing, with one exception: a K3 hold always sends the stop (BR-002), whatever the status read at the press or on release and without the A10 cancel, so a locked pad is kill only and can always stop the agent. For an agent that is already stopped the menu makes it a no-op (A9); for one whose only closed key is the write gate it writes both keys and so ends remote decide calls (#2093).
3. Use case ends. A restart of the pad service comes back unlocked.

### A7: Knob at the end of a range

**Trigger:** a `step_setting` asks to move past the end while the option is already at its first or last value (step 4, 5 or 8)
**Flow:**

1. Nothing is written and the command returns error `at_limit` (no wrap; BR-005). A step of n that would pass the end stops at the end and writes it (success; BR-005); only a value already at the end gives `at_limit`. The pad plays the limit cue (BR-009). The admin mode keeps its own wrapping for `cycle_variant` options (UC-012).
2. Use case ends.

### A8: Unknown option or value

**Trigger:** `step_setting`, `preview_setting`, `agent_switch` or `set_backend` names an option, mode, direction or backend outside the table (step 4, 5 or 6)
**Flow:**

1. System returns `success=false`, error `bad_option`, and changes nothing (a `preview_setting` shows no pulse).
2. Use case ends.

### A9: Agent already stopped or already running

**Trigger:** K3 hold while the agent is in the state the gesture asks for (step 6)
**Flow:**

1. System treats the gesture as a no-op that still reports its voice line (stopped stays stopped), and does not touch the saved level (BR-003). A resume is a no-op only while `enabled` is on, the level is not `none` and `interventions_enabled` is on; with the gate off or unreadable the resume opens it (BR-003, #2093). A stop is a no-op when `enabled` is off or the level is `none` (BR-002).
2. Use case ends.

### A10: Agent status changed or unknown on K3

**Trigger:** K3 is held for its hold time (step 6) and the status read when K3 went down and the one read on release disagree on "stopped" (BR-002), or one of the two reads is unknown (BR-013)
**Flow:**

1. When both reads are known and disagree on "stopped" (for example, someone stopped the agent from the dashboard during the hold), the pad (unlocked; a locked pad sends the stop, A6) cancels the gesture, sends nothing and plays the cancel cue (BR-009), as K4 does in A5.
2. When the status read at the press is unknown, or the read on release is, the pad sends the stop (BR-002: both writes attempted; A9: a stopped agent stays stopped). It never sends the resume without a known status at both ends of the hold.
3. Use case ends; the host repeats the gesture if a resume was wanted.

## Postconditions

### Success Postconditions

- The command's effect is in the flag service (persisted for the admin settings and the backend, in memory for `enabled` and `interventions_enabled`, BR-001) or in the menu (a started game); the host heard the confirming voice line or sound.

### Failure Postconditions

- Nothing changed beyond what the error code says (`partial:<key>` names a half-applied kill); the host heard the failure, refusal, limit or cancel cue. No command is queued for later.

## Business Rules

### BR-001: Writes go through the menu; keys written

The pad service sends `ProcessInput` commands to the menu and writes no flag itself; the menu writes through the flag service ([UC-053](UC-053.md)). Besides the keys the controller admin mode writes ([UC-013](UC-013.md) BR-001, narrowed to admin mode by this use case), the pad commands write: `agent/enabled` in memory only (no `persist` field; the registry row has no persist, the kill switch must not survive a restart, [UC-045](UC-045.md) step 7), `agent/interventions_enabled` in memory only, written only by the resume (BR-003; no persist in the registry either, so a restart returns to its fail-closed default `off`, #2093), `agent/decision.backend` persisted (the operator's choice, C-018), `agent/interventions_allowed` persisted (as UC-013), `user/audio_volume.master` persisted, `game/shield.activation` persisted, or its persisted value cleared for `automatic` (BR-018). The pad commands add no network exposure: `ProcessInput` and `/flags/` are already reachable on port 80 (the security follow-up of #2050 covers them).

### BR-002: Stopped, kill order and result

"Stopped" means `enabled` is off, `interventions_allowed` is `none` or the write gate `interventions_enabled` is off (it cannot act, FR-051; #2093), in every rule below, with two exceptions that check only `enabled` and the level: the stop's no-op (A9), because a closed gate does not end decide calls, so a stop of an agent whose only closed key is the gate still writes both keys (an unlocked K3 hold resumes such an agent, a locked one stops it, A6); and the ladder (BR-003, BR-004), which moves the live level of an agent whose only closed key is the gate, since the resume keeps a level that is not `none`. The stop writes `interventions_allowed` = `none` first (that write blocks the agent at the coordinator gate and, at `none`, ends remote decide calls, [UC-013](UC-013.md) Post-S-1), then `enabled` = off. The menu attempts both and returns `ok`, `partial:<key>` (one write failed) or `failed` (both failed). The level is read from the flag service, never from the menu's in-process flagd value ([UC-013](UC-013.md) BR-003). It saves the previous level in memory only when that level is not `none`. A ladder step (BR-004) of a running agent down to `none` leaves the agent stopped (level `none`, `enabled` stays on): the menu saves the level the step left, and a resume restores it (BR-003).

### BR-003: Resume and saved level

The resume applies the saved level, or `ambient` when none is saved, to `interventions_allowed` only if the current level is still `none`; any other current level (for example one an admin set after the kill) is kept (last write wins). It then sets the agent's write gate `interventions_enabled` = on (FR-051; in memory, BR-001), so a resumed agent acts and does not only observe, and last `enabled` = on, so `enabled` is never switched on before the gate (#2093). All writes are attempted whatever an earlier one did; a failed one is reported as A3 says. The stop never writes `interventions_enabled` (BR-002): a stopped agent is held by its level and `enabled`, and the gate stays as the resume left it. The saved level lives in menu memory; after a menu restart it is lost and the resume level is `ambient`, never `full`. The resume needs no knob confirm and plays its own voice line, as the stop does. While the agent is stopped (`enabled` off or level `none`, BR-002) the K3 + knob ladder (BR-004) changes only the saved level, so a stopped agent is never re-enabled or raised by the ladder; only the resume does that. When `enabled` or the level cannot be read, a ladder step in either direction writes nothing, leaves the saved level unchanged, plays no voice line and returns `flag_service_unavailable` (fail closed, BR-010; A3: a read or write fails); the stop still writes both keys (BR-002).

### BR-004: Level and backend

The level ladder is the one of [UC-013](UC-013.md) step 3 and A1 (none, ambient, standard, full), clamped, never wrapping. The new level is committed when K3 is released, escalation or restriction alike, with `steps=n` (BR-005); a release without a turn writes nothing. The backend ([UC-044](UC-044.md): `rules`, `claude`, `openai`, `jev`) is chosen with K7 + knob and committed when K7 is released.

### BR-005: Coalesced writes

A layer setting (mode, sensitivity, teams, agent level, backend, shield mode) is committed once, when the layer key is released, with `steps=n` for the turns counted; a turn count that nets to zero writes nothing, and a step of n that would pass the end of the range stops at the end (A7). The volume is committed after a 250 ms pause in turning (it has no layer key). One command is one flag write, so a knob never writes one value per detent. The knob may be smooth (no detents; the maintainer's 0xCB 1337 sends about 25 events per turn), so a step is `operator_pad.knob_events_per_step` raw knob events (default 4, range 1 to 12; a value outside it counts as 4) in one direction, counted separately for the volume and for each layer key. A change of direction restarts the count. A remainder short of a step is dropped, never written: on the layer key's release, after the 250 ms pause in turning that commits the volume, and when the device goes away. The knob press is unaffected. A live preview of a layer setting announces per step, not per raw event.

### BR-006: Master volume and mute

The knob sets `user/audio_volume.master` (a multiplier on everything the audio service plays, applied at play time and on a flag change; steps stop at both ends). Mute sets the same flag to its `mute` variant (0.0); the pad remembers the variant from before the mute and restores it on unmute. The menu status carries the master variant (`audio_volume_master`, [services.md](../specs/services.md) §3.1), so after a pad restart the pad knows the room is muted; with no remembered variant it restores the flag's default variant (`max`). The steps go by the variants' values, low to high (`mute` 0.0, `quiet` 0.3, `normal` 0.6, `loud` 0.8, `max` 1.0), one variant per detent; the menu orders numeric variants by value regardless of the order the flag service lists them in (a guard: the flag service lists them in file order, which is value order today). The music keeps playing while muted. The `play_audio` flag is not used for the mute: switching it off stops the music, and switching it on does not bring it back.

### BR-007: Gestures

The pad decides tap or hold from the time between press and release only, measured on a monotonic clock when the event is read (never the wall clock, which a Pi without a real-time clock steps after boot); the tap limit is 400 ms (`operator_pad.tap_ms`); a release between the tap limit and the hold time cancels. Each hold time must be longer than the tap limit: when the timing flags break that, the pad keeps the default timings and logs a warning. A second press of a key that is already down (its release was lost) restarts that key's timing and drops its layer turns. A knob turn while a layer key is down marks that key used: its release does nothing else. A knob press while a layer key is held belongs to that layer: it is not a mute, and its release triggers no tap or hold action, even if the layer key is released first. The layer's setting still commits on layer-key release per BR-005. While a chord is down every key is blocked until all keys are up. Auto-repeat and a release without a press are ignored.

### BR-008: Roster of a pad force-start

A pad `force_start` builds the roster from the live controller manager as in [UC-014](UC-014.md) steps 3 and 4 and BR-001, but no serial represents the pad: no host is added, none is flashed, none is kept by ghost pruning.

### BR-009: Cues without a display

Every outcome has a voice or sound form (LED primary, audio reinforces). The pad's words come from the voice catalog ([UC-031](UC-031.md) BR-007; #2106): a refusal says "Not possible", a limit says "Maximum" (stepping up) or "Minimum" (stepping down) at most once per second (a burst of `at_limit` refusals, for example a knob turned on at the end of the range, gives one cue, not one per refusal, #2105), a cancel says "Cancelled", and a menu the pad cannot reach gives the failure cue followed by "No connection". The failure cue is two `SFX_BEEP_LOUD`, the same as the menu plays for a failed write. Each stop / resume direction has its own voice line (the menu's), and the lock says "Pad locked" / "Pad unlocked" (A6). An unknown key code keeps its short sound (A4). A cue of more than one clip (an announcement, BR-011, or the failure cue with its words) plays in the background: the pad handles the next key event at once, and a cue that hangs never holds up the input.

### BR-010: Fail closed, never queue

A command that cannot be applied now is dropped with its error code. The pad does not queue, retry or replay a gesture, including after the device or the menu comes back.

### BR-011: Key layout

The layout (an action fires on release, except where noted; the numbers in brackets are the main scenario steps):

| Key | Tap | Hold | Hold + knob |
|---|---|---|---|
| Knob alone | master volume (BR-006); press = mute / unmute | | |
| K1 GAME | start a game (lobby only) | | choose the mode, committed on release of K1 |
| K2 SENS | announce "Sensitivity", then the value (from `GetMenuStatus`) | | sensitivity automatic / 0 to 4 (lobby only; `automatic` clears the operator value, BR-018) |
| K3 AGENT | announce "Agent", then the status (from `GetMenuStatus`; "stopped" per BR-002, including a closed write gate; the refusal cue when the status is unknown, BR-013) | 1 s: stop / resume the agent | intervention level (BR-004) |
| K4 END | | 1.5 s: force-end (running) / force-start (lobby) | |
| K5 TEAMS | announce "Teams", then the value (from `GetMenuStatus`) | | `num_teams` automatic / 2 to 6 (lobby only; `automatic` clears the operator value, BR-018) |
| K6 INSTR | toggle spoken instructions (lobby only; the toggle reads `GetMenuStatus`; the menu's voice line "Instructions on" / "off" names itself) | | shield mode automatic / instant / trigger / hold (lobby only, BR-018), committed on release of K6 |
| K7 BACKEND | announce "Backend", then its name: Rules, Claude, OpenAI or Jev (from `GetMenuStatus`) | | decision backend, committed on release of K7 |
| K8 PAGE | reserved (phase 2: next display page) | 3 s: lock / unlock the pad (A6) | |

A tap announcement (#2106, FR-196) plays the label, then the value once the label has ended (the length the audio service reports). It runs in the background (BR-009). A new announcement replaces one still playing (its clip stops and its value is not played), a failure cue is not repeated while one still plays, and an unplugged pad or a stopping service drops every cue still to come. An unknown value gives the refusal cue alone. The menu's voice line for a committed setting is unchanged: the value only, no label.

### BR-012: Error codes

`game_active`, `at_limit`, `flag_service_unavailable`, `partial:<key>`, `failed`, `stale`, `bad_option` ([services.md](../specs/services.md) §3.1). A refusal of a pad command is `success=false`; `force_start`, `step_setting` and the web `start_game` (UC-010 A8, #2176; it also publishes `game_start_rejected`) return `game_active`.

### BR-013: K3 hold direction

The direction of a K3 hold is the operator's intent at the press: the status read when K3 went down decides stop (running) or resume (stopped, BR-002). The read on release only confirms it; a disagreement on "stopped" cancels (A10). A status is unknown when the read failed or timed out, when its `agent_enabled_state` is not `on` or `off` (the menu reports `unknown` when it cannot resolve `agent/enabled`, and a menu older than #2101 sends an empty value), when its `agent_interventions_enabled_state` is not `on` or `off` (the same for `agent/interventions_enabled`; a menu older than #2093 sends an empty value), or when its agent level is empty or outside the ladder of BR-004 (the menu reports an agent flag it cannot resolve as an empty variant). The `interventions_allowed` variants `probe` and `shadow_experimental` are not on the ladder, so the pad treats them as unknown too: a K3 hold at either level always sends the stop and never the resume (fail closed, accepted, #2101). A K3 tap (BR-011) whose `agent_enabled_state` or `agent_interventions_enabled_state` is not `on` or `off` plays the refusal cue and never announces "stopped" or a level (#2101, #2093); a tap with the gate resolved `off` announces "stopped" (BR-002). With an unknown status the only direction is the stop (fail closed): it is idempotent (A9) and always attempts both writes (BR-002). A locked pad sends the stop whatever the status (A6).

### BR-014: Which input nodes are the pad

An input node is the pad when its USB vendor:product is `operator_pad.device` and it reports at least one key code of `operator_pad.keymap`. The PS Move ids (`054c:03d5`, `054c:0c5e`) are never opened or grabbed, whatever the flag says. Every pad node must be grabbed: when one of them cannot be grabbed (after the `EBUSY` retries), the attach fails, the nodes already grabbed are released and the next rescan tries again, so no pad key ever reaches the console.

### BR-015: Mode feedback on every lobby controller

A mode change from the pad (step 4) is announced on two channels once, when K1 is released, for the final mode only (the turns are coalesced, BR-005): the menu plays the mode's voice line ([UC-011](UC-011.md) step 3 voice map, `GAME_MODE_VOICE`) and sends every lobby controller (CONNECTED or READY; not the admin controller, not IDLE) a 600 ms pulse in the mode's colour (the UC-011 LED map, `GAME_MODE_COLORS`), the same pulse admin mode shows on the admin controller. When the pulse ends each controller shows the new mode's lobby colour (dim connected, bright ready), which the selection itself sets ([UC-011](UC-011.md) step 6, BR-005). A step refused with `at_limit` or `game_active` gives no voice and no pulse (A1, A7). The pulse never cuts short an identify ([UC-004](UC-004.md) BR-005) or a battery display running on that controller: the controller manager skips the pulse there, and the new lobby colour shows when that effect ends. Admin mode is unchanged.

### BR-016: Keys by F key

### BR-017: Live preview

While a layer key (K1, K2, K3, K5, K6, K7) is the only key down and the pad is not locked, each step of the knob (BR-005: a step, not a raw event) recomputes the value the release would commit (#2106, FR-197): **Known gap (#2222):** the K2 and K5 preview of `automatic` is voice only (no LED `preview_setting`); only the commit shows the double white flash. K6 previews it on the LEDs.

- The value comes from the status read when the layer key went down plus the net steps counted so far, along the same ladder and with the same clamping as the menu's `step_setting` and the pad's backend step (`lib/setting_ladders.py` `preview_value`). Someone else changing the setting during the hold is not seen; the menu's voice line on the commit says the result.
- The label (BR-011) plays once, at the first step of the hold. A tap announcement still playing then stops (its value is not played, audio group `pad_announce`), so the preview never talks over it. The lock words (A6) play with no group, so a hold never cuts them.
- The value plays `operator_pad.preview_debounce_ms` (default 150) after the last step, never before the label has ended (the length the audio service reports); a new step restarts the wait, so steps closer together than the wait speak only the value the knob stopped on. A new value stops a preview clip still playing (audio clip group `pad_preview`).
- A value equal to the last one spoken in this hold is not repeated. A step past the end of the range gives the limit word instead ("Maximum" / "Minimum", at most once per second, BR-009).
- Nothing is written before the release (BR-005): a step sends no `step_setting`. The one command a hold sends before its release is the K1 `preview_setting` (below), which writes nothing.
- The release (or a chord, a lost device or dropped input events) cancels a value still waiting and stops the preview group, then the release commits as before (BR-005) and the menu voices the result (its voice line is unchanged).
- With no status at the press, or a value the status does not tell (for example an unreadable agent switch, BR-013, or an unknown backend), the preview is silent; it never guesses.
- A lobby-only layer (K1, K2, K5, K6) while the game is live gives one "Not possible" for the hold and no values (A1); the release is refused as before and does not repeat the word.
- The preview runs in the background like every multi-clip cue (BR-009): the pad handles the next key event at once.
- `operator_pad.preview_enabled` off turns the preview off; the commit is unchanged.
- LED stays primary (BR-009): when the debounce of a step ends (without waiting for the label), a K1 hold sends the menu `preview_setting` (`option=current_game`, `mode=<mode>`) for each previewed mode that differs from the last one shown, and the menu pulses that mode's colour on every lobby controller (the BR-015 pulse, no voice, no write, no selection; refused with `game_active` while live and `bad_option` for a mode outside the ladder, A1, A8). It is sent in the background with a 1 s deadline, in order (a pulse waits for the one before it; a pulse not yet sent when the hold ends, or one a newer step replaced, is dropped; one already sent is not cancelled), never retried (BR-010), and its answer plays no cue. A hold that ends without a commit (a net of zero steps, a chord, a lost device, dropped input events, or a release the pad does not send because the status read at release is missing or live) after it sent another mode as its last pulse sends `preview_setting` once more, after that pulse, with the mode read at the press, so the lobby pulses the selected mode's colour again; the pulse ends on the selected mode's lobby colour either way (BR-015). A K6 hold does the same with `preview_setting` (`option=shield.activation`, `mode=<shield mode>`) and the shield-mode pulse of BR-018, including the pulse of the mode read at the press when the hold ends without a commit after it showed another mode. Other layers send no LED preview.

### BR-018: Shield mode layer and the `automatic` rung

K6 + knob steps the operator's shield activation mode `game/shield.activation` ([flags.md](../specs/flags.md) §4, [UC-040](UC-040.md) BR-019, BR-027; #2215) along the knob ladder **automatic, instant, trigger, hold**, clamped, never wrapping (BR-005, A7), committed once on the release of K6 through the menu's `step_setting` (option `shield.activation`). K6 keeps its tap (the instructions toggle, BR-011): a turn marks K6 used, so its release commits the shield mode and toggles nothing (BR-007).

- **Key.** K6 was chosen because the pad has no free key (BR-011): every key has a tap or a hold, and K6 is the only one whose hold and hold + knob were both empty; its tap is unchanged. K8's tap is reserved for the display pages (phase 2) and its hold is the lock, and K4's hold is force-end / force-start, so a layer on either would sit next to an action the operator must never trigger by mistake.
- **The `automatic` rung of other settings (#2222).** The rule below is shared: the settings in `lib/setting_ladders.py` `KNOB_LADDERS` (`sensitivity`, `num_teams`, `shield.activation`) have the knob ladder `automatic` followed by their value ladder, and one helper (`clamp_step` over `KNOB_LADDERS`, one menu code path `_step_knob_setting`) serves the menu's `step_setting` and the pad's preview, so the two stay identical. For each: the knob starts at the operator's persisted value; with none it starts at the rung of the **effective** value (the pad reads it from `GetMenuStatus` at the press, the menu from the flag's view at the commit, so preview equals commit), `automatic` is the bottom rung reached by turning down past the lowest value, a net of zero steps writes nothing, and an effective value outside the ladder starts at `automatic`, a value is written persisted, `automatic` is one clear of the persisted admin value (`DELETE /game/<key>?persist=true`) so the flag file's default (`sensitivity`: or an agent `real` promotion, FR-017's W5) applies again, `automatic` is the bottom of the ladder (a further step down is `at_limit`), a clear or write that fails or an unreadable operator value is A3 (`flag_service_unavailable`), the step is lobby only (A1, refused with `game_active`, `automatic` included), the voice is the one shared "Automatic" line (no per-setting wording) after the setting's label, and the commit shows the double white flash on the lobby controllers (the K2 and K5 previews speak it but send no `preview_setting`, a known gap: only the commit flashes, so the LED cue of the `automatic` preview is missing there, #2222). **Decided per setting:** `sensitivity` and `num_teams` get `automatic` (a flag-file default and, for sensitivity, an agent promotion exist). `force_all_start` and `game_instructions` do not: they are two-state toggles (the K6 tap flips instructions; "up means on", BR-004) and a third "no operator value" state on a toggle has no meaning the host can hear. `audio_volume.master` does not: the knob is a free volume control with a mute (BR-006) and clearing it would jump the volume. Adding a setting later is one entry in `KNOB_LADDERS`. `GetMenuStatus` reports operator-set against default for all settings with the rung in the one map `operator_settings` ([services.md](../specs/services.md) §3.1).
- **Knob position.** The knob starts at the operator's persisted value (an in-memory stage overlay or the baseline may differ from it); with no operator value it starts at the rung of the effective value (#2222: the first click up from `trigger` is `hold`, not `instant`), and `automatic` is the bottom rung. The menu reads it from the flag service (the `admin_value` of the flag's view) at the commit, and `GetMenuStatus` reports it in `operator_settings["shield.activation"]` next to the effective `shield_activation` ([services.md](../specs/services.md) §3.1). `GetMenuStatus` never calls the flag service itself: it serves the value of the last background read (one at menu start, then at most 2 s old, and set by each commit; a setting that cannot be read is left out of the map; a read that was in flight during a commit is dropped, so it never puts the old value back) and, until the first read lands (or when a setting cannot be read), no key for it in `operator_settings`, so the live preview of that setting is silent then (BR-017: never a guess). A clear or a write that fails in any way, an unexpected error included, is A3.
- **Write.** A mode (instant, trigger, hold) is written as a persisted admin value, like the other pad settings ([flags.md](../specs/flags.md) §13.3, [UC-053](UC-053.md) A2): it wins over the flag file's default and survives a restart of the flag service; an in-memory stage overlay written later wins over it until that overlay is cleared or the flag service restarts (last write wins, A2). The flag service ranks stack > admin > real, so a persisted operator mode also outranks a later agent `real` promotion of the shield mode (FR-162, [flags.md](../specs/flags.md) §4a): the operator's choice wins until it is cleared. **`automatic` clears it**: the commit is one clear of the persisted admin value (`DELETE /game/shield.activation?persist=true`, as `scripts/flags.sh clear game shield.activation --persist`), so the flag file's default or an agent `real` promotion applies again. A clear that fails is A3 (`flag_service_unavailable`, the failure cue); an operator value the menu cannot read writes nothing and is `flag_service_unavailable` too (fail closed, BR-010). The agent does not write the flag today (C-034).
- **Lobby only.** Refused with `game_active` and "Not possible" while the game lifecycle is live (A1), `automatic` included: `trigger` is read at each grant and `hold` is latched when a game starts (UC-040 BR-027), so a change applies to the next game; this matches #2096, where a later agent promotion of a mode happens only between games. Only Free-for-All honours `trigger` and `hold` (UC-040 BR-019); the pad does not check the selected mode.
- **Voice.** The label "Shield mode" (BR-011, BR-017) and one line per rung: "Automatic", "Instant", "Trigger", "Hold" (the voice catalog, [UC-031](UC-031.md) BR-007). "Automatic" does not say the mode that then applies. A K6 tap still toggles the instructions; the shield mode has no tap announcement.
- **LED.** On a commit the menu sends every lobby controller (CONNECTED or READY; not the admin controller, not IDLE) a 600 ms pulse in the mode's colour: instant white, trigger yellow, hold blue (the BR-015 pulse with another colour table, with the same restore of the lobby colour and the same skip of a controller showing an identify or the battery). `automatic` shows as a double white flash instead (two 150 ms flashes 300 ms apart), a pattern no mode cue uses. The live preview shows the same cues (BR-017). A step refused with `at_limit` or `game_active` gives no voice and no LED cue.
