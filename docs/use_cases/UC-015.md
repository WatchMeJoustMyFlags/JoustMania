# Use Case: Operate the Game with the Operator Pad

## Overview

**Use Case ID:** UC-015
**Use Case Name:** Operate the Game with the Operator Pad
**Primary Actor:** Host
**Goal:** Start and end games, pick the mode, change the lobby settings, stop or resume the agent and set the volume from one USB macro pad (8 keys and a knob), without a controller in admin mode and without a laptop
**Trigger:** Host presses, holds or turns a key of the pad
**Status:** Approved
**Requirements:** FR-190, FR-191, FR-192, FR-193, FR-194, FR-195

The key layout is BR-011 (an action fires on release, except where noted).

Work in progress (#2050; remove this paragraph after the hardware check of #2050 PR8): this use case is the spec for phase 1 of the operator pad, the key mapping only. There is no display yet (the OLED is phase 2), so every result is a voice line, a sound or a controller LED cue. The menu side is built (#2050 PR3: the `ProcessInput` commands `force_start`, `step_setting`, `agent_switch`, `set_backend`; #2050 PR4: `GetMenuStatus`, `lifecycle_generation` and the `stale` check of A5); the pad service code is in `services/operator_pad/` (#2050 PR6: gestures, actions, device, status reads, telemetry) and deploys as the `operator-pad` image under the `operator-pad` compose profile (#2050 PR7; on the Pi `COMPOSE_PROFILES=operator-pad` in `.env.local`, [UC-060](UC-060.md)); it reads the `operator` flag set (#2087; a key flagd cannot resolve falls back to its code default). The integration test and the check on the Pi hardware are #2050 PR8; FR-190 to FR-195 stay Open until then. The pad is an optional service (`operator-pad` compose profile, [services.md](../specs/services.md) §2): a stack without it behaves exactly as before.

This use case includes the rules of [UC-011](UC-011.md) (mode), [UC-012](UC-012.md) (settings), [UC-013](UC-013.md) (agent level), [UC-014](UC-014.md) (force-start) and [UC-027](UC-027.md) (force-end) by reference; it does not copy them. Where the pad differs, a business rule below says so.

## Preconditions

- **Pre-1:** The `operator-pad` service runs, the pad is plugged in and the service holds an exclusive grab of its input devices (BR-014: which nodes count as the pad).
- **Pre-2:** The pad firmware sends the fixed key codes (K1 = F13, K2 = F14, K3 to K8 = F18 to F23, knob press = F15, knob turn A = F16 and B = F17; the `operator_pad.keymap` default). The pad is a Vial keyboard (`cb00:1337`) whose events arrive on its main keyboard interface. Knob direction A is counter-clockwise (left) and B is clockwise (right); B raises the volume or steps a setting forward. Physical layout: 8 keys plus the knob press at the top right; top row K1, K2 and the knob; middle row K3 to K5; bottom row K6 to K8. All tap and hold timing happens on the host. The keys by F key code: BR-016.
- **Pre-3:** The menu is RUNNING (UC-010 Pre-conditions). The pad sends its commands to the menu only; it writes no flag itself (BR-001).

## Main Success Scenario

1. Host taps K1 in the lobby.
2. System (the pad service) reads `GetMenuStatus` and, when `lifecycle_live` is false, asks the menu to start through `ProcessInput` `start_game` (the menu's A8 guard, [UC-010](UC-010.md) A8, still refuses while a game is starting or running, with the unchanged `game_start_rejected` answer of BR-012).
3. System starts the game as in [UC-010](UC-010.md) step 5 onwards; a game that starts is announced by the usual countdown.
4. Host holds K1 and turns the knob: System steps the selected mode ([UC-011](UC-011.md) steps 2 to 5, `step_setting` option `current_game`), one voice line for the mode when K1 is released (the [UC-011](UC-011.md) voice map) and a short pulse of the mode's colour on every lobby controller (BR-015); a turn marks K1 as used, so the release does not start a game (BR-007).
5. Host holds K2, K5 or K3 and turns the knob: System steps the setting by the turns counted while the key was down in one `step_setting` call (`steps=n`, BR-005) when the key is released (the agent level and the backend included); the new value is announced (UC-012 voices) and written as the same persisted admin value as the controller does ([UC-053](UC-053.md) A2).
6. Host holds K3 for 1 s: System stops the agent (BR-002) or resumes it (BR-003), the direction taken from the status read when K3 went down (BR-013), and plays a distinct voice line for each direction.
7. Host holds K4 for 1.5 s and releases: System force-ends the primary game ([UC-027](UC-027.md) steps 1 to 5) or, in the lobby, force-starts ([UC-014](UC-014.md) steps 3 to 5, with the roster of BR-008).
8. Host turns the knob: System sets the master volume (BR-006) and plays a short sound at the new level; Host presses the knob: System mutes or unmutes.

## Alternative Flows

### A1: A game is starting or running

**Trigger:** a lobby-only command arrives while the menu's game lifecycle is live (step 2, 4, 5 or 7; #2054)
**Flow:**

1. System refuses in the menu, not only in the pad. The new pad commands `force_start` and `step_setting` (`sensitivity`, `num_teams`, `game_instructions`, `force_all_start`, and the mode with K1 + knob) return `success=false`, error `game_active`, and change nothing. The legacy web `start_game` keeps its answer (`success=true` plus a `game_start_rejected` event, [UC-010](UC-010.md) A8, BR-012) and so does the dashboard's `select_game` (UC-011 A1); the pad never relies on that answer for K1: it refuses the tap itself when the status it read at the press shows `lifecycle_live`, and the menu's guard is the backstop.
2. System plays the refusal cue (BR-009) once per refused gesture.
3. Use case ends. Not refused while a game runs: the volume (BR-006), the agent switch and level (BR-002 to BR-004), the backend (BR-004) and force-end (step 7).

### A2: Admin mode is open

**Trigger:** a pad command that writes a setting or starts a game arrives while a controller is in admin mode ([UC-012](UC-012.md)) (step 2 or 5)
**Flow:**

1. The last write wins; no lock is taken. A pad `force_start` first closes the admin session (`abandon_session`, reason `operator_pad_start`) so the admin lock and its span end; the admin controller is not added to the roster (BR-008).
2. Use case continues at step 2 (a start) or step 5 (a setting).

### A3: Flag service down or refusing

**Trigger:** a write of the pad command fails: the flag service does not answer within the writer's 500 ms deadline ([UC-053](UC-053.md) A8, NFR-052) or refuses (`503 no_sync_stream`, [UC-053](UC-053.md) A7) (step 5)
**Flow:**

1. System fails closed: it does not retry and does not queue the command (BR-010). `ProcessInput` returns `success=false` with the error `flag_service_unavailable`; a kill that wrote only one of its two keys returns `partial:<key>` with the key that failed, and a kill whose two writes both failed returns `failed` (BR-002); every other failed write returns `flag_service_unavailable`. A write that timed out is re-read once from the flag service before it counts (as [UC-013](UC-013.md) A3, #2095): when the flag service now serves the written variant, the write succeeded. One exception: a `current_game` step whose persisted write fails still succeeds, because the selection takes effect in menu memory (the next start uses it) and only its survival across a menu restart is lost.
2. System plays the failure cue (BR-009: two loud beeps), distinct from the success voice lines and from every level cue, and records a span and a metric.
3. Use case ends; the host sees nothing change and retries by hand. The last resort to stop the agent is `docker stop joustmania-agent` (talk runbook).

### A4: Device missing or unknown keys

**Trigger:** the pad is not plugged in, is unplugged mid-use, or sends a key code outside the table (step 1; Pre-1, Pre-2)
**Flow:**

1. System rescans for the device (hotplug) and never fails the other services; the menu, the dashboard and the controllers work as before. A rescan waits the rescan interval after every detach, so a node that fails right after the attach never makes a busy loop. A read of any node that fails for any reason counts as the device gone (detach, rescan), never as a pad that stays attached and reads nothing.
2. System resets every gesture in progress when the device disappears (a key held at the time never fires), and also when the kernel reports lost input events (`SYN_DROPPED`): a key whose release may have been lost never turns a later tap into a hold.
3. System ignores an unknown key code and counts it; after a firmware reset that leaves only unknown codes it logs a warning and plays one cue (BR-009).
4. Use case ends.

### A5: Stale state on K4

**Trigger:** the game state changed between the press and the release of K4 (step 7): a game ended during a lobby hold, or one started during an end hold
**Flow:**

1. System reads the menu status (`GetMenuStatus`, [services.md](../specs/services.md) §3.1) when K4 goes down and again on release. When the `lifecycle_generation` or the state class (lobby / live) differs, the pad cancels the gesture, sends nothing and plays the cancel cue (BR-009).
2. For `force_start` the pad sends `expected_generation` with the generation it captured when K4 went down (not the one read on release), so the menu is the authority over the whole hold; the menu refuses a mismatch with `success=false`, error `stale`, so any other caller is protected too.
3. Use case ends; the host repeats the gesture if still wanted.

### A6: Pad locked

**Trigger:** Host held K8 for 3 s (step 1; BR-011)
**Flow:**

1. System toggles the lock and plays a cue for each direction (no display yet) and sets the pad's Scroll Lock LED while locked.
2. While locked the pad sends nothing, with one exception: the stop direction of the agent switch (K3 hold, BR-002) still works, so a locked pad can always stop the agent.
3. Use case ends. A restart of the pad service comes back unlocked.

### A7: Knob at the end of a range

**Trigger:** a `step_setting` asks to move past the end while the option is already at its first or last value (step 4, 5 or 8)
**Flow:**

1. Nothing is written and the command returns error `at_limit` (no wrap; BR-005). A step of n that would pass the end stops at the end and writes it (success; BR-005); only a value already at the end gives `at_limit`. The pad plays the limit cue (BR-009). The admin mode keeps its own wrapping for `cycle_variant` options (UC-012).
2. Use case ends.

### A8: Unknown option or value

**Trigger:** `step_setting`, `agent_switch` or `set_backend` names an option, direction or backend outside the table (step 4, 5 or 6)
**Flow:**

1. System returns `success=false`, error `bad_option`, and changes nothing.
2. Use case ends.

### A9: Agent already stopped or already running

**Trigger:** K3 hold while the agent is in the state the gesture asks for (step 6)
**Flow:**

1. System treats the gesture as a no-op that still reports its voice line (stopped stays stopped), and does not touch the saved level (BR-003).
2. Use case ends.

### A10: Agent status changed or unknown on K3

**Trigger:** K3 is held for its hold time (step 6) and the status read when K3 went down and the one read on release disagree on "stopped" (BR-002), or one of the two reads is unknown (BR-013)
**Flow:**

1. When both reads are known and disagree on "stopped" (for example, someone stopped the agent from the dashboard during the hold), the pad cancels the gesture, sends nothing and plays the cancel cue (BR-009), as K4 does in A5.
2. When the status read at the press is unknown, or the read on release is, the pad sends the stop (BR-002: both writes attempted; A9: a stopped agent stays stopped). It never sends the resume without a known status at both ends of the hold.
3. Use case ends; the host repeats the gesture if a resume was wanted.

## Postconditions

### Success Postconditions

- The command's effect is in the flag service (persisted for the admin settings and the backend, in memory for `enabled`, BR-001) or in the menu (a started game); the host heard the confirming voice line or sound.

### Failure Postconditions

- Nothing changed beyond what the error code says (`partial:<key>` names a half-applied kill); the host heard the failure, refusal, limit or cancel cue. No command is queued for later.

## Business Rules

### BR-001: Writes go through the menu; keys written

The pad service sends `ProcessInput` commands to the menu and writes no flag itself; the menu writes through the flag service ([UC-053](UC-053.md)). Besides the keys the controller admin mode writes ([UC-013](UC-013.md) BR-001, narrowed to admin mode by this use case), the pad commands write: `agent/enabled` in memory only (no `persist` field; the registry row has no persist, the kill switch must not survive a restart, [UC-045](UC-045.md) step 7), `agent/decision.backend` persisted (the operator's choice, C-018), `agent/interventions_allowed` persisted (as UC-013), `user/audio_volume.master` persisted. The pad commands add no network exposure: `ProcessInput` and `/flags/` are already reachable on port 80 (the security follow-up of #2050 covers them).

### BR-002: Stopped, kill order and result

"Stopped" means `enabled` is off or `interventions_allowed` is `none`, in every rule below. The stop writes `interventions_allowed` = `none` first (that write blocks the agent at the coordinator gate and, at `none`, ends remote decide calls, [UC-013](UC-013.md) Post-S-1), then `enabled` = off. The menu attempts both and returns `ok`, `partial:<key>` (one write failed) or `failed` (both failed). The level is read from the flag service, never from the menu's in-process flagd value ([UC-013](UC-013.md) BR-003). It saves the previous level in memory only when that level is not `none`. A ladder step (BR-004) of a running agent down to `none` leaves the agent stopped (level `none`, `enabled` stays on): the menu saves the level the step left, and a resume restores it (BR-003).

### BR-003: Resume and saved level

The resume applies the saved level, or `ambient` when none is saved, to `interventions_allowed` only if the current level is still `none`; any other current level (for example one an admin set after the kill) is kept (last write wins). It then sets `enabled` = on. The saved level lives in menu memory; after a menu restart it is lost and the resume level is `ambient`, never `full`. The resume needs no knob confirm and plays its own voice line, as the stop does. While the agent is stopped (either condition of BR-002) the K3 + knob ladder (BR-004) changes only the saved level, so a stopped agent is never re-enabled or raised by the ladder; only the resume does that. When `enabled` or the level cannot be read, a ladder step in either direction writes nothing, leaves the saved level unchanged, plays no voice line and returns `flag_service_unavailable` (fail closed, BR-010; A3: a read or write fails); the stop still writes both keys (BR-002).

### BR-004: Level and backend

The level ladder is the one of [UC-013](UC-013.md) step 3 and A1 (none, ambient, standard, full), clamped, never wrapping. The new level is committed when K3 is released, escalation or restriction alike, with `steps=n` (BR-005); a release without a turn writes nothing. The backend ([UC-044](UC-044.md): `rules`, `claude`, `openai`, `jev`) is chosen with K7 + knob and committed when K7 is released.

### BR-005: Coalesced writes

A layer setting (mode, sensitivity, teams, agent level, backend) is committed once, when the layer key is released, with `steps=n` for the turns counted; a turn count that nets to zero writes nothing, and a step of n that would pass the end of the range stops at the end (A7). The volume is committed after a 250 ms pause in turning (it has no layer key). One command is one flag write, so a knob never writes one value per detent. The knob may be smooth (no detents; the maintainer's 0xCB 1337 sends about 25 events per turn), so a step is `operator_pad.knob_events_per_step` raw knob events (default 4, range 1 to 12; a value outside it counts as 4) in one direction, counted separately for the volume and for each layer key. A change of direction restarts the count. A remainder short of a step is dropped, never written: on the layer key's release, after the 250 ms pause in turning that commits the volume, and when the device goes away. The knob press is unaffected. A live preview of a layer setting announces per step, not per raw event.

### BR-006: Master volume and mute

The knob sets `user/audio_volume.master` (a multiplier on everything the audio service plays, applied at play time and on a flag change; steps stop at both ends). Mute sets the same flag to its `mute` variant (0.0); the pad remembers the variant from before the mute and restores it on unmute. The menu status carries the master variant (`audio_volume_master`, [services.md](../specs/services.md) §3.1), so after a pad restart the pad knows the room is muted; with no remembered variant it restores the flag's default variant (`max`). The steps go by the variants' values, low to high (`mute` 0.0, `quiet` 0.3, `normal` 0.6, `loud` 0.8, `max` 1.0), one variant per detent; the menu orders numeric variants by value regardless of the order the flag service lists them in (a guard: the flag service lists them in file order, which is value order today). The music keeps playing while muted. The `play_audio` flag is not used for the mute: switching it off stops the music, and switching it on does not bring it back.

### BR-007: Gestures

The pad decides tap or hold from the time between press and release only, measured on a monotonic clock when the event is read (never the wall clock, which a Pi without a real-time clock steps after boot); the tap limit is 400 ms (`operator_pad.tap_ms`); a release between the tap limit and the hold time cancels. Each hold time must be longer than the tap limit: when the timing flags break that, the pad keeps the default timings and logs a warning. A second press of a key that is already down (its release was lost) restarts that key's timing and drops its layer turns. A knob turn while a layer key is down marks that key used: its release does nothing else. A knob press while a layer key is held belongs to that layer: it is not a mute, and its release triggers no tap or hold action, even if the layer key is released first. The layer's setting still commits on layer-key release per BR-005. While a chord is down every key is blocked until all keys are up. Auto-repeat and a release without a press are ignored.

### BR-008: Roster of a pad force-start

A pad `force_start` builds the roster from the live controller manager as in [UC-014](UC-014.md) steps 3 and 4 and BR-001, but no serial represents the pad: no host is added, none is flashed, none is kept by ghost pruning.

### BR-009: Cues without a display

Every outcome has a voice or sound form (LED primary, audio reinforces). The failure cue is two `SFX_BEEP_LOUD`; refusal, limit and cancel cues are the existing short sounds; the limit cue plays at most once per second (a burst of `at_limit` refusals, for example a knob turned on at the end of the range, gives one cue, not one per refusal, #2105); each stop / resume direction and each lock direction has its own voice line. The cue assets are the existing ones (no new asset in phase 1).

### BR-010: Fail closed, never queue

A command that cannot be applied now is dropped with its error code. The pad does not queue, retry or replay a gesture, including after the device or the menu comes back.

### BR-012: Error codes

`game_active`, `at_limit`, `flag_service_unavailable`, `partial:<key>`, `failed`, `stale`, `bad_option` ([services.md](../specs/services.md) §3.1). A refusal of a pad command is `success=false`; the legacy `start_game` answer (`success=true` with a `game_start_rejected` event, UC-010 A8) is unchanged and stays for the dashboard; only `force_start` and `step_setting` return `game_active`.

### BR-013: K3 hold direction

The direction of a K3 hold is the operator's intent at the press: the status read when K3 went down decides stop (running) or resume (stopped, BR-002). The read on release only confirms it; a disagreement on "stopped" cancels (A10). A status is unknown when the read failed or timed out, when its `agent_enabled_state` is not `on` or `off` (the menu reports `unknown` when it cannot resolve `agent/enabled`, and a menu older than #2101 sends an empty value), or when its agent level is empty or outside the ladder of BR-004 (the menu reports an agent flag it cannot resolve as an empty variant). The `interventions_allowed` variants `probe` and `shadow_experimental` are not on the ladder, so the pad treats them as unknown too: a K3 hold at either level always sends the stop and never the resume (fail closed, accepted, #2101). A K3 tap (BR-011) whose `agent_enabled_state` is not `on` or `off` plays the refusal cue and never announces "stopped" (#2101). With an unknown status the only direction is the stop (fail closed): it is idempotent (A9) and always attempts both writes (BR-002). The stop bypass of a locked pad (A6) applies.

### BR-014: Which input nodes are the pad

An input node is the pad when its USB vendor:product is `operator_pad.device` and it reports at least one key code of `operator_pad.keymap`. The PS Move ids (`054c:03d5`, `054c:0c5e`) are never opened or grabbed, whatever the flag says. Every pad node must be grabbed: when one of them cannot be grabbed (after the `EBUSY` retries), the attach fails, the nodes already grabbed are released and the next rescan tries again, so no pad key ever reaches the console.

### BR-015: Mode feedback on every lobby controller

A mode change from the pad (step 4) is announced on two channels once, when K1 is released, for the final mode only (the turns are coalesced, BR-005): the menu plays the mode's voice line ([UC-011](UC-011.md) step 3 voice map, `GAME_MODE_VOICE`) and sends every lobby controller (CONNECTED or READY; not the admin controller, not IDLE) a 600 ms pulse in the mode's colour (the UC-011 LED map, `GAME_MODE_COLORS`), the same pulse admin mode shows on the admin controller. When the pulse ends each controller shows the new mode's lobby colour (dim connected, bright ready), which the selection itself sets ([UC-011](UC-011.md) step 6, BR-005). A step refused with `at_limit` or `game_active` gives no voice and no pulse (A1, A7). The pulse never cuts short an identify ([UC-004](UC-004.md) BR-005) or a battery display running on that controller: the controller manager skips the pulse there, and the new lobby colour shows when that effect ends. Admin mode is unchanged.
