# Use Case: Operate the Game with the Operator Pad

## Overview

**Use Case ID:** UC-015
**Use Case Name:** Operate the Game with the Operator Pad
**Primary Actor:** Host
**Secondary Actors:** Operator (installs the pad)
**Goal:** Start and end games, pick the mode, change the lobby settings, stop or resume the agent and set the volume from one USB macro pad (8 keys and a knob), without a controller in admin mode and without a laptop
**Trigger:** Host presses, holds or turns a key of the pad
**Status:** Approved
**Requirements:** FR-190, FR-191, FR-192, FR-193, FR-194, FR-195

The key layout is BR-011 (an action fires on release, except where noted).

Planned work (#2050; remove this paragraph when the code lands): this use case is the spec for phase 1 of the operator pad, the key mapping only. There is no display yet (the OLED is phase 2), so every result is a voice line, a sound or a controller LED cue. Nothing here is built; the rows it adds carry `Open` and #2050. The pad is an optional service (`operator-pad` compose profile, [services.md](../specs/services.md) §2): a stack without it behaves exactly as before.

This use case includes the rules of [UC-011](UC-011.md) (mode), [UC-012](UC-012.md) (settings), [UC-013](UC-013.md) (agent level), [UC-014](UC-014.md) (force-start) and [UC-027](UC-027.md) (force-end) by reference; it does not copy them. Where the pad differs, a business rule below says so.

## Preconditions

- **Pre-1:** The `operator-pad` service runs, the pad is plugged in and the service holds an exclusive grab of its input devices.
- **Pre-2:** The pad firmware sends the fixed key codes (K1 to K8 = F13 to F20, knob turn = F21 / F22, knob press = F23). All tap and hold timing happens on the host.
- **Pre-3:** The menu is RUNNING (UC-010 Pre-conditions). The pad sends its commands to the menu only; it writes no flag itself (BR-001).

## Main Success Scenario

1. Host taps K1 in the lobby.
2. System (the pad service) asks the menu to start through `ProcessInput` `start_game` (the menu's A8 guard, [UC-010](UC-010.md) A8, refuses while a game is starting or running).
3. System starts the game as in [UC-010](UC-010.md) step 5 onwards; a game that starts is announced by the usual countdown.
4. Host holds K1 and turns the knob: System steps the selected mode ([UC-011](UC-011.md) steps 2 to 5, `step_setting` option `current_game`), one voice line for the mode when K1 is released; a turn marks K1 as used, so the release does not start a game (BR-007).
5. Host holds K2, K5 or K3 and turns the knob: System steps the setting by the turns counted while the key was down in one `step_setting` call (`steps=n`, BR-005) when the key is released; the new value is announced (UC-012 voices) and written as the same persisted admin value as the controller does ([UC-053](UC-053.md) A2).
6. Host holds K3 for 1 s: System stops the agent (BR-002) or resumes it (BR-003) and plays a distinct voice line for each direction.
7. Host holds K4 for 1.5 s and releases: System force-ends the primary game ([UC-027](UC-027.md) steps 1 to 5) or, in the lobby, force-starts ([UC-014](UC-014.md) steps 3 to 5, with the roster of BR-008).
8. Host turns the knob: System sets the master volume (BR-006) and plays a short sound at the new level; Host presses the knob: System mutes or unmutes.

## Alternative Flows

### A1: A game is starting or running

**Trigger:** a lobby-only command arrives while the menu's game lifecycle is live (step 2, 4, 5 or 7; #2054)
**Flow:**

1. System refuses in the menu, not only in the pad: `ProcessInput` returns `success=false`, error `game_active`, and changes nothing. This holds for `start_game`, `force_start`, and `step_setting` of `sensitivity`, `num_teams`, `game_instructions` and `force_all_start`, and for the mode (K1 + knob; the dashboard's `select_game` keeps its behaviour, UC-011 A1).
2. System plays the refusal cue (BR-009) once per refused gesture.
3. Use case ends. Not refused while a game runs: the volume (BR-006), the agent switch and level (BR-002 to BR-004), the backend (BR-004) and force-end (step 7).

### A2: Admin mode is open

**Trigger:** a pad command that writes a setting or starts a game arrives while a controller is in admin mode ([UC-012](UC-012.md)) (step 2 or 5)
**Flow:**

1. The last write wins; no lock is taken. A pad `force_start` first closes the admin session (`abandon_session`, reason `operator_pad_start`) so the admin lock and its span end; the admin controller is not added to the roster (BR-008).
2. Use case continues at step 2 (a start) or step 5 (a setting).

### A3: Flag service down or refusing

**Trigger:** a write of the pad command fails: the flag service does not answer within the writer's 500 ms deadline ([UC-053](UC-053.md) A8, NFR-052) or refuses (`503 no_sync_stream`, [UC-053](UC-053.md) A7) (step 5)
**Flow:**

1. System fails closed: it does not retry and does not queue the command (BR-010). `ProcessInput` returns `success=false` with the error `flag_service_unavailable`; a kill that wrote only one of its two keys returns `partial:<key>` with the key that failed (BR-002).
2. System plays the failure cue (BR-009: two loud beeps), distinct from the success voice lines and from every level cue, and records a span and a metric.
3. Use case ends; the host sees nothing change and retries by hand. The last resort to stop the agent is `docker stop joustmania-agent` (talk runbook).

### A4: Device missing or unknown keys

**Trigger:** the pad is not plugged in, is unplugged mid-use, or sends a key code outside the table (step 1; Pre-1, Pre-2)
**Flow:**

1. System rescans for the device (hotplug) and never fails the other services; the menu, the dashboard and the controllers work as before.
2. System resets every gesture in progress when the device disappears (a key held at the time never fires).
3. System ignores an unknown key code and counts it; after a firmware reset that leaves only unknown codes it logs a warning and plays one cue (BR-009).
4. Use case ends.

### A5: Stale state on K4

**Trigger:** the game state changed between the press and the release of K4 (step 7): a game ended during a lobby hold, or one started during an end hold
**Flow:**

1. System reads the menu status (`GetMenuStatus`, [services.md](../specs/services.md) §3.1) when K4 goes down and again on release. When the `lifecycle_generation` or the state class (lobby / live) differs, the pad cancels the gesture, sends nothing and plays the cancel cue (BR-009).
2. For `force_start` the pad sends `expected_generation` with the generation read on release; the menu refuses a mismatch with `success=false`, error `stale`, so any other caller is protected too.
3. Use case ends; the host repeats the gesture if still wanted.

### A6: Pad locked

**Trigger:** Host held K8 for 3 s (step 1; BR-011)
**Flow:**

1. System toggles the lock and plays a cue for each direction (no display yet) and sets the pad's Scroll Lock LED while locked.
2. While locked the pad sends nothing, with one exception: the stop direction of the agent switch (K3 hold, BR-002) still works, so a locked pad can always stop the agent.
3. Use case ends. A restart of the pad service comes back unlocked.

### A7: Knob at the end of a range

**Trigger:** a `step_setting` would pass the first or last value of its range (step 4, 5 or 8)
**Flow:**

1. System stops at the end: nothing is written and the command returns error `at_limit` (no wrap; BR-005). The pad plays the limit cue (BR-009). The admin mode keeps its own wrapping for `cycle_variant` options (UC-012).
2. Use case ends.

### A8: Unknown option or value

**Trigger:** `step_setting`, `agent_switch` or `set_backend` names an option, direction or backend outside the table (step 4, 5 or 6)
**Flow:**

1. System returns `success=false`, error `bad_option`, and changes nothing.
2. Use case ends.

### A9: Agent already stopped or already running

**Trigger:** K3 hold while the agent is in the state the gesture asks for (step 6)
**Flow:**

1. System treats the gesture as a no-op that still reports its voice line (stopped stays stopped), and does not touch the saved level (BR-003).
2. Use case ends.

## Postconditions

### Success Postconditions

- The command's effect is in the flag service (persisted for the admin settings and the backend, in memory for `enabled`, BR-001) or in the menu (a started game); the host heard the confirming voice line or sound.

### Failure Postconditions

- Nothing changed beyond what the error code says (`partial:<key>` names a half-applied kill); the host heard the failure, refusal, limit or cancel cue. No command is queued for later.

## Business Rules

### BR-001: Writes go through the menu; keys written

The pad service sends `ProcessInput` commands to the menu and writes no flag itself; the menu writes through the flag service ([UC-053](UC-053.md)). Besides the keys the controller admin mode writes ([UC-013](UC-013.md) BR-001, narrowed to admin mode by this use case), the pad commands write: `agent/enabled` in memory only (no `persist` field; the registry row has no persist, the kill switch must not survive a restart, [UC-045](UC-045.md) step 7), `agent/decision.backend` persisted (the operator's choice, C-018), `agent/interventions_allowed` persisted (as UC-013), `user/audio_volume.master` persisted. The pad commands add no network exposure: `ProcessInput` and `/flags/` are already reachable on port 80 (the security follow-up of #2050 covers them).

### BR-002: Kill order and result

"Stopped" means `enabled` is off or `interventions_allowed` is `none`. The stop writes `interventions_allowed` = `none` first (that write blocks the agent at the coordinator gate and, at `none`, ends remote decide calls, [UC-013](UC-013.md) Post-S-1), then `enabled` = off. The menu attempts both and returns `ok`, `partial:<key>` or `failed`. It saves the previous level in memory only when that level is not `none`.

### BR-003: Resume order and saved level

The resume restores the saved level first, only when `interventions_allowed` is still `none` (a level an admin set since the kill is kept: last write wins), then sets `enabled` = on. The saved level lives in menu memory; after a menu restart it is lost and the resume level is `ambient`, never `full`. The resume needs no knob confirm and plays its own voice line, as the stop does. While the agent is stopped the K3 + knob ladder (BR-004) updates only the saved level and never re-enables the agent.

### BR-004: Level and backend

The level ladder is the one of [UC-013](UC-013.md) step 3 and A1 (none, ambient, standard, full), clamped, never wrapping; an escalation (a higher level than the current one) is committed with a knob press, a restriction on release. The backend ([UC-044](UC-044.md) rules, claude, openai, jev) is chosen with K7 + knob and committed with a knob press; a release without the press cancels.

### BR-005: Coalesced writes

A layer setting (mode, sensitivity, teams, level) is committed once, when the layer key is released, with `steps=n` for the turns counted; a turn count that nets to zero writes nothing. The volume is committed after a 250 ms pause in turning. One command is one flag write, so a knob never writes one value per detent.

### BR-006: Master volume and mute

The knob sets `user/audio_volume.master` (a multiplier on everything the audio service plays, applied at play time and on a flag change; steps stop at both ends). Mute sets the same flag to its `mute` variant (0.0); the pad remembers the variant from before the mute and restores it on unmute. The music keeps playing while muted. The `play_audio` flag is not used for the mute: switching it off stops the music, and switching it on does not bring it back.

### BR-007: Gestures

The pad decides tap or hold from the time between press and release only; a release between the tap limit and the hold time cancels. A knob turn while a layer key is down marks that key used: its release does nothing else. A knob press while a layer key is held binds its action on the press and its release is swallowed (it does not mute). While a chord is down every key is blocked until all keys are up. Auto-repeat and a release without a press are ignored.

### BR-008: Roster of a pad force-start

A pad `force_start` builds the roster from the live controller manager as in [UC-014](UC-014.md) steps 3 and 4 and BR-001, but no serial represents the pad: no host is added, none is flashed, none is kept by ghost pruning.

### BR-009: Cues without a display

Every outcome has a voice or sound form (LED primary, audio reinforces). The failure cue is two `SFX_BEEP_LOUD`; refusal, limit and cancel cues are the existing short sounds; each stop / resume direction and each lock direction has its own voice line. The cue assets are the existing ones (no new asset in phase 1).

### BR-010: Fail closed, never queue

A command that cannot be applied now is dropped with its error code. The pad does not queue, retry or replay a gesture, including after the device or the menu comes back.

### BR-011: Key layout

The layout (an action fires on release, except where noted; the numbers in brackets are the main scenario steps):

| Key | Tap | Hold | Hold + knob |
|---|---|---|---|
| Knob alone | master volume (BR-006); press = mute / unmute | | |
| K1 GAME | start a game (lobby only) | | choose the mode, committed on release of K1 |
| K2 SENS | announce the value | | sensitivity 0 to 4 (lobby only) |
| K3 AGENT | announce the status | 1 s: stop / resume the agent | intervention level (BR-004) |
| K4 END | | 1.5 s: force-end (running) / force-start (lobby) | |
| K5 TEAMS | announce the value | | `num_teams` 2 to 6 (lobby only) |
| K6 INSTR | toggle spoken instructions (lobby only) | | |
| K7 BACKEND | announce the backend | | decision backend, committed with a knob press |
| K8 PAGE | reserved (phase 2: next display page) | 3 s: lock / unlock the pad (A6) | |

### BR-012: Error codes

`game_active`, `at_limit`, `flag_service_unavailable`, `partial:<key>`, `stale`, `bad_option` ([services.md](../specs/services.md) §3.1). A refusal is `success=false`; the old `start_game` answer (`success=true` with a `game_start_rejected` event) stays for the dashboard.
