# Use Case: Connect a Controller and Join the Lobby

## Overview

**Use Case ID:** UC-002
**Use Case Name:** Connect a Controller and Join the Lobby
**Primary Actor:** Player
**Secondary Actors:** Operator
**Goal:** Get a paired controller connected and shown as present in the lobby
**Status:** Tested
**Requirements:** FR-002, FR-003, FR-004, FR-006, NFR-001, NFR-002

## Preconditions

- The controller was paired (UC-001).
- The controller manager runs with a backend set that includes a real adapter (`backend` flag, read at startup; default `rust`, also used when the flag is empty or cannot be read, BR-003). The mock adapter is always added.
- The menu is running.

## Main Success Scenario

1. Player presses the PS button.
2. System's HID backend opens the device and streams sensor data (≈ 1 kHz).
3. System discovers the controller on its next discovery check (1 Hz) and routes it to one adapter (per-serial `bluetooth_backend` targeting, then the rollout, then the default). Discovery is the only path that adds or removes a route. A pass that finishes after the backend shut down installs no routes and closes the handles it opened.
4. System assigns the controller a stable name (generated from the serial on first sight, persisted).
5. System publishes a connect event on the button stream.
6. System's menu registers the controller as CONNECTED and lights its LED in the selected game mode's colour at 30 % brightness.

## Alternative Flows

### A1: Controller disconnects

**Trigger:** The serial disappears from the backend (step 6, or any time later). A failed or timed-out rust-hid discovery pass is not a disappearance: the adapter keeps its controllers until 3 passes in a row have failed (about 3 s when rust-hid refuses at once, about 15 s when each 5 s call times out), then they all disconnect here; a successful pass resets the count (#2125).
**Flow:**

1. System removes it from the lobby and publishes a disconnect event.
2. System sets `controller_connected` to 0 for that serial and removes its `controller_info{serial,name}` series.
3. During a game, System also reports the disconnect to the game, which eliminates the player (UC-020 A2). A game gets only the disconnects of its own stream and of its roster controllers that dropped and are not back when that stream opens (BR-004).
4. Use case ends.

### A2: Operator renames the controller

**Trigger:** Operator calls RenameController (gRPC / connect-proxy; the dashboard has no rename UI) (step 4, or any time later)
**Flow:**

1. System stores the new name in the names file.
2. For a connected controller, System replaces its `controller_info{serial,name}` series: the old label set is removed, so only the current name is exported (the agent names targeted players from it, UC-041).
3. The controller manager's roster (`GetConnectedControllers`) shows the new name, and games started after the rename use it on player spans (state_builder copies the tracked name into the controller state and the game fills `player.name` from it). A game already running keeps the old name.
4. Use case ends.

### A3: Lobby idle

**Trigger:** No button press for `idle.timeout_minutes` (default 15) (step 6)
**Flow:**

1. System switches connected controllers to IDLE (LED off) and animates up to `sentinel.count` sentinel controllers (UC-010 A2).
2. Use case ends.

### A4: Controller reconnects

**Trigger:** A controller that was connected earlier in this controller-manager run connects again (step 3)
**Flow:**

1. System runs steps 4 and 5 (name, connect event), then restores the controller's last base LED colour, only if one was set before (the serial is in `base_colors`); the colour is restored after the event is published.
2. Use case continues at step 6.

### A5: Button stream reconnects

**Trigger:** The menu's button stream to the controller manager drops and reconnects (step 5, or any time later)
**Flow:**

1. System clears all lobby state (controller states, ready flags, button and battery state), so every READY player is un-readied.
2. The controller manager sends a connect event for every connected controller again.
3. Use case continues at step 6.

### A6: Ghost controller

**Trigger:** A connect or disconnect event lists the connected controllers, and the lobby holds a controller that is not in that list (step 5, or any time later)
**Flow:**

1. System removes the ghost from the lobby as if it had disconnected and increments `menu_ghost_controllers_pruned_total`.
2. Use case continues at step 6.

## Postconditions

### Success Postconditions

- The controller is tracked by the controller manager and shown CONNECTED in the lobby.

### Failure Postconditions

- The controller is not in the roster; no lobby state exists for it.

## Business Rules

### BR-001: One adapter per controller

Each controller is served by exactly one adapter per discovery cycle; routing changes apply on the next cycle without a reconnect.

### BR-002: Reserved mock controllers are hidden

Mock controllers reserved for shadow games never appear in the lobby roster.

### BR-003: rust-hid is the default Bluetooth backend

Real controllers are read through rust-hid by default: the `backend` flag defaults to `rust` (the controller manager adds `mock`), `bluetooth_backend` defaults to `rust`, and every compose stack that reads real hardware (`docker-compose.yml`, `docker-compose.lite.yml`) starts the rust-hid service. The python-hid backend is opt-in only (maintainer decision, #1371). Opting in needs all three: the `python-hid` compose profile (on the Pi a systemd `Environment=COMPOSE_PROFILES=python-hid` drop-in, since `.env` is tracked), `backend=python_rust` so the python adapter is loaded next to rust, **and** `bluetooth_backend=python` so serials and pairing are routed to it; with only the `backend` change, `bluetooth_backend`'s default `rust` keeps every controller on rust-hid (#1402). A manual python canary without the opt-in is refused rather than silently staying on rust (UC-052 A3). When the profile is inactive, `scripts/setup/joustmania-start.sh` removes a stale `joustmania-python-hid` container left by an older install (#1402). It is slated for removal after the talk. `scripts/talk-preflight.sh` FAILs when the `backend` flag names `rust` and the rust-hid container is not running and healthy, and skips the check (INFO) when docker is unreachable.

### BR-004: A game only gets disconnects from its own stream

The controller manager reports a disconnect to every game stream (a gameplay stream that sent player colours) open when the controller drops, once each, in the stream's next frame. A disconnect from before a game stream opens reaches no game: a controller that dropped, reconnected and joined the next game is not eliminated at that game's first frame (#1607). A roster controller (one in the stream's colours config) that was reported disconnected and is not connected again when the stream opens is still reported, in the stream's first frame, so a player who drops before the stream opens (during the instructions clip, or while the game reconnects its stream) is still eliminated (UC-020 A2). A roster controller the controller manager has not discovered yet (a freshly added mock) is not a disconnect. A game stream that opens while another is running (a shadow game) does not take the running game's pending disconnects.
