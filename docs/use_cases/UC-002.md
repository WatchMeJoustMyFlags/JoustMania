# Use Case: Connect a Controller and Join the Lobby

## Overview

**Use Case ID:** UC-002
**Use Case Name:** Connect a Controller and Join the Lobby
**Primary Actor:** Player
**Secondary Actors:** Operator
**Goal:** Get a paired controller connected and shown as present in the lobby
**Status:** Tested
**Requirements:** FR-002, FR-003, FR-004, FR-006, NFR-001, NFR-002, NFR-054, NFR-055

## Preconditions

- The controller was paired (UC-001).
- The controller manager runs with a backend set that includes a real adapter (`backend` flag, read at startup; default `rust`, also used when the flag is empty or cannot be read, BR-003). The mock adapter is always added.
- The menu is running.

## Main Success Scenario

1. Player presses the PS button.
2. System's HID backend opens the device and streams sensor data (≈ 1 kHz).
3. System discovers the controller on its next discovery check (1 Hz) and routes it to one adapter (per-serial `bluetooth_backend` targeting, then the rollout, then the default). Discovery is the only path that adds or removes a route. A pass that finishes after the backend shut down installs no routes and closes the handles it opened. The routed controller's HCI adapter (from rust-hid's sysfs walk, none for mock and USB; rust-hid resolves it once when it opens the device, on a discovery pass and on an on-demand `Open` alike, #2200) is exported as `controller_adapter_info{serial,adapter}` and shown on the dashboard card (UC-035 BR-009).
4. System assigns the controller a stable name (generated from the serial on first sight, persisted).
5. System publishes a connect event on the button stream.
6. System's menu registers the controller as CONNECTED and lights its LED in the selected game mode's colour at 30 % brightness.

## Alternative Flows

### A1: Controller disconnects

**Trigger:** The serial disappears from the backend (step 6, or any time later), or the controller stays listed but sends no fresh report for `silent_disconnect_seconds` (a silent link, BR-007). A failed or timed-out discovery pass of an adapter (rust-hid, or python-hid when loaded) is not a disappearance: the adapter keeps its controllers until 3 passes in a row have failed (about 3 s when the HID service refuses at once, about 15 s when each 5 s call times out; with both the rust and the python adapter loaded and both stuck, a pass waits on both, about 10 s, so the drop takes about 30 s), then they all disconnect here; a successful pass resets the count (#2125, #2140).
**Flow:**

1. System removes it from the lobby and publishes a disconnect event.
2. System sets `controller_connected` to 0 for that serial and removes its `controller_info{serial,name}` series.
3. During a game, System also reports the disconnect to the game, which eliminates the player (UC-020 A2). A game gets only the disconnects of its own stream and of its roster controllers that dropped and are not back when that stream opens (BR-004).
4. System ends the controller's feedback in the controller manager: the running effect, the shield, charge and hold layers with their cues, the background rumble and the rumble stop timers (#2471). The reconnect rebuilds the LED from the owner (A4, BR-008).
5. Use case ends.

### A2: Operator renames the controller

**Trigger:** Operator calls RenameController (gRPC / connect-proxy; the dashboard has no rename UI) (step 4, or any time later)
**Flow:**

1. System stores the new name in the names file.
2. For a connected controller, System replaces its `controller_info{serial,name}` series: the old label set is removed, so only the current name is exported (the agent names targeted players from it, UC-041).
3. The controller manager's roster (`GetConnectedControllers`) shows the new name, and games started after the rename use it on player spans (state_builder copies the tracked name into the controller state and the game fills `player.name` from it). A game already running keeps the old name.
4. Use case ends.

### A3: Lobby idle

**Trigger:** No button press for `idle.timeout_minutes` (default 15) (step 6)
**Flow:**

1. System switches connected controllers to IDLE (LED off) and animates up to `sentinel.count` sentinel controllers (UC-010 A2).
2. Use case ends.

### A4: Controller reconnects

**Trigger:** A controller that was connected earlier in this controller-manager run connects again (step 3)
**Flow:**

1. System runs steps 4 and 5 (name, connect event), then writes the controller's LED with the colour its current owner gives (BR-008): a player the running game eliminated for its disconnect gets the out state, a live player its game colour, any other controller its last lobby colour if one was set before (the serial is in `base_colors`); the colour is written after the event is published, and sent again even when it did not change (BR-008). A controller that came back from a silent link (BR-007) registers here the same way. When the controller comes back on another adapter, the adapter label moves with it; a rediscovery that reports no adapter name clears the stored adapter, so the old `hciN` is not kept (UC-035 BR-009, #2133).
2. Use case continues at step 6.

### A5: Button stream reconnects

**Trigger:** The menu's button stream to the controller manager drops and reconnects (step 5, or any time later)
**Flow:**

1. System clears all lobby state (controller states, ready flags, button and battery state), so every READY player is un-readied.
2. The controller manager sends a connect event for every connected controller again.
3. Use case continues at step 6.

### A6: Ghost controller

**Trigger:** A connect or disconnect event lists the connected controllers, and the lobby holds a controller that is not in that list (step 5, or any time later)
**Flow:**

1. System removes the ghost from the lobby as if it had disconnected and increments `menu_ghost_controllers_pruned_total`.
2. Use case continues at step 6.

### A7: rust-hid stops answering

**Trigger:** rust-hid's gRPC server does not answer its own health check 5 times in a row (one probe every 3 s, 3 s each), or its device-manager loop polls no input for 15 s, also when it is busy only on queued commands (step 2, or any time later; NFR-054, #2125)
**Flow:**

1. rust-hid flushes its logs, traces and metrics (at most 1 s, so the trip reason reaches Loki) and exits with code 70; the compose restart policy starts it again (compose does not act on `unhealthy` by itself). On SIGTERM / SIGINT (`docker stop`) rust-hid first switches every controller's LED and rumble off (each writer sends its off; waits at most 2 s), flushes the same way off the runtime workers, and exits 0; a stop that has not ended after 5 s is cut short by a plain thread (#2373).
2. The controller manager's `StreamIO` stream to rust-hid ends; its next discovery pass after the restart opens the stream and the controllers again (the same recovery as a manual `docker restart joustmania-rust-hid`); `close_all()` cancels the adapter's `StreamIO` call, and a reader that ends for any other reason (the stream failed, a frame it could not convert) cancels its own call before the adapter can reopen, so rust-hid (or python-hid) never keeps serving a stream the controller manager has dropped (#2266, `test_hid_stream_cancel.py`); rust-hid gives each `StreamIO` registration an id, so the late end of an old call never unregisters the reopened stream (only the newest registration streams), and a stream whose call ended without an unregister is unregistered on the device loop's next pass instead of being polled for nobody (#2371); a new registration first drains every open controller's queued input reports without sending them, so the stream starts with fresh input, never with reports (or a press) queued while no stream read them (#2372); `close_all()` (shutdown) is final: a discovery pass that races it opens no stream afterwards, and a command (an LED colour, a rumble) that a stopping stream took from the queue but never sent is sent first by the next stream, never twice (#2275), and never after a newer command: the next stream merges its queue only once the stopping stream's take is done, so an old colour never follows the new one (#2351); commands still queued when the stream ended are coalesced per serial before the next stream opens: the LED colour is state and the latest queued colour wins (no older colour replays before it; a full queue of 256 refuses the newest command; the controller manager's 20 Hz LED batch counts an output (colour + rumble) as sent only once the queue took it, so it sends it again on its next tick, #2355), while rumble changes stay in order and carry that latest colour (#2304); controllers missed by a discovery pass during the restart go through A1 and come back through A4. A rust-hid that hangs at controller-manager startup does not hold the start: the startup Discover / Open calls run in a worker thread, the adapters start concurrently, at most 8 s in all (`INIT_ADAPTER_TIMEOUT_S`), so the event loop stays free and the server's 10 s startup wait can fire; an adapter past the bound starts with no controllers and the 1 s discovery check finds them once rust-hid answers (#2351). Cost of a restart during a game: every controller goes through A1, so the game eliminates every player (UC-020 A2), and they come back through A4 after the game. Test: `services/controller_manager/tests/test_rust_adapter.py::TestStreamReconnection` (stream reopen and re-discovery); the game-elimination part is covered by UC-020 A2 tests, no end-to-end restart test exists. `joustmania-status` names a rust-hid that is still running but unhealthy as FAIL with `docker restart joustmania-rust-hid` (UC-060 BR-005).
3. Use case continues at step 6.

## Postconditions

### Success Postconditions

- The controller is tracked by the controller manager and shown CONNECTED in the lobby.

### Failure Postconditions

- The controller is not in the roster; no lobby state exists for it.

## Business Rules

### BR-001: One adapter per controller

Each controller is served by exactly one adapter per discovery cycle; routing changes apply on the next cycle without a reconnect.

### BR-002: Reserved mock controllers are hidden

Mock controllers reserved for shadow games never appear in the lobby roster.

### BR-003: rust-hid is the default Bluetooth backend

Real controllers are read through rust-hid by default: the `backend` flag defaults to `rust` (the controller manager adds `mock`), `bluetooth_backend` defaults to `rust`, and every compose stack that reads real hardware (`docker-compose.yml`, `docker-compose.lite.yml`) starts the rust-hid service. The python-hid backend is opt-in only (maintainer decision, #1371). Opting in needs all three: the `python-hid` compose profile (on the Pi a systemd `Environment=COMPOSE_PROFILES=python-hid` drop-in, since `.env` is tracked), `backend=python_rust` so the python adapter is loaded next to rust, **and** `bluetooth_backend=python` so serials and pairing are routed to it; with only the `backend` change, `bluetooth_backend`'s default `rust` keeps every controller on rust-hid (#1402). A manual python canary without the opt-in is refused rather than silently staying on rust (UC-052 A3). When the profile is inactive, `scripts/setup/joustmania-start.sh` removes a stale `joustmania-python-hid` container left by an older install (#1402). It is slated for removal after the talk. `scripts/talk-preflight.sh` FAILs when the `backend` flag names `rust` and the rust-hid container is not running and healthy, and skips the check (INFO) when docker is unreachable.

### BR-004: A game only gets disconnects from its own stream

The controller manager reports a disconnect to every game stream (a gameplay stream that sent player colours) open when the controller drops, once each, in the stream's next frame. A disconnect from before a game stream opens reaches no game: a controller that dropped, reconnected and joined the next game is not eliminated at that game's first frame (#1607). A roster controller (one in the stream's colours config) that was reported disconnected and is not connected again when the stream opens is still reported, in the stream's first frame, so a player who drops before the stream opens (during the instructions clip, or while the game reconnects its stream) is still eliminated (UC-020 A2). A roster controller the controller manager has not discovered yet (a freshly added mock) is not a disconnect. A game stream that opens while another is running (a shadow game) does not take the running game's pending disconnects.

### BR-005: Controller output never blocks rust-hid

rust-hid writes LED and rumble reports from one writer thread per controller, never from the device loop or a gRPC worker. Each controller keeps one pending value: the LED colour is the last one asked for, rumble keeps the highest value since the last write (a short pulse is not lost) and the latest follows in the next write. A controller gets at most `rust_hid.output_rate_hz` reports per second (flag, default 20), so effects and lobby repaints cannot fill the Bluetooth output queue (the kernel's "Output queue is full", #2125). Identical values are still sent: the controller manager's 2 s LED keep-alive keeps the LED lit. Pairing calls (GetUSBControllers, PairController) run off the gRPC workers (NFR-055). A queued Discover or Open whose caller already gave up (its reply channel closed) is skipped, so an abandoned command enumerates and opens nothing (NFR-055, #2140). A write stuck in the kernel holds its controller's device, so that controller's input freezes while rust-hid stays healthy: a write in flight for more than 1 s is logged once (WARN, then INFO once the write returned or the controller was closed) and shown as `rust_hid_output_write_in_flight_seconds{serial}`; it is reported only, never a watchdog restart (NFR-055, #2142).

### BR-006: A discovery pass opens a controller once and never reads a polled one

A rust-hid discovery pass enumerates the attached controllers (so a new one is found on the next 1 Hz check, step 3) but opens only those that are not open yet and not claimed by another adapter; an open controller is never reopened. While the controller manager's input stream is registered, a pass reads no report from an open controller (every report goes to the stream); the device loop's own poll marks a controller whose read fails, and the next pass drops it (A1) before it enumerates, so a controller that reconnected is opened again in that same pass. Without a registered stream, a non-forced pass reads each open controller once to find the dead ones (#2314); a stream whose call has ended no longer counts as registered once the device loop has unregistered it (A7 step 2, #2371). While a stream is registered, a Discover request's `force` flag has no effect (nothing is read either way) and `verify_only` still skips the enumeration (#2374).

### BR-007: A silent link is a disconnect

A tracked controller that sends no fresh report (a poll that returns a new sample) for `silent_disconnect_seconds` (`controller` flag, default 3 s, clamped to 1 to 10 s, read live on every discovery pass; flags.md §6) is disconnected as in A1, although the Bluetooth link is still up and the backend still lists it (out of range, #2466). The normal report gap is 20 to 50 ms (p95), so the limit never trips on a working link. The silence is measured in the 1 Hz discovery step from the connection-quality gap window (UC-035 BR-005), up to the last 100 Hz poll batch and with the poll loop's own stalls subtracted, so a late or stalled poll loop never disconnects a controller; the 100 Hz poll pays nothing for it. During a game the disconnect reaches the game (A1 step 3), which eliminates the player (UC-020 A2), so a player cannot stay in the game by walking out of range and a dead link does not keep a player alive. While the backend still lists it, the controller manager polls the silenced controller on each discovery pass; once the poll returns a new sample it registers again (A4). A silenced controller the backend stops listing comes back through the normal discovery path. A silent drop also forgets the controller's stored LED colour and rumble in the backend (its route stays because the backend still lists it), so its next registration never replays a stale game or death colour. A HID stream outage longer than the limit (rust-hid stalled but still listing its controllers) disconnects every controller at once, which in a game eliminates every player, as a rust-hid restart does (A7).

### BR-008: The LED is written on every (re)registration, by its current owner

When a controller registers (step 3 or A4) the controller manager writes its LED and does not skip the write as unchanged: the backend sends the output again on its next 20 Hz LED tick, whatever it sent before the re-open, and once more 0.5 s later (`LED_RESEND_DELAY_S`), so a first write that the re-opened device dropped or that raced its readiness is repeated (#2466). The colour comes from the controller's current owner, never from a colour cached for another owner: a player of an open game stream's roster whose disconnect that stream was handed (BR-004) and that the game no longer lists alive (its last alive filter) was eliminated by it (UC-020 A2), so it gets the out state (LED off) once, not its game colour; the off is not stored as its base colour, so the game's own effects can still repaint it. A roster player that registers for the first time after the stream opened, or whose disconnect the game dropped because its frames came back during the intro (BR-004, the player stays alive), gets its game colour. Any other controller gets its last lobby colour, and the menu repaints it on the connect event (step 6). The delayed resend is cancelled when the controller disconnects again or the controller manager stops. When a game stream closes, the game colours of its players that are not connected are dropped, so a player who dropped during a game and comes back in the lobby never shows the old game colour; so is an output the game wrote to them while they were away (below).

An LED or rumble write that reaches the backend for a controller with no adapter route (it is disconnected; in practice an effect's restore or a shield or cue rumble, and a base-colour write only in the moment between the discovery swap and the drop, since game effects and base colours for an untracked controller are refused before the backend) is not lost: the backend keeps it as the wanted output (#2471). Nothing is sent to the controller before it has registered again: once routed again, the LED batch skips it and any further write to it is held the same way; the registration releases the output just before the owner's colour is written, which is newer and wins; a controller whose registration fails keeps its LED unwritten, not stale. A dead player stays off when it reconnects: the death effect marks its base colour off from its first moment (not only after the red hold), and a (re)opened game stream configures a dead player's colour as off (UC-030 BR-006), so a reconnect before the game's next alive filter or after a stream reopen (whose new stream was handed no disconnect) restores off, never the game colour. A silent drop (BR-007) cancels the running effect; the effect's end does not write the game colour back, because the controller is no longer tracked (#2484).
