# Use Case: Operate the Stage Pi

## Overview

**Use Case ID:** UC-060
**Use Case Name:** Operate the Stage Pi
**Primary Actor:** Operator
**Goal:** The Pi comes up on its own into a known, pinned version of the full stack, the game works even when observability or the network does not, and a version change is one command that can be undone
**Trigger:** The Pi boots (the autostart unit runs), or the operator runs `joustmania-status`, the upgrade command or the rollback command
**Status:** Approved
**Requirements:** FR-180, FR-181, FR-182, FR-183, NFR-026, NFR-027, C-040, C-041, C-042

Planned work (#2027; remove this paragraph when the code lands): this use case is the spec for the start-up hardening. Landed so far: the unit and the safe start-script basics (PR 2a: no teardown, plain `stop`, bounded retries, `JOUSTMANIA_UNIT_REV`, `start.env` state); the upgrade command with rollback and the image tag derived from a pinned checkout (PR 3: A2, A3, BR-003); the offline pull logic, the two-phase start, the boot-time refusal of A4, `joustmania-status`, the LED and `setup.sh` are still open. Scripts: `scripts/setup/joustmania.service` (one systemd unit), `joustmania-start.sh`, `joustmania-compose.sh`, `lib-joustmania.sh`, `joustmania-upgrade.sh`, and the new `joustmania-status` command. Findings: the start-up audit of 2026-10-23 (#2027).

## Preconditions

- **Pre-1:** The Pi runs Docker and the autostart is installed (`scripts/setup/install_autostart.sh`).
- **Pre-2:** The checkout is pinned (C-040): a release tag or an exact commit sha at or after `MIN_PINNABLE`, with `.env.local` carrying the keys (UC-070 Pre-2) and no `IMAGE_TAG` (BR-003).

## Main Success Scenario

1. System (the autostart unit, ordered after `docker.service`, `network-online.target` and `bluetooth.service`) runs `joustmania-start.sh` as one unit; there is no second unit and no health timer.
2. System checks the pin (BR-003): the checkout is a release tag or exact sha, and the image tag derived from HEAD (BR-003) is exported and is the effective one (checked with `docker compose config --images`). It never runs `git pull` and never contacts the registry to look for a newer version.
3. System starts the game services first: `docker compose pull --policy missing` with a timeout, then `docker compose up --pull never` for the game services (BR-001, BR-002). It then polls the game containers until they are running and healthy, within the game-phase readiness timeout (N of NFR-027, plan default 120 s); the exit code of `up --wait` is only a hint (FR-181).
4. System starts the observability services (Jaeger, Loki, VictoriaMetrics, Grafana, the collector) in the same unit run, inline. The phase has its own timeout (300 s). A failure or timeout here is logged and makes the state `degraded` (A1); the unit exit code stays 0 and the game services keep running.
5. System sets the state `ok` and the ACT LED solid on (C-042); the unit ends `active (exited)`. `ExecStartPost` runs `joustmania-status --led` once to apply the LED. The operator sees the state with `joustmania-status` (BR-005).

## Alternative Flows

### A1: Observability does not come up

**Trigger:** One or more observability services fail to start or never become healthy (step 4)
**Flow:**

1. System keeps the game services running and records the failed service names.
2. System sets the state `degraded`: the ACT LED blinks at 1 Hz and `joustmania-status` lists the services that are down (FR-181, FR-183).
3. Use case ends. The game is playable; the collector and the game services do not wait for the backends (UC-035 A3).

### A2: Upgrade

**Trigger:** Operator runs the upgrade command with a target release tag or exact commit sha, which changes the pin (step 2)
**Flow:**

1. System refuses the target when it is `latest`, a branch name, or older than `MIN_PINNABLE` (C-040), and changes nothing.
2. System pulls the target's images first (while the old version keeps running), then switches the checkout to the target; `IMAGE_TAG` derives from the checkout, so no environment file is rewritten.
3. System applies the new version by restarting the unit (BR-006: the start limit is reset first, and a start systemd refuses is reported as refused, never judged unhealthy) and checks the result as in main steps 3 to 5.
4. System removes superseded `joustmania` images only after the new version is healthy; the previous version stays recorded for A3.
5. Use case ends. A failed pull (no network, missing image) changes nothing: the checkout and the running version stay as they were.

### A3: Rollback

**Trigger:** The new version is not healthy after A2 step 3 (automatic), or the operator runs `joustmania-upgrade` with the rollback option (step 2)
**Flow:**

1. System switches the checkout back to the previous recorded version (on its branch when it ran from one, so the image tag is the one it ran with) and restarts the unit (the start limit reset first, BR-006), with the old images (still on the Pi, A2 step 4); when an image that version resolves is missing, it switches the checkout back and starts nothing. It refuses to move a branch that has moved on since, and a refused or failed switch reports that nothing changed. The record names the rollback target from before the checkout until the restart is judged, so a rollback cut off in between (power loss, ssh hang-up) is finished by the next rollback on the same version and never toggles back to the failed one.
2. System sets the state `failed` if the old version does not come up either; otherwise `ok` (or `degraded`, A1) and reports that the upgrade was rolled back. A start systemd refuses (BR-006) is reported as refused with the recovery command, not as a failed version.
3. Use case ends. With `--no-rollback` the failed new version is left in place for inspection.

### A4: Pin mismatch

**Trigger:** The checkout is a branch, or the version is older than `MIN_PINNABLE` (step 2)
**Flow:**

1. System does not start the game services, sets the state `failed` (ACT LED 5 Hz) and writes the reason where `joustmania-status` shows it.
2. Operator fixes the pin (checkout a release tag or sha, or run A2/A3) and restarts the unit.
3. Use case ends.

### A5: Game services do not start

**Trigger:** A game container exits or is not healthy within the start timeout (step 3)
**Flow:**

1. System sets the state `failed` (ACT LED 5 Hz), records the failed services and leaves observability alone; the unit ends failed and systemd retries it a bounded number of times (3 in 15 minutes). The limit holds only for attempts of up to about 4.5 minutes each (the 4th start is refused only while 3 x (attempt + 30 s restart delay) <= 900 s): three attempts that each run into the 900 s start timeout take longer than 15 minutes and are never stopped by it; the pull timeout and the two-phase start of step 3 bound those attempts (#2027 PR 2b, still open). The limit is for these automatic retries; deliberate operator restarts do not spend it (BR-006).
2. Use case ends. A reboot with unchanged images still recreates 0 containers (NFR-026).

## Postconditions

### Success Postconditions

- The pinned version of the full stack runs; the state is `ok` or `degraded`, shown by the ACT LED and `joustmania-status`.
- A reboot with unchanged images and configuration recreated 0 containers (NFR-026).
- The LED is applied once at the end of the start (`ExecStartPost`: `joustmania-status --led`). Accepted gap: a crash after the start is not shown on the LED until the next boot or a manual `joustmania-status` (no health timer, by decision).

### Failure Postconditions

- The state is `failed`; no container was removed that was running before the boot, and the checkout still names a pinned version.

## Business Rules

### BR-001: Offline is not a failure

With no network, or with no new image, the boot recreates nothing: `pull --policy missing` fetches only an absent image (with a timeout, ignoring pull failures), `up --pull never` then runs the images that are on the Pi. The Pi must start the game from local images alone (FR-180).

### BR-002: Missing images only start what exists

Services whose image exists still start, and nothing is torn down. A missing game image makes the state `failed` (A5); a missing observability or agent image makes it `degraded` (A1).

### BR-003: Pin to a release or an exact commit

The pinned version is a release tag (`joustmania-vX.Y.Z`, image tag `X.Y.Z`) or an exact commit sha (image tag the 40-character sha). `latest` and `main` are refused. `MIN_PINNABLE` is the first release that contains #2040, because older releases have no `agent` image; its value is recorded here (and in `MIN_PINNABLE` of `scripts/setup/joustmania-upgrade.sh`) at the release cut (maintainer step), and C-040 stays Open until then. Until it is recorded the upgrade command refuses a target that does not contain the #2040 commit (`02e7752d`); it always refuses a target without `scripts/setup/joustmania-upgrade.sh`, because the Pi could not be upgraded or rolled back from it. In pin mode the image tag derived from HEAD is exported and wins over `.env` and `.env.local`; an `IMAGE_TAG` in `.env.local` that differs is ignored and reported as a status WARN (not A4). Boot never changes the pin (C-040).

### BR-004: Game before observability

The game services are started and judged before the observability phase, and nothing in the observability phase can fail the unit (FR-181).

### BR-005: One status vocabulary

The state is `starting`, `ok`, `degraded` or `failed`. Under `/sys/class/leds/ACT` (fallback `led0`) the script writes `trigger` first, then `delay_on` and `delay_off`: `starting` = trigger `heartbeat`; `degraded` = `timer` 500/500 ms (1 Hz); `failed` = `timer` 100/100 ms (5 Hz); `ok` = `default-on` (solid on, not a restored saved trigger). With no LED (dev box) or no permission it logs one line and exits 0. `joustmania-status` prints the state, the pinned version, the effective image tag and the failed services (C-042, FR-183).

### BR-006: Operator restarts do not spend the start limit

The unit's start limit (3 starts in 900 s, A5) stops a crash loop of automatic retries; it is never weakened. The upgrade command's restarts (A2 upgrade, A3 automatic rollback and `--rollback`) are deliberate, so each runs `sudo systemctl reset-failed joustmania` first, and an upgrade, a rollback and another upgrade inside 15 minutes all start. When systemd still refuses a start (`systemctl show -p Result` is `start-limit-hit`), the command resets and retries once; a second refusal is reported as "refused by systemd" with the recovery command `sudo systemctl reset-failed joustmania && sudo systemctl start joustmania`, and is never taken as an unhealthy version: no automatic rollback follows a refused start. `joustmania-upgrade --status` shows `start-limit-hit` with the same recovery command (#2102).
