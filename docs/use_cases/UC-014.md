# Use Case: Force-Start a Game

## Overview

**Use Case ID:** UC-014
**Use Case Name:** Force-Start a Game
**Primary Actor:** Host
**Goal:** Start a game now, without waiting for every connected player to ready up
**Status:** Tested
**Requirements:** FR-013, FR-007

## Preconditions

- Host is in admin mode (UC-012).

## Main Success Scenario

1. Host holds the trigger.
2. System shows a charging LED effect that fades over a fixed 2 s; the start fires once the trigger has been held for `force_all_start_seconds` (default 3 s).
3. System builds the roster: all connected controllers if `force_all_start` is on, otherwise the ready controllers plus the host.
4. System asks the controller manager for the live roster and drops serials that are no longer connected (never the host).
5. System flashes white, exits admin mode, publishes `game_requested` and starts the game (UC-010 from step 5).

## Alternative Flows

### A1: Released early

**Trigger:** Host releases the trigger before the hold time (step 2)
**Flow:**

1. System cancels the charge and restores the white admin LED.
2. Use case ends.

### A2: Live roster unavailable

**Trigger:** GetConnectedControllers fails or does not answer within 2 s (step 4; `LIVE_ROSTER_RPC_TIMEOUT_SECONDS`, a code constant, #2378)
**Flow:**

1. System keeps the roster as is and increments `menu_force_start_reconcile_failed_total`.
2. Use case continues at step 5.

### A3: Fewer players than the mode's minimum

**Trigger:** Roster has fewer controllers than the selected mode's minimum, two at least (step 5; UC-010 BR-001, BR-002)
**Flow:**

1. System publishes `game_start_cancelled`, announces "not enough players" by voice and returns to the lobby (UC-010 A3).
2. Use case ends.

### A4: A game is already starting or running

**Trigger:** The host's force-start fires while the menu's game lifecycle is live (step 5; #2054)
**Flow:**

1. System refuses the start as in UC-010 A8 (`game_start_rejected`, reason `game_active`; silent while a game is starting or running, a beep only in the lobby-restart window); the live game is not cancelled.
2. Use case ends.

### A5: Force-start from the operator pad

**Trigger:** the host holds K4 in the lobby on the operator pad ([UC-015](UC-015.md) step 7, #2050) (step 1)
**Flow:**

1. System builds the roster as in step 3 and 4 and BR-001 without a host serial, closes an open admin session (UC-015 A2) and refuses with `game_active` or `stale` under UC-015 A1 and A5.
2. Use case continues at step 5 (no admin exit, no host flash).

**Known gap (#2050):** the menu side of A5 is built (`force_start`, `services/menu/servicer.py`) and tested under UC-015 tags (`services/menu/tests/test_pad_commands.py`, UC-015 main, A1, A2, BR-008), but no test carries a UC-014 A5 tag yet, so A5 is not part of this use case's `Tested` evidence.

## Postconditions

### Success Postconditions

- A real game runs with the forced roster.

### Failure Postconditions

- No game starts.

## Business Rules

### BR-001: Ghost pruning

A controller missing from the controller manager's live roster is never part of a forced roster (#1153).

**Code / tests:** `services/menu/handlers/admin.py` (`_force_start_threshold`, `_start_trigger_hold_tracking`, `handle_trigger_release`, `_prune_ghosts_with_live_roster`, `handle_force_start`), `services/controller_manager/feedback_manager.py` (`_effect_force_start_charge`); `services/controller_manager/servicer.py` (`GetConnectedControllers`); tests `services/menu/tests/`.

### BR-002: Force-start skips the ready check, not the minimum

A force-start starts without waiting for every connected controller to be READY, but the forced roster still needs the selected mode's minimum (UC-010 BR-001): a forced Traitor game with three controllers is cancelled (A3) like a ready-path start (#1862).

**Code / tests:** `services/menu/servicer.py` (`_run_game_lifecycle`); tests `services/menu/tests/test_servicer.py` (`TestModeMinimumPlayers`).
