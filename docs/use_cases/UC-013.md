# Use Case: Stop the Agent from the Controller

## Overview

**Use Case ID:** UC-013
**Use Case Name:** Stop the Agent from the Controller
**Primary Actor:** Host
**Goal:** Restrict, stop or allow again the agent's interventions from the controller, without a laptop
**Trigger:** Host wants the agent to do less (or more) during or between games
**Status:** Tested
**Requirements:** FR-019, FR-050, NFR-050, NFR-052, C-008, C-030, C-032

## Preconditions

- Host is in admin mode (UC-012).

## Main Success Scenario

1. Host presses Move until the `agent_control` option (purple) is selected.
2. Host presses Start to restrict (or Select to escalate).
3. System reads the current level from the flag service (BR-003), steps `interventions_allowed` along the ladder none, ambient, standard, full and writes the new level as a persisted admin setting ([UC-053](UC-053.md) A2), clamped at both ends; it never wraps (Start at `none` stays `none`, Select at `full` stays `full`).
4. System gives feedback: none = red / "off", ambient = turquoise / "1", standard = orange / "2", full = green / "3".
5. The new level reaches the agent and the game coordinator within the write-propagation bound (NFR-050); the agent's next decision and the coordinator's next check use the new allow-list. The agent evaluates flags without a resolver cache, so a changed level is seen on its next read ([flags.md §1.3](../specs/flags.md#13-reload-semantics), #1715); the coordinator's check is independent.

## Alternative Flows

### A1: Current value is off the ladder

**Trigger:** the current `interventions_allowed` value is off the ladder: `probe` (only `noop` allowed) or `shadow_experimental` (`full` plus the shadow-only interventions), set by an operator; or it is another value outside the ladder (step 3). A level that cannot be read at all is A5
**Flow:**

1. System jumps to `none` in either direction (Start and Select alike), the safe floor; Select from `shadow_experimental` therefore also lands on `none`.
2. Use case continues at step 4.

### A2: Agent control not available

**Trigger:** the menu was started without a connection to the flag service for the agent flag set (step 3)
**Flow:**

1. System logs a warning ("Agent control unavailable") and does nothing: no write, no LED pulse, no voice line.
2. Use case ends; `interventions_allowed` is unchanged.

### A3: Flag service refuses or cannot be reached

**Trigger:** the flag service refuses the write (for example `503 no_sync_stream` while flagd is not connected, [UC-053](UC-053.md) A7) or does not answer within the writer's 500 ms deadline ([UC-053](UC-053.md) A8, NFR-052) (step 3)
**Flow:**

1. System logs the failure (an error for a refusal, critical when the flag service cannot be reached) and does not retry. A write that timed out has an unknown outcome: the flag service may have applied it after the deadline (#2095). The system re-reads the level from the flag service once, with the same 500 ms deadline, before it reports anything: when the flag service now serves the new level, the write counts as applied and the use case continues at step 4 (no error cue); when it serves another level, or the re-read fails too, the write is reported as not applied and the flow goes on at step 2.
2. System gives an error cue on the admin controller: a short red LED pulse (400 ms, speed 10), then the voice line "Not saved" (`admin_not_saved`, #1746; the LED is the primary cue and the voice only reinforces it, and a failed voice never drops the pulse); no level colour and no level voice line, so it cannot be mistaken for the `none` level (#1705). An unexpected exception raised by the write itself is a write that failed and gives the same cue; an error in the feedback after a write that applied does not.
3. Use case ends; `interventions_allowed` is unchanged, and flagd keeps serving the previous level to the agent and the coordinator. One exception: after a timed-out write that the re-read did not confirm (the re-read failed, or answered before the write applied), a write that landed late may have changed the level. The next press reads the flag service again (BR-003), so it steps from the level that is actually set.

### A4: Level applied but not persisted

**Trigger:** the flag service applies the level but reports it as not persisted. Since #2368 this happens only when the flag service runs with persistence off (`FLAG_SERVICE_STATE_FILE=off`); a failed save of the state file ([UC-053](UC-053.md) A12) is rolled back and answered `500 persist_failed`, which is the refusal of A3 (step 3)
**Flow:**

1. System logs an error ("applied but NOT persisted").
2. Use case continues at step 4; the level holds until the flag service restarts, which brings back the last level its state file holds (or the baseline, `ambient` in the shipped flag files).

### A5: Current level cannot be read

**Trigger:** the flag service read of step 3 fails (unreachable, no answer within 500 ms, or an error answer) (step 3)
**Flow:**

1. Start (restrict): System still writes `none`, the safe floor, so the kill direction works without a readable level; the use case continues at step 4, or at A3 when that write fails too.
2. Select (escalate): System writes nothing, because it never raises a level it cannot read, and gives the A3 error cue as a short red LED pulse only: nothing was attempted to save, so no "Not saved" line.
3. Use case ends after step 2; `interventions_allowed` is unchanged.

## Postconditions

### Success Postconditions

- The agent and the game coordinator permit only the intervention types of the selected level ([flags.md](../specs/flags.md) `interventions_allowed`) and block every other one `not_allowed`, an answer already in flight included (the agent's own check after a restart, step 5); at `none` no intervention passes and the agent makes no remote decide call ([UC-040](UC-040.md) BR-005, A14).
- The level is a persisted admin setting: it survives a restart of the flag service ([UC-053](UC-053.md) A2, FR-018), unless A4 applied.

### Failure Postconditions

- `interventions_allowed` is unchanged, except a late write after a timed-out write that the re-read did not confirm (A3 step 3); after A3, or a Select in A5, the host has also seen the error cue.

## Business Rules

### BR-001: Only one agent key (admin mode)

In admin mode the menu writes only `interventions_allowed` (the permission gate) of the agent set; every other agent key, the kill switch `enabled` included ([UC-045](UC-045.md)), is operator-owned. The operator pad ([UC-015](UC-015.md) BR-001, #2050) is a second human surface and also writes `enabled` (in memory) and `decision.backend` (persisted), through menu commands only; this rule and its test cover the controller admin path.

### BR-002: Two independent checks

See [UC-040](UC-040.md) BR-004: the agent and the game coordinator each check the allow-list.

### BR-003: Step from the flag service's view

The ladder steps from the level the flag service serves (`effective_default` of `GET /agent/interventions_allowed`, through the menu's writer, 500 ms deadline). It never steps from the menu's in-process flagd value: the flag service applies a write before it answers, while flagd catches up only within the propagation bound (NFR-050). Without this rule, a second press right after a write, or after a write that timed out client-side but applied (A3, #2095), steps from the old level again. The operator pad's ladder, stop and resume read the level the same way ([UC-015](UC-015.md) BR-002).
