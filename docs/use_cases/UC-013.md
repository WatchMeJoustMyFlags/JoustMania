# Use Case: Stop the Agent from the Controller

## Overview

**Use Case ID:** UC-013
**Use Case Name:** Stop the Agent from the Controller
**Primary Actor:** Host
**Goal:** Restrict or stop agent interventions without a laptop
**Status:** Implemented
**Requirements:** FR-019, FR-050, C-008

## Preconditions

- Host is in admin mode (UC-012).

## Main Success Scenario

1. Host presses Move until the `agent_control` option (purple) is selected.
2. Host presses Start to restrict (or Select to escalate).
3. System steps `interventions_allowed` in `agent.json` along the ladder none, ambient, standard, full.
4. System gives feedback: none = red / "off", ambient = turquoise / "1", standard = orange / "2", full = green / "3".
5. flagd reloads `agent.json`; the agent's next decision and the coordinator's next check use the new allow-list.

## Alternative Flows

### A1: Current value is off the ladder

**Trigger:** `interventions_allowed` is `probe` or `shadow_experimental` (step 3)
**Flow:**

1. System jumps to `none` in either direction.
2. Use case continues at step 4.

## Postconditions

### Success Postconditions

- With `none`, the agent can only answer `noop` and every non-noop decision is blocked `not_allowed`; the coordinator also rejects any intervention not in the list.

### Failure Postconditions

- `agent.json` is unchanged (write failure logged CRITICAL).

## Business Rules

### BR-001: Only one agent key

The menu writes only `interventions_allowed` in `agent.json`; every other agent key is operator-owned.

### BR-002: Two independent checks

The allow-list is enforced by the agent (permission chain) and by the game coordinator (enforcement chain).
