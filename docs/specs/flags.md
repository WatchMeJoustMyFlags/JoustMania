OpenFeature flags served by flagd are the **only** control surface of the system:
human settings, the agent's governor, the agent's own interventions and the infrastructure rollout
are all flags (northstar constraint C-002). This catalog lists every flag on `main`. The flag sets and their files are
generated by `make specs` into [generated/flag-counts.md](generated/flag-counts.md) (#1280); the per-set flag counts are not committed, so two PRs that each add a flag do not conflict: `make specs-counts` prints them and CI shows them in the Telemetry Contract job summary (#2152); the `ci/` copies (§12) are not counted. (`services/flagd/controller.ci-rust.json`, loaded by nothing, was deleted in #1416.)

Rule (see [CONTRIBUTING](../CONTRIBUTING.md#spec-driven-development-aiup)): a new flag, a new variant, a
changed default or a new reader/writer updates this file in the same PR.

**Provider readiness (#1329, UC-010 A5 / BR-004).** A named provider is READY only after its first sync from flagd. Until then, every evaluation returns the code default with `ProviderNotReadyError`, and the `TracingHook` records that error on the current span. `lib/feature_flags.py` `wait_for_provider_ready(domain, deadline_seconds)` waits for READY, bounded by the deadline. The SDK runs the READY handler on whichever thread emits the event: the provider's init thread, the flagd watcher thread, or the caller of `add_handler` when the provider is already READY. The waiter is therefore woken on its own event loop with `loop.call_soon_threadsafe`. The handler is removed once the wait ends. The controller manager waits at startup (5 s per domain). The game coordinator waits per game (real and agent-started shadow games), before the game is created: up to 5 s, and only for those of `system`, `controller`, `game`, `agent`, `user` and `interventions` that are still NOT_READY. STALE and ERROR are not waited on, because with the in-process resolver they still serve the last-synced flags. `observability` is left out on purpose: it is read at process start (export intervals) and does not shape a game; its one per-game read, `telemetry.experiment_game_parent` (§10, #2223), happens when the game root span starts, before the wait, so a game started before the `observability` provider is READY gets its code default `link`. After a wait the coordinator re-reads its process-wide runtime config in an empty evaluation context, so a shadow session's `game_kind` / experiment targeting cannot leak into it (`services/game_coordinator/flag_readiness.py`). The OpenFeature client used for the wait is reused per domain, and a domain's status is read through that client (`lib/feature_flags.py` `provider_status`). `api.provider_registry.get_provider_status` takes a provider object and reports NOT_READY for a domain string.

**Agent and rust-hid readiness (#1713, UC-045 A3).** Both use the in-process resolver against `flagd:8015` and wait for flagd without a deadline that can end the sync for good. go-sdk-contrib flagd v0.8.0 (re-checked in #1942; v0.6.0 behaved the same) gives `Init` one deadline; when it passes before the first sync, the provider never starts its event loop, its event buffer (5) fills after a few flag changes and the sync stops applying data, so later flips are lost (the in-process form of #1709). `Init` also fails at once on a STALE / ERROR event before the first sync (flagd refusing the stream), with the same result. The agent therefore wraps each provider (`syncedProvider`): a provider is built only once a TCP probe of the sync port succeeds (probes 250 ms apart, doubling to 10 s); its `Init` gets no effective deadline, so it waits for the first sync (logged at WARN every 10 s while it waits); an `Init` that fails on an error event is shut down and a fresh provider is built after a pause of 1 s doubling to 5 min, logged at WARN, with no overall limit. Residual bound: v0.8.0 never frees a failed build (its service `Init` waits on a channel that ignores its context: about one goroutine and 300 KB each), so a flagd that accepts TCP but refuses the stream (for example a wrong selector) costs at most one build per domain per 5 min, about 10 MB per hour for the three domains; a flagd that is down costs only probes. Until the first sync the SDK keeps the domain NOT_READY. While the domain is not READY (before the first sync, and when the sync stream is lost: STALE or ERROR until flagd sends again) every agent read returns its code default, as when flagd was unreachable on the RPC resolver: `enabled`, `interventions_enabled`, `rollout_enabled` and `remediation_allowed` fail closed, and so do `experiments_enabled` and `experiment_dynamic_enabled` (no env fallback since #1907). Unlike the Python services, the agent does not keep serving the last-synced values while STALE. After flagd sends a configuration the provider cannot parse (ERROR), the next valid configuration, even one identical to the last good one, sends READY again, so the agent's reads are served again at once (v0.8.0; v0.6.0 waited for the next configuration that changed a flag). The sync stream reconnects on its own (backoff 500 ms to 1 s). v0.8.0 also ends the sync stream every 10 min and opens it again at once (`StreamDeadlineMs`, default 600000): this sends no event and the resent configuration changes no flag, so reads stay served; the provider logs `sync stream established` at INFO each time (once per domain per 10 min). Every in-process read runs under a context timeout equal to the `Init` deadline (one timer per read, which never fires with the agent's deadline). Sync keepalive (#1768): flagd v0.16.0's sync server set no keepalive enforcement policy, so grpc-go's default applied (at most one client ping per 5 min, none without an open stream; a faster client collected ping strikes and got GOAWAY `too_many_pings`, which dropped the stream and made the agent fail closed for about a second). Since flagd v0.18.0 (#1945) the sync server is served by connect over net/http, which enforces no minimum ping interval and permits pings without a stream (`--keep-alive-min-time` and `--keep-alive-permit-without-stream` are accepted no-ops), so no client ping cadence draws that GOAWAY any more; the client options below are kept unchanged. v0.6.0 hard-coded a 30 s ping without a stream, which drew that GOAWAY every 2 to 3 min on an idle stream, and v0.8.0's own options still ping without a stream (its default keepalive time 0, documented as off, is raised to grpc's 10 s minimum); the agent therefore dials the sync stream with its own options (`WithGrpcDialOptionsOverride`: plaintext, the retry policy above with at most 4 attempts as in v0.8.0, keepalive ping every 10 min with a 5 s timeout and only while the stream is open), as the Python services do (`keep_alive_time=600000`). Trade-off: flagd sends no heartbeat on an idle stream, so a half-open connection can go unnoticed for up to about 10 min (OS TCP keepalive starts only after 2 h); in that window the agent stays READY on the last-synced values and would miss a kill-switch flip. This is accepted because the agent and flagd share one host and compose network, and a shorter ping (for example 30 s) is what flagd up to v0.16 rejected with GOAWAY `too_many_pings`. rust-hid sends no HTTP/2 keepalive pings (the crate's `keep_alive_time_ms` default is 0; only OS TCP keepalive), so its stream is not affected. The lifecycle holder is reloaded on every `PROVIDER_CONFIGURATION_CHANGED` and, as the safety net, every 1 s. rust-hid builds its provider only once flagd's sync port accepts a TCP connection, retried with backoff (500 ms to 5 s) in the background, and again if the build fails (the crate's own first-sync wait is 5 s); until then `grpc_rpc_spans` reads its code default (off). Every flagd client points at the sync port: each compose file and each image that sets `FLAGD_PORT` sets 8015 (`tests/contract/test_flagd_client_ports.py`, #2090); a client on the RPC port (8013) gets the TCP connection but never a first sync. Once built, the crate's sync stream reconnects on its own (backoff 500 ms to 2 s) and keeps the last-synced values while flagd is away. Tests: `services/agent/flags/synced_provider_test.go` (late first sync, lost stream), `services/agent/flags/latestart_test.go` (a real gRPC sync server that accepts TCP before it serves: one provider build, reads fail closed until READY, then every flip is seen; the identical configuration after a parse error is served again; a DISABLED `enabled` reads off; the opt-in canary `TestUpstreamFlagdLateInit_StillWedges`, run with `FLAGD_UPSTREAM_CANARY=1`, fails once upstream fixes the late-init bug so the wrapper can be re-evaluated), `services/agent/flags/keepalive_test.go` (keepalive within flagd's ping policy, sync over the override dial options), `tests/service/test_agent_flag_live.py` (late flagd, flagd restart mid-run, flips of already-read flags, an idle stream held 150 s without a drop), `tests/service/test_rust_hid_flag_live.py`.

### 1.2 Evaluation context

- API level (Python): `service_name`, `service_namespace`, `language`, `hostname`, `game_kind=real` (`lib/feature_flags.py:115-131`).
- Per game (transaction context): `targetingKey=game_mode`, `game_mode`, `controller_count`, `game_kind`, optional `sensitivity`, `experiment_id`, `arm` (`lib/feature_flags.py:487-587`). Calibration reads add `gameId` (`lib/feature_flags.py:284-295`).
- Interventions are evaluated per live session with `{targetingKey=serial, gameId}` (`services/game_coordinator/interventions.py:1052-1066`).
- Every intervention handler (and revert handler and agent cue) runs on the game loop through `GameLoopDispatcher.run`, and the manager sets the game's own transaction context around it (`flag_eval_context` on the game, `services/game_coordinator/interventions.py:run_in_game_flag_context`; restored afterwards). A flag read inside a handler therefore sees the API-level context, the game's transaction context (`targetingKey=game_mode`, `game_mode`, `controller_count`, `sensitivity`, `game_kind` (`shadow` in a shadow game), `experiment_id`, `arm`; before the game's run starts only `game_kind`, `experiment_id` and `arm`) and its own invocation context, which wins (#1970; before, handlers saw only the API-level context, #1837, #1872). The handler-read flags are declared in `services/game_coordinator/handler_flag_reads.py` (today `shield.activation`, `shield.charge_expiry_seconds`, `windows` and the `user` flag `agent_intervention_cue`). Targeting on them may use only the variables declared there, checked over `services/flagd/*.json` and `services/flagd/ci/*.json` (`tests/contract/test_flagd_resolution.py`); `services/game_coordinator/tests/test_handler_flag_reads.py` drives every handler and fails for a read that is not declared. Because handlers see the game's context, an experiment-arm value on `windows` reaches the `pacing_profile` read in that arm's games, and the lever is then blocked as `experiment_override` (§4, UC-043 BR-005); real and non-experiment shadow games resolve every handler-read flag as before.
- `game_kind` vocabulary for flags is `real` / `shadow`; the protected value is `real`. An experiment-arm value is rendered by the flag service (`services/flag-service/state/render.go`) as the rung `{"and": [{"!=": [{"var": "game_kind"}, "real"]}, {"==": [{"var": "experiment_id"}, "<id>"]}, {"==": [{"var": "arm"}, "experimental"]}]}` in front of the baseline targeting, so the control arm, every other experiment and every real game fall through (FR-138). The agent's gate checks a dry run of each write before it writes (`services/agent/experiment/gate.go`). Every experiment has an id: a proposer proposal is declared as a registry experiment (`exp_<hex>`); there is no unscoped form. The flag service drops an experiment's arm values once no registered game has carried its id, and nobody wrote them, for `FLAG_SERVICE_EXPERIMENT_IDLE` (default 2 h, NFR-051). Telemetry uses `primary` / `shadow`; see [entity_model.md](../entity_model.md#game_session).

### 1.3 Reload semantics

| Term | Meaning |
|---|---|
| **live** | Evaluated at use time (each call, cycle or tick). Takes effect once flagd has the new configuration from the flag service. |
| **event-refreshed** | Cached, re-read on OpenFeature `PROVIDER_CONFIGURATION_CHANGED`. Effectively live. |
| **per-game** | Read at game start (menu `StartGameConfig` or game `__init__`) and frozen for that game. |
| **startup** | Read once at process start. **Restart required.** |

Startup-only flags: controller `backend`; observability `metrics_export_interval_ms`,
`otel_bsp_schedule_delay_millis`; user `menu_auto_start`, `audio_volume.lobby_music`,
`audio_volume.menu_sound`, `audio_volume.menu_voice`.

Propagation (write accepted to value served): the flag service pushes the new configuration on the open sync
stream at once; `tests/service/test_flag_propagation.py` measures it for NFR-050. A baseline file change takes
effect only on the next start of the flag service (`scripts/flags.sh restart`).

**Traceability:** C-002, C-033, NFR-050 / UC-012, UC-044, UC-053 / `docker-compose.yml`, `lib/feature_flags.py`, `lib/flag_service_writer.py`, `services/agent/flags/` / `lib/tests/`, `services/agent/flags/*_test.go`, `tests/service/test_flag_propagation.py`.

### 3.2 `goal.profile` schema (planned, #2479)

Each variant is an object `{"terms": [ {"characteristic": <name>, "min": <number|null>, "max": <number|null>, "phase": "whole"|"endgame", "weight": <number>} ]}`:

File: [`services/flagd/interventions.json`](../../services/flagd/interventions.json).

The agent's tier-1 write surface: bounded, in-game, reversible. Written only by the agent action sink (gated by `interventions_enabled`) through the flag service, and always for one registered game: every value is rendered as targeting on that game's `gameId` (and on the player's serial for a per-player flag), resolves in no other game, and is dropped when the game ends ([UC-053](../use_cases/UC-053.md) BR-003, FR-136). The game coordinator `InterventionManager` re-reads the set on every flagd configuration change. **State** flags resolve the game's value; **event** flags (`eliminate_player`, `revive_player`, `audio_cue`, `controller_effect`, `end_game`) resolve the game's event list `{"epoch","seq","events":[last 16]}` and the coordinator applies every event with a seq above the last one it applied, exactly once (UC-053 BR-006, FR-137); a game starts with an empty list, so nothing of an earlier game is replayed. Per-player **level** flags (`player_sensitivity_factor`, `player_handicap_factor`) apply to the players whose level changed during the game, and a player whose level returns to neutral has its factor reset to 1.0 as a revert ([UC-040 BR-017](../use_cases/UC-040.md#br-017-per-player-levels-belong-to-one-game), #1317). Per-player **grant** flags (`shield_seconds`, `toughness_boost_seconds`, `soft_penalty_action`) get a fresh generated variant per write, so a same-value re-grant is a change and fires once ([UC-040 BR-012](../use_cases/UC-040.md#br-012-a-per-player-grant-applies-once-per-decision)). `end_game` is in the deciding game's event list and ends only that game ([UC-040 BR-011](../use_cases/UC-040.md#br-011-end_game-ends-only-the-game-it-was-decided-for)). Value formats and the writer mapping: [decide-contract.md §11](decide-contract.md#11-from-decision-to-game-effect); bounds and scopes: §13.1.

**Consistency with the allow-list after a reconnect** ([UC-053](../use_cases/UC-053.md) A9 step 4, #1552). The coordinator holds `interventions` and `agent` on separate in-process sync streams, which reconnect one by one, in no fixed order, after a flagd restart. The flag service therefore stamps every `interventions` flag and `agent/interventions_allowed` (no other flag) with the snapshot it rendered them from: flag metadata `snapshotEpoch` (its boot epoch) and `snapshotVersion` (its snapshot version), so every write moves both stamps. After reading an intervention, and before it moves any baseline, the coordinator compares the stamp of `end_game` (its interventions set) with the stamp of `interventions_allowed`. While the allow-list is from another epoch, older or unstamped, the intervention is deferred: nothing is applied, blocked or recorded, and no baseline moves. The `agent` stream's catch-up fires a configuration change, which re-evaluates it against the current allow-list (applied, or blocked `not_allowed`). A stale allow-list therefore never decides an intervention, wider (fail closed) or narrower (nothing is lost). An unstamped `interventions` set (file-sourced flagd, as in the contract tier) is not gated. A probe that fails is treated as a lag (fail closed). The probe and the allow-list stamp are resolved through the provider, bypassing the OpenFeature hooks, so they do not appear in the evaluation metrics; the allow-list stamp is read at most once per evaluation pass unless the probe moves past it. A deferral is visible: `game_intervention_deferrals_total`, `game_intervention_deferral_age_seconds` and a rate-limited WARNING once it lasts longer than 5 s ([telemetry.md §10.2](telemetry.md#102-metrics)). The flag service refuses to start when `FLAG_SERVICE_SETS` serves `interventions` without `agent`, since every intervention would then be deferred for good. Because every write moves both stamps, one write fires a configuration change on the written set, on `interventions` and on `agent`. Code: `services/flag-service/state/render.go` (`snapshotStamped`), `services/game_coordinator/interventions.py` (`_allow_list_lags`).

## 13. Mutable-flag registry

> Enforced by the flag service since PR #1417 (epic #1407, [UC-053](../use_cases/UC-053.md), FR-132, FR-133;
> design: [architecture/flag-service.md](../architecture/flag-service.md)).

A flag changes at runtime **only** if it has a row here,
only within its bounds and only in its scope. Every other flag of every set is the **read-only baseline**: it
changes by a reviewed edit of the flag file and a restart of the flag service (C-033). The registry file
`services/flag-service/registry.yaml` encodes this table; a change to one updates the other in the same PR.

There are **no writer roles and no authorization** (local party game, decided by the maintainer; architecture
note D11). The "Today's writer" column says who writes the flag, for orientation only.

**Kinds:** `state` = one value per scope; `level` = per-player value, re-applied as a whole; `grant` = per-player
value with a fresh variant per write (the coordinator fires on a variant change); `event` = per-game event list
`{"epoch","seq","events":[last K]}` written with `POST` (UC-053 BR-006); `overlay` = stack-wide value rendered as a
`defaultVariant` substitution, so baseline targeting still wins.

**Scopes:** `game` = targeting on `gameId` of a registered game; `game+serial` = `gameId` and `targetingKey`
(a serial of that game); `stack` = the default for every reader; `experiment+arm` = `game_kind != "real"` and
`experiment_id` and `arm`; `real` = the real default (promotion); `fraction` = `fractional` on `targetingKey` (the bucket is murmur3 of the canonical CBOR of `[flagKey, targetingKey]` since flagd v0.18.0 and the Python provider 0.6.0, #1945: the upgrade re-bucketed the serials of a live fraction overlay once; flagd, the Python provider and the agent's flagd core hash the same way, pinned by `tests/contract/fractional_buckets.json`, checked by `tests/contract/test_fractional_bucketing.py` and `services/agent/flags/fractional_bucketing_test.go`).
Game-scoped values are dropped when the game ends (FR-135).

**Persist:** `yes` = an admin setting that **may** be persisted: a write that asks for it (`"persist": true`, the
menu admin) is written to the service's own state file and restored at start (FR-018, C-030); the same flag
written without it (a stage script, a test) stays in memory. `no` = a write asking to persist is `400 malformed`.
Every value not persisted lives in memory only (architecture note §10.1).

**Failed save, kill switches (#2368, UC-053 A12):** when the state file cannot be saved (or was unreadable at
start), a persisted `PUT` or `DELETE ?persist=true` is refused with `500 persist_failed` and nothing changes in
memory; with a state file unreadable at start that includes a persisted `DELETE` with no admin value in memory, because
the file may still hold one (a flag whose row has no persist cannot be in the file: its `DELETE ?persist=true` stays a plain `204`, uncounted). The exception covers the persisted kill-switch flags, a fixed set in the flag service's
code (`registry.killSwitches`), not a registry.yaml attribute (released images parse the checkout's registry.yaml
strictly). This list is its single source of truth, kept in sync by a test: `agent/interventions_allowed`. A safety
stop must take effect now, so a write or clear of it applies in memory and answers `persisted: false` (`PUT`) or
`204` with `X-Flag-Persisted: false` (`DELETE`), counted in `flagservice_admin_persist_errors_total` and not
counted as persisted in `flagservice_overlays`; a restart brings back what the file holds (services.md §7.2). Only a
row with persist `yes` can be in the set: `enabled` is a kill switch too, but it takes no persisted write
(`400 malformed`), so a failed save never affects it.

**Persisted vs overlay (who writes which, #1682):** a persisted value is an **operator choice** (the menu admin,
`agent-backend.sh` for the decision backend and model); an in-memory overlay is a **stage beat** or a test
(`talk-stage.sh`, the dry-run scripts, fixtures). A persisted write replaces an in-memory overlay of the same
flag. An overlay written over a persisted value is temporary: it wins while it lasts, and a flag-service restart or
a reboot drops it and brings the persisted value back. `talk-stage.sh reset` therefore also deletes the persisted
decision backend and model (`DELETE …?persist=true`), and `talk-preflight.sh` WARNs while a remote backend is
persisted.

Renamed grant flags carry no persisted state (`toughness_boost_seconds`, formerly `partial_shield_seconds`, is not `persist`, is game-scoped and is dropped with its game): there is nothing to migrate. The persisted `interventions_allowed` stores a variant name only, so its content follows the baseline file (#1838).

**Real write (`real_write: no_live_real_game`, #2096, UC-043 A17, C-034):** a registry row may carry this attribute. A `PUT` of such a flag in scope `real` (the promotion overlay) is refused with `409 real_game_live` while any registered game scope (`PUT /games/{gameId}`, the reconcile call) has a `game_kind` other than exactly `shadow`. The check fails closed: `real`, an empty kind and any unknown kind all block (targeting differs: there only `real` matches the real rung, FR-041). The write is accepted again once every such scope ends (`DELETE /games/{gameId}`, the reconcile or the 1 h last-seen expiry). The check runs under the same lock as the game registration, so a registration and a write cannot interleave. Such a write may not carry `ttl_seconds` (`400 malformed`): an expiring overlay would revert on a timer, mid-game, without passing the guard. A plain `DELETE` of the `real` overlay is never refused: it is the kill switch's revert (UC-045). A watch or re-watch revert opts in to the guard with `?unless_real_game=true` (#2236): such a `DELETE` of a flag marked `real_write: no_live_real_game` in scope `real` is refused with `409 real_game_live` under the same rule and the same lock as the `PUT` (fails closed; nothing is cleared). On a flag without the attribute, or in another scope, the parameter changes nothing; a value that is not a boolean is `400 malformed`. The agent sends it for its own watch and re-watch reverts of hold keys and keeps such a revert waiting on the 409 (UC-043 A17 step 3); the kill switch never sends it. **Compare-and-delete (`?if_writer=<label>`, #1877, UC-043 A18):** a `DELETE` of the `real` overlay may carry this opt-in precondition (like If-Match): the overlay is cleared only when its stored writer equals the label, compared and cleared under one lock, else `412 writer_mismatch` and nothing changes. A missing overlay is a `204` that clears nothing. It is evaluated after every other check, so with `?unless_real_game=true` a live real game gives `409 real_game_live` first. It is valid only in scope `real` (elsewhere, and empty, `400 malformed`). It is not the informational writer label, which is never checked (D11). Every revert of the agent sends `if_writer=promotion`, the kill switch's included: every overlay the agent writes carries writer `promotion`, so it never blocks the kill switch from clearing one, and another writer's overlay is never removed. The agent maps a `409 real_game_live` on its promotion write to the outcome `deferred` and retries it after the game. **Write precondition (`?if_writer_in=<labels>`, #2260, UC-043 A19):** a `PUT` of the `real` overlay may carry a comma-separated list of writer labels (opt-in, like If-Match): the overlay is written only when the stored real overlay's writer is in the list, or when no real overlay is present and the list holds an empty entry (`if_writer_in=promotion,` = the promotion's own overlay or none), compared and written under one lock, else `412 writer_mismatch` and nothing changes. An overlay without a writer label matches no entry. It is evaluated after every other check (a dry run included), so a live real game on a hold key gives `409 real_game_live` first. It is valid only in scope `real` (elsewhere, repeated, over 16 entries or an entry over 80 characters, `400 malformed`). A `PUT` without it writes unconditionally, as before. The agent's promotion write sends `if_writer_in=promotion,`, so a promotion never overwrites a real overlay another writer (a script, a maintainer on the API) set; it maps the `412` to outcome `discarded` (reason `real_overlay_owned_by_another_writer`), also for a write waiting in the deferred queue. A mid-game `DELETE` is harmless for the running game: it latches its hold values and its activation at game start, and a game latched to `hold` stays `hold` (UC-040 BR-027), so the revert applies from the next game. Other scopes are not affected.

Windows in which a running real game is not registered, so the guard does not see it (the latch makes each harmless for that game; the next game reads the new value from its start): (a) after a flag-service restart, until the coordinator reconciles (it reads the boot epoch from `GET /healthz` every 2 s, and reconciles every 15 s); (b) the coordinator awaits `PUT /games/{gameId}` for at most 200 ms (`REGISTER_AWAIT_SECONDS`) and then plays unregistered until its retry (2 s) or the reconcile (15 s); (c) closed by #2217: the 1 h expiry counts from the last registration or reconcile entry (`last_seen_at`), so a real game that the coordinator keeps reconciling every 15 s stays registered however long it runs; it expires only when not seen for 1 h (UC-053 A11).

The attribute is on the eight hold keys of §13.3 (`shield.activation`, `shield.energy_max_seconds`, `shield.energy_budget_seconds`, `shield.energy_initial_seconds`, `shield.recharge_per_second`, `shield.min_burst_seconds`, `shield.hold_rumble_intensity`, `shield.empty_pulse_ms`); their scope is `stack or experiment+arm or real` since FR-162 (#2096 PR-7b-2a), so the guard is in force.

**Description (`description`, #2345):** one line, in game terms, of what the flag does, at most 120 characters (the cap bounds the experiment proposer's prompt). **Required** on every row whose scope includes `experiment+arm` (the experiment catalog, §13.3): the flag service refuses to start when such a row has none, or when a description is longer or spans lines; optional on every other row. It is served in the row's `policy` by the read endpoints and is informational: no write is checked against it.

**Bounds** are the declared variants of the baseline file unless a range, a payload schema or `free string` is
given. Ranges are inclusive and pinned to the reader's own clamp (`difficulty_handlers.py` factors 0.5 to 2.0, `lifecycle_handlers.py` toughness boost and soft penalty, `games/base.py` ramp_tempo 15 s and tempo ramp 0.1 to 10 s), so the registry never rejects a value the game would apply.
`free string` accepts any string value up to 512 characters (a declared variant name still selects that
variant); it exists for values only a test fixture or an operator knows, such as a fake server's URL (re-review N5).
A `variant` naming a declared variant is always within bounds (restricted to the listed variants where a list is
given); a `value` equal to a declared variant's value selects that variant. Event payloads are checked by the
service for shape and serials (a serial of the game); whether the player is still alive and whether a sound id
exists in the audio catalog are checked by the game coordinator and the audio service, which hold that state.

The rows with scope `experiment+arm` are the **experiment catalog** (#1092, #1415): the gameplay calibration
flags an experiment may change. Capacity (`max_concurrent_games`, `max_shadow_games`), lobby and ceremony
(`force_all_start*`, `countdown_phase_duration_ms`, `winner_rainbow_duration_ms`), team structure (`num_teams`,
`random_assignment`, `traitor.count_tiers`), scoring and threshold tables and `shadow_policy` are not in it. The
proposer and the dynamic declarer read the catalog from the flag service (`GET /game`, the `policy` of each
flag), and a value outside the bounds is refused with `out_of_bounds`. A numeric range covers the declared
variants with headroom; "same shape" accepts an object with exactly the default variant's keys and value kinds, and every number of it within 0 to 2 times the largest value any declared variant holds for that key (so `windows` cannot be set to a value no preset comes near; the ceiling is derived from the baseline variants, the registry has no field for it, #2369). A `pattern` `float` segment takes plain decimals only (`2`, `2.5`); hex floats, `inf`, `nan` and exponents do not match.

**Every catalog key is read on the shadow-game path (#2366, #2392, [UC-043](../use_cases/UC-043.md) BR-009):** an experiment arm runs as shadow games the agent starts with a fixed `StartGameConfig` (JoustFFA; `services/agent/gamerunner/operations.go` `buildStartConfig`) whose `sensitivity` is the arm's own value: the shadow spawner resolves the `game` flag `sensitivity` with the arm's evaluation context (`game_kind` shadow, `game_mode`, `experiment_id`, `arm`; `services/agent/shadow_spawner.go` `armSpec`, `flags.Flags.ShadowGameInt`), and a shadow game without an experiment keeps `SHADOW_GAME_SENSITIVITY` ([UC-046](../use_cases/UC-046.md) BR-019). An unreadable or out-of-range value refuses the spawn (the pair is rolled back and retried next tick). A catalog key must therefore be read by the game coordinator in the game's flag context (`read_*_flag("game", key, ..., game_id=...)`, which carries `game_kind`, `experiment_id` and `arm`), or be resolved by the agent with the arm's evaluation context into the shadow `StartGameConfig`. A key only the menu reads into `StartGameConfig` would give two identical arms, so `nonstop.time_limit_seconds`, `invincibility_seconds`, `fight_club.min_rounds` and `werewolf.reveal_time_seconds` left the catalog (scope `real` only; a promotion of an experiment concluded before the change still writes) and the `invincibility_4_5` seed variant was removed. **Mode-specific keys (#2392):** `nonstop.respawn_seconds`, `nonstop.spawn_protection_seconds` (NonStop), `fight_club.round_seconds` (FightClub), `tournament.match_seconds`, `tournament.time_between_matches_seconds` (Tournament), `werewolf.werewolf_fraction` (Werewolf), `zombie.*` (Zombies) and `death_grace_period_seconds` (read in `games/base.py` for every mode, used only by Swapper and Zombies) stay in the catalog, but the dynamic declarer and the proposer offer a key only when the shadow game's mode (`SHADOW_GAME_MODE`, JoustFFA) reads it. The one table of these keys and their modes is `catalogKeyModes` in `services/agent/shadow_mode_keys.go`; a key without an entry acts in every mode. Shadow games are JoustFFA only today, so none of the ten is offered; a shadow game in another mode picks up its keys with no change. A W5 promotion and a hand-set `experiment_seed` are not filtered. A rehydrated experiment on a key that left the catalog ends `discarded` (`not_experimentable`, UC-043 A10). ## 14. Ownership composition: invalidation and visibility

> Normative rules moved from [OWNERSHIP_MODEL.md](../OWNERSHIP_MODEL.md) sections 5 and 6.1 (epic #1546, D2). That
> document keeps the ownership principle (section 1), the parameter table (section 3) and the composition of the two
> contested runtime parameters (section 4: sensitivity, grace/shield); it points here for the two rules below.

### 14.1 The invalidation rule

> **A human baseline change invalidates the active agent override for that parameter.**

The human is the source of truth for intent. When the admin changes a baseline the agent is currently overriding, the
human's new value wins **immediately** and the agent's active override for *that parameter* is dropped (caveat: no
production code path calls `set_baseline_sensitivity`, so today this invalidation is reachable only through the
game-object API; a mid-game admin flag edit is not pushed into a running game):

- The agent does not keep an override pinned over a fresh human decision. Otherwise the admin's deliberate change would
  silently no-op while the agent's transient delta persisted.
- Invalidation is **per parameter**, not global: changing `sensitivity` cancels an active `global_sensitivity_override`
  but leaves an active `shield_seconds` untouched.
- After invalidation the agent may **re-propose** against the new baseline on its next decision. The human change resets
  the baseline the agent composes against; it is not a veto of the agent.

Implementation for `sensitivity` (verified against the code): the game keeps a human `baseline_sensitivity` and an agent
`sensitivity_override` layer; `game.sensitivity` is the effective value. `BaseGameMode.set_baseline_sensitivity` (the
target of assigning `game.sensitivity`) sets the baseline and clears the override; clearing the override from the agent
path (`handle_global_sensitivity_override`, value -1) returns to the **current** baseline, never to the game-start
snapshot (`configured_sensitivity`, telemetry only). The same shape applies to any future contested parameter.
Grace/shield needs no invalidation: it composes with `max(grace_until, invincible_until)` (OWNERSHIP_MODEL section 4.2).

**Traceability:** C-008 / UC-012, UC-040 / `services/game_coordinator/games/base.py`,
`services/game_coordinator/difficulty_handlers.py`.

### 14.2 The visibility contract

The human admin must be able to tell agent activity apart from a malfunction. A conforming implementation provides at
least:

- a **distinguishable signal** when the agent applies an in-game delta (an LED pattern, audio cue or dashboard
  indicator that is clearly agent action, not a game event and not "admin mode is broken");
- a signal that identifies **what** changed at the granularity of the parameter table (OWNERSHIP_MODEL section 3), so the
  admin can reconcile observed behaviour with the baseline.

Agent actions are already audited as spans (`agent.decision`, intervention events) and metrics
(`game_interventions_total`); the contract is the human-facing, on-device surfacing of that activity, not new
instrumentation.

Surfaces (#818):

1. **Truthful admin announcement (shipped, #1739).** Selecting an option in admin mode (Move, UC-012 step 3) announces the
   EFFECTIVE value (voice line, LED colour): `AdminModeHandler._effective_variant` (`services/menu/handlers/admin.py`)
   resolves the option through the live flagd `game` client and maps the value back to a variant name, so an active
   agent override is announced, not the baseline `defaultVariant`. It falls back to the baseline when the client is
   missing or the value matches no variant; with the flag service unreadable nothing is announced beyond the option
   colour. Stepping a value (Select / Start, Circle) writes the baseline and announces the new setting; when an agent
   overlay makes the effective value differ, it follows with the magenta agent cue and the effective value
   (UC-012 BR-006).
2. **On-device cue.** When the coordinator applies a **HARD-class** intervention (`spec.weight >= WEIGHT_HARD`, in
   `services/game_coordinator/interventions.py`; `end_game` is excluded because its game has just ended, UC-040
   BR-018) it emits a short magenta `GAME_EFFECT_PULSE` on the affected controller(s), broadcast for non-targeted
   actions (`InterventionManager._emit_agent_cue`). It is gated by the `agent_intervention_cue` toggle in the `user`
   set (§9; default on, off in `ci/`), so it can be muted for demos, and is best-effort: a failure never breaks the
   intervention path. MEDIUM and SOFT interventions are silent so gameplay is not disrupted.

**Traceability:** C-008 / UC-012, UC-040 / `services/menu/handlers/admin.py`,
`services/game_coordinator/interventions.py`.
