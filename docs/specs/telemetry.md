## 3. Spans

### 3.1 gRPC (all Python services, rust-hid)

| Span | Kind | Gate | Source |
|---|---|---|---|
| `{Service}/{Method}` (e.g. `GameCoordinatorService/ForceEndGame`) | CLIENT / SERVER | flag `grpc_rpc_spans` (default variant `enabled`), evaluated per RPC; when flagd is unreachable or the flag is missing the Python check falls back to **false** (no RPC spans) | `lib/grpc_tracing.py` (`_rpc_spans_enabled`) |
| `grpc.server` (rust-hid) | SERVER | same flag | `services/rust-hid/src/grpc_tracing.rs:105-115` |
| renamed: `StreamButtonEvents`, `StreamGameplayData` (CM); `PlaySound:{sound}`, `PlayMusic:{dir}`, `ChangeTempo:{x}x`, `SetVolume:{pct}` (audio) | SERVER | | `services/controller_manager/servicer.py` (`StreamButtonEvents`, `StreamGameplayData`); `services/audio/servicer.py` (`PlaySound`, `PlayMusic`, `ChangeTempo`, `SetVolume`) |

Audio span attributes: `PlaySound:{sound}` carries `audio.file`; `PlaySound` and `PlayMusic` carry `audio.muted=true` when `play_audio` is off (read at use time); `PlaySound` carries `audio.silent=true` when `play_audio` is on but the audio hardware is not open yet, so nothing is heard (#1387). `PlaySound` carries `audio.duration_seconds`, the clip length it returns in `PlaySoundResponse.duration_seconds` (0 when nothing is heard; UC-020 A5, #1550). `StopSound` (server span, unrenamed) carries `audio.stopped`, the number of channels it stopped (UC-020 A5, #1586).

Python `{Service}/{Method}` CLIENT spans cover the whole call: a unary call ends at its status, a server-, client- or bidi-stream when the RPC terminates (completed, failed, or cancelled by `call.cancel()` or a cancelled read task; a stream the caller drops ends when it is garbage collected; closing the channel alone does not end an open stream, its reader keeps waiting), with no work per message. A unary call in flight does end when its channel closes. `rpc.grpc.status_code` is the final code; a non-OK status sets the span status ERROR, except a cancel by the caller (cancelled call or task, garbage collection, a unary call ended by closing its channel), which leaves it unset; a `CANCELLED` sent by the server is ERROR. Covers the async channels from `lib/grpc_utils.create_channel` and the HID adapters' sync unary calls; the sync `StreamIO` stream has no span (#1879). When `grpc_rpc_spans` is on, the `traceparent` sent with the call carries the CLIENT span, so the receiving SERVER span (Python `{Service}/{Method}`, the renamed audio/CM spans, rust-hid `grpc.server`) is its child, as with connect-proxy's `otelgrpc` client. With no CLIENT span (`grpc_rpc_spans` off or flagd unreachable; the former `OTEL_GRPC_CLIENT_SPANS` env var is removed, #1907), the caller's current span is sent as before. The sync `StreamIO` stream has no CLIENT span and still sends the caller's span (#1897).

Python `{Service}/{Method}` SERVER spans record the status the RPC really ended with (#1896). `rpc.grpc.status_code` is the code of `context.abort(code)` (read from the servicer context, the `AbortError` is re-raised), the code a handler set with `context.set_code(X)` before returning normally, or OK. A non-OK code sets the span status ERROR; a handler that fails with any other exception (including a downstream call's error that escapes it) records the code set on the context, else UNKNOWN (ERROR, exception event recorded). The span status description is the handler's `details` text when set, else the code name. A handler cancelled because the client cancelled the call (or the server stops) records `CANCELLED` and leaves the span status unset, the same convention as the CLIENT span above. This holds for unary, server-, client- and bidi-stream handlers and is decided once per RPC, with no work per message.

connect-proxy: `otelhttp` server spans (`/health` filtered) and `otelgrpc` client spans only.

**gRPC health checks are not traced** (#2286): the collector's `filter/grpc_health` processor drops every span whose `rpc.service` is `grpc.health.v1.Health` (Go, Rust) or `Health` (the package-stripped form `lib/grpc_tracing.py` records for the Python services) from the `traces` pipeline (Jaeger and the agent), whatever service recorded it. Docker healthchecks and watchdog probes call the RPC as before; on the stage Pi 1362 of 1500 Jaeger spans were health checks.

**Elapsed game time.** The agent's in-game elapsed time (`elapsed_s` in the decide state, `duration` in the rules
and the `agent.evaluate` log line) is `game_duration_seconds` while that gauge is fresh, i.e. its value advanced
within the last 5 s. When the gauge is missing or stale during an active game, the agent derives the elapsed time
from when it saw `game_active` go 0 → 1, never going below the last gauge value. Within a game the value never
decreases. At game end the duration every game-end consumer (experiment conclusion, retro, summary, proposer) sees is
the larger of the gauge and the agent's own start → end time, because the coordinator's final set can arrive after
`game_active` 0 (UC-041 A3, BR-003; `services/agent/gamecontext/store.go` `effectiveDurationLocked`).

**Game end.** The agent ends a game on the first of three signals (UC-041 A4, BR-005; #1494): the `game_active`
1 → 0 datapoint; the game root span arriving (OTLP exports a span once it ended, and the root span ends with the
game's session; the duration bracket then closes at the span's end time and a later `game_active` 1 for that game id
is ignored); or the game's `game_active` series staying silent for 60 s (`gameActiveStaleAfter`; the coordinator
exports every 100 ms, so this leaves margin for a collector restart; the bracket closes at the last datapoint).
`OnGameEnd` fires once per game whichever comes first, so a dropped 0 no longer keeps the game's partition from being
evicted. In a game-id partition every end latches: game ids are never reused, so a later `game_active` 1 for an ended
game id is ignored, also after the partition was evicted (the multiplexer remembers the last 512 ended ids). The
timeline's "end" phase event is stamped at the game's own end, so the start → end bracket game-end consumers derive
from it (`experiment_loop.go` `withEffectiveDuration`) matches the store's. The snapshot carries the end reason
(`GameContext.EndReason`: `zero`, `root_span`, `stale`). A `stale` end means the agent's telemetry for the game broke:
it increments `agent_game_end_stale_total{game_kind}` (`primary` / `shadow`), the experiment loop releases an experiment game without a
fitness sample (and records no recent-real sample for a real game), and the retro, game summary and proposer skip it
(`services/agent/gamecontext/store.go` `endGameLocked`, `EndGameFromRootSpan`, `EvictStale`; `gamecontext/multiplexer.go`;
`services/agent/gameend.go`).

intervals later (`metrics_export_interval_ms`, so about 3 s), without blocking, because the `game_active` 1 → 0
datapoint is the agent's fastest game-end signal (the root span and the 60 s stale backstop are later, §4.4). Game-state series (`GAME_STATE_GAUGES`) that the game loop writes after

**Jaeger query API (#2283).** Every Jaeger reader in this repository, the dashboard SPA (`services/dashboard/src/jaeger.ts`), the talk pre-flight and the integration tests (`tests/integration/jaeger_v3.py`), uses the query API v3 through `/jaeger/api/v3` (gRPC-gateway JSON; Jaeger 2.21 removes the legacy `/api/services` and `/api/traces` search). A search is `GET /jaeger/api/v3/traces` with `query.serviceName`, `query.operationName`, `query.attributes` (a JSON object of string tags, AND), `query.searchDepth` (traces) and the required `query.startTimeMin` / `query.startTimeMax` (RFC 3339, UTC). The dashboard still never sends a browser-clock time: `query.startTimeMin` is the Unix epoch on a cold start, then the span-derived start of the incremental window (agent clock), and `query.startTimeMax` is the fixed bound `2100-01-01T00:00:00Z`; the talk pre-flight and the tests run on the Jaeger host and send their own clock. The answer is OTLP JSON (`result.resourceSpans[].scopeSpans[].spans[]`, all matching traces in one list, ids in hex, times in ns as strings); the readers group it by `traceId` into the span fields they used before (operation = `name`, parent = `parentSpanId`, tags = `attributes`, span events = `events`, service = the resource's `service.name`). `404` with `No traces found` is an empty answer, not an outage. Grafana's Jaeger datasource (`services/grafana/provisioning/datasources/jaeger.yml`, URL `http://jaeger:16686/jaeger`, base path included since #2283) reads services, operations and single traces through v3 (`[feature_toggles] jaegerEnableGrpcEndpoint`), but Grafana 13.0.2 still sends its trace search to the legacy `/api/traces` (jaeger#7594), which Jaeger 2.22 (the pinned version since #2311) no longer serves. The two `agent.decide` trace-search table panels (Agent Decisions & Interventions, Talk) were therefore replaced in #2311 by VictoriaMetrics panels on the existing `agent_decisions_total` (no new metric): a time-range table by `game_kind`, `action`, `blocked`, `block_reason` and a decisions / min time series by `action` and `game_kind`; single traces are opened in the Jaeger UI at `/jaeger/`.

Many Python metric names have no consumer in a dashboard, the agent, the dashboard SPA or a
script (all `menu_*`, `psmove_*`, `audio_*` and others; `make specs-counts` prints the count); they
are kept for ad-hoc analysis. `tests/contract/test_telemetry_contract.py` (#1357) checks the agent's and the dashboards' names against the producers. The §6.2 catalog and its counts are **generated** from the same scans (#1280; the counts are printed by `make specs-counts` and the Telemetry Contract job summary, not committed, #2152): one row per Python metric name, each Consumers cell equal to what the consumer scans find (Grafana and SPA PromQL, the agent's ingest constants, the name as a word in non-test `tools/` and `scripts/` source), and the **no** rows in Emitted equal to the metrics nothing records. ## 8. Naming rules

Rules (from `.claude/rules/development.md`): metric names prefixed with the service (`game_`, `controller_`,
`menu_`, `audio_`, `agent_`), counters end in `_total`, histograms in `_seconds` / `_bytes` (or a base unit),
span names in dot notation for new spans, attributes namespaced as in §2.1.
Every Go `Span*` / `Attr*` constant value must appear in this spec as its exact string (a `ns.*` mention or a
`.suffix` shorthand does not document a key, so write the full key); `make spec-refs-check` fails on a new
undocumented one, and `docs/specs/notes/spec-refs-baseline.json` lists the ones still open (growth needs the
`spec-baseline-growth` label, #1280).

Known violations on `main` (do not copy them; fix opportunistically, D-T6): gauge `active_controllers_total`;
`games_*`, `bluetooth_*`, `event_bus_*`, `psmove_*` and `grpc_requests_total` / `grpc_request_duration_seconds`
without a service prefix; `bluetooth_device_last_seen_timestamp` without a unit suffix; gauges `menu_idle_controllers_count`
and `menu_sentinel_controllers_count`, whose `_count` suffix collides with the histogram `_count` series; histograms
`controller_streamed_per_frame`, `controller_poll_batch_size`, `controller_led_controllers_updated_per_batch`,
`game_accel_distribution`, `agent_intervention_effect_delta`; `game_loop_jitter_ms` in milliseconds; most
coordinator / menu spans in snake_case; rust `grpc.server` vs Python `{Service}/{Method}`.

**Signal hash:** FNV-1a/64 over the controller's delivered frames in order, each frame encoded as the signed
32-bit little-endian integer ⌊intensity · 1000 + 0.5⌋ (milli-g, rounded half up); for an archetype with a
`trigger_policy` (UC-046 BR-018, #2096) each frame adds one byte after the value, 1 when the trigger is pressed on that
frame and 0 otherwise, so the hash of an archetype without a policy is unchanged; rendered as 16 lowercase hex digits.
intensity is computed in IEEE-754 double precision; the milli-g rounding keeps the hash stable across Python builds,
and golden tests pin it. **Checkpoints:** the hash value after every r delivered frames (one per second of game time).
The total number of delivered frames depends on wall-clock lag (a dead player leaves the stream filter a few frames
after its death; the winner's stream runs until the game is torn down), so replays compare the checkpoints on their
common prefix, not the final hash.

**Journal:** the experiment journal records the same facts: a `pattern_pinned` event (selection, pinned names,
parameter objects, parameter digests, safety cap and a note when the cap fell back to 300), `archetype`,
`params_digest`, `rng_seed` and `flag_digest` on each `game_assigned`, a `pattern_game_ended` event (outcome,

sequence) per pattern game, and a `pattern_pair_rerun` / `pattern_archetype_skipped` decision note when a pair runs
again or an archetype is skipped (UC-046 BR-015); a rerun after a real game preempted the pair
(`preempted_by_real_game`) is noted as `pattern_pair_rerun_preempted` instead, and one after a stale end (UC-041 A4) as
`pattern_pair_rerun_stale`; neither uses up the 3-rerun budget.
The experiment's conclusion (`outcome` event) reports the timeout count and rate per arm and whether one arm timed out
clearly more often (UC-046 BR-013), followed by the `agent_ended` count and rate per arm when any game ended that way;
both rates are over the arm's pattern games that ended with a sample (`winner`, `tie`, `timeout`, `agent_ended`).

**Liveness check (BR-008):** the runner asks the agent's telemetry multiplexer at the game's start, once per
second while it runs and at its end whether another partition reports `game_active` with an update in the last
10 s; stale partitions are ignored.

**Replay check:** read `pattern.archetype`, `pattern.params_digest`, `game.rng_seed`, `pattern.stream_rate_hz`, the

and compare: per-slot checkpoints equal on their common prefix (NFR-040), `pattern.elimination_order` and
`pattern.winner_slot` equal (NFR-041), and the sequence of rules decisions as (`intervention` type,
`pattern.target_slot`) equal (NFR-042). Only games with `pattern.replay_exact=true` and the same
`pattern.params_digest` and `pattern.flag_digest` on both sides are compared. `scripts/pattern-replay-check.sh
<archetype> [seed]` runs the archetype twice with the one-shot runner and performs this comparison on the two runs
(it reads the `PATTERN_REPLAY_RECORD` line the one-shot runner prints), and `scripts/pattern-replay-check.sh --against
<record>` replays one recorded game: the record is a saved `PATTERN_REPLAY_RECORD` JSON or a `pattern_game_ended`

## 10. Flag service (epic #1407)

> Delivered in PR #1417 for [UC-053](../use_cases/UC-053.md) (FR-139, NFR-050 to NFR-053). Service identity
> `flag-service` (namespace `infrastructure`), Go OTel SDK, metrics every 1 s like the agent; HTTP server spans
> from `otelhttp`, so a write sits under the caller's span (W3C propagation). New attribute namespace
> `flagservice.*`; the flag itself uses the OTel feature-flag semantic convention keys `feature_flag.key`,
> `feature_flag.set.id` and `feature_flag.result.variant` / `feature_flag.result.value`, so a Jaeger search by
> flag key finds both evaluations and writes. There are no roles (architecture note D11): `flagservice.writer`
> is the caller's informational label.

### 10.1 Spans

| Span | Kind | Attributes | When |
|---|---|---|---|
| `flagservice.write` | internal, child of the HTTP server span (`PUT`/`POST`/`DELETE /{flagSetId}/{flagName}`) | `feature_flag.key`, `feature_flag.set.id`, `feature_flag.result.variant` (generated variant), `feature_flag.result.value` (the value as JSON text), `flagservice.op` (`set`, `append`, `clear`, `dry_run`), `flagservice.kind` (`state`, `level`, `grant`, `event`, `overlay`), `flagservice.scope` (`stack`, `game`, `game+serial`, `experiment+arm`, `real`, `fraction`), `flagservice.result` (`ok`, `rejected`, `error`), `flagservice.reason` (reason code, services.md §7.2), `flagservice.writer`, `flagservice.write_reason` (the caller's informational `reason`), `flagservice.cleared` (`DELETE`: values removed), `flagservice.seq` (event writes), `flagservice.epoch`, `flagservice.snapshot_version`, `flagservice.persisted`, `game.id`, `game.kind`, `player.serial`, `experiment.id`, `experiment.arm`, `decision.intervention_id` (from `decision_id`) | every write, accepted or rejected |
| `flagservice.game.register` | internal | `game.id`, `game.kind`, `player.count`, `experiment.id`, `experiment.arm`, `flagservice.coordinator_instance`, `flagservice.result` | `PUT /games/{gameId}` |
| `flagservice.game.end` | internal | `game.id`, `flagservice.reason` (`ended`, `reconciled`, `expired`), `flagservice.dropped_values`, `flagservice.coordinator_instance` | `DELETE /games/{gameId}`, a scope dropped by the reconcile call or by expiry |
| `flagservice.sync.push` | internal, linked to the triggering `flagservice.write` | `flagservice.snapshot_version`, `flagservice.snapshot_bytes`, `flagservice.streams`, `flagservice.epoch` | each merged configuration sent to the open sync streams |
| `flagservice.baseline.load` | internal | `feature_flag.set.id` (one event per set), `flagservice.flags`, `flagservice.admin_values` (restored from the state file), `flagservice.admin_dropped` (stale entries dropped), `flagservice.epoch`, `flagservice.result` | start |

### 10.2 Metrics

| Metric | Type | Labels | Meaning |
|---|---|---|---|
| `flagservice_writes_total` | counter | `flag_set`, `flag`, `op`, `result`, `reason` | every write (UC-053 BR-005) |
| `flagservice_write_duration_seconds` | histogram | `op` | validate + render + acknowledge (NFR-053) |
| `flagservice_propagation_seconds` | histogram | | write accepted → merged configuration handed to every open sync stream; the end-to-end target of NFR-050 is measured by the integration test against flagd |
| `flagservice_live_games` | gauge | `game_kind` | registered game scopes |
| `flagservice_game_scopes_expired_total` | counter | | scopes dropped by expiry (UC-053 A11) |
| `flagservice_experiments_expired_total` | counter | | experiments whose arm values were dropped because no registered game carried their id for `FLAG_SERVICE_EXPERIMENT_IDLE` (NFR-051) |
| `flagservice_scope_values` | gauge | `flag_set` | game-scoped and experiment values held (NFR-051) |
| `flagservice_snapshot_bytes` | gauge | | size of the last merged configuration (NFR-051) |
| `flagservice_sync_streams` | gauge | | open `SyncFlags` streams. flagd opens **one** stream that carries every served set, so the value is 1 per connected flagd (no per-set label); 0 means flagd is not connected and flag writes return 503 `no_sync_stream` |
| `flagservice_sync_rejected_total` | counter | `reason` | rejected `SyncFlags` / `FetchAllFlags` calls; `reason="unknown_selector"` (unknown selector key) or `"unknown_flag_set"` (a set that is not served) means a misconfigured client or flagd |
| `flagservice_overlays` | gauge | `flag_set`, `persisted` | stack overlays in effect |
| `flagservice_admin_persist_errors_total` | counter | | failed writes of the state file (the persisted write or clear is rolled back and answered `500 persist_failed`; a persisted kill switch, flags.md §13, still applies in memory and reports not persisted, #2368) |
| `flagservice_admin_state_corrupt_total` | counter | | state files that did not parse at start and were moved aside to `admin.json.corrupt-<ts>`; the service started from the baseline |
| `game_intervention_event_gaps_total` | counter | `flag` | game-coordinator: an event list read whose oldest event is newer than the last applied seq + 1 (more than K events between two reads, architecture note §6) |
| `game_intervention_deferrals_total` | counter | | game-coordinator: deferral episodes of the cross-set gate ([UC-053](../use_cases/UC-053.md) A9 step 4, #1552): the allow-list it holds lagged the `interventions` set it holds, so interventions waited. One per episode, not per deferred flag; a steady-state episode lasts milliseconds |
| `game_intervention_deferral_age_seconds` | gauge | | game-coordinator: age of the current deferral episode, 0 when none. Re-checked every 5 s while deferred, so a stuck `agent` stream shows as a growing age; past 5 s the coordinator also logs a WARNING (at most one per 30 s) naming both snapshot stamps |
| `game_flag_configuration_changes_total` | counter | | game-coordinator: PROVIDER_CONFIGURATION_CHANGED events its providers received. Since #1552 every flag-service write moves the snapshot stamps of the `interventions` set and of `agent/interventions_allowed`, so one write is counted about three times (the written set, `interventions`, `agent`); read it as push activity, not as a write count. A change that names no flag the runtime config reads is logged at DEBUG |

Labels never carry `game_id`, `serial` or the free-text `writer` (unbounded cardinality); those live on the
spans. The names follow §8: service prefix `flagservice_`, counters end `_total`, histograms in seconds.
